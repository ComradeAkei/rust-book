# 16.3. Что оптимизатор делает с UB

*Неопределённое поведение* (undefined behavior, UB) — это не «работает как повезёт». Это обещание
программиста компилятору: «такого не случится». Компилятор обещанию верит
и на нём строит оптимизации. Поэтому у UB два следствия: оно убирает
проверки, которые были бы нужны, и распространяется назад — вырезает код
до точки, где обещание нарушилось бы. Оба видны в ассемблере.

## Проверка границ стоит ветку

Индекс по [срезу][g-slice] проверяет границы: сравнение длины и ветка на [панику][g-panic].

```rust
{{#include ../../code/ch16/src/codegen.rs:checked}}
```

```asm
ch16_checked:
    cmp   rdx, rsi                      ; индекс против длины
    jae   .LBB2_2                       ; выход за границу → паника
    mov   eax, dword ptr [rdi + 4*rdx]  ; иначе загрузка
    ret
.LBB2_2:
    ...
    call  core::panicking::panic_bounds_check
```

Тот же доступ через `get_unchecked` перекладывает проверку на
вызывающего (предусловие в `# Safety`) — и ветка исчезает:

```rust
{{#include ../../code/ch16/src/codegen.rs:unchecked}}
```

```asm
ch16_unchecked:
    mov   eax, dword ptr [rdi + 4*rdx]  ; одна загрузка
    ret                                 ; ни сравнения, ни вызова
```

Это и есть цена, которую убирает `unsafe`: сравнение и предсказуемый
переход. В горячем цикле, где индекс заведомо в границах, разница
измерима — но платить за неё приходится доказательством предусловия, а
не надеждой. Проверяет это `asm`-тест главы: он собирает release и
сверяет, что в `ch16_checked` есть `cmp` и `panic_bounds_check`, а в
`ch16_unchecked` — ни того, ни другого.

## Обещание распространяется назад

`unreachable_unchecked` говорит компилятору: «сюда поток не придёт». Если
он всё же придёт — UB. Компилятор пользуется этим, вырезая всё, что вело
бы в недостижимую точку.

```rust
{{#include ../../code/ch16/src/codegen.rs:assume}}
```

Раз нечётное `n` вело бы в `unreachable_unchecked`, компилятор заключает:
`n` всегда чётное, значит `n / 2 * 2 == n`. Тело функции сворачивается до
«вернуть `n`»:

```asm
ch16_assume_even:
    mov   eax, edi   ; вернуть n как есть
    ret              ; ни деления, ни маскирования
```

Это ровно механизм из [мотивирующей проблемы](index.md): там
разыменование `tun` «пообещало» `tun != NULL`, и проверка на `NULL`
стала недостижимым — для компилятора — кодом, который он удалил. Разница
в том, что здесь обещание даёт программист осознанно и под `unsafe`, а в
C оно возникло само из разыменования, молча.

<div class="box trap">

**Ловушка.** Соблазн «подсказать оптимизатору» через
`unreachable_unchecked` или `assume` почти всегда проигрышный: выигрыш —
несколько инструкций, цена ошибки — UB на всей программе. Прежде чем
писать такое, проверяют, что обычный `match` с `unreachable!()` (паника,
не UB) компилятор и так сворачивает — часто сворачивает.

</div>

<div class="box c">

**Как в C.** Ровно то же делает любой C-компилятор с `-O2`: знаковое
переполнение, разыменование `NULL`, выход за массив — всё это посылки,
из которых оптимизатор выводит и удаляет код. Отличие не в оптимизаторе,
а в том, что в C эти посылки берутся из обычных операций без пометки, а в
Rust — только из `unsafe`, где программист их и ставит.

</div>
