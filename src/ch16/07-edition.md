# 16.7. Гигиена unsafe и edition 2024

`unsafe` работает только с дисциплиной вокруг него. Edition 2024 сделала
часть этой дисциплины обязательной.

## unsafe-операции внутри unsafe fn

Раньше тело `unsafe fn` целиком считалось `unsafe`-блоком: любую опасную
операцию в нём можно было написать без пометки. Это скрывало, где именно
риск. В edition 2024 линт `unsafe_op_in_unsafe_fn` включён, и внутри
`unsafe fn` опасные операции всё равно требуют своего `unsafe`-блока:

```rust
pub unsafe fn get_unchecked(slice: &[i32], i: usize) -> i32 {
    debug_assert!(i < slice.len());
    // SAFETY: предусловие функции — i в границах; переложено на вызывающего.
    unsafe { *slice.get_unchecked(i) }
}
```

Теперь видно, что опасна одна строка, а `debug_assert!` и подпись —
безопасны. Это тот же код, что в [16.1](01-abilities.md).

## Атрибуты #[unsafe(...)]

Атрибуты, у которых есть последствия для безопасности, в edition 2024
пишут с обёрткой `unsafe(...)`: `#[unsafe(no_mangle)]`,
`#[unsafe(export_name = ...)]`, `#[unsafe(link_section = ...)]`. Имя без
украшения или своя секция компоновки могут столкнуться с чужим символом
или лечь в особую область памяти — отсюда пометка. В примере кодогенерации
([16.3](03-ub.md)) функции помечены именно так:

```rust
#[inline(never)]
#[unsafe(no_mangle)]
pub fn ch16_checked(v: &[u32], i: usize) -> u32 {
    v[i]
}
```

## Ссылки на static mut запрещены

Про запрет ссылок на `static mut` и переход на `&raw mut` — в
[16.1](01-abilities.md). Это закрыло целый класс ошибок: `&mut` на
глобальную переменную слишком легко сосуществовала со второй такой же,
давая две `&mut` без единого сырого указателя.

## unsafe extern

Блоки `extern` в edition 2024 пишут `unsafe extern`: объявляя сигнатуру
чужой функции, вы отвечаете за её правильность, и компилятор верит вам на
слово. Это граница с C — ей посвящена [глава 18](../ch18.md).

## Дисциплина, которую не навязывает компилятор

- **Комментарий `// SAFETY:` к каждому `unsafe`-блоку.** Он объясняет,
  почему предусловия соблюдены. Линт clippy `undocumented_unsafe_blocks`
  (из группы `restriction`) требует его на каждом блоке; в этой книге он
  есть всюду. Пустой или неверный `// SAFETY` хуже отсутствующего — он
  создаёт ложную уверенность.
- **Предусловия `unsafe fn` под заголовком `# Safety`** (английским, см.
  ловушку в [16.1](01-abilities.md)). Линт `missing_safety_doc` требует
  его на каждой публичной `unsafe fn`.
- **Miri в обеих моделях.** Тест обычным `cargo test` исполняет одну
  трассу на настоящем железе, где UB часто «работает». Miri исполняет ту
  же трассу по правилам абстрактной машины и ловит то, что железо
  прощает. Обе модели алиасинга — потому что одной официальной пока нет
  ([16.5](05-models.md)).

<div class="box trap">

**Ловушка.** «Тесты проходят» не доказывает корректность `unsafe`. UB
может прятаться на трассе, которую тест не прошёл, или проявиться только
под другим уровнем оптимизации, другим аллокатором, другим расположением
стека. Доказательство корректности `unsafe` — это рассуждение в
`// SAFETY` плюс Miri, а не зелёный `cargo test`. Каталог задачи A
нарочно собран из UB, которые обычный запуск не замечает, а Miri ловит
на каждом.

</div>

<div class="box check">

**Проверь себя.** Зачем `unsafe_op_in_unsafe_fn`, если тело `unsafe fn` и
так пишет автор функции? Затем, что автор — тоже читатель при ревью и
через полгода. Явный `unsafe`-блок отмечает единственную опасную строку
среди десяти безопасных; без него каждая строка `unsafe fn` одинаково
«подозрительна», и настоящий риск теряется.

</div>
