# 16. unsafe и неопределённое поведение

## Мотивирующая проблема

В C неопределённое поведение невидимо и может прятаться в любой строке.
Вот функция из драйвера `tun` ядра Linux (CVE-2009-1897), сжатая до сути:

```c
struct sock *sk = tun->sk;   /* разыменование tun */
if (!tun)                    /* проверка на NULL — уже после */
    return POLLERR;
/* ... дальше работаем с sk ... */
```

Здесь сначала читают поле через `tun`, а потом проверяют `tun` на `NULL`.
Компилятор рассуждает так: раз `tun->sk` уже прочитан, то `tun` не `NULL`
— иначе была бы UB, а её «не бывает». Значит проверка `if (!tun)` всегда
ложна, и её **можно удалить**. GCC её и удалял. Нулевой `tun` проходил
дальше, и получалась запись по управляемому атакующим адресу — из
невинной на вид проверки вырос эксплойт ядра.

Мина не в проверке и не в разыменовании по отдельности, а в их порядке
плюс в праве компилятора считать, что UB не случается. Ни один из них C
не покажет: `-Wall` молчит, программа «работает» на тесте, а под другим
компилятором или уровнем оптимизации ломается.

## Что делает Rust

Rust не отменяет неопределённое поведение — оно существует и в нём, с
теми же последствиями. Но Rust его **локализует**: всё, что способно
вызвать UB, требует ключевого слова `unsafe`, а безопасный код вне
`unsafe` этого не может в принципе. Разыменование сырого указателя вне
`unsafe` — ошибка компиляции (E0133), а не удалённая проверка.

- `unsafe` даёт ровно пять новых возможностей и ничего сверх них
  ([16.1](01-abilities.md)). Оно **не** выключает проверки заимствования,
  не разрешает гонки и не «отключает безопасность».
- `unsafe` — это договор: вызывающий обещает соблюсти предусловия,
  записанные в документации. Нарушил — UB. Весь смысл в том, чтобы
  запереть `unsafe` в маленькой функции с безопасной сигнатурой, внутри
  которой предусловия доказаны ([16.6](06-api.md)).
- UB в Rust перечислимо ([16.2](02-invariants.md)): недопустимое значение
  типа, выход за границы выделения, висячий указатель, нарушение
  алиасинга, чтение неинициализированной памяти, гонка. Каждый пункт
  ловит Miri — интерпретатор, исполняющий программу по правилам
  абстрактной машины.
- Что оптимизатор делает с UB и с его отсутствием — видно в ассемблере
  ([16.3](03-ub.md)): проверка границ стоит ветку, а `unsafe`-обещание её
  убирает и распространяет назад.

За это платят дисциплиной: каждый `unsafe`-блок сопровождают
комментарием `// SAFETY:`, который объясняет, почему предусловия
соблюдены, и проверяют код под Miri в обеих моделях алиасинга. «Тесты
проходят» корректности `unsafe` не доказывает — тест исполняет одну
трассу, а UB может прятаться на другой.

## Код главы

Все фрагменты взяты из файлов репозитория и проверяются:

```console
$ cargo test -p ch16                          # примеры, asm-тест, doc-тесты
$ cargo +nightly miri test -p ch16            # те же под Miri (Stacked Borrows)
$ MIRIFLAGS=-Zmiri-tree-borrows cargo +nightly miri test -p ch16   # и Tree Borrows
$ cargo +nightly miri test -p ch16-solutions  # решения задач B и C
$ bash code/ch16/ub/run.sh                     # каталог UB (A), unsound (C), расхождение (D)
```

Ассемблер снят с release-сборки `rustc 1.97.0` для
`x86_64-unknown-linux-gnu` закреплённым `cargo rustc --emit asm` с
синтаксисом Intel. Вся глава — хостовая: `unsafe` и UB разбирают там, где
работает Miri; целей Cortex-M у неё нет.
