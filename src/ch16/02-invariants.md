# 16.2. Инварианты валидности и безопасности

`unsafe`-код держится на инвариантах — утверждениях, которые обязаны быть
истинны. Их два вида, и путать их опасно.

**Инвариант валидности** (validity invariant) — то, чему значение обязано
удовлетворять *всегда*, иначе само его существование — неопределённое
поведение. `bool` — это строго `0` или `1`. Ссылка не бывает нулевой и
висячей. `char` — не любой `u32`. Создать значение, нарушающее валидность,
— мгновенное UB, даже если его ни разу не прочитать: компилятор уже строит
на валидности свои выводы.

```rust
{{#include ../../code/ch16/src/invariants.rs:validity}}
```

**Инвариант безопасности** (safety invariant) — то, на что опирается
безопасный код через `unsafe`. Его можно нарушить без немедленного UB, но
тогда ломается тот самый безопасный код, который на него рассчитывал.
Пример — строка, про которую `unsafe`-конструктор пообещал, что в ней одни
ASCII-байты: безопасный метод режет её по одному байту без проверки границ
символа.

```rust
{{#include ../../code/ch16/src/invariants.rs:safety}}
```

Разница практическая: нарушив валидность, вы получаете UB сразу и
везде; нарушив безопасность — отложенное UB там, где на инвариант
обопрётся `unsafe`. Инвариант безопасности держит не система типов, а
`unsafe`-конструктор, поэтому **граница доверия — весь [модуль][g-module]**: любой
безопасный код в том же модуле может собрать `Ascii` из не-ASCII через
приватное поле и сломать `first_upper`. Вот почему `unsafe`-типы держат в
маленьких модулях с узким интерфейсом.

## Перечень неопределённого поведения

UB в Rust перечислимо — это не «всё, что компилятор не любит», а
конечный список. Главные пункты:

- **Недопустимое значение типа** — нарушен инвариант валидности (`bool`
  вне `{0,1}`, нулевая ссылка, неинициализированный примитив).
- **Выход за границы выделения** — чтение или запись вне блока, который
  распределитель отдал, в том числе через `get_unchecked` с плохим
  индексом или `ptr::add` за край.
- **Висячий указатель** — обращение к памяти после её освобождения
  (use-after-free) или к локальной переменной после выхода из её
  области.
- **Нарушение алиасинга** — две живые `&mut` на одну ячейку или `&mut`
  одновременно с `&` ([16.5](05-models.md)).
- **Невыровненный доступ** — чтение `u32` по адресу, не кратному 4.
- **Чтение неинициализированной памяти** — `assume_init` раньше времени.
- **Гонка данных** — два потока обращаются к одной ячейке без
  синхронизации, и хотя бы один пишет.

Каждый пункт ловит Miri. Задача A этой главы — каталог таких фрагментов:
по одному на каждый пункт, кроме гонки данных (для неё нужен второй
поток, и её разбирают в [главе 14](../ch14/index.md)), и Miri на каждом
сообщает об ошибке.

<div class="box check">

**Проверь себя.** Почему `let b: bool = unsafe { transmute(2u8) };` — UB
уже в этой строке, хотя `b` ещё не прочитали? Потому что компилятор
вправе исходить из валидности `b` немедленно: например, свернуть
`match b { true => .., false => .. }` в таблицу из двух веток без
проверки, что значение вообще одно из двух. Нарушенная валидность делает
такой вывод ложным — и дальше возможно что угодно.

</div>

<div class="box hood">

**Под капотом.** Miri исполняет программу по правилам абстрактной машины
Rust: у каждого указателя отслеживается, на какое выделение он имеет
право, инициализирована ли память побайтно, не нарушен ли алиасинг. Это
не [санитайзер][g-sanitizer] поверх настоящего кода (как [ASan][g-asan] в C), а интерпретатор
[MIR][g-mir] — поэтому Miri ловит и то, что на реальном железе «случайно
работает»: невыровненный доступ на x86, чтение чуть за концом буфера,
живущее до ближайшей страницы. Цена — Miri в сотни раз медленнее, и под
ним гоняют тесты, а не продакшен.

</div>
