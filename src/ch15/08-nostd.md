# 15.8. Коллекции без кучи и фрагментация

На микроконтроллере кучи может не быть вовсе, а если есть — она крохотная
и своя. Эта глава до сих пор молча полагалась на глобальный распределитель;
здесь его нет по умолчанию, и коллекции выбирают исходя из этого.

## heapless: ёмкость в типе

Крейт `heapless` даёт `Vec`, `String`, `Deque`, `FnvIndexMap`, которые
держат элементы прямо в себе, а ёмкость получают параметром типа. Памяти
они не просят никогда: место кончилось — вставка возвращает `Err`. На
микроконтроллере это обычный исход, а не авария.

```rust

```

Девятый датчик в карту на восемь не влезает, и его номер возвращается
вызывающему — решать, что делать, будет он, а не распределитель. То же с
отчётом в `heapless::String<16>` (вместо `snprintf` в `char[16]`) и
очередью кадров в `Deque`:


Размеры этих коллекций известны при компиляции — элементы внутри, рядом
длина:

```rust

```

На 32-битной цели `Vec<u8, 16>` — 20 байт (16 данных + 4 на длину
`usize`), а `Vec<u8, 16, u8>` — 17: третий параметр задаёт тип длины, и
`u8` экономит три байта. `String<16>` — 20, `Deque<[u8;18], 4>` — 84,
`FnvIndexMap<u16, i32, 8>` — 100. Для сравнения `alloc::vec::Vec<u8>` —
12 байт, но за ними стоит куча.

## heapless push без вызовов

```rust
{{#include ../../code/ch15/src/codegen.rs:hpush}}
```

Горячий путь — сравнение длины с константой-ёмкостью, без единого вызова.
На `x86_64`:

```asm
ch15_hpush:
    mov   rax, [rdi]          ; len
    cmp   rax, 7
    ja    .full
    mov   [rdi + 4*rax + 8], esi  ; buf[len] = x
    lea   rcx, [rax + 1]
    mov   [rdi], rcx          ; len += 1
.full:
    cmp   rax, 8
    setb  al                  ; вернуть len < 8 (было место)
    ret
```

На Cortex-M3 те же действия — но в одной условной группе `itttt`:

```asm
ch15_hpush:
    ldr    r2, [r0]           ; len
    cmp    r2, #7
    itttt  ls                 ; если len <= 7, выполнить следующие 4
    addls  r3, r2, #1
    strls  r3, [r0]           ; len += 1
    addls.w r0, r0, r2, lsl #2
    strls  r1, [r0, #4]       ; buf[len] = x
    movs   r0, #0
    cmp    r2, #8
    it     lo
    movlo  r0, #1
```

`itttt ls` — особенность Thumb-2: одно сравнение и до четырёх инструкций
под его условием без ветвлений. На Cortex-M0 (`thumbv6m`) блока `it` нет,
и компилятор ставит обычный `bhi`:

```asm
ch15_hpush:
    ldr    r2, [r0]
    cmp    r2, #7
    bhi    .full
    adds   r3, r2, #1
    str    r3, [r0]
    lsls   r3, r2, #2          ; r3 = len * 4
    adds   r0, r0, r3
    str    r1, [r0, #4]
.full:
    ...
```

На M0 нет и адресации со сдвигом регистра (`[r0, r2, lsl #2]`), поэтому
индекс умножается на 4 отдельной инструкцией `lsls`. Тест
`rustc_heapless_push_no_calls` в `tests/asm.rs` проверяет, что ни на одной
цели в теле нет `call`/`bl`.

## Когда куча всё-таки есть

Если кучу подключить (крейт `embedded-alloc`), заработают `alloc::Vec`,
`Box`, `String`. Прошивка `firmware/ch15-heap` ставит распределитель
`LlffHeap` на статический массив в 4 КиБ и повторяет опыты главы на
Cortex-M0, M3 и M4F — результат на всех трёх одинаков:

```rust
{{#include ../../firmware/ch15-heap/src/main.rs:heap}}
```

```console
$ cd firmware && cargo run --release -p ch15-heap
куча 4096 байт, занято 0, свободно 4096
Vec<u32> до 100 элементов: ёмкость 128, переездов 6
```

`LlffHeap` — простой распределитель-список, у него нет своего `realloc`,
поэтому рост `Vec` всегда выделяет новый блок и копирует: шесть переездов
на пути к ёмкости 128, тогда как glibc на хосте растил бы на месте. На
микроконтроллере это важно: каждый переезд оставляет освобождённую дыру.

## Фрагментация

Куча в 4 КиБ переживает несколько циклов выделения и освобождения, и дыры
в ней накапливаются:

```rust
{{#include ../../firmware/ch15-heap/src/main.rs:fragment}}
```

```console
8 блоков по 480: занято 3872, свободно 224
каждый второй освобождён: занято 1952, свободно 2144
800 байт одним куском: memory allocation failed because the memory allocator returned an error
после освобождения соседа: 800 байт есть
```

Свободно 2144 байта — но одним куском в 800 байт их не выдать: свободные
480-байтовые дыры стоят вперемешку с занятыми блоками, и ни одна не
вмещает 800. Стоит освободить соседний блок, и две дыры сливаются в одну
— запрос проходит. Это фрагментация: памяти хватает, а подряд её нет.
`try_reserve_exact` здесь не авария, а рабочий инструмент: он сообщает о
нехватке, и прошивка решает, что делать, вместо того чтобы упасть.

<div class="box trap">

**Ловушка.** `vec![0u8; 5000]` не умеет вернуть ошибку: при нехватке он
зовёт `handle_alloc_error`, а в `no_std` это паника. Последний опыт
прошивки просит 5000 байт у кучи в 4096 — и завершается паникой
«memory allocation of 5000 bytes failed». Там, где память может не
найтись, нужен `try_reserve`, а не `vec!` или `push`.

</div>
