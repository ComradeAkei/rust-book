# 15. Коллекции и аллокация

## Мотивирующая проблема

Станция телеметрии хранит последние измерения каждого датчика. На C это
обычно самодельная хеш-таблица: массив, своя хеш-функция, открытая
адресация. Вот её сердцевина — так пишут в каждом втором проекте:

```c
struct slot { char *name; long value; int used; };
struct table { struct slot *slots; size_t cap, len; };

static size_t hash(const char *s) {        /* K&R, «The C Programming Language» */
    size_t h = 0;
    for (; *s; s++) h = *s + 31 * h;
    return h;
}

long *get(struct table *t, const char *name) {
    size_t i = hash(name) % t->cap;
    while (t->slots[i].used) {
        if (strcmp(t->slots[i].name, name) == 0)
            return &t->slots[i].value;        /* указатель внутрь slots */
        i = (i + 1) % t->cap;
    }
    return NULL;
}
```

В этом коде три мины, и ни одну компилятор не покажет.

1. `get` возвращает указатель внутрь массива `slots`. Следующая вставка
   может переполнить таблицу, вызвать `realloc`, и массив переедет. Все
   ранее выданные указатели станут висячими — и те, что лежат в
   локальных переменных вызвавшего. Это тот же висячий указатель, что и
   у `realloc` из [главы 3](../ch03/index.md), только спрятанный за
   абстракцией.
2. `hash` — функция из учебника Кернигана и Ритчи. На настоящих данных
   она неплоха, но это открытая функция без секрета: кто угодно
   подберёт имена с одинаковым хешем, таблица выродится в список, и
   каждая вставка станет линейным поиском. Мы это измерим: на подобранных
   именах одна вставка делает **4095** сравнений вместо **13**.
3. `strcmp`, `used`, `% cap` в каждом шаге — и ни одной проверки, что
   `name` вообще не `NULL`, что таблица не заполнена целиком (тогда цикл
   не кончится), что при копировании строки хватило памяти.

Rust даёт те же структуры данных в стандартной библиотеке — и устраняет
все три мины на уровне типов и устройства.

## Что делает Rust

- `Vec`, `String`, `HashMap`, `BTreeMap`, `VecDeque`, `BinaryHeap` — в
  `std`, проверены, отлажены. Самодельная таблица в прикладном коде —
  почти всегда преждевременная и опасная оптимизация.
- Указатель внутрь коллекции — это заём (`&mut V`), и пока он жив,
  вставка в ту же коллекцию не компилируется: E0502. Висячий указатель
  после `realloc` в Rust — ошибка компиляции, а не загадочный сбой в
  проде.
- `HashMap` по умолчанию берёт SipHash-1-3 со случайным ключом на каждый
  запуск. Подобрать коллизии заранее нельзя: это защита от HashDoS,
  встроенная в тип. Где секрет не нужен (ключи свои, не из сети), ставят
  быстрый хешер одной строкой.
- Аллокатор — это тип, реализующий `GlobalAlloc`. Его можно заменить на
  свой: считающий, арену, пул. На микроконтроллере, где `malloc` нет,
  коллекции `heapless` живут на стеке, а их размер известен при
  компиляции.

За всё это платят знанием устройства: как растёт `Vec`, когда `malloc`
переходит на `mmap`, почему `Vec<Box<T>>` в разы медленнее `Vec<T>` при
обходе, сколько памяти занимает узел `HashMap`. Эта глава — про
устройство, потому что без него коллекции применяют вслепую.

## Код главы

Все фрагменты взяты из файлов репозитория и проверяются:

```console
$ cargo test -p ch15                          # примеры и наблюдения
$ cargo +nightly miri test -p ch15            # те же под Miri
$ cargo run -p ch15 --example growth          # рост Vec и переходы malloc на mmap
$ cargo run -p ch15 --example swiss           # раскладка SwissTable
$ cargo run -p ch15 --example registry        # вырождение самодельной таблицы
$ cargo run -p ch15 --example bench           # локальность, хешеры, поиск
$ cargo run -p ch15 --example trace           # аллокатор-трассировщик
$ cd firmware && cargo run --release -p ch15-heap   # куча и фрагментация на Cortex-M
```

Числа в тексте сняты на rustc 1.97.0 для `x86_64-unknown-linux-gnu`
(glibc 2.39), `thumbv6m-none-eabi`, `thumbv7m-none-eabi` и
`thumbv7em-none-eabihf`. Ассемблер — `cargo asm --simplify` из
release-сборки. Размеры блоков распределителя и число системных вызовов
зависят от версии аллокатора; здесь это glibc 2.39 и `hashbrown` из std
1.97.
