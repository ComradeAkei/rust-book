# 15.6. Аллокатор: GlobalAlloc, Layout, арены

Всё, что до сих пор выделяло память, звало один и тот же распределитель —
глобальный. Это тип, реализующий `GlobalAlloc`, и его можно заменить
своим: считающим обращения, ареной, пулом фиксированных блоков. На хосте
по умолчанию стоит системный `malloc`, на микроконтроллере — тот, что вы
поставите сами ([раздел 15.8](08-nostd.md)).

## Layout: размер и выравнивание

Распределитель работает не с типами, а с `Layout` — парой «размер,
выравнивание». `Layout::extend` складывает раскладку по правилам C — ровно
то, что компилятор делает для `repr(C)` из [главы 6](../ch06/02-repr-c.md):

```rust
{{#include ../../code/ch15/src/alloc_api.rs:repr_c}}
```

Для полей `u8`, `u32`, `u16` это даёт смещения `[0, 4, 8]`, размер 12,
выравнивание 4 — и тест сверяет их с `offset_of!` настоящей `repr(C)`-структуры.
`Layout::array::<u64>(n)` считает раскладку массива и возвращает ошибку
при переполнении: размер, который не влезает в `usize`, нельзя даже
попросить.

## alloc и dealloc вручную

Выделить блок напрямую — как `malloc` и `free`, только типизированно:

```rust
{{#include ../../code/ch15/src/alloc_api.rs:manual}}
```

Три отличия от C бросаются в глаза. Блок нулевого размера просить нельзя —
это UB, поэтому `n == 0` отсечён заранее. Память из `alloc` не
инициализирована — читать до записи нельзя, Miri ловит это. И `dealloc`
получает тот же `Layout`, что `alloc`: распределителю не обязательно
хранить размер в заголовке блока, его сообщает вызывающий (в C `free`
знает размер сам — отсюда лишнее слово на каждый блок).

<div class="box c">

**Как в C.** `malloc` прячет размер блока в скрытом заголовке перед
указателем, чтобы `free` знал, сколько освобождать. Rust передаёт
`Layout` обратно в `dealloc`, и заголовок не нужен: `Vec` и `Box` хранят
размер и так. Экономия — слово на каждый блок, а заодно нет шанса вызвать
`free` с неверным указателем на середину блока: тип не даст.

</div>

## Свой глобальный распределитель

`GlobalAlloc` — это четыре метода: `alloc`, `alloc_zeroed`, `realloc`,
`dealloc`. Распределитель-трассировщик записывает каждое обращение, а сам
работу делает системный:

```rust
{{#include ../../code/ch15/src/alloc_api.rs:impl}}
```

Ставится он атрибутом `#[global_allocator]` на статическую переменную:

```rust
{{#include ../../code/ch15/examples/trace.rs:install}}
```

С этого момента каждое выделение в программе проходит через `Trace`.
Записывать обращения сложнее, чем кажется: запись не должна сама выделять
память (иначе каждое выделение звало бы распределитель рекурсивно),
поэтому буфер записей — массив атомиков фиксированного размера, а флаг
«сейчас пишем» лежит в `thread_local` с `const`-инициализацией и без
`Drop`:

```rust
{{#include ../../code/ch15/src/alloc_api.rs:trace}}
```

`record` включает запись на время вызова `f` и возвращает список обращений:

```rust
{{#include ../../code/ch15/src/alloc_api.rs:record}}
```

Пример `trace` прогоняет через него разные операции:

```console
$ cargo run -p ch15 --example trace
vec![1u32, 2, 3]                 alloc 12/4
vec![0u64; 1000]                 alloc_zeroed 8000/8
Vec<u32>, 9 раз push             alloc 16/4, realloc 16→32/4, realloc 32→64/4
String::from("датчик")           alloc 12/1
format!("{}={}", s, v)           alloc 8/1, realloc 8→16/1
Vec<()>, 1000 раз push           ничего
HashMap::new()                   ничего
HashMap<u32, u32>, 1 insert      alloc 52/16
BTreeMap<u32, u32>, 12 insert    alloc 96/4, alloc 104/8, alloc 200/8, alloc 104/8, dealloc 96/4
into_boxed_slice при len < cap   alloc 100/1, realloc 100→4/1
drop(Vec<u32> на 16)             dealloc 64/4
```

Здесь видно всё, о чём шла речь: `vec![0u64; 1000]` — это `alloc_zeroed`
(распределитель сам зануляет, не пишет тысячу нулей следом); девять `push`
проходят ёмкости 4→8→16 через `realloc`; `Vec<()>` и пустой `HashMap` не
выделяют ничего; первый ключ `HashMap<u32,u32>` — это 52 байта; рост
`BTreeMap` виден как череда узлов (104 — лист, 200 — внутренний);
`into_boxed_slice` при неполном векторе ужимает буфер `realloc`-ом.
Аллокатор-счётчик из этого же семейства — задача [B](10-tasks.md) и шаг
проекта [П15](11-project.md).

## Арены

Когда у множества мелких объектов одна судьба — они живут до конца разбора,
потом уничтожаются все разом, — выделять каждый отдельно расточительно.
Арена (bump-аллокатор) выделяет большой кусок и раздаёт из него по
указателю, сдвигая границу; освобождение — сброс всей арены сразу.
Синтаксическое дерево — классический случай: это задача [C](10-tasks.md),
где арена сравнивается с `Box` по времени, памяти и числу системных
вызовов.
