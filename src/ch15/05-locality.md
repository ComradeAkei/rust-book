# 15.5. Локальность данных

Выбор коллекции — это чаще выбор раскладки памяти, чем выбор асимптотики.
Процессор читает память не байтами, а кэш-линиями по 64 байта, и угадывает
наперёд (аппаратная предвыборка), когда доступ идёт подряд. Коллекция, чьи
элементы лежат рядом, обгоняет ту, что прыгает по куче, в разы — при одной
и той же O(n).

узел — отдельное выделение):

Пример `bench`, время на один элемент при суммировании:

```console
$ cargo run --release -p ch15 --example bench
Vec<u64>:                      0.40 нс
Vec<Box<u64>>, по порядку:     2.55 нс
Vec<Box<u64>>, вперемешку:    12.59 нс
LinkedList<u64>, подряд:       5.18 нс
LinkedList<u64>, вперемешку:  22.71 нс
```

`Vec<u64>` — 0,4 нс на элемент: предвыборка успевает подать следующую
линию, процессор почти не ждёт память. `Vec<Box<u64>>` даже при блоках,
выделенных подряд, уже 2,5 нс — лишнее разыменование и восемь байт
указателя вместо данных. Стоит перемешать порядок обхода — 12,6 нс:
каждый элемент в своей линии, предвыборка бессильна. `LinkedList`
медленнее всех: обход по определению последователен (адрес следующего
узла известен только после чтения текущего), и вперемешку это 22,7 нс —
в полсотни раз медленнее вектора.

<div class="box ref">

**Как устроена память.** Промах кэша последнего уровня стоит порядка
сотни тактов — десятки наносекунд. `Vec<u64>` на 10 000 элементов — это
80 КБ, восемь значений в линии: один промах на восемь элементов, и тот
предсказан. Список из тех же значений вразброс — промах почти на каждый
узел, и ни один не предсказан, потому что адрес узла становится известен
только после чтения предыдущего. Отсюда правило: по умолчанию `Vec`, а
`LinkedList` — только когда действительно нужны O(1)-склейка списков или
стабильные адреса узлов. На практике почти никогда.

</div>

## VecDeque::get без деления

`VecDeque` — кольцо, и `get(i)` должен превратить логический индекс в
физический с учётом смещения головы. Наивно это `(head + i) % cap` с
делением. Но `head < cap` и `i < len ≤ cap`, так что сумма меньше
`2 · cap`, и остаток сводится к одному сравнению и условному вычитанию —
деления нет. Степенью двойки ёмкость при этом быть не обязана:
`VecDeque::with_capacity(10)` даёт ровно 10.

```rust
{{#include ../../code/ch15/src/codegen.rs:deque_get}}
```

На `x86_64`:

```asm
ch15_deque_get:
    cmp   rsi, [rdi + 24]   ; i >= len? -> None
    jae   .none
    add   rsi, [rdi + 16]   ; i + head
    mov   rax, [rdi]        ; cap
    xor   ecx, ecx
    cmp   rsi, rax
    cmovae rcx, rax         ; если i+head >= cap, вычесть cap
    mov   rax, [rdi + 8]    ; ptr
    sub   rsi, rcx
    mov   edx, [rax + 4*rsi]; buf[i + head - (cap или 0)]
    mov   eax, 1            ; Some
    ret
.none:
    xor   eax, eax          ; None
    ret
```

Ни `div`, ни `idiv`: вместо остатка — сравнение и `cmovae` (условное
пересылание без ветвления). Тест `rustc_deque_index_without_division` в
`tests/asm.rs` проверяет, что в теле нет инструкций деления. Это цена
кольца: индексация чуть дороже, чем у `Vec` (там просто `ptr + i`), но
без деления и без ветвления.
