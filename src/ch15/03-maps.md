# 15.3. HashMap: SwissTable и SipHash

`HashMap` в `std` — это порт SwissTable, таблицы с открытой адресацией из
библиотеки `hashbrown` (та же, что в Abseil у Google). От самодельной
таблицы из вступления она отличается тремя вещами: раскладкой,
рассчитанной на кэш и SIMD; ключом хеша, случайным на каждый запуск; и
тем, что указатель в неё — это заём.

## entry вместо «проверить, потом вставить»

Счёт измерений по датчику на C — это `get`, потом, если не нашлось,
`put`: два поиска. `entry` делает один:

```rust
{{#include ../../code/ch15/src/maps.rs:entry}}
```

`entry(n)` находит место ключа один раз и отдаёт его под изменение:
`or_insert(0)` кладёт ноль, если ключа не было, и в обоих случаях
возвращает `&mut` на значение. Ни `contains_key`, ни повторного поиска.

## Указатель в таблицу не переживает вставку

```rust,compile_fail
let mut m: HashMap<&str, u32> = HashMap::new();
m.insert("adc0", 0);
let adc = m.get_mut("adc0").unwrap();
m.insert("i2c0", 0);   // таблица может вырасти и переехать
*adc += 1;             // E0499: adc всё ещё заимствует m
```

Это та же мина, что указатель `long *` внутрь `slots` в C: вставка роняет
таблицу в новый буфер, и прежний указатель висит. В Rust `get_mut` даёт
`&mut`, а `insert` требует второго `&mut` — E0499, два изменяющих займа.
Компилятор не даёт висячему указателю появиться.

## Как устроена SwissTable

Блок таблицы — это массив корзин (пар ключ-значение) и за ним
управляющий массив из одного байта на корзину плюс 16 байт хвоста.
Пример `swiss` читает управляющие байты только что выделенной таблицы:

```console
$ cargo run -p ch15 --example swiss
HashMap<u64, u64>, 15 ключей: ёмкость 28, корзин 32, блок 560 байт = 32 × 16 + 32 + 16
управление: 00 2d 5b ff ff 45 72 ff ff 5c ff 0a ff 74 ff 21 ff ...
хвост:      00 2d 5b ff ff 45 72 ff ff 5c ff 0a ff 74 ff 21 (копия первых 16)
ключ  300: h1 =  9, h2 = 5c, байт 5c в позиции 9
ключ  700: h1 =  1, h2 = 2d, байт 2d в позиции 1
ключ 1100: h1 = 24, h2 = 7e, байт 7e в позиции 24
```

Хеш ключа делится надвое. Младшие биты (`h1`) выбирают группу из 16
корзин, с которой начинается поиск; старшие семь (`h2 = hash >> 57`) —
байт-метка, которая ложится в управляющий массив:

```rust
{{#include ../../code/ch15/src/maps.rs:h1h2}}
```

Управляющий байт `0xff` — пустая корзина, `0x80` — удалённая
(надгробие), иначе это `h2` живого ключа. Поиск читает сразу 16
управляющих байтов одной SIMD-инструкцией, сравнивает их с `h2` искомого
ключа и проверяет только совпавшие корзины. Отсюда хвост в 16 байт —
копия первых: группа у края таблицы читается без выхода за буфер.

<div class="box hood">

**Под капотом.** Блок таблицы — `round16(корзин × pair) + корзин + 16`
байт, где `pair` — размер пары ключ-значение. Для `HashMap<u64, u64>`
(`pair = 16`) ёмкости растут как 3, 7, 14, 28, 56…, а блоки — 84, 152,
288, 560 байт. `HashMap<u32, u32>` при трёх ключах — 52 байта,
`HashSet<u8>` — 48 (минимум 16 корзин). Без SSE2 и под Miri группа не 16,
а 8 байт (выравнивание 8). Тест `observed_swiss_table_blocks` в
`tests/alloc.rs` сверяет эти размеры с реально выданными распределителю.

</div>

## SipHash и защита от HashDoS

По умолчанию `HashMap` хеширует ключи SipHash-1-3 со **случайным** ключом,
который выбирается при создании каждой таблицы. Подобрать заранее набор
ключей с одинаковым хешем нельзя: ключ хеша неизвестен и у каждого
процесса свой. Это защита от атаки HashDoS — когда злоумышленник шлёт
данные, вырождающие таблицу в список.

Чтобы увидеть, от чего защита, возьмём хеш из K&R (раздел 6.6 их книги —
ровно функция `hash` из вступления) и натравим на него подобранные имена.
У строк «Aa» и «BB» один хеш K&R, а значит, и у любой их склейки равной
длины:


```rust

```

Пример `registry` вставляет 8192 имени в таблицу с каждым хешером:

```console
$ cargo run --release -p ch15 --example registry
SipHash, обычные имена:  8192 штук,    0.1 сравнений на вставку,   0.8 мс
SipHash, имена из Aa/BB:  8192 штук,    0.1 сравнений на вставку,   0.9 мс
K&R    , обычные имена:  8192 штук,   13.1 сравнений на вставку,   1.0 мс
K&R    , имена из Aa/BB:  8192 штук, 4095.5 сравнений на вставку, 111.2 мс
```

С SipHash подобранные имена ничем не отличаются от обычных: 0,1 сравнения
на вставку. С K&R обычные имена дают 13 сравнений (функция посредственная,
но рабочая), а подобранные — **4095,5**: таблица выродилась в линейный
поиск, и 8192 вставки заняли сто миллисекунд вместо одной. Это и есть
HashDoS, и именно его убирает случайный ключ SipHash.

## Быстрый хешер, когда секрет не нужен

SipHash медленнее простых хешеров: он криптографический. Когда ключи свои,
не из сети (числа датчиков, внутренние идентификаторы), атака невозможна,
и SipHash можно заменить на быстрый: `FxHashMap` из `rustc-hash` или
`foldhash`. Это одна строка — смена параметра `S` в `HashMap<K, V, S>`.
По замеру из примера `bench` поиск по 4096 ключам `u64` стоит 11,0 нс на
SipHash, 2,0 нс на Fx и 2,1 нс на foldhash. На миллионе ключей разрыв
сужается (48,5 против 11,6 нс): там всё больше решают промахи кэша, а не
сам хеш.

```console
[13, 3, 1, 6, 15, 0, 7, 9, 11, 4, 10, 2, 5, 8, 14, 12]
```

<div class="box trap">

**Ловушка.** Нельзя полагаться на порядок обхода `HashMap`: ни в тестах,
ни в выводе, ни тем более в протоколе. Код, который «работал», потому что
ключи случайно шли по порядку, сломается на другом запуске. Нужен
порядок — берите `BTreeMap` (следующий раздел) или соберите ключи в `Vec`
и отсортируйте.
