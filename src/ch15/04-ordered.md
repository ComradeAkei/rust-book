# 15.4. BTreeMap, VecDeque, BinaryHeap

`HashMap` быстр, но не хранит порядок. Когда нужен обход по возрастанию
ключа или запрос «все измерения за интервал времени», берут
упорядоченную коллекцию — или отсортированный `Vec`.

## BTreeMap: запросы по диапазону

`BTreeMap` держит ключи отсортированными в B-дереве и умеет отдавать
отрезок:

```rust
{{#include ../../code/ch15/src/ordered.rs:btree_range}}
```

`range(from..to)` находит начало за O(log n) и дальше идёт по ключам в
порядке возрастания. На самодельной хеш-таблице такой запрос потребовал
бы обойти всё и отсортировать.

<div class="box hood">

**Под капотом.** Узел `BTreeMap` — не два указателя на потомков, как в
бинарном дереве, а массив из нескольких пар и массив ссылок на потомков
(до 11 пар и до 12 потомков). Это ради кэша: один узел — несколько
кэш-линий подряд, а не прыжок по куче на каждое сравнение. Для
`BTreeMap<u32, u32>` лист занимает 104 байта, внутренний узел — 200.
Тест `observed_btree_nodes` сверяет эти размеры с выданными
распределителю.

</div>

## Отсортированный Vec часто быстрее

Если измерения приходят уже по времени и таблица не меняется после
загрузки, `BTreeMap` не нужен: отсортированный `Vec` с двоичным поиском
кладёт данные подряд, одним куском, и обгоняет дерево на обходе.

```rust
{{#include ../../code/ch15/src/ordered.rs:sorted_vec}}
```

`partition_point` — двоичный поиск первой точки, где условие становится
ложным. Два вызова дают границы отрезка. По замеру из `bench` на поиск
одного ключа:

```console
$ cargo run --release -p ch15 --example bench
    1024 ключей: Vec + binary_search   8.1 нс, BTreeMap  38.1 нс, HashMap  10.9 нс
   65536 ключей: Vec + binary_search  32.2 нс, BTreeMap  81.6 нс, HashMap  14.2 нс
 1048576 ключей: Vec + binary_search 207.4 нс, BTreeMap 175.8 нс, HashMap  46.1 нс
```

На тысяче ключей отсортированный `Vec` даже обгоняет `HashMap`: данные в
одной кэш-линии, хеш считать не надо. С ростом размера двоичный поиск
начинает платить за промахи кэша на каждом шаге (`log n` прыжков по
большому массиву), и на миллионе ключей `BTreeMap` его догоняет, а
`HashMap` уходит вперёд: один-два промаха на поиск против двадцати. Вывод
не «что-то всегда быстрее», а «измерьте на своём размере»: на малых
таблицах отсортированный срез бьёт обе карты.

## VecDeque: кольцо последних измерений

`VecDeque` — это `Vec`, замкнутый в кольцо: добавление и удаление с обоих
концов за O(1). Он идеален для окна последних `N` измерений — старое
уходит с головы, новое приходит в хвост, буфер не растёт после первых `N`:

```rust
{{#include ../../code/ch15/src/ordered.rs:window}}
```

`with_capacity(n)` выделяет буфер один раз, а `push` при полном кольце
сначала снимает голову (`pop_front`), потом дописывает хвост — без
реаллокации. `as_slices` отдаёт две части кольца: от головы до конца
буфера и от начала буфера (кольцо «перехлестнулось»). Этот приём — основа
шага проекта [П15](11-project.md), где у каждого датчика своё кольцо.

<div class="box trap">

**Ловушка.** `VecDeque` — кольцо, поэтому его элементы в памяти не всегда
подряд: `as_slices` может вернуть две части. Если нужен один непрерывный
срез, есть `make_contiguous`, но он сдвигает элементы. Индексация
`deque[i]` работает, но это не адрес `ptr + i`, а вычисление с учётом
головы.

</div>

## BinaryHeap: очередь по сроку

Опрос датчиков по расписанию — это «достать ближайший срок». `BinaryHeap`
— двоичная куча: вершина всегда максимум. Чтобы вершиной был ближайший
(минимальный) срок, элементы оборачивают в `Reverse`:

```rust
{{#include ../../code/ch15/src/ordered.rs:timers}}
```

`push` и `pop` — O(log n), `peek` — O(1). `due(now)` снимает с вершины
все сроки, не превышающие `now`, в порядке возрастания. Пара
`(срок, датчик)` сравнивается по сроку в первую очередь, поэтому при
равных сроках порядок определяется номером датчика — детерминированно,
без случайности `HashMap`.
