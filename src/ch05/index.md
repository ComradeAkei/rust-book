# 5. Времена жизни

## Мотивирующая проблема

Прошивка читает конфигурацию построчно и хранит записи «ключ = значение».
Чтобы не копировать строки, запись хранит указатели прямо в буфер
строки: `parse` ставит `'\0'` на месте `=` и перевода строки и запоминает
два начала.

```c
{{#include ../../code/ch05/c/config.c}}
```

Три строки на входе, три записи на выходе — и все одинаковые:

```console
$ printf 'rate=100\nport=uart1\nmode=burst\n' | ./config
mode = burst
mode = burst
mode = burst
```

`fgets` каждый раз пишет в тот же `line`, и все записи смотрят в него.
Последняя прочитанная строка — `mode=burst`, её и видят все три записи.
Если в конце файла есть пустая строка, она перепишет начало буфера, и
ключи превратятся в перевод строки, а значения уцелеют только потому,
что лежат дальше:

```console
$ printf 'rate=100\nport=uart1\nmode=burst\n\n' | ./config

 = burst

 = burst

 = burst
```

Обращения к освобождённой памяти здесь нет: `line` жив до конца `main`.
Поэтому молчат все инструменты, которые ловили ошибки в главах 3 и 4:
`gcc -Wall -Wextra -fanalyzer`, `clang --analyze`, [AddressSanitizer][g-asan] и
[UBSan][g-ubsan]. Память цела, испорчены данные: указатель пережил *содержимое*, на
которое указывал. В C этот контракт живёт в комментарии к функции —
«указатели действительны до следующего вызова `fgets`» — и проверить его
нечем. Обычное лекарство — `strdup` для каждого поля, то есть выделение
памяти на каждую строку конфигурации.

## Что делает Rust

Тот же код на Rust не компилируется (текст — в [doc-тесте][g-doctest]
`code/ch05/src/config.rs`):

```text
error[E0502]: cannot borrow `line` as mutable because it is also borrowed as immutable
  --> config_0.rs:17:27
   |
17 |     while input.read_line(&mut line).unwrap() > 0 {
   |                           ^^^^^^^^^ mutable borrow occurs here
18 |         if let Some(e) = parse(&line) {
   |                                ----- immutable borrow occurs here
...
23 |     for e in &cfg {
   |              ---- immutable borrow later used here
```

Ошибка та же, что в главе 4, — читатель и писатель. Новое в другом.
Компилятор смотрел только на сигнатуру `parse`:

```rust,ignore
struct Entry<'a> {
    key: &'a str,
    val: &'a str,
}

fn parse(line: &str) -> Option<Entry<'_>>
```

и из неё узнал, что запись [заимствует][g-borrowing] `line`. Тело `parse` он при проверке
`main` не читал. Связь между входной и выходной ссылкой записана в типах.

- *Время жизни* (lifetime) — имя для участка программы, на котором ссылка
  действительна. Пишется `'a`, стоит в типах ссылок (`&'a str`) и
  структур (`Entry<'a>`). Сигнатура `fn parse<'a>(line: &'a str) ->
  Option<Entry<'a>>` говорит: запись действительна, пока действителен
  `line`.
- В простых сигнатурах времена жизни можно не писать: их подставляют три
  правила [элизии][g-elision] (раздел [5.1](01-elision.md)). `parse` выше — как раз
  такой случай.
- Структура со ссылками объявляет время жизни параметром и не может
  пережить данные, на которые смотрит. Разбор без копирования — [срезы][g-slice]
  входного буфера вместо `strdup` — становится безопасным
  (раздел [5.2](02-structs.md)).
- Время жизни существует только во время компиляции. В машинном коде
  его нет, функции, которые различаются только временами жизни,
  компилируются в одну (раздел [5.3](03-static.md)).

Исправленная программа читает весь текст сразу и разбирает его без
копирования — записи смотрят в текст, а текст не меняется, пока они
живы:

```rust
{{#include ../../code/ch05/src/config.rs:entry}}
```
