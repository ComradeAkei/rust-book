# 5.1. Аннотации и правила элизии

## Откуда взята ссылка

Функция выбирает из двух строк более длинную:

```rust,ignore
pub fn longest(a: &str, b: &str) -> &str {
    if a.len() >= b.len() { a } else { b }
}
```

Тело правильное, но компилятор отказывается:

```text
error[E0106]: missing lifetime specifier
 --> elision_0.rs:3:37
  |
3 | pub fn longest(a: &str, b: &str) -> &str {
  |                   ----     ----     ^ expected named lifetime parameter
  |
  = help: this function's return type contains a borrowed value, but the signature does not say whether it is borrowed from `a` or `b`
help: consider introducing a named lifetime parameter
  |
3 | pub fn longest<'a>(a: &'a str, b: &'a str) -> &'a str {
  |               ++++     ++          ++          ++
```

Подсказка в `help` объясняет причину: по сигнатуре не видно, у какого
аргумента заимствован результат. А проверять вызовы компилятор будет
именно по сигнатуре — так же, как в главе 4 он проверял `push`, не читая
её тела. Пусть вызывающий освобождает `b` и продолжает пользоваться
результатом: допустимо это или нет, зависит от того, откуда результат.
Тело может поменяться в следующей версии библиотеки, сигнатура — это
контракт.

Исправленная сигнатура с параметром времени жизни:

```rust
{{#include ../../code/ch05/src/elision.rs:longest}}
```

`<'a>` объявляет параметр, как `<T>` объявляет тип. `&'a str` — ссылка,
действительная по крайней мере на участке `'a`. Сигнатура говорит: обе
ссылки на входе действительны на `'a`, и результат действителен там же.
Конкретное `'a` выбирает компилятор в месте вызова — самый длинный
участок, на котором живы оба аргумента. Если один из них умрёт раньше,
результат умрёт вместе с ним:

```text
error[E0597]: `mode` does not live long enough
  --> elision_2.rs:9:27
   |
 8 |     let mode = String::from("burst");
   |         ---- binding `mode` declared here
 9 |     best = longest(&port, &mode);
   |                           ^^^^^ borrowed value does not live long enough
10 | }
   | - `mode` dropped here while still borrowed
11 | println!("{best}");
   |            ---- borrow later used here
```

Здесь `port` длиннее `"burst"`, и в действительности функция вернёт
ссылку на `port`, которая жива. Компилятор этого не знает и знать не
должен: по контракту результат может быть и `&mode`.

Аннотация ничего не продлевает. Она описывает отношения между ссылками,
которые и так есть, и не меняет, сколько живёт значение. Вернуть ссылку
на локальную строку нельзя никакой аннотацией:

```text
error[E0515]: cannot return reference to local variable `s`
 --> elision_1.rs:5:5
  |
5 |     &s
  |     ^^ returns a reference to data owned by the current function
```

Это функция `label(n: u32) -> &'static str` из doc-теста
`code/ch05/src/elision.rs`: `s` — `String`, созданная внутри, и после
`return` её буфер освобождён.

<div class="box c">

**Как в C.** Контракты времени жизни в C пишут в документации. `strtok`
возвращает указатель внутрь своего аргумента; `getenv` — в окружение
процесса, и строку может переписать следующий `getenv` или `setenv`;
`inet_ntoa` и `asctime` —
в свой статический буфер, который перепишет следующий вызов. Ошибка в
каждом случае та же, что во введении к главе, и компилятор C о контракте
не знает. В Rust первый контракт записывается как `fn(&'a str) -> &'a
str`, а «до следующего вызова» — как заимствование `&mut self`
(разделы [5.6](06-gat.md) и задача [5.A](08-tasks.md)).

</div>

## Три правила элизии

Большинство функций со ссылками времён жизни не пишут. Компилятор
подставляет их по трём правилам — это и называется *элизией* (lifetime elision):

1. Каждая ссылка на входе, у которой время жизни не указано, получает
   свой собственный параметр. `fn f(a: &str, b: &str)` значит `fn f<'a,
   'b>(a: &'a str, b: &'b str)`.
2. Если на входе ровно одно время жизни, оно достаётся всем ссылкам на
   выходе.
3. Если среди параметров есть `&self` или `&mut self`, ссылки на выходе
   получают время жизни `self`.

Если ни второе, ни третье правило не подходят, а ссылка на выходе есть,
это ошибка E0106, как у `longest`. Правила не пытаются угадать по телу,
они смотрят только на сигнатуру.

```rust
{{#include ../../code/ch05/src/elision.rs:elided}}
```

`trim_cr` и `trim_cr_explicit` — одна и та же функция: у `trim_cr`
одна ссылка на входе, и по правилу 2 результат получает её время жизни.
У `starts_with_ci` две ссылки на входе, но на выходе ссылок нет — правилу
1 этого достаточно.

Время жизни в типе-структуре тоже можно пропустить, но лучше показать
место знаком `'_`: `fn parse(line: &str) -> Option<Entry<'_>>`. Без
`<'_>` rustc 1.97 предупреждает (`mismatched_lifetime_syntaxes`,
включено по умолчанию): в такой сигнатуре одно и то же время жизни на
входе видно, а на выходе спрятано.

## Правило 3 и курсор по тексту

Третье правило удобно для методов, которые отдают часть объекта, — но
только пока данные принадлежат самому объекту. Курсор по чужому тексту
устроен иначе:

```rust
{{#include ../../code/ch05/src/elision.rs:parser}}
```

`Parser<'s>` хранит ссылку на текст, `'s` — время жизни текста. У
`rest_short` время жизни на выходе не указано, и правило 3 связывает
результат с `&self`, то есть с *парсером*. Срез при этом смотрит в
текст, который живёт дольше парсера, но сигнатура этого не говорит.
`tail` с `rest_short` вместо `rest` не компилируется:

```text
error[E0515]: cannot return value referencing local variable `p`
 --> elision_3.rs:7:5
  |
7 |     p.rest_short()
  |     -^^^^^^^^^^^^^
  |     |
  |     returns a value referencing data owned by the current function
  |     `p` is borrowed here
```

`rest` называет `'s` явно, и результат переживает парсер. То же у
`word`: `&mut self` заимствуется только на время вызова, а слово
получает `'s`. Поэтому в тесте два слова живут одновременно, хотя
каждое получено через `&mut p`:

```rust,ignore
let mut p = Parser::new("set baud 9600");
let a = p.word();
let b = p.word(); // два слова живы одновременно: ни одно не держит p
```

С `fn word(&mut self) -> Option<&str>` второй вызов дал бы E0499: первое
слово держало бы уникальное заимствование парсера.

<div class="box trap">

**Ловушка.** Правило 3 срабатывает и тогда, когда результат на самом
деле взят из аргумента: `fn find(&self, key: &str) -> &str` вернёт
ссылку со временем жизни `self`, даже если тело возвращает часть `key`, —
и тело не скомпилируется: «lifetime may not live long enough». Если результат не принадлежит объекту,
называйте время жизни явно.

</div>
