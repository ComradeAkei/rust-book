# 24. Процедурные макросы

Перед чтением вспомните [обычные макросы](../ch23/01-rules.md) и
[разницу между хостом и целью](../ch08/05-build-rs.md). Здесь одновременно
существуют две программы: макрос работает на компьютере разработчика и
пишет код; полученный код затем компилируется для Linux или
микроконтроллера. Разбирая пример, каждый раз спрашивайте: «это сейчас
выполняет генератор или это он записывает в будущую программу?»

## Мотивирующая проблема

Часть кода прошивки выводится из описаний, которые лежат вне программы на
C: адреса и поля регистров — из файла [SVD][g-svd] производителя, разбор
сообщений — из `.proto`, разбор конфигурации — из грамматики `.y`. В C
такой код пишет внешний генератор — отдельный шаг сборки:

```make
uart_regs.h: lm3s6965.svd gen_regs.py
	python3 gen_regs.py lm3s6965.svd > uart_regs.h

main.o: main.c uart_regs.h
```

Так устроены `protoc`, `bison`, SVDConv из [CMSIS][g-cmsis] и самописные скрипты, и у
всех одни и те же слабые места:

- генератор — отдельная программа со своей версией; её надо поставить на
  каждую машину и в CI, а выход разных версий различается;
- зависимости прописывают руками: забыли `uart_regs.h` в строке
  `main.o:` — и после правки SVD прошивка молча собирается со старым
  заголовком;
- ошибка в сгенерированном коде указывает в сгенерированный файл
  (`uart_regs.h:1412`), а не в строку описания, из-за которой она
  появилась;
- генератор не видит программу. Он знает SVD, но не знает структур из
  `main.c`: функцию печати или проверку размера для своей структуры
  программист пишет руками или [X-macro][g-x-macro] (глава 23).

Есть и код, который генерировать не из чего, но который подчиняется
правилам, не видным компилятору. Обработчик прерывания в C — функция с
правильным именем: [таблица векторов][g-vector-table] из `startup.s` в стиле CMSIS
ссылается на `UART0_IRQHandler`, а там стоит слабый псевдоним на
`Default_Handler`.
Опечатка в имени — и программа собирается, а прерывание уходит в
обработчик по умолчанию. Сигнатуру, запрет вызывать обработчик из кода и
работу со статическим состоянием тоже проверяет только ревьюер.

## Что делает Rust

**Процедурный макрос** (procedural macro) — функция на Rust, которую
компилятор вызывает во время компиляции: на входе [поток токенов][g-token-stream], на выходе
поток токенов. Живёт она в [крейте][g-crate] особого типа `proc-macro`
([8.6](../ch08/06-crate-types.md)): cargo собирает его для [хоста][g-host], а rustc
загружает как разделяемую библиотеку. Видов три:

- **derive** — `#[derive(Describe)]` на структуре: получает объявление
  типа и добавляет рядом новые элементы ([24.2](02-syn-quote.md));
- **атрибут** — `#[interrupt]` на функции: получает элемент и аргументы
  атрибута и *заменяет* элемент своим выходом ([24.4](04-attributes.md));
- **функциональный** — `token_tree!(...)` или `include_svd!("файл",
  "UART0")`: получает токены в скобках ([24.1](01-tokens.md), задача D).

Ответы на слабые места генератора:

- макрос — обычная зависимость с версией в `Cargo.lock`, и cargo собирает
  его сам;
- макрос видит программу: derive получает поля структуры и генерирует код
  из них, атрибут — сигнатуру функции и проверяет её;
- у каждого токена есть **спан** (span) — место в исходнике, — и макрос сам
  выбирает, куда покажет ошибка: в поле структуры, в литерал атрибута, в
  имя прерывания ([24.3](03-spans.md));
- сгенерированный код проходит все проверки типов и [заимствований][g-borrowing], как
  рукописный;
- файл, который прочитал макрос, становится зависимостью сборки (задача D).

Цена — тоже своя: макрос исполняет произвольный код на машине
разработчика, а библиотека разбора [`syn`][g-syn] — самый тяжёлый крейт в сборке
многих проектов ([24.6](06-cost.md)). И макрос нужно тестировать: не
только код, который он порождает, но и ошибки, которые он выдаёт
([24.5](05-testing.md)).

- Токены и три вида макросов ([24.1](01-tokens.md)) — крейт `proc-macro`,
  `TokenStream` и `TokenTree`, `proc_macro` против `proc_macro2`.
- syn и [quote][g-quote] ([24.2](02-syn-quote.md)) — разбор объявления, сборка кода
  шаблоном, [обобщения][g-generic], пути от `::core`, своё имя крейта.
- Спаны, ошибки и [гигиена][g-hygiene] ([24.3](03-spans.md)) — `syn::Error`, хорошие и
  плохие спаны, `const`-проверки, `call_site` и `mixed_site`.
- Атрибуты ([24.4](04-attributes.md)) — [атрибуты-помощники][g-helper-attribute] и `#[interrupt]`
  в духе cortex-m-rt: проверка сигнатуры, `static mut`, [переходник][g-trampoline].
- Тестирование ([24.5](05-testing.md)) — [модульные тесты][g-unit-test] на proc_macro2,
  [снимки][g-snapshot] ошибок trybuild, снимки раскрытия.
- Где и почём ([24.6](06-cost.md)) — макрос исполняется на хосте, время
  сборки syn, повторный запуск и зависимости от файлов.

Главная мысль главы: процедурный макрос пишет два текста — код для
компилятора и сообщения об ошибках для человека. Первый проверит
компилятор, второй — никто, кроме автора макроса. Макросы отличаются друг
от друга не столько тем, что генерируют, сколько тем, куда указывают их
ошибки.

## Код главы

Макросы примеров лежат в крейте `code/ch24-macros`, а их применения,
[трейты][g-trait] и функции, на которые ссылается сгенерированный код, — в
`code/ch24`. Задачи — в `exercises/ch24` и `solutions/ch24`, у каждого
из них свой крейт макросов (`*-macros`). Макросы раскрываются на хосте, а
их код — [`no_std`][g-no-std]: `ch24` [без возможности][g-feature] `std` собирается на все три
[цели][g-target] Cortex-M, а решения задач B–D использует прошивка
`firmware/ch24-tasks`.

```console
$ cargo test -p ch24 -p ch24-macros   # примеры, снимки ошибок и раскрытия, сборка для хоста
$ cargo test -p ch24-solutions        # задачи A–D
$ cd firmware && cargo run --release -p ch24-expand   # задача A в QEMU
$ cd firmware && cargo run --release -p ch24-tasks    # задачи B–D в QEMU
```

Сообщения компилятора в главе — снимки trybuild (раздел
[24.5](05-testing.md)), снятые с rustc 1.97: тест `rustc_ui` сверяет их с
закреплённым компилятором при каждом прогоне. Раскрытие макросов
показывает `rustc -Zunpretty=expanded` (флаг nightly; на stable его
открывает `RUSTC_BOOTSTRAP=1` — только для осмотра, не для сборки),
`cargo expand` печатает то же. Библиотеки — syn 3.0.9, quote 1.0.47,
proc-macro2 1.0.107 и trybuild 1.0.119.
