# 24.6. Где и почём выполняется макрос

## На хосте, даже для Cortex-M

Крейт `ch24` собирается без std для любой из трёх целей Cortex-M. Тест
`rustc_proc_macro_is_built_for_host` собирает его под thumbv7m-none-eabi
с `cargo build -v` и смотрит, что получилось:

- команда rustc для `ch24_macros` — `--crate-type proc-macro` и *без*
  `--target`, то есть для хоста; для `ch24` — `--target
  thumbv7m-none-eabi`;
- `target/debug/deps/libch24_macros-….so` — ELF для x86-64 (поле
  `e_machine` равно 62), 8,3 МБ в отладочной сборке вместе с syn;
- `target/thumbv7m-none-eabi/debug/deps/libch24-….rlib` — библиотека для
  Cortex-M.

Сборка под Cortex-M — это две сборки в одной: хостовая (сценарии сборки,
макросы и их зависимости) и целевая. У них разные возможности
зависимостей ([8.4](../ch08/04-features.md)) и разные флаги: `RUSTFLAGS`
при явном `--target` относятся только к цели
([0.5](../ch00/05-checks.md)). Отсюда и свобода макроса: он может
пользоваться std, кучей и файловой системой, даже когда код, который он
порождает, — `#![no_std]`. `include_svd!` из задачи D читает XML
крейтом roxmltree на `String` и `Vec`, а его выход работает в прошивке
без кучи.

Свобода та же, что у `build.rs` ([8.5](../ch08/05-build-rs.md)): макрос
исполняется внутри rustc с правами пользователя, который запустил
сборку, и может читать любые его файлы. Добавить в проект зависимость с
процедурным макросом — значит дать её коду выполниться на каждой машине,
где проект собирают, включая CI.

## Время сборки

Чистая сборка `ch24` в отладочном профиле на четырёх ядрах (rustc 1.97,
`cargo build --timings`):

| Крейт | Время | Начало |
|---|---|---|
| proc-macro2, quote, unicode-ident и их сценарии сборки | ≈0,7 с | 0,05 с |
| syn 3.0.9 (возможность `full`) | 2,54 с | 0,73 с |
| ch24-macros | 0,61 с | 3,26 с |
| ch24 | 0,12 с | 3,90 с |
| всего | 4,0 с | |

(медиана трёх прогонов под thumbv7m-none-eabi). Почти две трети времени
— syn, и это критический путь: `ch24` не может начаться, пока не собран
его макрос, а макрос — пока не собран syn. Возможности syn меняют время
(один syn, та же машина): по умолчанию 1,5 с, с `full` — 2,2 с, с одними
`derive`, `parsing` и `proc-macro` — 1,1–1,3 с. В исходниках syn 51 787
строк. Макросу, которому хватает разбора
`DeriveInput`, `full` не нужен; атрибуту на функции, как `#[interrupt]`,
нужен — без него syn не разбирает тело функции.

В выпускной сборке картина та же, хотя кажется, что макрос должен
собираться с оптимизациями. По умолчанию cargo собирает сценарии сборки,
процедурные макросы и все их зависимости без оптимизаций
(`[profile.release.build-override]` с `opt-level = 0`): под
`cargo build --release -v` у syn и `ch24_macros` нет `-C opt-level`, у
`ch24` — `opt-level=3`. Код макроса выполняется недолго, а собирается
каждый раз, поэтому так быстрее. Если макрос сам тяжёлый — разбирает
файл SVD на сотни периферий, — `opt-level = 3` в `build-override`
ускорит раскрытие ценой более долгой сборки макроса.

syn в сборке прошивки обычно уже есть. `cargo tree -d` в `firmware/`:

```text
syn v2.0.119
└── cortex-m-macros v0.7.8 (proc-macro)
    └── cortex-m v0.7.9
syn v3.0.9
├── ch24-solutions-macros v0.1.0 (proc-macro)
│   └── ch24-solutions v0.1.0
└── cortex-m-rt-macros v0.7.7 (proc-macro)
    └── cortex-m-rt v0.7.7
```

(`cargo tree -i syn@…`). Две мажорные версии syn собираются в одной
прошивке, потому что cortex-m и cortex-m-rt обновились в разное время
(так же дважды собираются embedded-hal 0.2 и 1.0 и nb 0.1 и 1.1). Макросы
задач главы — на syn 3 и третьей сборки не добавили: одну версию cargo
собирает один раз на весь граф.

## Каждый раз заново

Результат раскрытия не кешируется: макрос выполняется при каждой
компиляции крейта, который его вызывает, — после любой правки в этом
крейте. Инкрементальная компиляция кеширует то, что идёт *после*
раскрытия. Поэтому:

- раскрытие должно быть **детерминированным**. Выход, собранный обходом
  `HashMap` (порядок зависит от случайного зерна), даёт разные токены при
  каждой сборке — и разный код, и лишнюю перекомпиляцию всего, что от
  него зависит. Порядок — из входа, `Vec` или `BTreeMap`;
- макрос не должен зависеть от времени, сети и случайных чисел;
- дорогая работа повторяется. Пересборка крейта, где раскрывается
  `include_svd!` для двух UART, после `touch src/lib.rs` занимает 0,06 с
  — разбор XML и генерация в эту цифру входят, но файл маленький.

## Файлы и переменные окружения

Макрос, который читает файл, должен сказать об этом cargo — иначе после
правки файла крейт не пересоберётся, и прошивка выйдет со старыми
адресами регистров. API для этого, `proc_macro::tracked::path`,
нестабилен (issue #99515). Работающий на stable приём — вставить в выход
`include_bytes!` того же файла:

```rust,ignore
const _: &[u8] = include_bytes!("/полный/путь/lm3s6965.svd");
```

`include_bytes!` записывает файл в dep-info крейта (`target/…/*.d`), и
cargo следит за ним, как за исходником. Тест
`rustc_d_svd_is_build_dependency` проверяет, что путь к SVD там есть.
Байты не попадают в программу: безымянная константа никем не
используется.

Относительный путь в аргументе макроса — относительно чего? Текущий
каталог rustc выбирает cargo, и это корень рабочего пространства, а не
крейта. Каталог крейта, который вызвал макрос, дают переменная
окружения `CARGO_MANIFEST_DIR` (cargo задаёт её при каждом запуске rustc,
а макрос живёт в процессе rustc) — от него `include_svd!` и считает
путь. Сами переменные окружения читаются `std::env::var`, но cargo не
узнает, что от них что-то зависит: `tracked::env_var` тоже нестабилен.

## Когда процедурный макрос не нужен

- **`macro_rules!`** (глава 23) — без отдельного крейта и без syn,
  раскрывается быстрее. Его хватает, когда вход — свой, регулярный
  синтаксис, как у `flags!` и `peripheral!` из задач 23.B и 23.C.
  Процедурный нужен, когда надо разобрать *чужой* синтаксис —
  объявление структуры, сигнатуру функции, — указать ошибкой в точное
  место или прочитать файл.
- **`build.rs` с генерацией в `OUT_DIR`** и `include!` — генератор
  работает один раз на сборку, cargo следит за файлами через
  `cargo:rerun-if-changed`, а сгенерированный файл можно открыть и
  прочесть. Так часто встраивают `prost` и `bindgen`.
- **генерация заранее** — svd2rust запускают один раз и публикуют
  результат как обычный крейт (PAC). Сравнение с `include_svd!` по
  размеру кода и времени сборки — задача D и её разбор.
- **`const fn` и обобщения** (глава 25) — когда «генерировать» нужно не
  код, а значения.
