# 30.2. criterion и divan

Функция `bench` из раздела 30.1 — полсотни строк, и в ней уже есть
прогрев, выборки, медиана и разброс. Библиотеки замеров делают то же
тщательнее и добавляют то, чего своими руками не хочется: оценку
погрешности, сравнение с прошлым прогоном, выбор числа повторов,
отчёт. Две самые распространённые — criterion и divan.

## criterion

Замеры живут в `benches/` и подключаются в `Cargo.toml` крейта:

```toml
[dev-dependencies]
# Без графиков (plotters) и без rayon: отчёт — текст в терминале.
criterion = { version = "0.7.0", default-features = false, features = ["cargo_bench_support"] }
divan = "0.1.21"

[[bench]]
name = "crit"
harness = false
```

`harness = false` обязателен: без него cargo собирает замер со
стандартной тестовой обвязкой libtest, та ищет функции `#[bench]`, не
находит и печатает `running 0 tests` — `main` от criterion просто не
вызывается. Сам замер:

```rust,ignore
{{#include ../../code/ch30/benches/crit.rs:crit}}
```

`b.iter` вызывает замыкание столько раз, сколько решит criterion, и
сам отправляет результат в `black_box`; вход в `black_box` — наша
забота.

```console
$ cargo bench -q -p ch30 --bench crit
sum_squares/1000        time:   [379.35 ns 386.63 ns 394.59 ns]
Found 8 outliers among 100 measurements (8.00%)
  5 (5.00%) high mild
  3 (3.00%) high severe
sum_squares/10000       time:   [3.5834 µs 3.6301 µs 3.6833 µs]
Found 5 outliers among 100 measurements (5.00%)
  5 (5.00%) high severe
sum_squares/100000      time:   [35.678 µs 36.408 µs 37.271 µs]
Found 9 outliers among 100 measurements (9.00%)
  9 (9.00%) high severe
```

Строки «Benchmarking … Warming up / Collecting / Analyzing», которые
criterion печатает по ходу, здесь опущены. Что за ними стоит:

- **прогрев** — 3 секунды вызовов без счёта; заодно criterion узнаёт,
  сколько длится один вызов;
- **100 выборок за 5 секунд**, и не одинаковых: в выборке k — k·d
  вызовов, где d подобрано так, чтобы всё уложилось в 5 секунд (для
  тысячи чисел — 13 миллионов вызовов на все выборки). Время на вызов —
  наклон прямой через начало координат по точкам «вызовов в выборке —
  время выборки». Вес у точки тем больше, чем длиннее выборка, и
  постоянная цена самого замера (`Instant::now`, цикл) размазывается
  на тысячи вызовов;
- **три числа в скобках** — нижняя граница, оценка и верхняя граница
  95-процентного доверительного интервала. Интервал получен бутстрепом:
  criterion сто тысяч раз пересобирает набор выборок случайным выбором
  с возвращением и смотрит, как гуляет оценка;
- **выбросы** — выборки за пределами «заборов Тьюки» (квартиль ± 1,5 и
  ± 3 межквартильных размаха — mild и severe). Все выбросы здесь
  «high»: прерывание или вытеснение делает выборку только длиннее,
  быстрее положенного она не бывает.

Числа сходятся с нашим `bench`: 3,63 мкс на десять тысяч против
3840 нс медианы — 0,36–0,38 нс на число.

## Сравнение с прошлым прогоном — и шум

criterion сохраняет результаты в `target/criterion/` и при следующем
запуске сравнивает с ними. Второй запуск, код не менялся:

```console
$ cargo bench -q -p ch30 --bench crit
sum_squares/1000        time:   [367.99 ns 375.92 ns 386.17 ns]
                        change: [−5.1639% −1.5606% +2.1909%] (p = 0.41 > 0.05)
                        No change in performance detected.
sum_squares/10000       time:   [3.9868 µs 4.0999 µs 4.2293 µs]
                        change: [+9.4324% +13.291% +17.656%] (p = 0.00 < 0.05)
                        Performance has regressed.
sum_squares/100000      time:   [36.945 µs 37.890 µs 39.024 µs]
                        change: [−5.4848% +0.0297% +5.3561%] (p = 0.99 > 0.05)
                        No change in performance detected.
```

«Performance has regressed» на +13 % — без единого изменения в коде.
Тест criterion честный: он проверяет гипотезу «среднее время то же» и
отвергает её, если вероятность такой разницы случайно меньше 5 %
(`p = 0.00`), а сама разница больше порога шума — 1 % по умолчанию. Но он предполагает, что выборки независимы и машина та же.
Виртуальная машина с соседями эти предположения нарушает: частота и
доступное время меняются на минуты, и все сто выборок второго прогона
оказались в «медленной» полосе. На такой машине порог в 1 % бессмыслен;
его поднимают флагом, и сравнивают с сохранённой базой осознанно:

```console
$ cargo bench -p ch30 --bench crit -- --save-baseline before
$ # ... изменение кода ...
$ cargo bench -p ch30 --bench crit -- --baseline before --noise-threshold 0.05
```

Ещё надёжнее сравнивать не время, а то, что от шума не зависит, —
число инструкций (раздел [30.4](04-cachegrind.md)).

## divan

divan — более новая библиотека с тем же назначением и другим
устройством: замеры объявляются атрибутом, параметры — прямо в нём.

```rust,ignore
{{#include ../../code/ch30/benches/div.rs:div}}
```

```console
$ cargo bench -q -p ch30 --bench div
Timer precision: 22 ns
div           fastest       │ slowest       │ median        │ mean          │ samples │ iters
╰─ squares                  │               │               │               │         │
   ├─ 1000    359.7 ns      │ 708.6 ns      │ 360.9 ns      │ 364.4 ns      │ 100     │ 800
   ├─ 10000   3.532 µs      │ 16.27 µs      │ 3.538 µs      │ 3.715 µs      │ 100     │ 100
   ╰─ 100000  31.86 µs      │ 55.19 µs      │ 34.9 µs       │ 35.18 µs      │ 100     │ 100
```

divan сначала меряет точность часов (22 нс, как наш `clock_step`), а
потом подбирает число вызовов в выборке так, чтобы выборка была много
длиннее этой точности: 8 вызовов на выборку для тысячи чисел (800 на
сто выборок), по одному — для больших. Отчёт — не доверительный
интервал, а сводка выборок: самая быстрая, самая медленная, медиана и
среднее. Разница между медианой и средним (3,538 и 3,715 мкс) и
«slowest» в 16 мкс — те же выбросы, которые criterion считает
отдельно.

Что выбрать. criterion — когда нужна история и сравнение с базой:
сохранённые в `target/criterion` результаты сравнивает между собой,
например, critcmp. divan — когда замеров много
и хочется короткой записи: параметры, обобщённые функции
(`#[divan::bench(types = [...])]`), замер выделений памяти
(`divan::AllocProfiler`) из коробки; прогон быстрее. Оба собирают профиль
bench, а он наследует release.

<div class="box trap">

**Ловушка: подготовка внутри замера.** `bencher.bench(|| …)` и
`b.iter(|| …)` мерят всё, что внутри замыкания. Создание вектора
`(0..n).collect()` здесь стоит снаружи; перенесите его внутрь — и замер
покажет выделение памяти и заполнение, а не сумму. Для подготовки,
которая должна быть свежей на каждый вызов (сортировка портит вход),
есть `iter_batched` у criterion и `with_inputs` у divan: они готовят
вход вне замеряемого времени.

</div>
