# 30.6. Цена проверок: границы, переполнение, `RefCell`; ветвления

Rust платит за безопасность проверками, которых в C нет: индекс
сверяется с длиной, сложение в debug — с переполнением, `borrow_mut` —
с флагом заимствования. Разделы [1.6](../ch01/06-slices-str.md) и
[13.5](../ch13/05-codegen.md) показали, как LLVM убирает проверку
границ из цикла: выносит её до цикла или раздваивает цикл на векторную
часть без проверок и хвост с ними. Здесь — что остаётся после
оптимизатора, сколько оно стоит в наносекундах и почему почти всегда
мало. Каждая проверка — условный переход, поэтому вторая половина
раздела о том, когда переход дорог.

Граница цикла `n` чужая, и в `sum_indexed` каждое `v[i]` формально
проверяется. В ассемблере (тест `rustc_bounds_checks`) проверка одна, до
цикла, — тот же приём, что у `ch01_sum_first` в разделе 1.6:

```text
ch30::bounds::sum_indexed:
        test rdx, rdx
        je .LBB45_1
        lea rax, [rdx - 1]
        cmp rsi, rax
        jbe .LBB45_11
        ...
.LBB45_7:
        movdqu xmm2, xmmword ptr [rdi + 4*rax]
        paddd xmm1, xmm2
        movdqu xmm2, xmmword ptr [rdi + 4*rax + 16]
        paddd xmm0, xmm2
        add rax, 8
        cmp rcx, rax
        jne .LBB45_7
        ...
.LBB45_11:
        push rax
        lea rdx, [rip + .Lanon.25e7c247477188ea63ac0154dfe40e4f.30]
        mov rdi, rsi
        call qword ptr [rip + core::panicking::panic_bounds_check@GOTPCREL]
```

`n − 1 < len` проверено один раз, дальше — векторный цикл по восемь
чисел. `sum_sliced` и `sum_iter` начинаются с `cmp rdx, rsi; ja` —
проверки среза `&v[..n]` — и продолжаются тем же циклом;
`sum_unchecked` — тем же циклом без проверки. Четыре функции, один
внутренний цикл, и замер не отличает их друг от друга:


В трёх прогонах подряд `sum_indexed` — 0,14–0,15 нс на число, `sum_iter`

стала бы неопределённым поведением (раздел [0.5](../ch00/05-checks.md)).

`sum_indexed` проверяет до цикла, а паникует так, будто дошла до
плохого элемента: `mov rdi, rsi` передаёт в `panic_bounds_check` индекс,
равный длине. Так можно, потому что сумма до паники никому не видна.
`sum_sliced` падает на срезе, ещё до цикла, с другим сообщением. Тела у
`sum_sliced` и `sum_iter` почти одинаковые — порядок двух `xor` в
начале да адрес `.Lanon…` с файлом и строкой места паники. Из-за этого
адреса слить их, как двойников из раздела [30.5](05-compiler.md), LLVM
не может: у функций, которые по-разному сообщают о панике, разный код.

## Проверка, которая осталась

Проверку нельзя вынести, если индекс приходит из данных:

```rust,ignore
{{#include ../../code/ch30/src/bounds.rs:hist}}
```

```text
ch30::bounds::hist_slice:
        ...
.LBB42_2:
        movzx eax, byte ptr [rdi + r8]
        cmp rcx, rax
        jbe .LBB42_5
        inc dword ptr [rdx + 4*rax]
        inc r8
        cmp rsi, r8
        jne .LBB42_2

ch30::bounds::hist_array:
        ...
.LBB41_6:
        movzx ecx, byte ptr [rax]
        inc dword ptr [rdx + 4*rcx]
        movzx ecx, byte ptr [rax + 1]
        inc dword ptr [rdx + 4*rcx]
        movzx ecx, byte ptr [rax + 2]
        inc dword ptr [rdx + 4*rcx]
        movzx ecx, byte ptr [rax + 3]
        add rax, 4
        inc dword ptr [rdx + 4*rcx]
        cmp rax, rdi
        jne .LBB41_6
```

В `hist_slice` на каждом байте `cmp rcx, rax; jbe` — длина `h`
неизвестна, а каждый `inc` виден снаружи, поэтому паника обязана
случиться ровно на первом плохом байте, после всех предыдущих
инкрементов. Цикл и не развёрнут. В `hist_array` длина — часть типа,
`u8` всегда меньше 256, и проверять нечего: цикл развёрнут вчетверо.
Цена оставшейся проверки — от 10 до 55 % в разных прогонах (0,40–0,69
нс на байт против 0,36–0,50): переход не берётся ни разу, предсказатель
угадывает его всегда, и платим мы только местами в конвейере под `cmp`
и `jbe` и потерянным развёртыванием. Тест
`observed_bounds_checks_cost_little` требует только, чтобы разница была
меньше двух раз.

<div class="box trick">

**Трюк: проверить один раз и запомнить в типе.** Если функция получает
срез, а работает с фиксированной длиной, проверку можно сделать один
раз и закрепить в типе: `let h: &mut [u32; 256] =
h.try_into().expect("256 счётчиков");`. Дальше компилятор знает длину,
и цикл становится циклом `hist_array`. То же для входа: `chunks_exact(N)`
отдаёт куски, длину которых оптимизатор знает, и проверку в
`<[u8; N]>::try_from` из такого куска он убирает; `as_chunks::<N>()`
(Rust 1.88) сразу даёт срез массивов `&[[T; N]]` и остаток.

</div>

Когда цикл пишет в память, а граница чужая, LLVM раздваивает его, как
`ch13_mix_index` в разделе 13.5:


```text
ch30::bounds::scale_into:
        ...
        cmp rcx, rsi
        mov rax, rsi
        cmovb rax, rcx
        lea r9, [r8 - 1]
        cmp rax, r9
        cmovae rax, r9
        ...
```

Два `cmov` — это `min(v.len(), out.len(), n − 1)`: столько шагов
заведомо пройдут обе проверки, их делает векторный цикл без проверок, а
остаток — скалярный, с двумя проверками на шаг. Записи до паники при

## Проверка переполнения

В release `+` заворачивает по модулю 2ⁿ, в debug — паникует (раздел
[1.2](../ch01/02-overflow.md)); профиль с `overflow-checks = true` даёт
панику и в release. Сколько это стоит, видно на сумме, где всё
остальное бесплатно:

```rust,ignore
{{#include ../../code/ch30/src/checks.rs:overflow}}
```

`strict_add` (стабилен с Rust 1.91) — то, во что превращается `+` с
проверкой. Ассемблер (тест `rustc_overflow_and_refcell`):

```text
ch30::checks::sum_strict:
        xor eax, eax
        test rsi, rsi
        je .LBB48_4
        xor ecx, ecx
.LBB48_2:
        add eax, dword ptr [rdi + 4*rcx]
        jb .LBB48_5
        inc rcx
        cmp rsi, rcx
        jne .LBB48_2
        ...
.LBB48_5:
        push rax
        lea rdi, [rip + .Lanon.1d4a91c0bed97d44da353e8af4d34689.9]
        call qword ptr [rip + core::num::imp::overflow_panic::add@GOTPCREL]
```

Сама проверка — один `jb` по флагу переноса после `add`, почти даром.
Дорого другое: цикл перестал быть векторным. Паника обязана случиться
на том сложении, где переполнилась частичная сумма, а у векторного
цикла частичные суммы другие — восемь отдельных сумм по полосам.
`sum_wrapping` — восемь чисел за оборот, `sum_strict` — одно, и
разница — 0,12–0,15 против 0,35–0,37 нс на число, в 2,5–3 раза (тест
`observed_bounds_checks_cost_little` требует больше полутора).

`sum_wide` возвращает тот же ответ, что `sum_strict` (`None` вместо
паники), но знает то, чего не знает компилятор: у неотрицательных
слагаемых частичные суммы только растут, и проверить достаточно
полную. Сумма в `u64` векторизуется (`paddq`, четыре числа за оборот —
полосы вдвое шире) и стоит 0,18–0,21 нс на число.

Так что `overflow-checks = true` в release почти ничего не стоит в
коде, где сложения разбросаны между загрузками и вызовами, и стоит
векторизации в плотной арифметике. Включить проверки в release и
написать горячие циклы через `wrapping_*` или широкий тип — обычный
компромисс.

## Флаг `RefCell`

Раздел [14.5](../ch14/05-cells.md) показал одиночный `borrow_mut`:
проверка флага и инкремент, а запись −1 и возврат нуля оптимизатор
убрал. В цикле то же самое — и даже лучше:

```rust,ignore
{{#include ../../code/ch30/src/checks.rs:refcell}}
```

```text
ch30::checks::hist_refcell:
        push rax
        test rsi, rsi
        je .LBB49_10
        cmp qword ptr [rdx], 0
        jne .LBB49_11
        movzx eax, byte ptr [rdi]
        inc dword ptr [rdx + 4*rax + 8]
        ...
.LBB49_8:
        movzx ecx, byte ptr [rax]
        inc dword ptr [rdx + 4*rcx + 8]
        ...
        jne .LBB49_8
.LBB49_9:
        mov qword ptr [rdx], 0
```

Флаг проверен один раз: первый оборот вынесен из цикла вместе с
проверкой, а дальше — тот же развёрнутый вчетверо цикл, что у
`hist_array` и `hist_cell`, только счётчики со смещением 8, за флагом.
В конце флагу записан 0 — тот, что вернул бы последний `RefMut`.
`hist_refcell_once` с одним заимствованием на весь цикл компилируется
в то же. Время одинаковое: 0,37–0,39 нс на байт у обоих вариантов с
`RefCell`, 0,39–0,44 у `hist_cell` (и 0,62 в одном прогоне — шум).

Флаг возвращается в цикл, когда внутри заимствования есть вызов, сквозь
который оптимизатор не видит:

```rust,ignore
{{#include ../../code/ch30/src/checks.rs:refcell_call}}
```

```text
ch30::checks::hist_refcell_call:
        ...
.LBB52_2:
        test rax, rax
        jne .LBB52_7
        movzx r13d, byte ptr [r12 + rbp]
        mov qword ptr [rbx], -1
        mov edi, r13d
        call r14
        add dword ptr [rbx + 4*r13 + 8], eax
        mov rax, qword ptr [rbx]
        inc rax
        mov qword ptr [rbx], rax
        inc rbp
        cmp r15, rbp
        jne .LBB52_2
        ...
.LBB52_6:
        inc qword ptr [rbx]
        mov rdi, rax
        call _Unwind_Resume@PLT
```

Функция за указателем `weight` могла бы заглянуть в тот же `RefCell`,
поэтому перед вызовом флаг честно записан в память (−1), а после —
перечитан и увеличен обратно до нуля. Блок `.LBB52_6` — путь
раскрутки: если `weight` запаникует, `Drop` стража `RefMut` вернёт флаг
и тогда. У `hist_cell_call` в цикле только загрузка байта, вызов и
`add`. Разница во времени — 1,45–1,85 против 1,34–1,66 нс на байт, в
пределах шума: шесть инструкций с флагом теряются на фоне косвенного
вызова. И это как раз тот случай, ради которого `RefCell` существует:
повторный вход через вызов, который может добраться до того же
значения.

## Ветвления

Все проверки выше — условные переходы, которые не берутся никогда, и
предсказатель угадывает их всегда. Дорогой переход — тот, исход
которого зависит от данных:

```rust,ignore
{{#include ../../code/ch30/src/branches.rs:select}}
```

```rust,ignore
{{#include ../../code/ch30/src/branches.rs:count}}
```

```text
ch30::branches::select_branchy:
        ...
.LBB58_3:
        movzx r13d, byte ptr [r12 + rbp]
        test r13b, r13b
        jns .LBB58_4
        cmp r15, qword ptr [rbx]
        jne .LBB58_8
        ...

ch30::branches::select_branchless:
        ...
.LBB59_8:
        cmp r10, rax
        mov r8, rax
        cmovb r8, r10
        cmp r8, rbx
        ja .LBB59_13
        movzx r11d, byte ptr [rdi + r10]
        inc r10
        mov byte ptr [r9 + r8], r11b
        shr r11d, 7
        add rax, r11
        cmp rsi, r10
        jne .LBB59_8
```

`b >= 128` — это знаковый бит байта, и в `select_branchy` он стал
переходом `jns` прямо по данным; за ним — проверка ёмкости вектора
перед `push`. В `select_branchless` перехода по данным нет: `n.min(i)` —
`cmovb`, `(b >= 128) as usize` — `shr 7`, байт пишется всегда.
Проверка границы `ja` осталась — LLVM не доказал, что `n.min(i)` меньше
длины, — но она, как и все проверки выше, не берётся никогда.
`count_big` LLVM сам сделал без перехода и векторным (`psrlw` на 7 и
маска), правда, всего по четыре байта за оборот: счётчик — `usize`, и
каждый байт расширен до 64 бит.

```console
$ cargo run -q -p ch30 --release --bin branches
random    branchy: 4.800 нс на байт
random branchless: 0.706 нс на байт
random      count: 0.419 нс на байт
sorted    branchy: 0.687 нс на байт
sorted branchless: 0.659 нс на байт
sorted      count: 0.400 нс на байт
```

Одна и та же функция, те же 4 МиБ байтов, только порядок другой:
на случайных данных `select_branchy` в семь раз медленнее, чем на
отсортированных (4,8–5,1 против 0,69–0,73 нс на байт в трёх прогонах),
а `select_branchless` от порядка не зависит (0,66–0,76). Случайный
байт не меньше 128 с вероятностью ½, угадать его нельзя, и промах
приходится в среднем на каждый второй байт: (4,8 − 0,69) / 0,5 ≈ 8 нс
на промах. Тест `observed_branches_random_vs_sorted` требует, чтобы
случайные данные были медленнее в три раза.

Промахи видны и без счётчиков процессора — cachegrind моделирует
предсказатель:

```console
$ valgrind --tool=cachegrind --cache-sim=no --branch-sim=yes target/release/branches random branchy
random    branchy: 31.013 нс на байт
==626== I refs:        744,213,061
==626== Branches:      111,621,293  (111,620,237 cond + 1,056 ind)
==626== Mispredicts:    16,787,086  ( 16,786,679 cond +   407 ind)
==626== Mispred rate:         15.0% (       15.0%     +  38.5%   )
```

Сводка — по всей программе, вместе с созданием данных и сортировкой. По
функциям (`cg_annotate`, тест `branch_model_sees_mispredictions`;
байтов — 8 вызовов по 4 МиБ, 33 554 432):

| Прогон | Ir на байт | Условных переходов на байт | Промахов модели |
|---|---|---|---|
| `select_branchy`, случайные | 9,00 | 2,50 | 16 773 141 — 0,4999 на байт |
| `select_branchy`, отсортированные | 9,00 | 2,50 | 27 |
| `select_branchless`, случайные | 12,00 | 2,00 | 18 |

Инструкций одинаково при любом порядке, переходов тоже — различаются
только промахи. Переходов в `select_branchy` два с половиной на байт:
выход из цикла, `jns` и для отобранной половины — проверка ёмкости. Без
ветвления инструкций на треть больше (12 против 9), и всё равно оно
в семь раз быстрее на случайных данных: промах стоит дороже десятка
инструкций.

<div class="box hood">

**Под капотом: предсказатель и `cmov`.** Процессор выбирает следующие
инструкции раньше, чем выполнил переход, — по предсказанию, и
выполняет их наперёд. Промах — сброс всего, что начато после перехода,
и выборка с верного адреса: потеря примерно на глубину конвейера,
порядка 15–20 тактов у современных ядер. Предсказатель помнит историю
каждого перехода и общую историю последних переходов, поэтому длинные
серии (отсортированные данные) и короткие повторяющиеся узоры он
угадывает почти всегда, а случайные данные — с вероятностью ½.
Модель cachegrind проще: 16 384 двухбитных счётчика, номер счётчика
считается из адреса перехода и исхода нескольких последних, — и
промахов она даёт больше реального (задача 30.D это покажет).

`cmov` превращает зависимость по управлению в зависимость по данным:
промахов нет, но результат ждёт и условия, и обоих значений.
Когда переход предсказуем, он выгоднее: процессор не ждёт условия и
выполняет дальше по угаданной ветке — в том числе начинает следующую
загрузку из памяти. Поэтому LLVM выбирает между ними по эвристикам, а
на x86 у него есть отдельный проход, который превращает `cmov` в циклах
обратно в переходы. `std::hint::select_unpredictable(c, a, b)` (Rust
1.88) просит оставить выбор без перехода: исход непредсказуем.
Двоичный поиск в задаче 30.D сравнивает оба способа — и на больших
массивах переход снова выигрывает.

</div>

<div class="box trap">

**Ловушка: данные замера.** На отсортированных данных `select_branchy`
быстр и даже чуть дешевле по инструкциям; на случайных — в семь раз
медленнее. Замер ветвящегося кода на удобных данных — та же ошибка,
что замер с известным заранее ответом (раздел [30.1](01-measure.md)):
меряется не та программа, что будет работать. Данные для замера берут
с тем же распределением, что в работе, — или записывают настоящие.

</div>

<div class="box c">

**Как в C.** В C проверки границ нет, и `for (i = 0; i < n; i++) s +=
v[i];` с чужим `n` clang 18 с `-O2` компилирует в тот же векторный
цикл, что `sum_sliced`, — без единой проверки (GCC 13 векторизует его
только с `-O3`); `-fsanitize=bounds` добавляет проверки только для
массивов известного размера. Беззнаковое переполнение в C заворачивает,
знаковое — неопределённое поведение; `__builtin_add_overflow` — аналог
`checked_add`, `-ftrapv` и `-fsanitize=signed-integer-overflow` —
аналоги `overflow-checks`. С ними сумма `int` теряет векторизацию так
же, как `sum_strict`: проверено на clang 18 и на GCC 13 с `-O3`, а
сумма `unsigned` остаётся векторной. Для ветвлений —
`__builtin_expect` и, только в clang, `__builtin_unpredictable` —
аналог `select_unpredictable`.
