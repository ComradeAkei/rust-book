# 30.7. Память: раскладка данных, ложное разделение, выделения

Обход матрицы в разделе [30.4](04-cachegrind.md) показал, что одни и те
же инструкции в другом порядке обращений к памяти стоят вдвое и вчетверо
дороже. Здесь — три случая, которые встречаются в каждой второй
программе: как лежат записи, которые читает горячий цикл; что бывает,
когда два потока пишут в соседние слова; сколько стоит выделение памяти
в цикле.

## Массив структур и структура массивов

Журнал станции — записи по 32 байта, из которых для среднего значения
нужны четыре:


Тот же журнал можно хранить столбцами — отдельный вектор на каждое
поле:

```rust,ignore
{{#include ../../code/ch30/src/memory.rs:soa}}
```

`#[repr(C)]` у `Reading` здесь не ради C: опыт считает, сколько записей
помещается в строку кэша, и порядок полей не должен зависеть от
компилятора (без `repr` rustc вправе их переставить, а задание CI со
случайной раскладкой так и делает, раздел [16.2](../ch16/02-invariants.md)).

```console
$ cargo run -q -p ch30 --release --bin memory layout
AoS: 2.937 нс на запись, SoA: 0.213 нс
```

В четырёх прогонах — 2,70–2,98 против 0,20–0,23 нс на запись, в 12–15
раз. Байтов на запись читается в восемь раз меньше: столбец значений —
16 МиБ, журнал целиком — 128 МиБ, а из памяти приходят строки кэша
целиком, вместе с ненужными полями. cachegrind это подтверждает точно
(тест `layout_misses_follow_bytes_read`, модель D1 32 КиБ, LL 8 МиБ;
двенадцать проходов по 4 Ми записей):

| Функция | Записей | D1mr | На запись |
|---|---|---|---|
| `sum_aos` | 50 331 648 | 25 165 836 | 1/2 — две записи на строку |
| `sum_soa` | 50 331 648 | 3 145 764 | 1/16 — шестнадцать `i32` на строку |

Остальное — векторизация. В `sum_aos` значения отстоят на 32 байта, и
цикл скалярный, развёрнутый вчетверо, — по `movsxd` на запись:

```text
ch30::memory::sum_aos:
        ...
.LBB58_5:
        movsxd r9, dword ptr [r8 - 96]
        add r9, rax
        movsxd rax, dword ptr [r8 - 64]
        movsxd r10, dword ptr [r8 - 32]
        add r10, rax
        add r10, r9
        movsxd rax, dword ptr [r8]
        add rax, r10
        add rdx, 4
        sub r8, -128
        cmp rsi, rdx
        jne .LBB58_5
```

В `sum_soa` значения подряд, и LLVM собрал векторный цикл: `movq`
загружает два `i32`, `pcmpgtd` с нулём и `punpckldq` расширяют их со
знаком до `i64` (в SSE2 нет `pmovsxdq`), `paddq` складывает — четыре
записи за оборот. Тест `observed_memory_layout_and_sharing` требует,
чтобы SoA была быстрее хотя бы втрое.

Структура массивов выигрывает, когда горячий цикл читает одно-два поля
из многих. Когда каждая запись нужна целиком — разобрать кадр, вывести
строку журнала, — массив структур не хуже, а вставка и удаление в нём
проще: одна операция вместо одной на столбец. Промежуточный вариант —
вынести горячие поля в отдельную маленькую структуру, а холодные — в
другую, параллельную ей.

## Ложное разделение

Раздел [20.6](../ch20/06-padding.md) объяснил ложное разделение и
лекарство — выравнивание. Здесь — сколько оно стоит на этой машине и
как его искать. Два потока, у каждого свой счётчик:

```rust,ignore
{{#include ../../code/ch30/src/memory.rs:sharing}}
```

`fetch_add`, результат которого не нужен, — это `lock inc qword ptr
[rsi]`; цикл LLVM развернул ввосьмеро. Двадцать миллионов инкрементов
в каждом потоке; `Adjacent` — третий вариант, счётчики в соседних
64-байтных строках одной 128-байтной пары:

```console
$ for i in 1 2 3 4; do target/release/memory sharing; done
два счётчика в одной строке: 618ms, в соседних: 120ms, в разных: 132ms
два счётчика в одной строке: 575ms, в соседних: 125ms, в разных: 133ms
два счётчика в одной строке: 578ms, в соседних: 154ms, в разных: 132ms
два счётчика в одной строке: 601ms, в соседних: 142ms, в разных: 121ms
```

В одной строке — в 4–5 раз медленнее. Порознь каждый `lock inc` стоит
около 6 нс (120 мс на 20 млн), вместе — 29–31: каждая запись
забирает строку из кэша соседнего ядра. Соседние строки на этой машине
уже не мешают друг другу: 120–154 мс против 121–133, разница в шуме.
`Padded` всё же выровнен на 128, как `CachePadded` из crossbeam на
x86-64: соседний предвыборщик Intel (с Sandy Bridge) тянет в L2 строки
парами, и на других процессорах и нагрузках соседняя строка может
оказаться общей. Запас в 64 байта на счётчик — дёшево, если счётчиков
по одному на поток. `Packed` выровнен на 64 с обратной целью: пара из 16
байт без выравнивания могла бы лечь на границу двух строк — и опыт
показал бы не то.

<div class="box trap">

**Ловушка: профилировщик ложного разделения не видит.** perf покажет
время в `lock inc`, но не скажет почему; valgrind выполняет потоки по
очереди, и cachegrind общей строки не моделирует вовсе. На железе со
счётчиками процессора ложное разделение находит `perf c2c` — по
событиям «загрузка попала в изменённую строку чужого ядра» (HITM). В
виртуальной машине без PMU остаётся время, поэтому тест на этот опыт —
`observed_`, с порогом в полтора раза, и только когда процессоров
два или больше.

</div>

## Выделения в горячем цикле

```rust,ignore
{{#include ../../code/ch30/src/memory.rs:alloc}}
```

Программа `memory` собрана с распределителем-счётчиком `Counted` из
шага проекта главы 15 ([15.11](../ch15/11-project.md)) и печатает,
сколько вызовов распределителя случилось за 100 000 строк:

```console
$ cargo run -q -p ch30 --release --bin memory alloc
 format!: 140 нс на строку, выделений 200019, 1412458 байт
  write!: 63 нс на строку, выделений 19, 1412458 байт
```

Число выделений — точное и одинаковое в каждом прогоне (тест
`allocations_are_counted_exactly`). У `format!` — ровно два на строку и
19 на общий буфер. Почему два: `format!` заранее оценивает длину по
литеральным кускам шаблона, но если шаблон начинается с подстановки, а
литералов меньше 16 байт (у нас — два пробела и перевод строки), он не
выделяет ничего. Первая запись выделяет минимальные 8 байт, строка
журнала длиннее (`"0 0 -1000\n"` — 10 байт), и буфер растёт до 16: одно
выделение и одно `realloc` на строку, и одно освобождение после
`push_str`. Общий буфер растёт удвоением, пока не вместит 1,4 МБ, —
это 19 вызовов, и у `write!` других выделений нет.

Времена шумят сильнее: в разных прогонах 124–202 нс против 53–98, и в
них входит цена самого счётчика — `Counted` делает пять атомарных
операций на пару выделение — освобождение. Тот же опыт под divan, с его
собственным счётчиком (`AllocProfiler`, раздел [30.2](02-criterion.md)),
на тысяче строк:


divan разделяет вызовы по видам: `alloc` — 1000 строк по 8 байт и
общий буфер, `grow` — 1000 ростов строк до 16 байт и 11 удвоений
буфера, `dealloc` — 1000 освобождённых строк по 16 байт (буфер
возвращается из замера и освобождается вне его). `max alloc` — сколько
блоков было живо одновременно: два у `format!` (буфер и строка), один у
`write!`. В четырёх прогонах быстрейший замер — 79–124 мкс против
49–67, то есть около 30 нс на строку: столько стоят два вызова
распределителя и одно освобождение. Это немного по сравнению с
форматированием трёх чисел — и потому `format!` в цикле так долго
остаётся незамеченным, пока строк не станут миллионы.

<div class="box trick">

**Трюк: один буфер на весь цикл.** Если строка нужна отдельно — для
сравнения, для ключа словаря, — её можно не создавать заново, а
переиспользовать: `line.clear(); write!(line, ...)` перед каждой
записью. `clear` не освобождает память, и после первой длинной строки
выделений больше нет. Для `Vec` — то же: `v.clear()` вместо `Vec::new()`
в цикле, `extend` вместо `collect` во временный вектор.

</div>

<div class="box c">

**Как в C.** Всё это — и перестановка полей ради кэша, и `alignas(128)`
против ложного разделения (`std::hardware_destructive_interference_size` в
C++17), и `snprintf` в один буфер вместо `asprintf` на каждую строку — из
мира C. Разница в том, где прячутся выделения: в C каждое `malloc`
написано в коде явно, а в Rust их делают `format!`, `to_string`, `collect`
и `clone`, и счётчик выделений — самый быстрый способ их найти.

</div>
