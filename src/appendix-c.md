# Приложение C. Чек-лист ревью unsafe-кода

Безопасный код проверяет компилятор, а за каждый `unsafe` отвечают двое:
автор и тот, кто читает его код на ревью. Это приложение — рабочий
инструмент второго. Сначала идёт чек-лист по группам со ссылками на главы,
где разобран каждый пункт, затем пример: вектор фиксированной ёмкости,
который пришёл на ревью с четырьмя ошибками. Для каждой ошибки показано,
какой пункт чек-листа её ловит и что о ней говорят тесты, Miri, Clippy и
санитайзеры. В конце приложения тот же чек-лист дан простым текстом, чтобы
его можно было вставить в шаблон pull request.

## Код приложения

```console
$ cargo test -p appendix-c                   # тип после ревью
$ cargo +nightly miri test -p appendix-c     # то же под Miri
$ for t in push_past_capacity last_mut_through_shared panic_in_clone send_with_rc; do
>     cargo +nightly miri test -p appendix-c -- --ignored --exact before::tests::before_$t
> done                                       # тип до ревью, каждый тест отдельно
```

Тесты кода до ревью помечены `#[ignore]`: в них неопределённое поведение.
Запускать их нужно по одному. Miri останавливается на первом же UB, а без
Miri порча памяти в одном тесте может уронить весь тестовый процесс, и
результатов остальных вы не увидите. Вывод получен на rustc 1.97.0 и
nightly 1.101.0 (2026-10-20) для x86_64 Linux.

## C.1. Что проверяет ревью

Цель ревью — убедиться, что код **корректен** (sound): никакая
последовательность вызовов его безопасного API не приводит к
неопределённому поведению ([гл. 16](ch16.md)). Аргумент «так никто не
вызывает» не принимается. Если безопасная функция приводит к UB при
каком-то входе, её надо либо исправить, либо объявить `unsafe` и описать
условия в разделе `# Safety`.

Отсюда первое правило: смотреть нужно не на блок `unsafe`, а на модуль.
Блок опирается на инвариант, например «элементы `buf[..len]`
инициализированы», а нарушить этот инвариант может любой безопасный метод,
которому видно поле `len`. Граница безопасности проходит там, где
заканчивается видимость приватных полей, то есть по границе модуля.
Поэтому порядок ревью такой: какие поля и функции видны снаружи; какие
инварианты записаны и кто их меняет; и только потом каждый `unsafe` по
отдельности.

## C.2. Чек-лист

### Нужен ли `unsafe`

- [ ] Нет безопасной замены. `split_at_mut`, `get_disjoint_mut`,
  `mem::swap` и `mem::take`, `copy_from_slice`, `from_le_bytes`,
  `MaybeUninit::write`, `Cell` закрывают большую часть случаев, ради которых
  пишут `unsafe` ([гл. 14](ch14.md), [гл. 17](ch17.md)).
- [ ] Выигрыш измерен. Проверку границ оптимизатор часто убирает сам, и
  это видно в ассемблере ([гл. 30](ch30.md)).
- [ ] Блок `unsafe` охватывает одну операцию, а не полфункции
  (`clippy::multiple_unsafe_ops_per_block`).

### Граница и документация

- [ ] Инвариант, на который опирается `unsafe`, держат приватные поля.
  Нет публичного поля или безопасного метода, способного его нарушить.
- [ ] Инвариант записан в документации к типу, а не только в голове
  автора.
- [ ] У каждой `unsafe fn` и `unsafe trait` есть раздел `# Safety` с
  полным списком условий (`clippy::missing_safety_doc`).
- [ ] У каждого блока `unsafe` и каждого `unsafe impl` есть комментарий
  `// SAFETY:`. Он объясняет, почему каждое условие выполнено в этом месте,
  а не пересказывает код (`clippy::undocumented_unsafe_blocks`).
- [ ] Внутри `unsafe fn` небезопасные операции всё равно стоят в блоке
  `unsafe` (линт `unsafe_op_in_unsafe_fn`, в edition 2024 включён по
  умолчанию, [приложение B](appendix-b.md)).
- [ ] Безопасная функция не принимает сырой указатель, индекс или
  дескриптор, чтобы использовать его без проверки. Сюда же относится
  безопасность ввода-вывода: безопасная функция не закрывает чужой
  файловый дескриптор ([гл. 28](ch28.md)).
- [ ] Каждый `#[allow(clippy::...)]` рядом с `unsafe` обоснован. Подавленный
  линт — первое место, куда стоит посмотреть.

### Указатели

- [ ] Указатель не NULL. Если NULL невозможен по смыслу, в типе стоит
  `NonNull<T>` или ссылка ([6.4](ch06/04-niches.md)).
- [ ] Указатель выровнен для типа, через который читают. Приведение
  `*const u8` к `*const u32` требует проверки `is_aligned()` или чтения
  через `read_unaligned` ([6.7](ch06/07-packed.md)).
- [ ] `add` и `offset` не выходят за пределы выделенного объекта (на один
  элемент за конец можно указывать, но не читать). Вся арифметика длин и
  смещений не переполняется: в release `+` переполняется молча
  ([приложение A](appendix-a.md)).
- [ ] Объект, на который указывает указатель, ещё жив: не освобождён, его
  кадр стека не завершён, `Vec` не перевыделил буфер.
- [ ] Указатель получен из указателя на тот же объект (provenance), а не
  собран из целого числа. Если адрес приходится менять как число, есть
  `with_addr` и `map_addr` ([гл. 17](ch17.md)).
- [ ] Указатель, через который пойдёт доступ к соседним полям или ко всему
  объекту, выведен из указателя на весь объект, а не из ссылки на одно
  поле (пример `container_of` в [приложении A](appendix-a.md)).
- [ ] Память инициализирована до чтения. Это касается `MaybeUninit`,
  памяти из аллокатора, `Vec::set_len` и буферов, которые заполняет
  устройство.

### Валидность значений

- [ ] Каждое значение, созданное через `transmute`, `ptr::read`,
  `assume_init` или `from_raw_parts`, допустимо для своего типа: `bool`
  равен 0 или 1, `char` — скалярное значение Unicode, `enum` — один из
  вариантов, ссылка не NULL и выровнена, `str` содержит UTF-8
  ([гл. 16](ch16.md)).
- [ ] Данные извне (FFI, регистры, сеть) читаются как целые числа или байты
  и проверяются через `TryFrom`, а не превращаются сразу в `enum`
  ([приложение A](appendix-a.md)).
- [ ] `transmute` не применяется к типам с раскладкой `repr(Rust)`.
  Размеры и выравнивания, на которые опирается код, закреплены
  `const`-проверками ([6.2](ch06/02-repr-c.md)).
- [ ] При просмотре структуры как байтов учтено заполнение: байты
  заполнения не инициализированы, и читать их нельзя
  ([6.1](ch06/01-structs.md)).

### Алиасинг и времена жизни

- [ ] `&mut T` остаётся единственным путём к объекту всё время своей
  жизни. Два `&mut` на один объект не получаются ни из двух вызовов одного
  метода, ни через сырой указатель ([гл. 4](ch04/index.md)).
- [ ] Через `&T` никто не пишет, кроме как внутри `UnsafeCell`
  (`Cell`, `RefCell`, атомики и мьютексы построены на нём,
  [гл. 14](ch14.md)).
- [ ] Нет метода `&self -> &mut T` (`clippy::mut_from_ref`). Почти всегда
  это ошибка.
- [ ] Время жизни возвращаемой ссылки привязано к владельцу памяти.
  Функция вида `fn get<'a>(p: *const T) -> &'a T` даёт вызывающему любое
  время жизни, какое он попросит ([разд. 5.4](ch05/04-variance.md)).
- [ ] Сырой указатель, полученный из ссылки, не используется после того,
  как ту же память снова заняли через `&mut`.

### Паники и `Drop`

- [ ] Найдены все места, где может запаниковать код, который пишет не
  автор модуля: `clone`, `eq`, `cmp`, `hash`, `next`, `drop`, `fmt`,
  замыкания. К ним добавляются свои `assert!`, индексация и арифметика в
  debug ([гл. 7](ch07/index.md)).
- [ ] В каждой такой точке инвариант выполнен. Длина растёт только после
  записи элемента, либо состояние восстанавливает охранная структура с
  `Drop`.
- [ ] Корректность не держится на том, что деструктор будет вызван.
  `mem::forget` — безопасная функция, и утечка не должна приводить к UB.
- [ ] Значение, прочитанное через `ptr::read` или `assume_init_read`,
  больше не считается живым на старом месте, иначе оно будет уничтожено
  дважды.
- [ ] `Drop` контейнера уничтожает оставшиеся элементы, даже если
  деструктор одного из них запаниковал: `ptr::drop_in_place` для среза,
  а не цикл с `assume_init_drop`.

### `Send` и `Sync`

- [ ] Ручной `unsafe impl Send` или `Sync` ограничен по параметрам:
  `unsafe impl<T: Send> Send for X<T>`
  (`clippy::non_send_fields_in_send_ty`).
- [ ] Ручная реализация вообще нужна. Компилятор выводит `Send` и `Sync`
  сам, если ими обладают все поля. Выключают вывод сырые указатели и
  `NonNull`, и только тогда реализацию пишут вручную ([гл. 20](ch20.md)).
- [ ] Для `Sync` проверены все методы `&self`: если они меняют состояние,
  то только через атомики или блокировку.
- [ ] Тип, привязанный к потоку (например, к thread-local состоянию
  C-библиотеки), остаётся `!Send` благодаря полю
  `PhantomData<*const ()>`.
- [ ] Есть отрицательный тест: doc-тест `compile_fail`, который
  проверяет, что `X<Rc<_>>` нельзя отправить в другой поток.

### Чужой код: трейты, обобщения, макросы

- [ ] Безопасность памяти не зависит от правильности безопасных трейтов,
  которые реализует пользователь. `Ord` может быть непоследовательным,
  `Hash` — разным для равных значений, `ExactSizeIterator::len` — врать,
  `Deref` — каждый раз возвращать новый адрес. От них может зависеть
  результат, но не отсутствие UB. Если доверие необходимо, нужен
  `unsafe trait` ([гл. 16](ch16.md)).
- [ ] Обобщённый код проверен на типах нулевого размера: для них `add` не
  сдвигает указатель, а ёмкость не ограничена памятью
  ([6.5](ch06/05-zst.md)).
- [ ] Макрос, раскрывающийся в `unsafe`, не подставляет выражение
  пользователя внутрь блока `unsafe` ([гл. 23](ch23.md)).

### FFI

- [ ] Типы на границе — `#[repr(C)]`, `#[repr(transparent)]` или
  примитивы из `core::ffi`. `enum` из C принимается как целое
  ([приложение A](appendix-a.md), [гл. 18](ch18.md)).
- [ ] Сигнатуры в `unsafe extern` совпадают с заголовком C для каждой
  целевой платформы: `long` и `char` на x86_64 и Cortex-M разные. Надёжнее
  генерировать их bindgen.
- [ ] `safe fn` в блоке `unsafe extern` объявлены только функции без
  предусловий ([приложение B](appendix-b.md)).
- [ ] Память освобождает та сторона, которая её выделила:
  `Box::into_raw` возвращается через `Box::from_raw`, а `malloc` — через
  `free`.
- [ ] `CString` живёт, пока C держит указатель на него. На
  `CString::new(s).unwrap().as_ptr()` компилятор предупреждает
  (`dangling_pointers_from_temporaries`), но только в этом простом случае.
- [ ] Паника не уходит в C. Из функции `extern "C"` раскрутка невозможна,
  и процесс прерывается с сообщением «panic in a function that cannot
  unwind». Если раскрутка через C нужна, функцию объявляют
  `extern "C-unwind"`.
- [ ] `errno` читается сразу после вызова (`io::Error::last_os_error()`),
  до любого другого вызова libc.
- [ ] Потокобезопасность C-библиотеки отражена в `Send` и `Sync`
  обёртки.

### Конкурентность, прерывания, железо

- [ ] Общие изменяемые данные защищены атомиками или блокировкой.
  `static mut` нет, а ссылки на него в edition 2024 — ошибка компиляции
  ([приложение B](appendix-b.md)). Выбор `Ordering` объяснён комментарием
  ([гл. 21](ch21.md)).
- [ ] Данные, общие с обработчиком прерывания, защищены критической
  секцией или атомиками. На `thumbv6m` атомарного сравнения с обменом нет
  ([гл. 27](ch27.md)).
- [ ] Регистры периферии читаются и пишутся через `read_volatile` и
  `write_volatile` или обёртку над ними. Ссылки `&T` на память устройства
  не создаются: по ссылке компилятор вправе читать когда угодно
  ([6.9](ch06/09-registers.md)).
- [ ] Буфер, отданный DMA, не перемещается, не читается и не
  освобождается до конца передачи. Между записью в буфер и запуском DMA
  стоит барьер (`compiler_fence` или `fence`).
- [ ] В `asm!` перечислены все изменяемые регистры (`clobber_abi`), а
  опции `nomem`, `nostack`, `pure` соответствуют правде. Ложная опция —
  тоже UB ([гл. 19](ch19.md)).

### Инструменты

- [ ] Тесты проверяют результат, а не только отсутствие паники. Есть
  отдельные тесты на границу ёмкости, на панику в середине операции, на
  типы нулевого размера и типы с `Drop`.
- [ ] Тесты проходят под Miri в обеих моделях алиасинга:
  `cargo +nightly miri test` и то же с `MIRIFLAGS=-Zmiri-tree-borrows`.
  Код с потоками дополнительно гоняется на нескольких расписаниях
  (`-Zmiri-many-seeds=0..16`). Ошибка, найденная хоть одной моделью,
  считается ошибкой.
- [ ] То, что Miri не исполняет (FFI, `asm!`, обращения к устройствам),
  проверено санитайзерами на хосте (`-Zsanitizer=address`, для гонок
  `-Zsanitizer=thread` вместе с `-Zbuild-std`) и на железе или в QEMU.
- [ ] Тесты запускаются и в debug. В отладочной сборке стандартная
  библиотека проверяет предусловия части `unsafe`-функций
  (`slice::from_raw_parts`, `ptr::copy_nonoverlapping`), в release этих
  проверок нет.
- [ ] Для конкурентных структур есть loom, для небольших функций с
  инвариантами — Kani, для разбора входных данных — фаззинг
  ([гл. 31](ch31.md)).
- [ ] Код, который может неявно полагаться на раскладку `repr(Rust)`,
  проверен со случайной раскладкой (`-Zrandomize-layout`, задание `layout`
  в CI книги).

### Итоговый вопрос

- [ ] Можно ли, пользуясь только безопасным публичным API, получить UB?
  Если да, API некорректен, даже если сегодня так никто не вызывает.

## C.3. Разбор: вектор фиксированной ёмкости

Тип `StackVec<T, N>` хранит до `N` элементов в массиве
`[MaybeUninit<T>; N]` без кучи. Такой тип нужен в прошивке и в
обработчике прерывания, где аллокатора нет ([гл. 26](ch26.md)). На ревью
он пришёл в таком виде:

```rust
{{#include ../code/appendix-c/src/before.rs:before}}
```

Обычные тесты на этот код (`push`, `pop`, `as_slice` в пределах ёмкости)
проходят, и Miri на них молчит. Ошибки находятся, если идти по чек-листу,
и тесты ниже написаны уже после этого:

```rust,ignore
{{#include ../code/appendix-c/src/before.rs:before_tests}}
```

### Ошибка 1. Граница ёмкости

Пункт «`add` не выходит за пределы объекта». Проверка `self.len > N`
пропускает `len == N`, и третий `push` в вектор ёмкостью 2 пишет за конец
массива. В обычном прогоне это выглядит так:

```console
$ cargo test -p appendix-c -- --ignored --exact before::tests::before_push_past_capacity
thread 'before::tests::before_push_past_capacity' panicked at code/appendix-c/src/before.rs:93:9:
assertion `left == right` failed
  left: Ok(())
 right: Err(3)
thread 'before::tests::before_push_past_capacity' panicked at code/appendix-c/src/before.rs:64:31:
range end index 4 out of range for slice of length 2
...
panic in a destructor during cleanup
thread caused non-unwinding panic. aborting.
error: test failed, to rerun pass `-p appendix-c --lib`
```

Вторая паника объясняет, куда ушла запись. rustc положил поле `len`
сразу за массивом, и тройка затёрла длину: `len` стал равен 3, а после
`+= 1` — 4. Деструктор, вызванный при раскрутке после первой паники,
попытался взять срез `buf[..4]` и запаниковал снова, а паника внутри
раскрутки прерывает процесс. С другим порядком полей та же ошибка
испортила бы чужую память молча.

Miri в модели по умолчанию (Stacked Borrows) останавливается на самой
записи:

```console
$ cargo +nightly miri test -p appendix-c -- --ignored --exact before::tests::before_push_past_capacity
error: Undefined Behavior: attempting a write access using <135743> at alloc41963[0x8], but that tag does not exist in the borrow stack for this location
  --> code/appendix-c/src/before.rs:24:18
   |
24 |         unsafe { self.buf.as_mut_ptr().add(self.len).cast::<T>().write(v) };
   |                  ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ this error occurs as part of an access at alloc41963[0x8..0xc]
...
help: <135743> was created by a SharedReadWrite retag at offsets [0x0..0x8]
```

Указатель получен из `self.buf` и разрешает доступ к байтам `0x0..0x8`,
то есть к массиву, а запись идёт в байт `0x8`. Под Tree Borrows
(`MIRIFLAGS=-Zmiri-tree-borrows`) Miri эту запись не считает нарушением:
она остаётся внутри того же выделенного объекта. Программа проходит тот
же путь, что и нативно, и Miri сообщает «abnormal termination: the program
aborted execution». Miri не проверяет границы полей. Ошибку в этой модели
поймал тест, который сверяет результат `push` с ожидаемым.

### Ошибка 2. `&mut` из `&self`

Пункт «нет метода `&self -> &mut T`». `last_mut` принимает `&self`, а
возвращает `&mut T`. Через `&self` в памяти вектора ничего менять нельзя, а
два вызова `last_mut` дают две `&mut` на один элемент. Clippy такой метод
не пропускает: линт `clippy::mut_from_ref` по умолчанию на уровне deny, и
автору пришлось подавить его атрибутом `#[allow]`. Сам rustc молчит: его
линт `invalid_reference_casting` ловит только прямое приведение
`&T as *const T as *mut T`, а здесь указатель прошёл через `as_ptr()` и
`add`. Тест без Miri проходит, Miri ловит ошибку в обеих моделях:

```console
$ cargo +nightly miri test -p appendix-c -- --ignored --exact before::tests::before_last_mut_through_shared
```

### Ошибка 3. Паника посреди обновления

Пункт «в каждой точке паники инвариант выполнен». `extend_from_slice`
сначала увеличивает `len`, а потом клонирует элементы. Если `clone`
запаникует на втором элементе, `len` уже говорит «два элемента», а
инициализирован один. При раскрутке `Drop` вектора уничтожит и
неинициализированный слот. Тестовый тип `Fragile` паникует на втором
`clone` и записывает в журнал `id` каждого уничтоженного значения.
Ожидаем увидеть только клон первого элемента с `id` 101:

```console
$ cargo test -p appendix-c -- --ignored --exact before::tests::before_panic_in_clone
thread 'before::tests::before_panic_in_clone' panicked at code/appendix-c/src/before.rs:118:13:
clone №2 не удался
thread 'before::tests::before_panic_in_clone' panicked at code/appendix-c/src/before.rs:139:9:
assertion `left == right` failed
  left: [101, 2425393296]
 right: [101]
```

Второе число — мусор со стека, и от запуска к запуску оно разное. Будь в
`Fragile` вместо `u32` поле `String`, деструктор освободил бы указатель из
мусора. Miri находит само чтение неинициализированной памяти (в Tree
Borrows — то же сообщение):

```console
$ cargo +nightly miri test -p appendix-c -- --ignored --exact before::tests::before_panic_in_clone
error: Undefined Behavior: reading memory at alloc42333[0x4..0x8], but memory is uninitialized at [0x4..0x8], and this operation requires initialized memory
   --> code/appendix-c/src/before.rs:125:68
...
            0: <before::tests::Fragile as std::ops::Drop>::drop
...
            4: <before::StackVec<before::tests::Fragile, 4> as std::ops::Drop>::drop
                at code/appendix-c/src/before.rs:65:22: 65:42
```

В той же функции есть вторая, менее заметная проблема: проверка
`self.len + src.len() <= N` может переполниться. Для обычных типов срез
длиной около `usize::MAX` получить нельзя, а для типа нулевого размера
можно, и в release сложение молча перейдёт через ноль. Проверка, которая
не переполняется при соблюдённом инварианте `len <= N`, выглядит так:
`src.len() <= N - self.len`.

### Ошибка 4. `Send` без ограничения

Пункт «ручной `unsafe impl Send` ограничен по параметрам». Строка
`unsafe impl<T, const N: usize> Send for StackVec<T, N> {}` объявляет
вектор отправляемым в другой поток при любом `T`, в том числе при
`Rc<u8>`, у которого счётчик ссылок не атомарный. Тест отправляет вектор
с клоном `Rc` в поток, и оба потока клонируют его одновременно. Без
инструментов тест проходит: гонка за сто итераций может не проявиться.
Miri находит её в обеих моделях:

собранной с той же инструментацией (без `-Zbuild-std` rustc отказывается
смешивать сборки: «mixing `-Zsanitizer` will cause an ABI mismatch»):

### Что увидел каждый инструмент

| Ошибка | Обычный тест | Miri, Stacked Borrows | Miri, Tree Borrows | Clippy | ASan |
|---|---|---|---|---|---|
| 1. граница ёмкости | падает, процесс прерван | UB | не видит | не видит | не видит |
| 2. `&mut` из `&self` | проходит | UB | UB | `mut_from_ref` (был подавлен) | не видит |

| 4. `Send` без ограничения | проходит | гонка данных | гонка данных | `non_send_fields_in_send_ty` | не видит |

AddressSanitizer (`RUSTFLAGS=-Zsanitizer=address`) не увидел ни одной из
четырёх ошибок. Он следит за границами выделенных блоков и
освобождённой памятью, а все четыре ошибки происходят внутри живого
объекта. Без `clippy::undocumented_unsafe_blocks` никто не спросил бы и о
главном: на каждый из шести блоков `unsafe` в исходном коде этот линт
выдаёт «unsafe block missing a safety comment», а на `unsafe impl Send` —
«unsafe impl missing a safety comment». Попытка написать
комментарий `SAFETY` к `push` или к `last_mut` сама выводит на ошибку.
Ни один инструмент не нашёл всё. Работает связка: тесты, которые сверяют
результат, Miri в обеих моделях, линты и ревью по списку.

### После ревью

```rust
{{#include ../code/appendix-c/src/after.rs:after}}
```

Что изменилось, по пунктам чек-листа:

- инвариант записан в документации к типу, и каждый `SAFETY` ссылается на
  него;
- `push` проверяет `len == N` и пишет через индексацию с проверкой границ
  и `MaybeUninit::write`, без арифметики указателей;
- `last_mut` принимает `&mut self`, и `&mut T` выводится из уникальной
  ссылки через `assume_init_mut`;
- `extend_from_slice` увеличивает `len` после каждой записи, а проверка
  ёмкости не переполняется;
- `Drop` уничтожает элементы одним `ptr::drop_in_place` для среза
  `buf[..len]`: если деструктор элемента запаникует, остальные всё равно
  будут уничтожены, как в массиве и `Vec`. Цикл с `assume_init_drop`
  на первой же панике бросил бы их;
- ручного `Send` нет. Компилятор выводит его из поля
  `[MaybeUninit<T>; N]`, и doc-тест `compile_fail,E0277` проверяет, что
  вектор с `Rc` отправить в поток нельзя.

Тесты исправленного типа проходят и нативно, и под Miri в обеих моделях:

```console
$ cargo +nightly miri test -p appendix-c
test result: ok. 6 passed; 0 failed; 4 ignored; 0 measured; 0 filtered out
$ MIRIFLAGS=-Zmiri-tree-borrows cargo +nightly miri test -p appendix-c --lib
test result: ok. 6 passed; 0 failed; 4 ignored; 0 measured; 0 filtered out
```

<div class="box trap">

**Ловушка: «Miri молчит, значит, всё в порядке».** Miri проверяет только
те пути, которые прошли тесты, и только в выбранной модели алиасинга.
Ошибки 1–4 не видны ни одному тесту, который кладёт в вектор меньше `N`
элементов, не паникует в `clone` и не отправляет вектор в другой поток.
Поэтому тесты пишут по чек-листу: на каждую точку паники, на каждую
границу и на каждый `unsafe impl` — свой тест.

</div>

<div class="box hood">

**Под капотом: проверки предусловий в debug.** Начиная с Rust 1.78
отладочная сборка проверяет предусловия части `unsafe`-функций
стандартной библиотеки, даже если сама библиотека собрана в release.
Невыровненный указатель в `slice::from_raw_parts` в debug даёт:

```text

This indicates a bug in the program. This Undefined Behavior check is optional, and cannot be relied on for safety.
```

Процесс прерывается, раскрутки нет. В release та же программа молча
печатает результат. Это ещё одна причина гонять тесты в обоих профилях.

</div>

## C.4. Чек-лист для копирования

```text
Ревью unsafe

[ ] Безопасной замены нет, выигрыш измерен, unsafe-блок охватывает одну операцию
[ ] Инвариант держат приватные поля модуля и записан в документации типа
[ ] # Safety у каждой unsafe fn и unsafe trait; // SAFETY: у каждого блока и unsafe impl
[ ] Безопасные функции не используют чужие указатели, индексы, дескрипторы без проверки
[ ] Каждый #[allow(clippy::...)] рядом с unsafe обоснован
[ ] Указатели: не NULL, выровнены, в пределах объекта, объект жив, provenance сохранён
[ ] Арифметика длин и смещений не переполняется (в release + молча переполняется)
[ ] Память инициализирована до чтения; байты заполнения не читаются
[ ] Значения допустимы для типа: bool, char, enum, ссылки, str; внешние данные проверяются
[ ] &mut уникален; через &T не пишут вне UnsafeCell; нет &self -> &mut T
[ ] Время жизни ссылок привязано к владельцу, а не выбрано вызывающим
[ ] Все точки паники чужого кода найдены, инвариант в них выполнен
[ ] Утечка (mem::forget) не ведёт к UB; нет двойного уничтожения после ptr::read
[ ] Drop контейнера при панике деструктора добивает остальные: drop_in_place для среза
[ ] Send/Sync: вывод компилятора или ручной impl с ограничением T: Send / T: Sync
[ ] Отрицательный тест compile_fail на Send/Sync
[ ] Безопасность не зависит от Ord, Hash, Iterator, Deref пользователя; проверены ZST
[ ] FFI: repr(C), сигнатуры под каждую цель, владение памятью, CString живёт
[ ] FFI: паника не уходит в C (extern "C" прерывает процесс, иначе C-unwind); errno сразу
[ ] Общие данные: атомики или блокировка, нет static mut, Ordering обоснован
[ ] Прерывания: критическая секция; MMIO только volatile, без &T на регистры
[ ] DMA: буфер не трогается до конца передачи, барьеры на месте
[ ] asm!: clobber_abi и опции соответствуют правде
[ ] Тесты: граница ёмкости, паника посреди операции, ZST, типы с Drop; debug и release
[ ] Miri: Stacked Borrows и Tree Borrows, для потоков несколько сидов
[ ] Санитайзеры для FFI и asm!, проверка на железе или в QEMU
[ ] Итог: безопасный публичный API не может привести к UB
```
