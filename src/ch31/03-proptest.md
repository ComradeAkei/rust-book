# 31.3. Свойства вместо примеров: proptest

Тест-пример проверяет случаи, о которых подумал автор. *Тест-свойство*
(property-based test) формулирует то, что верно для *любого* входа, а
входы порождает генератор — сотни на прогон, каждый раз другие. Когда
свойство ломается, proptest уменьшает упавший вход до минимального, на
котором оно всё ещё ломается, и печатает его. Свойств, которые легко
сформулировать, несколько видов:

- **круговой обход** (round trip): `decode(encode(x)) == x`;
- **модель**: простая и медленная реализация, в правильности которой
  нет сомнений, против быстрой и сложной;
- **устойчивость**: на любом входе функция не паникует, а то, что она
  приняла, согласовано со входом;
- **инвариант**: длина не больше ёмкости, сумма равна сумме
  содержимого.

## Круговой обход и первая ошибка

Кадры по UART без поля длины часто разделяют байт-стаффингом SLIP
(RFC 1055): конец кадра — байт `END`, а `END` и `ESC` внутри данных
заменяются парами `ESC ESC_END` и `ESC ESC_ESC`. Первая версия
кодировщика забыла второе правило:


`vec(any::<u8>(), 0..64)` — *стратегия* (strategy): вектор длиной от 0 до
63 из любых байтов. Макрос `proptest!` превращает функцию в `#[test]`,
который 256 раз порождает `data` и проверяет тело. `prop_assert_eq!` вместо
`assert_eq!` возвращает ошибку, а не паникует: так proptest может
продолжить — уменьшать вход.

```console
$ PROPTEST_RNG_SEED=31 cargo test -p ch31 --test props -- --ignored --exact slip_v1_round_trip
running 1 test
test slip_v1_round_trip ... FAILED

failures:

---- slip_v1_round_trip stdout ----

thread 'slip_v1_round_trip' (16063) panicked at code/ch31/tests/props.rs:27:1:
Test failed: assertion failed: `(left == right)`
  left: `Err(BadEscape { at: 1, byte: 192 })`,
 right: `Ok([219])` at code/ch31/tests/props.rs:31.
minimal failing input: data = [
    219,
]
	successes: 0
	local rejects: 0
	global rejects: 0
```

Первый же вход сломал свойство — `successes: 0`. С этим зерном так вышло
случайно: в векторе средней длины 32 байт `ESC` (0xDB = 219) встречается
примерно в одном случае из восьми, но из 256 случаев таких наберутся
десятки, и прогон без зерна падает так же надёжно. Первый вход был длинным
и некрасивым, а в отчёте — один байт `ESC`. Это *уменьшение* (shrinking):
proptest пробует укоротить вектор и уменьшить каждый байт, оставляя
изменения, после которых свойство по-прежнему ломается, пока улучшать
нечего. Минимальный пример сразу называет причину: `ESC` записан как есть, и
декодер видит его как начало пары, за которой стоит `END` (192).

<div class="box hood">

**Под капотом: дерево значений.** Стратегия порождает не значение, а
`ValueTree` — значение вместе со способом его упростить. У вектора два
способа: выбросить элемент и упростить элемент; у числа — двоичный
поиск к нулю. `simplify` делает шаг вниз, `complicate` — шаг назад, если
упрощённое значение свойство уже не ломает. Поэтому уменьшение
работает и для составных стратегий: `prop_map` уменьшает аргумент и
применяет функцию заново, кортеж уменьшает компоненты по очереди. Свой
`Arbitrary` писать не нужно, пока стратегии собираются из готовых.

</div>

## Зерно, регрессии и `TestRunner`

Входы случайны, и упавший в CI тест может не повториться локально. Два
средства. Первое — зерно: `PROPTEST_RNG_SEED` фиксирует генератор, как в
отчёте выше. Второе — файл регрессий: упав, proptest записывает зерно
упавшего случая в файл по имени файла теста в каталоге
`proptest-regressions` рядом с исходниками, и следующий прогон начинает с
сохранённых случаев. Файл советуют хранить в git — тогда однажды найденная
ошибка проверяется у всех и всегда.

Макрос `proptest!` — обёртка над `TestRunner`. Его можно вызвать и
напрямую: так тест сам выбирает конфигурацию и получает результат
значением, а не паникой.

```rust,ignore
{{#include ../../code/ch31/tests/props.rs:runner}}
```

Тест `regression_file` запускает эту функцию дважды с файлом во
временном каталоге. После первого прогона в файле:

```text
# Seeds for failure cases proptest has generated in the past. It is
# automatically read and these particular cases re-run before any
# novel cases are generated.
#
# It is recommended to check this file in to source control so that
# everyone who runs the test benefits from these saved cases.
cc 0496ebd75c07f7cd1499e74ed5c9bb038f1fc97267718c3b850b2002dec8a36c # shrinks to [219]
```

Строка `cc` — зерно случая, а не сам вход: вход порождается из зерна
той же стратегией. Если стратегию поменять, старое зерно даст другой
вход, и регрессия перестанет проверять то, что проверяла. Для ошибок,
которые важно не повторить, надёжнее обычный тест-пример с минимальным
входом из отчёта: `decode(&encode(&[ESC]))`.

## Стратегии, которые доходят до сути

Свойство «на любом входе `decode` кадра не паникует» с входом
`vec(any::<u8>(), 0..300)` выглядит сильным, но почти ничего не
проверяет. Кадр проекта начинается маркером `0xA5`, у случайного буфера
он совпадает с вероятностью 1/256, а дальше ещё версия, тип, длина и
CRC. Тест `strategies_reach_different_depths` порождает по тысяче
входов двумя стратегиями и считает, где `decode` их отверг:

одного раза: переворачивает бит, обрезает, вставляет байт. Место порчи
— `Index`, доля, которая превращается в позицию, когда длина уже

Второе свойство — модель: табличная CRC проекта сверяется с побитовой.
Таблица — 256 констант, и ошибка в одной из них проявится только на
входах, которые до неё доходят; побитовая реализация — восемь строк,
которые легко проверить глазами.

## Модель для последовательности операций

Для структуры данных вход — не одно значение, а последовательность
операций. Стратегия порождает `Vec<Op>`, тест выполняет операции над
структурой и над моделью и сравнивает после каждой. Модель окна —
`VecDeque` с ограничением длины: медленно, зато очевидно.


Уменьшение здесь особенно полезно: из сотни операций, после которых
среднее разошлось, proptest оставит три-четыре, нужные для ошибки.
Веса в `prop_oneof!` (`3 =>`, `1 =>`) смещают поток к вставкам: иначе
окно редко заполнялось бы и вытеснение почти не проверялось.

<div class="box trap">

**Ловушка: свойство, повторяющее код.** «`mean` равен `sum / len`» —
плохое свойство, если `mean` так и написан: ошибка в формуле будет и в
коде, и в тесте. Модель должна быть *другой* реализацией, лучше всего —
проще по устройству: очередь вместо кольцевого буфера, побитовая CRC
вместо таблицы, поиск перебором вместо двоичного.

</div>

<div class="box c">

**Как в C.** Генераторы свойств для C и C++ есть — theft, RapidCheck, —
но в обиход они почти не вошли: это ещё одна внешняя библиотека со
своей сборкой рядом с тестовым фреймворком. Чаще в C ту же роль играет
фаззер (раздел [31.4](04-fuzz.md)) с `assert` внутри цели. Разница в
том, что фаззер ищет падение, а свойство ещё и называет, что именно
должно выполняться; минимальный пример фаззер тоже умеет искать, но
только на байтах, а не на структуре входа.
