# 31.4. Фаззинг: cargo-fuzz

<div class="box ref">

**Справка: фаззер с обратной связью по покрытию (coverage-guided
fuzzing).** libFuzzer — часть LLVM. Компилятор вставляет в каждый [базовый
блок][g-basic-block] программы счётчик (SanitizerCoverage), а перед каждым
сравнением — вызов, который запоминает оба операнда. Фаззер держит
*корпус* (corpus) — набор входов — и в цикле берёт вход, мутирует его
(переворачивает биты, вставляет и удаляет байты, склеивает два входа,
подставляет операнды подсмотренных сравнений) и запускает *цель фаззинга*
(fuzz target) — функцию, которая принимает вход. Вход, который зажёг новый
счётчик, попадает в корпус: от него будут мутировать дальше. Так фаззер
шаг за шагом проходит проверки, перед которыми случайные байты бессильны.
Падение цели — паника, аварийный сигнал, отчёт санитайзера — фаззер
сохраняет вход в файл `crash-<sha1>` и останавливается. Всё это идёт в
одном процессе, сотни тысяч запусков в секунду.

</div>

## Цель на сырых байтах

`cargo fuzz init` заводит в крейте каталог `fuzz` — отдельный крейт с
`[package.metadata] cargo-fuzz = true`, по бинарнику на цель. Здесь он
— свой workspace: `code/ch31` — член корневого workspace, и без пустой
таблицы `[workspace]` cargo причислил бы `fuzz` к корневому, а собирать
его нужно nightly-компилятором с особыми флагами. Цель — функция,
которой фаззер подаёт байты:

```rust,ignore
{{#include ../../code/ch31/fuzz/fuzz_targets/cmd_v1.rs:all}}
```

```console
$ cargo +nightly fuzz run cmd_v1 -- -seed=1 -runs=3000000
...
Done 3000000 runs in 11 second(s)
```

Три миллиона запусков — и падения нет. С профилем значений сравнений
(`-use_value_profile=1`, фаззер ценит и входы, которые приблизили
операнды сравнения друг к другу) — два миллиона за 21 секунду, тоже
чисто. При этом в разбор калибровки фаззер попал на 1698-м запуске:
маркер и CRC он проходит, подставляя операнды подсмотренных сравнений.
Не хватает другого. Чтобы упасть, нужны одновременно `n ≥ 9`, длина
нагрузки ровно `3 + 4·n`, столько же байтов во входе и верная CRC
поверх всего этого. А сигнала, который вёл бы от `n = 8` к `n = 9`, у
фаззера нет: обе команды проходят одни и те же блоки, пока девятая
точка не упадёт, — покрытие у них одинаковое, и `n = 9` с правильной
длиной надо угадать сразу.

## Вход-структура: `Arbitrary`

Помогает перенести согласование полей в цель. Фаззер даёт не байты, а
*форму* команды; длину, число точек и CRC считает обёртка:

```rust,ignore
{{#include ../../code/ch31/fuzz/fuzz_targets/cmd_v1_shape.rs:all}}
```

[`#[derive(Arbitrary)]`][g-derive] из крейта arbitrary строит `Shape` из
байтов фаззера: первые байты выбирают вариант, следующие — поля, длина
вектора `points` — тоже из байтов. Мутация одного байта теперь меняет
одно поле команды, а не ломает CRC.

```console
$ cargo +nightly fuzz run cmd_v1_shape -- -seed=1 -runs=300000
#2	INITED exec/s: 0 rss: 33Mb
WARNING: no interesting inputs were found so far. Is the code instrumented for coverage?
This may also happen if the target rejected all inputs we tried so far
...
thread '<unnamed>' (19200) panicked at code/ch31/src/cmd.rs:166:9:
index out of bounds: the len is 8 but the index is 8
...
SUMMARY: libFuzzer: deadly signal
MS: 1 InsertByte-; base unit: 45d7bb9e4bf0ef01f538b06a9bc974e673838a8a
...
Test unit written to fuzz/artifacts/cmd_v1_shape/crash-20dba98dadfa3346dbde1afc19ab9ad2b2844370
────────────────────────────────────────────────────────────────────────────────

Error: Fuzz target exited with exit status: 77
```

Падение — на 6508-м запуске, и с ASan, и без санитайзера (на 6441-м): это
паника [проверки границ][g-bounds-check], а не порча памяти.
Предупреждение в начале — не беда: первый вход пустой, а libfuzzer-sys
отвергает входы короче нижней оценки `Arbitrary::size_hint` для `Shape` —
нового покрытия такой вход не даёт. Сохранённый вход — 48 байт, которые
глазами не прочитать; `cargo fuzz fmt` печатает его как структуру через
`Debug`:

```console
$ cargo +nightly fuzz fmt cmd_v1_shape fuzz/artifacts/cmd_v1_shape/crash-20dba98dadfa3346dbde1afc19ab9ad2b2844370
Calibrate {
    sensor: 33667,
    points: [
        [
            118,
            124,
            255,
            255,
        ],
...
        [
            88,
            0,
            0,
            0,
        ],
    ],
}
```

Девять точек. `cargo fuzz run cmd_v1_shape <файл>` повторяет падение
на одном входе, `cargo fuzz tmin` пытается его укоротить. Найденный вход
стоит превратить в обычный тест — `nine_points` в `cmd.rs` строит ту же
команду руками. Исправленная версия отвечает ошибкой:

Цель `frames` — шаг сквозного проекта, о ней раздел
[31.10](10-project.md). Корпус между прогонами стоит хранить: прогон с
корпусом начинает там, где кончил прошлый, а `cargo fuzz cmin`
выбрасывает из корпуса входы, не дающие нового покрытия.

<div class="box hood">

**Под капотом: что собирает `cargo fuzz build`.** Цель собирается
nightly-компилятором в release с `-Cpasses=sancov-module` и
`-Cllvm-args=-sanitizer-coverage-*` (счётчики блоков, таблица адресов,
трассировка сравнений, глубина стека), с `-Cdebug-assertions` — а
значит, с проверками переполнения, — `--cfg fuzzing` и по умолчанию с
`-Zsanitizer=address`; `--sanitizer none` его убирает. Макрос
`fuzz_target!` определяет `LLVMFuzzerTestOneInput` — ту самую функцию,
которую libFuzzer зовёт в C, — и ставит [хук паники][g-panic-hook],
который вызывает `abort`: libFuzzer видит панику как аварийный сигнал
(«deadly signal»). Код выхода 77 — от самого libFuzzer: так он по умолчанию
(`-error_exitcode=77`) завершается, найдя падение, а cargo fuzz лишь
передаёт этот код дальше.

</div>

**Как в C.** Та же ошибка на C — `code/ch31/c`: таблица на восемь
точек — последнее поле структуры команды.

```c

```

```c
{{#include ../../code/ch31/c/cmd.c:calibrate_v1}}
```

GCC 13 и clang 18 с `-Wall -Wextra` молчат. Программа `replay.c`
подаёт ту самую команду на девять точек, а за структурой кладёт
«канарейку» `0xC0FFEE`:

```c
{{#include ../../code/ch31/c/replay.c:replay}}
```

Все четыре сборки — GCC и clang, с ASan и без — печатают одно и то же:
`parse_v1: 0, точек 9, за таблицей 0x41414141`. Разбор «успешен», а
поле за таблицей испорчено байтами калибровки. ASan молчит и здесь:
девятая точка ложится внутрь объемлющей структуры `frame`, а ASan
следит только за границами целых объектов. Цель libFuzzer по форме
команды (`fuzz_shape.c`) без ASan за два миллиона запусков ничего не
находит — порча тихая, падать нечему. С ASan — `stack-buffer-overflow`
на 4902-м запуске: в цели структура `command` — сама по себе объект на
стеке, и девятая точка выходит за него. Цель на сырых байтах, как и в
Rust, за три миллиона запусков до калибровки на девять точек не
доходит.

Разница не в фаззере — он один и тот же. Разница в том, что в Rust
выход за границы массива — проверка, которую фаззер видит как
падение, а в C — неопределённое поведение, которое видно, только если
санитайзер случайно следит именно за этой границей.

</div>

<div class="box trap">

**Ловушка: фаззер нашёл не всё.** «Миллион запусков без падений» — не
доказательство, а мера усилия: цель на сырых байтах проходила
калибровку тысячи раз и ни разу с девятью точками. Смотреть стоит на
покрытие: `cargo fuzz coverage` собирает цель с инструментированием
покрытия и прогоняет корпус, а `llvm-cov show` показывает, какие строки
корпус так и не выполнил. Строка `table.points[i] = …` выполнялась —
но покрытие строк не говорит, что при `i = 8`. Для «для всех входов» —
раздел [31.7](07-kani.md).

</div>
