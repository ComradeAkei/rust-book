# 31. Надёжность: тесты, фаззинг, верификация

## Мотивирующая проблема

Прошивка станции принимает команды хоста по UART. Разбор написан на C,
прошёл ревью, тесты зелёные. Через полгода в поле приходит команда
калибровки на девять точек, а таблица рассчитана на восемь: девятая
точка ложится поверх соседнего поля структуры, станция продолжает
работать и шлёт неверные значения. Что было у автора, чтобы этого не
случилось:

- **тесты — каждый сам себе.** В C нет стандартного способа написать и
  запустить тест: Unity, CMocka, Check, свой `main` с `assert`. Тесты
  живут в отдельном дереве и отстают от кода; пример из документации
  никто не компилирует;
- **примеры, придуманные человеком.** Тест проверяет команды, о которых
  автор подумал. Калибровку на девять точек он не написал, потому что о
  ней не подумал, — тест знает ровно то же, что код;
- **фаззинг — отдельный проект.** libFuzzer и AFL есть и для C, но цель
  нужно написать, собрать с правильными флагами, завести корпус. И даже
  с ними случайные байты редко проходят маркер, длину и CRC;
- **санитайзеры видят не всё.** ASan ловит выход за границы объекта, а
  девятая точка остаётся внутри объемлющей структуры — это не ошибка
  для ASan. Гонку в обработчике прерывания на хосте не воспроизвести;
- **доказать нельзя, только поискать.** CBMC умеет проверять C, но им
  почти никто не пользуется: модель окружения, циклы, указатели — всё
  руками;
- **кто проверит тесты.** Покрытие строк 100 %, а изменение `>` на `>=`
  в проверке длины ни один тест не замечает;
- **чужой код.** Библиотеку скопировали в `vendor/` три года назад.
  Какие в ней известные уязвимости и что выполняется при её сборке — не
  знает никто.

## Что делает Rust

Система типов снимает часть вопросов заранее: в безопасном коде нет
неопределённого поведения, выход за границы — паника, а не порча
соседа, гонка данных не компилируется. Остальное — логика, паники,
`unsafe`, FFI, порядок атомарных операций, зависимости — по-прежнему
надо проверять. Инструменты для этого в Rust те же, что в C, или их
прямые потомки, но собраны вокруг cargo:

- **`cargo test`** — модульные тесты рядом с кодом, интеграционные в
  `tests/`, примеры из документации компилируются и выполняются;
  `compile_fail` проверяет, что ошибочный код *не* собирается;
- **тесты без std** — логику прерывания отделяют от железа трейтом и
  проверяют на хосте детерминированно, а на Cortex-M3 в QEMU — с
  настоящим исключением;
- **proptest** — свойства вместо примеров: генератор входов и
  уменьшение контрпримера до минимального;
- **cargo-fuzz** — тот же libFuzzer, что у clang, но вход может быть
  структурой (`Arbitrary`), а не только байтами;
- **санитайзеры** — `-Zsanitizer=address` и `thread` на nightly, тот же
  рантайм из LLVM, что у clang;
- **Miri** — интерпретатор, который знает правила Rust о памяти и ловит
  неопределённое поведение, которое на железе «работает»; **loom**
  перебирает чередования потоков;
- **Kani** — проверка моделей на основе того же CBMC: «для всех входов»
  вместо «для этих»;
- **cargo-mutants** — проверяет сами тесты: портит код и смотрит, заметят
  ли они;
- **cargo-deny, cargo-audit, cargo-vet** — лицензии, известные
  уязвимости, сценарии сборки и ревью зависимостей по `Cargo.lock`.

Глава проходит эти инструменты по порядку на одном сквозном примере —
разборе команд станции и очереди из главы 21 — и для каждого показывает,
что он находит, а что пропускает. В конце — шаг сквозного проекта:
доказательства Kani, фаззинг и мутанты для разбора кадров телеметрии.

## Код главы

Библиотека — `code/ch31`: по модулю на тему, программа опытов для
санитайзеров `src/bin/san.rs`, тесты в `tests`. Цели фаззинга —
`code/ch31/fuzz`, свой workspace. То же на C — `code/ch31/c`. Логика
прерывания без std — крейт `code/ch31-irq`, прошивка с тестами —
`firmware/ch31-tests`. Демонстрация цепочки поставок —
`code/ch31/supply`, политика cargo-deny — `deny.toml` в корне. Задачи —
в `exercises/ch31` и `solutions/ch31`.

```console
$ cargo test -p ch31 -p ch31-irq                  # разделы 31.1–31.3, 31.5
$ bash firmware/run-demos.sh                      # раздел 31.2 вместе с прошивками других глав
$ bash code/ch31/fuzz/run.sh                      # раздел 31.4, нужны nightly и cargo-fuzz
$ bash code/ch31/c/run.sh                         # раздел 31.4, «Как в C»
$ bash code/ch31/miri/run.sh                      # раздел 31.6, нужен nightly с miri
$ RUSTFLAGS="--cfg loom" cargo test -p ch31 --release --test loom --target-dir target/loom
$ bash code/ch31/kani/run.sh                      # разделы 31.7 и 31.10
$ bash code/ch31/mutants/run.sh                   # разделы 31.8 и 31.10
$ bash code/ch31/supply/run.sh                    # раздел 31.9
$ cargo test -p ch31-solutions                    # задачи A–D
```

Каждый скрипт сверяет то, что утверждает текст: вердикт инструмента,
строку его отчёта, число запусков до падения. Фаззер, proptest и
скрипты идут с фиксированным зерном, поэтому числа воспроизводятся.
Опыты с санитайзерами — тест `tests/sanitizers.rs`: без nightly с
компонентом rust-src он пропускается, `CH31_REQUIRE_SANITIZERS` делает
пропуск ошибкой — так его запускает CI.

Вывод снят с rustc 1.97.0 и nightly 1.101.0 (2026-10-21, LLVM 23.1.4)
на x86-64: ядро 6.18, glibc 2.39, GCC 13.3, clang 18.1.3, QEMU 8.2.2,
proptest 1.12.0, cargo-fuzz 0.13.2 с libfuzzer-sys 0.4.13, loom 0.7.2,
Kani 0.68.0 с CBMC 6.11.0, cargo-mutants 27.1.0, cargo-deny 0.20.2,
cargo-audit 0.22.2, cargo-vet 0.10.3.
