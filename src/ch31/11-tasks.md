# 31.11. Задачи

Заготовки — в `exercises/ch31`, по модулю на задачу; функции с `todo!()`
собираются и паникуют только при вызове. Тесты, общие для заготовок и
решений, — `tests-shared/ch31.rs`. Каждая задача проверяется тем
инструментом, которому она посвящена: A — мутантами функций, B —
входами, на которых падали внедрённые ошибки, C — очередью «после почти
2⁶⁴ операций» против модели, D — прогоном cargo mutants по хранилищу
проекта и вектором из описания протокола.

```console
$ cargo test -p ch31-exercises             # все задачи
$ cargo test -p ch31-exercises task_c      # одна задача
$ cargo test -p ch31-solutions             # эталон
$ cd exercises/ch31/fuzz && cargo +nightly fuzz run packet   # задача B
$ cargo kani -p ch31-exercises             # доказательства задачи C
```

Прогон D запускает cargo mutants и без него пропускается с сообщением;
`CH31_REQUIRE_MUTANTS` делает пропуск ошибкой. С ним прогон эталона идёт
около минуты. Разборы — в [приложении E](../appendix-e/ch31.md), но
сначала попробуйте сами.

## A. Шесть свойств

Для каждой из шести функций нужны стратегия — какие входы порождать — и
свойство — что должно выполняться на любом из них. Функции даны и
верны; общие тесты прогоняют каждую пару «стратегия + свойство» с одним
зерном, 256 случаев, против верной функции и против её мутантов с
правдоподобными ошибками. Верная должна проходить, каждый мутант —
падать.

Подписи заданы, например:

```rust,ignore
pub fn sum_inputs() -> BoxedStrategy<Vec<u32>>;
pub fn sum_prop(f: fn(&[u32]) -> Option<u32>, xs: &[u32]) -> TestCaseResult;
```

Свойство получает проверяемую реализацию параметром — так одно и то же
свойство судит и верную функцию, и мутанта. Свойство, повторяющее код
функции, мутанта не поймает: нужна другая реализация (модель) или
утверждение, которое проверяется без вычисления ответа тем же способом
(раздел [31.3](03-proptest.md)). Мутант, которого случайные входы «по
умолчанию» не задевают, требует стратегии, которая целится в границы.

## B. Фаззинг парсеров глав 5 и 6

В `exercises/ch31/src/b_fuzz` — копии разбора заголовков IPv4 и TCP из
задачи 6.B и токенизатора конфигурации из задачи 5.B, по одной
внедрённой ошибке в каждой. Решения глав 5 и 6 не открывайте, пока не
найдёте ошибки сами.

Напишите два *оракула* (test oracles) — функции, которые на любом входе
гоняют разбор и паникуют, если он нарушил свойство:

```rust,ignore
/// Любые байты — как пакет IPv4 и как сегмент TCP. Паника, если разбор
/// паникует сам или принимает то, что с байтами не согласуется.
pub fn check_packet(data: &[u8]);

/// Любой текст. Паника, если токенизатор паникует сам или выдаёт
/// лексемы, которые с текстом не согласуются.
pub fn check_config(text: &str);
```

Цели фаззинга в `exercises/ch31/fuzz` уже зовут ваши оракулы:

```console
$ cd exercises/ch31/fuzz
$ cargo +nightly fuzz run packet
$ cargo +nightly fuzz run config
```

Одна из двух ошибок — паника, её находит и оракул «не падает». Вторая
ничего не роняет: разбор принимает то, чего принимать не должен, и
найдёт её только оракул, который сверяет результат с байтами. Найденные
ошибки исправьте в копиях. Тесты проверяют исправления — входами, на
которых ошибки проявлялись, — и оракулы: на правильных пакетах и
конфигурациях, на их обрезках и перевёрнутых битах и на двухстах
псевдослучайных входах они должны молчать.

## C. Очередь со свободно бегущими индексами

```rust,ignore
{{#include ../../exercises/ch31/src/c_ring.rs:ring}}
```

В главе 21 индексы [заворачиваются][g-wrapping] по модулю `N`, и один слот всегда
пуст. Здесь `head` и `tail` — счётчики записанных и прочитанных
элементов: их разность — длина, и заняты могут быть все `N` слотов.
Так часто пишут во встраиваемом коде.

Докажите с Kani, что `push` и `pop` не переполняются, не выходят за
границы и сохраняют порядок при любом `N` от 1 до 8 и из любого
состояния — его даёт `Ring::new_at`. Доказательства положите в модуль
`proofs` под `#[cfg(kani)]` в конце `c_ring.rs`. Найденные ошибки
исправьте так, чтобы очередь работала при любом `N`, без ограничений
на `N` вроде «только степени двойки». Тесты сравнивают очередь с
моделью `VecDeque` при всех `N` от 1 до 8, начиная и с нуля, и с
`usize::MAX / 2`, и в нескольких шагах от `usize::MAX`, а ещё гоняют
писателя и читателя в двух потоках через заворот.

Подсказка о времени: доказательство на заготовке при некоторых `N` идёт
минуты и дольше. Начните с малых `N`; для исправленной очереди каждое
`N` проходит за секунды.

## D. Ошибки, которых не видят инструменты

**Часть 1. Мутанты хранилища.** Хранилище измерений проекта
(`project/telemetry-store`, глава 15) со своими тестами:

```console
$ cargo mutants -p telemetry-store -- --test store
```

Несколько мутантов выживают. Допишите тесты в
`exercises/ch31/tests/d_store.rs` так, чтобы выживших не осталось, не
меняя хранилища. Проверка — общий тест `d_store_mutants_killed`:

```text
cargo mutants -p telemetry-store --test-package telemetry-store,ch31-exercises \
    --baseline skip -- --test store --test d_store
```

Счётчики распределителя проекта работают, только если в тестовом файле
объявлен [`#[global_allocator]`][g-global-allocator] — так, как в заголовке заготовки.
Среди выживших есть мутант, для которого нужен тест на большие блоки
памяти: подумайте, какие числа отличают `+` от `*`.

**Часть 2. Ошибка спецификации.** Из описания протокола станции, раздел
«Синхронизация времени»:

> Команда SYNC несёт 6 байт: `epoch_s` — секунды Unix, `u32`, затем
> `offset_ms` — поправка в миллисекундах, `i16`. Все многобайтовые поля
> передаются в сетевом порядке, старшим байтом вперёд. Пример: полночь
> 1 января 2026 года UTC с поправкой −250 мс — `69 55 B9 00 FF 06`.
