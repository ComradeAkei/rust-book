Заготовки — в `exercises/ch29`: ответы задачи A и разбор трассы задачи
D2 — в `src/`, модули ядра задач B, C и D1 — в `modules/`. Модули
собирает Kbuild, а не cargo, и с `CLIPPY=1`: линты ядра — часть
условия, предупреждение [clippy][g-clippy] в файле задачи роняет тест. Тесты,
общие для заготовок и решений, — `tests-shared/ch29.rs`; они собирают
модули, кладут их вместе с программой гостя `ch29-task-guest`
(`tests-shared/ch29-guest.rs`) в initramfs и для каждого сценария
загружают ядро в QEMU. Заготовки собираются и загружаются как есть, но
задач не решают.

```console
$ bash code/ch29/kernel/build.sh          # ядра главы, если ещё не собраны
$ cargo test -p ch29-exercises            # все задачи
$ cargo test -p ch29-exercises task_c     # одна задача
$ cargo test -p ch29-solutions            # эталон
```

Без собранного ядра тесты с QEMU пропускаются; разбор трассы и вывода
objdump задачи D2 проверяется и без него. Задача A грузит отладочное
ядро двенадцать раз — под TCG это несколько минут. Разборы — в
[приложении E](../appendix-e/ch29.md), но сначала попробуйте сами.

## C. Общий счётчик и эталон на C

Устройство `/dev/ch29-counter` хранит один счётчик `u64` на всех, кто его
открыл. Эталон — `tests-shared/ch29/c-ref/ch29_counter_c.c`,
`/dev/ch29-counter-c`; модуль на Rust должен вести себя так же:

- `write` — десятичное число, необязательный `+` впереди и один `\n` в
  конце; число прибавляется к счётчику. Не число, пустая запись или
  запись длиннее 23 байт — `EINVAL`, число больше `u64::MAX` — `ERANGE`,
  переполнение суммы — `EOVERFLOW`;
- `read` с позиции 0 снимает значение — строку `N\n` — для этого
  открытия; продолжение чтения отдаёт тот же снимок, даже если счётчик
  с тех пор изменился;
- `lseek` нет (`ESPIPE`), а `pread` с позиции 0 снимает значение заново;
- счётчик — под мьютексом ядра: одновременные записи из нескольких
  процессов не теряются.

Сеанс одинаковый для обоих устройств:

## D1. kobject-example на Rust

Перенесите на Rust образец ядра `samples/kobject/kobject-example.c`:
каталог `/sys/kernel/kobject_example` с файлами `foo`, `baz` и `bar`,
права 0664, в каждом — целое число. Абстракций kobject и sysfs в крейте
`kernel` 7.0 нет: понадобятся сгенерированные привязки
(`kernel::bindings`) и `unsafe`. Линты ядра требуют комментарий
`// SAFETY:` у каждого блока `unsafe` и раздел `# Safety` у каждой
`unsafe fn`, и тест собирает модуль с `CLIPPY=1`.

Сеанс одинаковый для образца и для модуля на Rust:


Образец ядро главы собирает само (`CONFIG_SAMPLE_KOBJECT=m`).

Вопросы к отчёту. На какое обещание sysfs опирается каждый ваш `unsafe`?

дал бы написать её так же? Макрос `__ATTR` в C проверяет права при
компиляции — что потерялось при переносе и как это вернуть?
