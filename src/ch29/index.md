# 29. Rust в ядре Linux

## Мотивирующая проблема

Драйвер на C живёт по правилам, которые компилятор не проверяет, и
нарушение почти любого из них не видно, пока ядро не упадёт:

- **откат на пути ошибки.** `init` [модуля][g-kernel-module] получает ресурсы по очереди, и
  отказ на шаге N обязан освободить N−1 ресурс в обратном порядке.
  Цепочка `goto err_*` держится на дисциплине: одна пропущенная метка —
  утечка, лишняя — двойное освобождение;
- **блокировка до последнего `return`.** `mutex_lock` в начале функции и
  `mutex_unlock` перед каждым выходом. Забытый на редком пути — и
  следующий вызов зависнет навсегда;
- **контекст.** В [атомарном контексте][g-atomic-context] — под спин-блокировкой, в
  обработчике прерывания — спать нельзя, а спать могут `kmalloc` с
  [`GFP_KERNEL`][g-gfp], `mutex_lock`, `msleep` и всё, что их зовёт. Типы C об этом
  не знают;
- **граница с пространством пользователя.** Указатель от пользователя
  нельзя разыменовать: только `copy_from_user`, которая возвращает число
  *не*скопированных байтов, а не код ошибки;
- **структуры, которые нельзя перемещать.** Мьютекс, список ожидания,
  `struct list_head` ссылаются сами на себя. `memcpy` такой структуры
  компилируется и даже работает — пока кто-нибудь не пойдёт по
  указателю в оригинал;
- **`void *private_data`.** Состояние открытого файла, контекст
  обработчика, данные устройства — всё через `void *` и приведение
  обратно, `container_of` и ручной подсчёт ссылок.

Отладочное ядро ([KASAN][g-kasan], [lockdep][g-lockdep], [kmemleak][g-kmemleak]) ловит многое из этого — но
только на путях, которые кто-то выполнил, и только если ядро собрано с
отладкой.

## Что делает Rust

В ядре нет std: ни кучи по умолчанию, ни потоков, ни [паники][g-panic] с
[раскруткой][g-unwinding]. Есть [крейт][g-crate] `kernel` — безопасные абстракции над C-API ядра,
написанные на Rust поверх сгенерированных привязок. Модуль на Rust
вызывает те же функции ядра, что модуль на C, но через типы, которые
знают правила:

- **ошибка — `Result<T, Error>`** с кодом errno внутри, и `?` вместо
  `goto`: ресурсы, полученные до отказа, освобождает `Drop`;
- **блокировка — охранник.** `lock()` возвращает значение, которое
  отпускает блокировку в `Drop`; данные под мьютексом доступны только
  через охранника;
- **выделение памяти — всегда с флагами.** `KBox::new(x, GFP_KERNEL)`,
  `v.push(x, GFP_ATOMIC)`: у каждого вызова, который может выделить
  память, флаги — обязательный аргумент, а отказ — `Err(AllocError)`;
- **pin-init.** Структуры, которые нельзя перемещать, создаются не
  значением, а инициализатором на месте, и тип [`Pin`][g-pinning] не даёт их
  переместить потом;
- **`Send` и `Sync`** работают и для работ в очереди ядра и
  обработчиков прерываний: счётчик без синхронизации не соберётся;
- **граница с пользователем — отдельные типы.** `UserSlice`,
  `IovIterSource`, `IovIterDest` копируют через границу и возвращают
  `EFAULT`; разыменовать адрес пользователя нельзя.

Чего Rust не исправляет: сон в атомарном контексте, порядок взятия
блокировок, ошибки логики. А паника Rust в ядре — не раскрутка стека, а
[oops][g-oops]. Всё это глава показывает в QEMU, на настоящем ядре.

## Код главы

Модули ядра лежат в `code/ch29/modules` и собираются системой сборки ядра
*Kbuild*, а не cargo: у каждого примера на Rust есть пара на C там, где
сравнение что-то показывает. `code/ch29/modules-fail` — модули, которые не
должны собираться. Крейт `code/ch29` — обвязка: на машине разработчика он
собирает модули, образ initramfs и запускает QEMU, а внутри машины
работает её init — программа на Rust, которая грузит модули и печатает
журнал ядра. Тест на каждый опыт загружает ядро заново и сверяет вывод с
текстом главы.

```console
$ bash code/ch29/kernel/build.sh     # два ядра 7.0: обычное и отладочное
$ cargo test -p ch29                 # опыты в QEMU, gdb, модули с ошибками
$ cargo test -p ch29-solutions       # задачи A–D
```

Без собранного ядра тесты пропускаются с сообщением. Нужны clang, lld и
llvm 18, QEMU для x86-64 и gdb; полный список и время сборки — в
разделе [29.2](02-build.md).

Ядро — Linux 7.0, rustc 1.97.0 (тот же, что у книги, с компонентом
`rust-src`), [bindgen][g-bindgen] 0.72.1, clang 18.1.3, QEMU 8.2.2, gdb 15.1. Вывод
снят в QEMU без KVM (эмуляция TCG) с двумя процессорами на машине с
Xeon 2,1 ГГц; в CI те же тесты идут под KVM. Адреса в выводе не
случайны — KASLR в ядре главы выключен, — но зависят от того, что
загружалось раньше; тесты сверяют области адресов, а не сами адреса.
