# 1. Скалярные типы и представление в памяти

## Мотивирующая проблема

Три строки на C, каждая из которых выглядит очевидной:

```c
{{#include ../../code/ch01/c/promote.c}}
```

```console
$ gcc -O2 -fsanitize=undefined promote.c && ./a.out       # GCC 13.3, x86_64
a + b > 255
promote.c:13:21: runtime error: signed integer overflow: 65535 * 65535 cannot be represented in type 'int'
x * x = 4294836225
~m = 0xfffffff0
```

Ни в одной строке программа не делает того, что написано. Сумма двух
`uint8_t` оказывается больше 255, потому что до сложения оба операнда
превратились в `int` (*integer promotion*). Произведение двух `uint16_t`
переполняет знаковый `int`, и это неопределённое поведение: *UBSan* (UndefinedBehaviorSanitizer,
[санитайзер][g-sanitizer] неопределённого поведения из GCC и Clang) ловит его, а без санитайзера программа печатает «правильное» число, пока
оптимизатор не решит иначе. Побитовое НЕ над `uint8_t` даёт не `0xF0`, а
32-битное `0xFFFFFFF0`, и сравнение ложно.

Все три ответа зависят от размера `int`, а его стандарт оставляет на
усмотрение реализации: не меньше 16 бит. На x86_64 и Cortex-M он 32-битный,
на AVR и MSP430 — 16-битный. Там `uint16_t` уже не помещается в `int` и
превращается в `unsigned int`: `x * x` перестаёт быть UB, зато
[заворачивается][g-wrapping] начиная с x = 256, а сумма двух `uint16_t` по 40 000 даёт
14 464.
Добавьте сюда приведение `float` к целому вне диапазона, которое тоже UB
(раздел [1.7](07-casts.md)), и окажется, что про арифметику на скалярах C
почти ничего не обещает.

## Что делает Rust

- Ширина каждого целого записана в имени типа: `u8`, `i32`, `u128`. Размер
  адреса — отдельные типы `usize` и `isize`. Неявных расширений нет:
  `u8 + u8` даёт `u8`, а `u8 + u16` не компилируется.
- Переполнение никогда не бывает неопределённым поведением. В отладочной
  сборке это [паника][g-panic], в release — заворачивание по модулю 2ⁿ, а методы
  `wrapping_`, `checked_`, `overflowing_`, `saturating_` и `strict_`
  позволяют выбрать поведение явно в любом [профиле][g-profile].
- `f32` и `f64` — это IEEE 754 без оговорок, а приведение `as` из числа с
  плавающей точкой в целое определено на всех входах: [насыщение][g-saturating] на
  границах, NaN превращается в 0.
- `char` — [скалярное значение Unicode][g-unicode-scalar], `bool` — ровно 0 или 1, `str` —
  всегда корректный UTF-8. Эти инварианты держит компилятор, и нарушить их
  можно только в `unsafe`.

Цена этих гарантий видна в ассемблере, и почти всегда она близка к нулю.
Глава показывает, во что каждая гарантия превращается на x86_64 и на трёх
ядрах Cortex-M.

## Код главы

```console
$ cargo test -p ch01 -p ch01-solutions              # примеры и решения
$ cargo asm -p ch01 --lib ch01_checked_add_i32      # ассемблер функции из раздела 1.2
$ cargo run -p ch01 --example floats                # поля чисел IEEE 754
$ cargo +nightly miri run -p ch01 --example bool_ub # Miri ловит bool со значением 2
$ bash code/ch01/c/run.sh                           # C-примеры главы на x86_64 и в QEMU
```

Числа в тексте получены на rustc 1.97.0 (LLVM 22.1.6) для
`x86_64-unknown-linux-gnu`, `thumbv6m-none-eabi` (Cortex-M0),
`thumbv7m-none-eabi` (Cortex-M3) и `thumbv7em-none-eabihf` (Cortex-M4F),
GCC 13.3, clang 18.1 и arm-none-eabi-gcc 13.2 с [newlib][g-newlib]. Ассемблер снят
командой `cargo asm` из release-сборки без директив отладочной
информации, если не сказано иное.
