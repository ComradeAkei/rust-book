# 1.6. Массивы, срезы и строки

## Массив — значение, срез — указатель с длиной

Массив `[T; N]` — значение фиксированного размера: N элементов подряд,
без заголовка. Длина — часть типа, `[u8; 4]` и `[u8; 5]` — разные типы.
Массив передаётся и присваивается целиком, как структура, и к указателю
не сводится:

```rust
{{#include ../../code/ch01/src/slices.rs:array}}
```

После `reversed(a)` исходный `a` не изменился: функция получила копию
четырёх байт. Для больших массивов это дорого, и их передают по ссылке.

Срез `[T]` — непрерывная последовательность элементов, длина которой
известна только во время выполнения. Работают с ним через ссылку `&[T]`
или `&mut [T]`, и эта ссылка «толстая»: пара из адреса первого элемента и
числа элементов. На x86_64 она занимает 16 байт, на Cortex-M 8. Ссылка на
массив `&[T; N]` — обычный указатель: длина известна из типа. Из массива,
`Vec` и другого среза срез получают диапазоном: `&a[1..3]`, `&v[..]`.

## Проверка границ

Индексация среза проверяет индекс всегда, в любом профиле:

```rust
{{#include ../../code/ch01/src/slices.rs:index}}
```

```text
$ cargo asm -p ch01 --lib ch01_get
ch01_get:
	cmp rdx, rsi
	jae .LBB19_2
	mov eax, dword ptr [rdi + 4*rdx]
	ret
.LBB19_2:
	push rax
	lea rax, [rip + .Lanon.53a0877f8bf66fa8d8525a9866c2298c.4]
	mov rdi, rdx
	mov rdx, rax
	call qword ptr [rip + core::panicking::panic_bounds_check@GOTPCREL]

$ cargo asm -p ch01 --lib --target thumbv7m-none-eabi ch01_get
ch01_get:
	cmp r2, r1
	itt lo
	ldrlo.w r0, [r0, r2, lsl #2]
	bxlo lr
	push {r7, lr}
	mov r7, sp
	...
	bl core::panicking::panic_bounds_check
```

Срез пришёл в двух регистрах (`rdi` — адрес, `rsi` — длина; на ARM `r0` и
`r1`), индекс в третьем. Проверка — одно беззнаковое сравнение: отрицательных
индексов у `usize` не бывает, так что `i < len` покрывает обе границы. На
Cortex-M3 и сравнение, и загрузка, и возврат уместились в блок `itt lo` без
единого перехода.

В цикле проверка обычно исчезает совсем:

```rust
{{#include ../../code/ch01/src/slices.rs:loops}}
```

`ch01_sum_indexed` и `ch01_sum_iter` компилируются в один и тот же код:
на x86_64 они отличаются только порядком двух инструкций, на Cortex-M3 —
распределением регистров. В обоих нет ни одной проверки границ: диапазон
`0..xs.len()` сам доказывает, что `xs[i]` в пределах среза. Цикл на
x86_64 векторизован (`movdqu` и `paddd` по восемь элементов за итерацию),
на Cortex-M3 развёрнут по четыре элемента с `ldm`.

Интереснее `ch01_sum_first`, где граница цикла чужая:

```text
$ cargo asm -p ch01 --lib ch01_sum_first
ch01_sum_first:
	test rdx, rdx
	je .LBB31_1
	lea rax, [rdx - 1]
	cmp rsi, rax
	jbe .LBB31_11
	cmp rdx, 8
	jae .LBB31_6
	...
.LBB31_11:
	push rax
	lea rdx, [rip + .Lanon.53a0877f8bf66fa8d8525a9866c2298c.6]
	mov rdi, rsi
	call qword ptr [rip + core::panicking::panic_bounds_check@GOTPCREL]
```

Компилятор не знает, что `n <= xs.len()`, но проверку из цикла всё равно
убрал: перед циклом стоит одна проверка `n − 1 < len`, а дальше тот же
векторный цикл без проверок. Это законно, потому что тело цикла ничего
не меняет снаружи: паника на индексе `len` случится до суммирования, а не
после, и отличить эти два исхода невозможно. Обратите внимание на `mov
rdi, rsi`: в сообщение о панике уходит индекс, равный длине, тот самый,
на котором упал бы исходный цикл.

Если тело пишет в память, такой номер не пройдёт: к моменту паники первые
элементы уже должны быть записаны. Тогда компилятор раздваивает цикл:
векторная часть идёт без проверок до безопасной границы
`min(len₁, len₂, n − 1)`, а хвост — по одному элементу с проверкой в
каждой итерации.

<div class="box trick">

**Трюк: одна проверка вместо многих.** Если граница приходит извне,
сделайте проверку явной один раз, до цикла: `let xs = &xs[..n];`. После
этого компилятор знает длину точно, а паника, если `n` слишком велико,
случится в одном понятном месте. Ещё надёжнее итераторы (`iter`, `zip`,
`chunks_exact`): они не индексируют вовсе, и проверять нечего. Метод
`get(i)` возвращает `Option` вместо паники, а `get_unchecked(i)` снимает
проверку совсем и требует `unsafe` (раздел [0.5](../ch00/05-checks.md)
показывает, чем это кончается при ошибке).

</div>

## str — байты UTF-8

`str` — срез байт, про который известно, что это корректный UTF-8.
Инвариант держится везде: строковые литералы проверяет компилятор, а
`core::str::from_utf8` проверяет байты во время выполнения и возвращает
ошибку, если последовательность обрывается или содержит запрещённые байты.
`&str`, как и `&[u8]`, — толстая ссылка из адреса и длины в байтах.
Нулевого байта в конце нет, и длина известна сразу, без `strlen`.

```rust
{{#include ../../code/ch01/examples/strings.rs:strings}}
```

```console
$ cargo run -p ch01 --example strings
len = 12, chars = 6
байты: [d0, bf, d1, 80, d0, b8, d0, b2, d0, b5, d1, 82]

thread 'main' (28264) panicked at code/ch01/examples/strings.rs:15:22:
end byte index 1 is not a char boundary; it is inside 'п' (bytes 0..2 of string)
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
```

`len()` считает байты, а не символы: шесть кириллических букв — это
двенадцать байт. Символы перечисляет `chars()`, и их подсчёт — проход по
всей строке. Индекс среза строки — тоже в байтах, и резать можно только
по границе символа: иначе получился бы `str` с половиной буквы, то есть
некорректный UTF-8. Поэтому `&s[..1]` паникует, а сообщение называет
символ и его байты. Правильный способ взять первый символ:

```rust
{{#include ../../code/ch01/src/slices.rs:str}}
```

<div class="box c">

**Как в C.** Массив в выражении превращается в указатель на первый
элемент, и в параметре функции `int a[16]` — это `int *a`: `sizeof(a)`
внутри функции вернёт размер указателя, а длину приходится передавать
отдельно и проверять вручную. Строка — указатель на байты до первого
нуля: длина стоит O(n), нулевой байт внутри данных обрывает строку, а о
кодировке язык не знает ничего. `strncpy` не добавляет завершающий ноль,
если строка не поместилась, и следующий `strlen` уходит за край буфера.
Срезы Rust несут длину с собой, и все эти ошибки превращаются либо в
ошибку компиляции, либо в панику с сообщением.

</div>
