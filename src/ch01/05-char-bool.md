# 1.5. char и bool

Оба типа выглядят как целые, но у каждого есть инвариант: не всякий набор
битов — допустимое значение. Компилятор опирается на эти инварианты при
оптимизации, а нарушить их можно только в `unsafe`.

## char — скалярное значение Unicode

`char` занимает 4 байта и хранит *скалярное значение Unicode* (Unicode scalar value): число от 0
до `0x10FFFF`, кроме диапазона суррогатов `0xD800..=0xDFFF`, которые
существуют только как половинки пар в UTF-16. Это не байт, как `char` в C,
и не «символ» в смысле того, что видит читатель: буква с ударением может
быть одним скалярным значением или двумя (буква и комбинируемый знак).

```rust
{{#include ../../code/ch01/src/chars.rs:char}}
```

Из произвольного `u32` в `char` можно попасть только через проверку:
`char::from_u32(0x44F)` даёт `Some('я')`, а `char::from_u32(0xD800)` и
`char::from_u32(0x11_0000)` — `None`. Обратно путь свободен:
`'я' as u32 == 0x44F`. Из `u8` приведение `as char` тоже разрешено, потому
что все 256 значений — допустимые скалярные значения, первые 256 кодов
Unicode совпадают с Latin-1: `0xE9_u8 as char == 'é'`. Приведение
`char as u8` оставляет младший байт кода и ничего не проверяет.

Строки хранят текст не в `char`, а в UTF-8, где одно скалярное значение
занимает от одного до четырёх байт:

| Символ | Код | Байты UTF-8 |
|---|---|---|
| `'A'` | U+0041 | `41` |
| `'я'` | U+044F | `D1 8F` |
| `'€'` | U+20AC | `E2 82 AC` |
| `'🦀'` | U+1F980 | `F0 9F A6 80` |

Таблица проверяется тестом `utf8_lengths` в `code/ch01/src/chars.rs`.

Недопустимые значения `char` компилятор использует как [нишу][g-niche] (глава 6,
раздел [6.4](../ch06/04-niches.md)): `size_of::<Option<char>>()` равно 4,
потому что `None` кодируется значением, которого у настоящего `char` не
бывает. Каким именно, язык не обещает; rustc 1.97 выбирает `0xFFFF_FFFF`.

## bool — ровно 0 или 1

`bool` занимает байт, и допустимы в нём только 0 (`false`) и 1 (`true`).
`true as u8` равно 1, а в обратную сторону приведения `as` нет вовсе.
Байт превращают в `bool` сравнением:

```rust
{{#include ../../code/ch01/src/chars.rs:bool}}
```

Что бывает, если инвариант нарушить, показывает пример с намеренной
ошибкой:

```rust
{{#include ../../code/ch01/examples/bool_ub.rs:bool_ub}}
```

[clippy][g-clippy] видит ошибку сразу (`transmute_int_to_bool`, подсказка
`byte != 0`), поэтому предупреждение в примере подавлено явно. Запуск:

```console
$ cargo run -p ch01 --example bool_ub
b = true, !b = true
b as u8 = 0, !b as u8 = 1
$ cargo run -p ch01 --example bool_ub --release
b = true, !b = true
b as u8 = 2, !b as u8 = 1
```

Значение одновременно истинно вместе со своим отрицанием, а его числовое
значение зависит от профиля. В отладочной сборке это видно по ассемблеру
`main`:

```text
$ cargo asm -p ch01 --example bool_ub --dev bool_ub::main
	...
	mov al, byte ptr [rsp + 6]
	and al, 1
	mov byte ptr [rsp + 78], al
	mov al, byte ptr [rsp + 6]
	xor al, -1
	and al, 1
	mov byte ptr [rsp + 79], al
	...
```

LLVM считает `bool` одним битом и при каждом чтении берёт из байта
младший бит: `b as u8` превращается в `2 & 1 = 0`, а `!b` — в
`(2 ^ 0xFF) & 1 = 1`. Форматирование же проверяет, не равен ли байт нулю,
и печатает `true` для обоих. В release компилятор, уверенный, что байт и
так 0 или 1, маску не ставит, и `b as u8` даёт 2. Ни один из ответов не
«правильный»: программа с неопределённым поведением не обязана быть
последовательной.

Miri останавливается на первой же ошибке, ещё до печати:

```console
$ cargo +nightly miri run -p ch01 --example bool_ub
error: Undefined Behavior: constructing invalid value of type bool: encountered 0x02, but expected a boolean
  --> code/ch01/examples/bool_ub.rs:16:28
   |
16 |     let b: bool = unsafe { std::mem::transmute::<u8, bool>(byte) };
   |                            ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ Undefined Behavior occurred here
```

Тем же способом ломаются `char` (значение `0xD800`), `&T` (нулевой адрес)
и `enum` (несуществующий вариант). Правило одно: значение недопустимого
вида — неопределённое поведение в момент создания, даже если его никто не
прочитал. Подробнее — в главе 16.

<div class="box c">

**Как в C.** `char` в C — байт, и знаковый он или нет, решает реализация:
на x86_64 Linux знаковый, на ARM Linux и в arm-none-eabi-gcc — беззнаковый.
`wchar_t` занимает 4 байта на Linux и 2 на Windows, где хранит единицы
UTF-16, а не символы. `_Bool` при преобразовании нормализует любое
ненулевое значение в 1, но объект `_Bool`, в который записали 2 через
`memcpy` или указатель на `char`, даёт неопределённое поведение при
чтении, ровно как в примере выше.

</div>
