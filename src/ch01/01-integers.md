# 1.1. Целые фиксированной ширины

В Rust двенадцать целых типов, и ширина каждого записана в имени:

| Ширина | Со знаком | Без знака | Аналог в C |
|---|---|---|---|
| 8 бит | `i8` | `u8` | `int8_t`, `uint8_t` |
| 16 бит | `i16` | `u16` | `int16_t`, `uint16_t` |
| 32 бита | `i32` | `u32` | `int32_t`, `uint32_t` |
| 64 бита | `i64` | `u64` | `int64_t`, `uint64_t` |
| 128 бит | `i128` | `u128` | `__int128` (расширение GCC и clang) |
| ширина адреса | `isize` | `usize` | `ptrdiff_t`, `size_t` |

Знаковые хранятся в дополнительном коде, и это гарантия языка, а не
свойство платформы. Типов вроде `int` и `long`, размер которых выбирает
реализация, нет. Литерал без суффикса и без подсказки из контекста имеет
тип `i32`, литерал с точкой — `f64`. Суффикс пишется прямо за числом:
`300_i32`, `0xFF_u8`, `1e10_f32`; подчёркивания между цифрами игнорируются
и нужны только для чтения.

## usize: ширина адреса

`usize` — тип индексов, длин и размеров. Он ровно такой ширины, как
указатель:

```rust
{{#include ../../code/ch01/src/ints.rs:usize}}
```

На x86_64 это 64 бита, на Cortex-M 32. Ограничение `isize::MAX` для длины
[среза][g-slice] в байтах не случайно: разность двух указателей внутри одного объекта
должна помещаться в `isize`, и аллокатор не выдаст блок больше. На
Cortex-M это 2 ГиБ, больше ОЗУ любого микроконтроллера, а на x86_64 —
8 эксбибайт.

Для своих данных `usize` годится только тогда, когда речь действительно о
памяти: длина буфера, индекс в массиве. Счётчик байт, переданных по [UART][g-uart]
за время работы, или метка времени в микросекундах на [хосте][g-host] поместятся в
`usize`, а на микроконтроллере переполнятся (2³² мкс — это 71 минута).

<div class="box trap">

**Ловушка: тесты на хосте не видят 32-битный `usize`.** Код

```rust,ignore
let total_us: usize = seconds * 1_000_000;
```

проходит все тесты на x86_64 и паникует в отладочной прошивке, как только
`seconds` превысит 4294. В release он молча завернётся (раздел
[1.2](02-overflow.md)). Для величин, которые не связаны с адресами,
выбирайте тип по диапазону значений (`u64` для микросекунд), а
библиотеку главы собирайте и под Cortex-M: `cargo build --target
thumbv7em-none-eabihf`.

</div>

## Порядок байт и выравнивание

Число в памяти — это байты, и Rust даёт к ним прямой доступ без
приведения указателей:

```rust
{{#include ../../code/ch01/src/ints.rs:bytes}}
```

Все [цели][g-target] книги little-endian, так что `bytes_in_memory(0x1122_3344)` даёт
`[0x44, 0x33, 0x22, 0x11]`. Для провода и файлов берут `to_le_bytes` и
`to_be_bytes` (и обратные `from_le_bytes`, `from_be_bytes`): они дают один
и тот же результат на любой платформе, и порядок байт видно в коде, а не в
документации к протоколу. Так кодируется кадр сквозного проекта в
[главе 6](../ch06/11-project.md).

Размер целого языком гарантирован, выравнивание — нет: его задаёт [ABI][g-abi]
платформы. `size_of` и `align_of` из `core::mem` отвечают на оба вопроса,
и тесты главы проверяют ответы на хосте. Для Cortex-M проверка сделана
при компиляции:

```rust
{{#include ../../code/ch01/src/ints.rs:arm_align}}
```

Константный блок вычисляется при каждой сборке под ARM, и неверное
предположение остановит её с ошибкой, указывающей на строку `assert!`.
Сборка под `thumbv6m-none-eabi`, `thumbv7m-none-eabi` и
`thumbv7em-none-eabihf` проходит, а на x86_64 атрибут `cfg` исключает
блок из сборки.

<div class="box ref">

**Справка: выравнивание по ABI.** Процессору удобнее читать число по
адресу, кратному его размеру, и ABI фиксирует, какое выравнивание обязан
обеспечить компилятор. [System V AMD64][g-system-v] (Linux на x86_64) требует для
`__int128` выравнивания 16, и Rust с версии 1.77 выравнивает `u128` так же,
иначе структуры с `u128` не совпадали бы с C. [AAPCS][g-aapcs] (ARM) выравнивает
64-битные типы на 8, а 128-битные по тем же 8. [Раскладка][g-layout] структур из
таких полей — тема [главы 6](../ch06/index.md).

</div>

## Integer promotion и явное расширение

В Rust тип результата арифметики совпадает с типами операндов, а операнды
обязаны совпадать между собой. `u8 + u8` — это `u8`, а `u8 + u16` — ошибка
компиляции:

```text
error[E0308]: mismatched types
 --> src/main.rs:4:17
  |
4 |     let s = a + b;
  |                 ^ expected `u8`, found `u16`
```

Чтобы получить ответ, который в C дала бы integer promotion, расширение
пишут явно:

```rust
{{#include ../../code/ch01/src/ints.rs:promote}}
```

`u16::from(a)` — преобразование без потерь (раздел [1.7](07-casts.md)): оно
существует только для пар типов, где потерь не бывает, поэтому опечатка
вроде `u8::from(x_u16)` не скомпилируется. Пример `promote` повторяет три
строки мотивирующей программы на C:

```rust
{{#include ../../code/ch01/examples/promote.rs:promote}}
```

```console
$ cargo run -p ch01 --example promote
a.wrapping_add(b)      = 44
a.checked_add(b)       = None
u16::from(a) + u16::from(b) = 300
x.checked_mul(x)       = None
u32::from(x) * u32::from(x) = 4294836225
!m                     = 0xf0
```

Каждая строка говорит, какой ответ нужен: остаток по модулю 256, признак
переполнения или точное значение в более широком типе. Побитовое НЕ (`!`
в Rust вместо `~`) над `u8` остаётся `u8`.

<div class="box c">

**Как в C.** Операнды типов меньше `int` перед арифметикой превращаются в
`int` (или в `unsigned int`, если `int` не вмещает все их значения), а
затем оба операнда приводятся к общему типу по *usual arithmetic
conversions*.
Результат зависит от размеров типов на платформе:

| Тип | x86_64 Linux ([LP64][g-lp64]) | Cortex-M (ILP32) |
|---|---|---|
| `int` | 4 | 4 |
| `long` | 8 | 4 |
| `void *`, `size_t` | 8 | 4 |
| выравнивание `long long`, `double` | 8 | 8 |

В заголовках таблицы — модели данных C, названные по буквам типов.
*LP64*: `long` (L) и указатель (P, pointer) — по 64 бита. *ILP32*: `int`
(I), `long` и указатель — по 32 бита.
Размеры сняты `sizeof` и `alignof` из GCC 13.3 и arm-none-eabi-gcc 13.2.
Код, в котором `long` хранит указатель или 64-битный счётчик, переносится
с x86_64 на ARM с ошибкой, которую не заметит ни компилятор, ни тест на
хосте.

</div>
