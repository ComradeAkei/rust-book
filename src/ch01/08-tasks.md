# 1.8. Задачи

Заготовки лежат в `exercises/ch01`, тесты, общие для заготовок и решений,
лежат в `tests-shared/ch01.rs`. Проверка:

```console
$ cargo test -p ch01-exercises            # все задачи
$ cargo test -p ch01-exercises task_b2    # одна задача
```

Пока задачи не решены, тесты падают на `todo!()` и на незаполненных
ответах. Крейт заготовок собирается с оптимизацией даже в профиле `dev`
(переопределение в корневом `Cargo.toml`): перебор в задаче B2 проходит
больше миллиарда чисел. Проверки переполнения при этом остаются
включёнными. Разборы решений — в [приложении E](../appendix-e/ch01.md),
но сначала попробуйте сами.

## A. Двенадцать приведений

Список выражений лежит в `code/ch01/src/task_a.rs`:

```text
№1  300_i32 as u8                          ваш ответ: 45, на самом деле: 44
```

Вторая часть — те же двенадцать выражений на C. Напишите их дважды: из

`code/ch01/c/run.sh`). Сведите ответы в таблицу. Для каждого выражения
ответьте в отчёте:

- что говорит о нём стандарт C: определено, определяется реализацией или
  неопределённое поведение;
- почему ответ «из констант» может отличаться от ответа «из переменных»
  и почему у GCC и clang константы сворачиваются по-разному;
- какая инструкция дала ответ на x86_64 и на Cortex-M4F.

Одно из выражений clang откажется компилировать. Какое и почему, и что
нужно написать на C, чтобы получить то же, что в Rust?

## B1. 128-битная арифметика на парах u64

В `exercises/ch01/src/b1_u128.rs` объявлен тип `U128 { lo: u64, hi: u64 }`.
Реализуйте для него три функции, не используя `u128` (кроме готовых
преобразований для тестов) и готовые помощники длинной арифметики:
`carrying_add` (стабилен с Rust 1.91) и пока нестабильный `widening_mul`:

- `ch01b_add(a, b) -> (U128, bool)` — сумма по модулю 2¹²⁸ и признак
  переноса из старшего разряда;
- `ch01b_mul_wide(a: u64, b: u64) -> U128` — полное произведение двух
  64-битных чисел, разложением на 32-битные половины;
- `ch01b_mul(a, b) -> U128` — произведение по модулю 2¹²⁸.

Тесты сравнивают ответы с встроенным `u128` на краевых значениях и на
двухстах тысячах случайных пар, в которых 32-битные четверти часто
состоят из одних нулей или единиц: так переносы через границы четвертей
случаются постоянно.

Затем снимите ассемблер своих функций и эталонов `ch01b_*_native` из того
же файла:

```console
$ cargo asm -p ch01-exercises --lib ch01b_add 0
$ cargo asm -p ch01-exercises --lib ch01b_add_native
$ cargo asm -p ch01-exercises --lib --target thumbv7em-none-eabihf ch01b_mul_wide 0
```

(Число в конце выбирает функцию, когда имя — префикс другого имени:
`cargo asm` покажет список.) В отчёте ответьте:

1. Узнал ли LLVM в вашем `ch01b_add` пару `add`/`adc` на x86_64? А цепочку
   `adds`/`adcs` на Cortex-M4F? Если на одной цели узнал, а на другой нет,
   объясните, что мешает.
2. Сколько инструкций умножения в вашем `ch01b_mul_wide` и в
   `ch01b_mul_wide_native` на x86_64? Почему разница так велика?
3. Какие инструкции умножения выбрал компилятор на Cortex-M4F и почему
   здесь ваше разложение на половины почти не проигрывает эталону?
   Что изменится на Cortex-M0?

## B2. Где кончается единица

Найдите наименьшее положительное `f32` x, при котором `x + 1.0 == x`.
Сначала аналитически: выведите ответ из устройства мантиссы и правила
округления и соберите его из полей формата через `f32::from_bits`, не
подбирая. Потом перебором всех битовых шаблонов. Обе функции — в
`exercises/ch01/src/b2_absorb.rs`. Тест проверит, что ответы совпали,
что предыдущее число единицу не поглощает и что ниже ответа нет ни одного
такого числа.

В отчёте ответьте:

1. Почему при переборе положительных чисел достаточно идти по битовым
   шаблонам в порядке возрастания и остановиться на первом найденном?
2. Монотонно ли свойство: если x поглощает единицу, поглощает ли её любое
   большее x? Найдите наименьшее x, начиная с которого единицу поглощают
   все числа, и объясните, что происходит между ним и вашим ответом.
3. Каков ответ для `f64`? Перебрать все шаблоны `f64` невозможно; почему
   двоичный поиск по шаблонам здесь может дать неверный ответ?

## C. Включены ли проверки

В `exercises/ch01/src/c_probe.rs` реализуйте функцию
`overflow_checks_enabled() -> bool`, которая во время выполнения
определяет, включены ли в сборке её крейта проверки переполнения. Без
атрибутов `cfg`, без макроса `cfg!` и без чтения переменных окружения.

Проверки переполнения и `debug_assertions` включаются отдельными ключами
профиля, и тест это использует: он собирает пример
`exercises/ch01/examples/probe.rs` дважды, с `dev`-профилем без проверок и
с `release`-профилем с проверками, и ждёт от функции `false` и `true`
соответственно:

```console
$ cargo run -p ch01-exercises --example probe --config profile.dev.overflow-checks=false
false
$ cargo run -p ch01-exercises --example probe --release --config profile.release.overflow-checks=true
true
```

В отчёте объясните, почему оптимизатор не выбросил вашу проверку: в
release-сборке без проверок функция должна честно вернуть `false`, а не
«что-нибудь», а со включёнными проверками — `true`. Что скажет компилятор,
если сложить в проверке две константы? Что будет с вашей функцией в
профиле с `panic = "abort"`?

## D. Одно округление или два

В `exercises/ch01/src/d_fma.rs` даны две функции: `ch01d_separate`
вычисляет `a * b + c`, `ch01d_fused` — `a.mul_add(b, c)`.

1. Найдите входы `DIFFER`, на которых функции дают разный результат.
   Объясните расхождение по битам мантиссы.
2. Найдите входы `CANCEL`, на которых `ch01d_separate` возвращает ровно
   ноль, а `ch01d_fused` — нет. Тест проверит, что слитный результат
   совпадает с точным значением `a · b + c`, посчитанным в `f64`. Что
   именно вернула FMA?
3. Реализуйте `product_error(a, b) -> (f32, f32)`: округлённое
   произведение `p` и его точную ошибку `e`, так что `a · b = p + e` без
   потерь. Одним вызовом FMA, без `f64` и других широких типов. Тест
   проверяет равенство на двухстах тысячах случайных пар через `f64`.
   При каких входах ваше `e` перестанет быть точным?

Затем сравните ассемблер `ch01d_separate` и `ch01d_fused` для трёх целей:
базового x86_64, x86_64 с FMA (`--target-cpu=x86-64-v3`) и Cortex-M4F.
Для последней понадобится nightly: в `core` слитное умножение-сложение
пока нестабильно, и заготовка включает его признаком `nightly`:

```console
$ cargo asm -p ch01-exercises --lib ch01d_fused
$ cargo asm -p ch01-exercises --lib --target-cpu=x86-64-v3 ch01d_fused
$ cargo +nightly asm -p ch01-exercises --lib --features nightly \
      --target thumbv7em-none-eabihf ch01d_fused
```

Если при первой сборке под новую цель nightly-версия `cargo asm` ответит
`Cannot locate the path to the asm file`, повторите команду: вторая
попытка находит уже собранный файл.

В отчёте ответьте: почему на Cortex-M4F раздельный вариант — тоже одна
инструкция, но результат у неё другой; во что обходится `mul_add` на
базовом x86_64 и где это видно в ассемблере; что получится на Cortex-M3,
где FPU нет вовсе.
