# 1.4. Плавающая точка: f32 и f64

`f32` и `f64` — двоичные форматы одинарной и двойной точности IEEE 754.
Язык не допускает вычислений с повышенной точностью за спиной программиста
и не переставляет операции: `a * b + c` — это ровно два округления в
указанном порядке на любой платформе. Отсюда воспроизводимость, но
отсюда же и то, что глобального ключа вроде `-ffast-math` в Rust нет.

## Поля числа

Число одинарной точности — 32 бита: знак, 8 бит смещённого порядка и 23
бита дробной части мантиссы. Ведущая единица мантиссы не хранится. Методы
`to_bits` и `from_bits` дают к этим битам прямой доступ без `unsafe`:
любые 32 бита — допустимое значение `f32`.

```console
$ cargo run -p ch01 --example floats
           1e0  0x3f800000  знак 0  порядок 127  мантисса 0x000000  ulp 1.1920929e-7
        -2.5e0  0xc0200000  знак 1  порядок 128  мантисса 0x200000  ulp 2.3841858e-7
          1e-1  0x3dcccccd  знак 0  порядок 123  мантисса 0x4ccccd  ulp 7.450581e-9
   1.6777216e7  0x4b800000  знак 0  порядок 151  мантисса 0x000000  ulp 2e0
 1.1754944e-38  0x00800000  знак 0  порядок   1  мантисса 0x000000  ulp 1e-45
         1e-45  0x00000001  знак 0  порядок   0  мантисса 0x000001  ulp 1e-45
           inf  0x7f800000  знак 0  порядок 255  мантисса 0x000000  ulp NaN
           NaN  0x7fc00000  знак 0  порядок 255  мантисса 0x400000  ulp NaN
```

Строка за строкой:

- `1.0` = 1,0 × 2⁰: порядок хранится со смещением 127, дробная часть
  нулевая. Шаг до следующего числа — `f32::EPSILON`, 2⁻²³.
- `-2.5` = −1,25 × 2¹: знак 1, порядок 128, дробь 0,25 = 2⁻² — это второй
  сверху бит дроби, `0x200000` (старший, `0x400000`, весит 2⁻¹).
- `0.1` в двоичной системе — бесконечная дробь. В 23 бита она не
  помещается и округляется вверх: последняя цифра `d` вместо `c` в
  периоде `...cccc`. Число в памяти чуть больше одной десятой.
- `16777216` = 2²⁴. Шаг между соседними числами здесь уже 2: целые выше
  2²⁴ представимы не все, а только чётные. Для `f64` та же граница — 2⁵³.
- `f32::MIN_POSITIVE` — наименьшее нормализованное число, порядок 1.
  Ниже идут денормализованные: порядок 0, ведущая единица не
  подразумевается, и точность падает вместе со значением. Наименьшее из
  них — `f32::from_bits(1)`, около 1,4 · 10⁻⁴⁵.
- Порядок 255 зарезервирован: при нулевой дроби это бесконечность, при
  ненулевой — NaN. `f32::NAN` в Rust — «тихий» NaN с единицей в старшем
  бите дроби.

Шаг удваивается на каждой степени двойки, и это главное свойство
формата: относительная точность постоянна (около 7 десятичных цифр для
`f32` и 16 для `f64`), а абсолютная падает с ростом числа.

## NaN, порядок и сортировка

NaN не равен ничему, включая себя. Поэтому `f32` реализует только
`PartialEq` и `PartialOrd`: сравнение может вернуть «несравнимо».
`Eq` и `Ord` требуют полного порядка, и их у `f32` нет. Следствие, на
которое натыкаются в первый же день:

```text
error[E0277]: the trait bound `f32: Ord` is not satisfied
   --> src/main.rs:3:7
    |
  3 |     v.sort();
    |       ^^^^ the trait `Ord` is not implemented for `f32`
```

Решений два, и выбор между ними — решение о данных:

```rust
{{#include ../../code/ch01/src/floats.rs:order}}
```

`total_cmp` реализует отношение totalOrder из IEEE 754: отрицательные NaN
меньше −∞, положительные больше +∞, а −0 меньше +0. Порядок совпадает с
порядком битовых шаблонов, если у отрицательных чисел инвертировать все
биты, кроме знакового, и так он и вычисляется — целочисленным
сравнением без ветвлений. Второй вариант трактует NaN как отсутствие
значения. Стандартные `f32::max` и `f32::min` ведут себя так же:
`f32::NAN.max(1.0)` равно 1.

<div class="box trap">

**Ловушка: два нуля.** `0.0 == -0.0` истинно, но биты у них разные
(`0x0000_0000` и `0x8000_0000`), и `1.0 / -0.0` даёт −∞. Хеш по
`to_bits` или сравнение через `total_cmp` считают нули разными, а `==`
одинаковыми. Если ключи `HashMap` — числа с плавающей точкой, приводите
−0 к +0 до хеширования, а NaN не пускайте вовсе.

</div>

## Программная плавающая точка на Cortex-M

На x86_64 сложение `f32` и `f64` — одна инструкция SSE (`addss`, `addsd`).
На Cortex-M всё зависит от ядра:

```rust
{{#include ../../code/ch01/src/floats.rs:soft}}
```

```text
$ cargo asm -p ch01 --lib --target thumbv7m-none-eabi ch01_fadd32
ch01_fadd32:
	push {r7, lr}
	mov r7, sp
	bl __aeabi_fadd
	pop {r7, pc}

$ cargo asm -p ch01 --lib --target thumbv7em-none-eabihf ch01_fadd32
ch01_fadd32:
	push {r7, lr}
	mov r7, sp
	vadd.f32 s0, s0, s1
	pop {r7, pc}

$ cargo asm -p ch01 --lib --target thumbv7em-none-eabihf ch01_fadd64
ch01_fadd64:
	push {r7, lr}
	mov r7, sp
	vmov r0, r1, d0
	vmov r2, r3, d1
	bl __aeabi_dadd
	vmov d0, r0, r1
	pop {r7, pc}
```

У Cortex-M0 и M3 блока плавающей точки нет, и каждая операция — вызов
функции из `compiler_builtins`. `__aeabi_fadd` — 12-байтная обёртка над
реализацией `__addsf3` (в выводе `nm -C` она называется
`compiler_builtins::float::add::__addsf3`, а неискажённое имя `__addsf3` —
такая же 12-байтная обёртка). Реализация занимает 474 байта кода Thumb-2
с ветками для денормализованных чисел, бесконечностей и NaN
(`__adddf3` для `f64` — 864 байта). Аргументы и результат идут в
целочисленных регистрах `r0`–`r3`: так велит [soft-float][g-soft-float] ABI цели
`thumbv7m-none-eabi`.

У Cortex-M4F есть FPU, но только одинарной точности (FPv4-SP). `f32`
складывается одной `vadd.f32`, а аргументы приходят в регистрах
`s0`–`s15` (hard-float ABI, суффикс `hf` в имени цели). `f64` на том же
ядре снова программная: пара `vmov` перекладывает аргументы из `d0`, `d1`
в целочисленные регистры, и вызывается `__aeabi_dadd`.

<div class="box trap">

**Ловушка: незаметный `f64` в прошивке.** Литерал `0.5` без суффикса в
выражении с переменной `f32` станет `f32`, но в выражении без других
подсказок — `f64`. Приведение `as f64` «для точности» или константа
`core::f64::consts::PI` в формуле тоже тянут за собой двойную точность.
На M4F это вызов функции в сотни байт вместо одной инструкции FPU, и
каждая операция проходит через десятки инструкций с ветвлениями. Проверяйте прошивку командой
`arm-none-eabi-nm -S --size-sort` на имена `__aeabi_d*`: если они есть,
где-то в коде живёт `f64`.

</div>

## FMA: умножение и сложение с одним округлением

Инструкция *FMA* (fused multiply-add) вычисляет `a · b + c` точно и
округляет результат один раз. Обычное выражение `a * b + c` округляет
дважды: после умножения и после сложения. Результаты иногда расходятся в
последнем бите, а иногда сильнее; где и почему, выясняет задача D.

Rust никогда не заменяет выражение на FMA сам, даже если процессор её
умеет:

```rust
{{#include ../../code/ch01/src/floats.rs:no_fma}}
```

```text
$ cargo asm -p ch01 --lib --target-cpu=x86-64-v3 ch01_mul_add_separate
ch01_mul_add_separate:
	vmulss xmm0, xmm0, xmm1
	vaddss xmm0, xmm0, xmm2
	ret

$ cargo asm -p ch01 --lib --target thumbv7em-none-eabihf ch01_mul_add_separate
ch01_mul_add_separate:
	push {r7, lr}
	mov r7, sp
	vmla.f32 s2, s0, s1
	vmov.f32 s0, s2
	pop {r7, pc}
```

На Cortex-M4F получилась одна инструкция, но это `vmla` — умножение с
накоплением, которое округляет произведение перед сложением. Слитная
версия называется `vfma`, и её компилятор здесь не выбрал: результат
изменился бы. Чтобы получить FMA, её просят явно методом `mul_add`:

```rust
{{#include ../../code/ch01/examples/fma.rs:fused}}
```

```text
$ cargo asm -p ch01 --example fma fma::fused
fma::fused:
	jmp qword ptr [rip + fmaf@GOTPCREL]

$ cargo asm -p ch01 --example fma --target-cpu=x86-64-v3 fma::fused
fma::fused:
	vfmadd213ss xmm0, xmm1, xmm2
	ret
```

На базовом x86_64 инструкции FMA может не быть, и компилятор вызывает
функцию `fmaf`. С `x86-64-v3` это одна `vfmadd213ss` (цифры в имени
говорят, какие операнды перемножаются, а какой прибавляется).

<div class="box hood">

**Под капотом: чей `fmaf`.** Можно подумать, что `fmaf` берётся из libm
glibc. В программе на Rust его даёт `compiler_builtins`, и выбирает
реализацию при первом вызове:

```console
$ nm -C target/release/examples/fma | grep fma
0000000000015070 t fma::main
00000000000150d0 t fma::fused
0000000000056990 t compiler_builtins::math::libm_math::arch::x86::fma::fmaf_fallback
0000000000056a50 t compiler_builtins::math::libm_math::arch::x86::fma::fmaf_with_fma
0000000000056a60 t compiler_builtins::math::libm_math::arch::x86::fma::fmaf_with_fma4
0000000000056a70 t compiler_builtins::math::libm_math::arch::x86::fma::fmaf::initializer
000000000005c1a8 d compiler_builtins::math::libm_math::arch::x86::fma::fmaf::FUNC
0000000000056970 t fmaf
```

`fmaf` делает косвенный вызов через указатель `FUNC`. Сначала там
записан `initializer`: он спрашивает у процессора `cpuid`, какие
расширения есть, кладёт в `FUNC` адрес подходящего варианта и вызывает
его. На этой машине (Intel Xeon с FMA) выбирается `fmaf_with_fma`, а это
`vfmadd213ss xmm0, xmm1, xmm2` и `ret`. Программная `fmaf_fallback` — 54
инструкции. Так что `mul_add` без `target-cpu` корректна на любом
процессоре и быстра на современном, но платит двумя косвенными переходами
за вызов.

</div>

На Cortex-M `mul_add` в стабильном Rust недоступен: метод живёт в `std`,
а прошивка собирается с `core`. В nightly он есть в `core` под
`#![feature(core_float_math)]` и на M4F компилируется в `vfma.f32`; задача D
показывает это на практике.

<div class="box c">

**Как в C.** Стандарт C разрешает компилятору сливать `a * b + c` в FMA
(*contraction*) и управляет этим директивой `#pragma STDC FP_CONTRACT`,
GCC — ключом `-ffp-contract`. GCC в режиме GNU C (по умолчанию) сливает агрессивно, в
режиме ISO C — нет:

```text
$ gcc -O2 -mfma -S fma.c                  # muladd: vfmadd132ss xmm0, xmm2, xmm1
$ gcc -O2 -mfma -std=c11 -S fma.c         # muladd: vmulss + vaddss
$ arm-none-eabi-gcc -O2 -mcpu=cortex-m4 -mfloat-abi=hard -mfpu=fpv4-sp-d16 -S fma.c
                                          # muladd: vfma.f32 s2, s0, s1
```

Один и тот же исходник даёт разные числа в зависимости от `-std` и
`-march`. Отсюда же старая проблема x87 на 32-битном x86: промежуточные
результаты хранились в 80-битных регистрах, и сравнение
`a + b == c` зависело от того, вытеснил ли компилятор значение в память.
`-ffast-math` разрешает ещё и переставлять операции и считать, что NaN не
бывает. В Rust ни одно из этих послаблений не включается флагом
компилятора: результат определяет исходник.

</div>
