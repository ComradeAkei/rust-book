# 7.3. Трейт Error и цепочки причин

## Что требует трейт

```rust,ignore
pub trait Error: Debug + Display {
    fn source(&self) -> Option<&(dyn Error + 'static)> { None }
    // description и cause устарели, provide нестабилен
}
```

Ошибка обязана уметь показать себя человеку (`Display`) и программисту
(`Debug`), а `source` по желанию отдаёт причину — ошибку уровня ниже.
Причины образуют односвязный список: «не удалось прочитать
конфигурацию» → «ключ rate: ожидалось число» → «invalid digit found in
string». Каждое звено знает только свой уровень.

Время жизни `'static` в `source` нужно для `downcast_ref`: проверка типа
через `TypeId` работает только для типов без заимствований (раздел 5.3).

## Цепочка из трёх уровней

Нижний уровень — позиция в тексте:

```rust
{{#include ../../code/ch07/src/chain.rs:leaf}}
```

Средний — ошибка разбора конфигурации. Каждый вариант хранит причину и
отдаёт её через `source`:

```rust
{{#include ../../code/ch07/src/chain.rs:middle}}
```

Верхний — контекст: что делала программа, когда всё сломалось. Это
универсальная обёртка над любой ошибкой. Крейт `anyhow` даёт то же
самое методом `.context(…)`, здесь всё сделано руками за двадцать
строк:

```rust
{{#include ../../code/ch07/src/chain.rs:context}}
```

`context` принимает замыкание, а не готовую строку: `format!` выполнится
только на пути ошибки, а путь успеха не выделяет память.

## Отчёт: обход цепочки

```rust
{{#include ../../code/ch07/src/chain.rs:report}}
```

`core::iter::successors` строит итератор, где каждый следующий элемент
вычисляется из предыдущего: здесь `e`, `e.source()`, `e.source().source()`
и так до `None`. Использование:

```rust
{{#include ../../code/ch07/src/chain.rs:usage}}
```

```text
ошибка: чтение station.ini, строка 3
  причина: ключ rate: ожидалось число
  причина: invalid digit found in string
```

Тест `report_walks_the_chain` сверяет этот текст и проверяет, что
последнее звено для строки без `=` — `SyntaxError` с нужной позицией,
полученный через `downcast_ref`.

## Сообщение или причина, но не оба

Документация трейта `Error` даёт правило: ошибка либо отдаёт причину
через `source`, либо включает её текст в своё сообщение, но не делает
и то и другое. Нарушить его легко:

```rust
{{#include ../../code/ch07/src/chain.rs:twice}}
```

```text
ошибка: плохое число: invalid digit found in string
  причина: invalid digit found in string
```

Любая программа, которая печатает цепочку (наш `report`, `anyhow`,
журнал сервиса), покажет причину дважды. Обратная ошибка — включить
текст причины в сообщение и не отдавать её через `source` — ломает
`downcast_ref` по цепочке: найти `ParseIntError` внизу уже нельзя.

<div class="box c">

**Как в C.** Ближайшее к цепочке причин в C — `perror` с префиксом и
соглашение «сначала сохрани `errno`, потом печатай». Контекст в C
обычно склеивают в буфер `snprintf`-ом на каждом уровне, и исходный код
ошибки после этого достаётся только разбором строки. В ядре Linux
вместо этого кладут код в указатель (`ERR_PTR(-EINVAL)`) и протаскивают
его через уровни, теряя по пути всё, кроме числа.

</div>

<div class="box trick">

**Трюк.** `Display` у ошибки пишется с маленькой буквы и без точки в
конце: так её удобно встраивать в чужие сообщения и печатать цепочкой.
Это соглашение стандартной библиотеки (`invalid digit found in string`),
и `clippy` его не проверяет, так что следите сами.

</div>
