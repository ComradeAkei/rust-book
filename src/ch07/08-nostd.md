# 7.8. Паника без ОС

## #[panic_handler]

В `no_std` нет ни хука паники, ни раскрутки, ни потоков, которые можно
остановить. `core` при панике только собирает сведения о ней в
`PanicInfo` и вызывает *обработчик паники* (panic handler) — функцию,
которую обязана предоставить сама программа:

```rust,ignore
#[panic_handler]
fn panic(info: &core::panic::PanicInfo) -> ! { … }
```

Тип `!` означает, что функция не возвращает управление: вернуться
некуда, код после паники не рассчитан на продолжение. Обработчик ровно
один на всю программу. Без него прошивка не соберётся:

```text
error: `#[panic_handler]` function required, but not found
```

А в программе с `std` свой обработчик не нужен и запрещён: он уже есть
в `std`, и второй даёт ошибку `E0152: found duplicate lang item
`panic_impl``. Хук `std::panic::set_hook` из раздела
[7.5](05-panic.md) — это надстройка `std` над тем же механизмом.

## Что делать в обработчике

Решение зависит от устройства. Варианты, от простого к сложному:

- остановиться в бесконечном цикле или на `bkpt`, чтобы отладчик
  увидел состояние (крейт `panic-halt`);
- перезапустить микроконтроллер через `SCB::sys_reset()` — для
  устройства без присмотра это часто лучший выбор;
- сообщить причину: по [semihosting][g-semihosting] под отладчиком
  (`panic-semihosting`), по [RTT][g-rtt] или [UART][g-uart] (`panic-probe` с `defmt`), в
  энергонезависимую память, чтобы прочитать после перезапуска;
- перевести выходы в безопасное состояние: выключить нагреватель,
  закрыть клапан. Это единственное, что обработчик обязан сделать на
  устройстве, которое чем-то управляет.

Прошивка `firmware/ch07-panic` читает таблицу коэффициентов по номеру
канала, который «пришёл снаружи», и на пятом канале выходит за
границу:

```rust
{{#include ../../firmware/ch07-panic/src/lib.rs:work}}
```

Обработчик с отчётом:

```rust
{{#include ../../firmware/ch07-panic/src/bin/report.rs:report}}
```

```console
$ cd firmware
$ cargo run --release -q -p ch07-panic --bin report
опрос каналов
канал прочитан
канал прочитан
канал прочитан
канал прочитан
паника в ch07-panic/src/lib.rs:24:5
index out of bounds: the len is 4 but the index is 4

$ cargo run --release -q -p ch07-panic --bin report --target thumbv6m-none-eabi
…
паника в ch07-panic/src/lib.rs:24:5
index out of bounds: the len is 4 but the index is 4
```

Тот же отчёт, что на [хосте][g-host], получен на Cortex-M3 и Cortex-M0 в QEMU.
Первым делом обработчик запрещает прерывания: состояние программы
неизвестно, и обработчик прерывания мог бы работать с испорченными
данными. Строка 24 — `GAINS[channel]` в `gain`.

## Сколько стоит сообщение

Второй обработчик ничего не печатает:

```rust
{{#include ../../firmware/ch07-panic/src/bin/silent.rs:silent}}
```

Обе прошивки выполняют одну и ту же работу, а строки в `run`
печатаются без форматирования, поэтому `core::fmt` попадает в образ
только из обработчика с отчётом:

| Прошивка | Cortex-M3, `text` | Cortex-M0, `text` |
|---|---|---|
| `report` | 5008 | 4468 |
| `silent` | 2028 | 1204 |

Размеры сняты `llvm-size` с release-сборки. Его столбец `text` — это
код вместе с [таблицей векторов][g-vector-table] и константами, то есть секции
`.vector_table`, `.text` и `.rodata`. Около трёх килобайт —
цена `core::fmt::write`, форматирования целых чисел и строк,
необходимых, чтобы напечатать `the len is 4 but the index is 4`. Из
`silent` компоновщик выбросил всё это: сообщение паники собирается в
`PanicInfo`, но раз обработчик его не читает, после [встраивания][g-inlining] и [LTO][g-lto]
код форматирования оказывается недостижимым. Из оставшихся 2 КБ почти
половину занимает таблица векторов прерываний (`__INTERRUPTS`, 960
байт), которая есть в любой прошивке.

<div class="box trap">

**Ловушка.** Тот же замер с `hprintln!("канал {}: усиление {}", …)` в
основном цикле даёт обратный результат: `silent` получается на
92 байта *больше* `report`. Форматирование уже нужно самой программе,
и молчаливый обработчик ничего не экономит, а мелкие различия в
встраивании решают дело. Экономия от обработчика без сообщения бывает
только там, где форматирования нет больше нигде. Проверяйте размер
`llvm-size` после каждого такого решения, а не рассуждением.

</div>

<div class="box trick">

**Трюк.** Если места совсем мало, nightly умеет убирать из паник всё,
включая место и сообщение: стратегия `-Cpanic=immediate-abort`
вместе с `-Zbuild-std` (раньше — фича `panic_immediate_abort`)
превращает любую панику в немедленный аварийный останов без хука,
сообщения и места. Цена — полное отсутствие диагностики. На хосте тот же приём сжимает программу задачи
7.C с 462 КБ до 66 КБ (приложение E).

</div>

<div class="box c">

**Как в C.** В прошивке на C роль обработчика паники играют
`assert_failed` из HAL производителя, `__assert_func` из [newlib][g-newlib] и
обработчик [HardFault][g-hardfault]. Каждый пишут отдельно, а выход за границу массива
не приводит ни к одному из них: он тихо портит соседнюю память. В Rust
все эти пути сходятся в одну функцию, а проверка границ встроена в
язык.

</div>

<div class="box check">

**Проверь себя.**

1. Почему обработчик паники возвращает `!`, а не `()`?
2. Что произойдёт, если обработчик паники сам вызовет функцию, которая
   паникует? Подумайте о стеке и о том, что раскрутки нет.
3. Почему в `silent` осталась функция `__cortex_m_rt_main` размером 798
   байт, если `run` в нём такая же, как в `report`?

</div>
