# 7.4. Проектирование типов ошибок

## Кому нужна ошибка

Тип ошибки — часть интерфейса, и выбирают его по тому, кто будет её
разбирать.

- **Библиотека, драйвер, протокол.** Вызывающий решает, что делать:
  повторить при тайм-ауте, пересинхронизироваться при плохой CRC,
  сдаться при отказе устройства. Ему нужен `enum` с вариантами, по
  которым можно сделать `match`, и с данными, нужными для решения.
- **Приложение, `main`, утилита.** Ошибку, скорее всего, только покажут
  человеку и запишут в журнал. Подойдёт `Box<dyn Error + Send + Sync>`
  или своя обёртка с контекстом из раздела [7.3](03-error-trait.md).

Крейты `thiserror` (для первого случая) и `anyhow` (для второго)
пишут тот же код, что разобран в этой главе, макросами. В учебнике мы
обходимся без них, чтобы было видно, что внутри, а в прошивках они
часто и не нужны.

## Размер ошибки платят все

Ошибка разбора, которая для удобства отладки хранит копию плохой строки:

```rust
{{#include ../../code/ch07/src/sizes.rs:fat}}
```

| Тип | Размер на x86_64 |
|---|---|
| `FatError` | 72 |
| `Result<u32, FatError>` | 76 |
| `Result<u32, Box<FatError>>` | 16 |
| `Result<(), Box<FatError>>` | 8 |

Размер `Result` — максимум из `Ok` и `Err` плюс признак, и вызывающий
отводит под результат столько места, даже если ошибок не бывает
никогда.

<div class="box hood">

**Под капотом.** Уровень выше передаёт ошибку через `?`. Версия с
ошибкой по значению, до первого перехода после проверки признака:

```text
ch07_outer_fat:
	push rbx
	sub rsp, 80
	mov rbx, rdi
	lea rdi, [rsp + 4]
	call qword ptr [rip + ch07_parse_fat@GOTPCREL]
	mov eax, dword ptr [rsp + 8]
	cmp dword ptr [rsp + 4], 1
	jne .LBB41_2
	mov ecx, dword ptr [rsp + 76]
	mov dword ptr [rbx + 72], ecx
	movups xmm0, xmmword ptr [rsp + 12]
	movups xmm1, xmmword ptr [rsp + 28]
	movups xmm2, xmmword ptr [rsp + 44]
	movups xmm3, xmmword ptr [rsp + 60]
	movups xmmword ptr [rbx + 56], xmm3
	movups xmmword ptr [rbx + 40], xmm2
	movups xmmword ptr [rbx + 24], xmm1
	movups xmmword ptr [rbx + 8], xmm0
	mov ecx, 1
	jmp .LBB41_3
```

Версия с ошибкой в куче, тот же участок:

```text
ch07_outer_boxed:
	push rbx
	sub rsp, 16
	mov rbx, rdi
	mov rdi, rsp
	call qword ptr [rip + ch07_parse_boxed@GOTPCREL]
	cmp dword ptr [rsp], 1
	jne .LBB40_2
	mov rax, qword ptr [rsp + 8]
	mov qword ptr [rbx + 8], rax
	mov eax, 1
	jmp .LBB40_3
```

В первой версии каждый уровень вызовов держит на стеке 80 байт под результат
нижнего уровня, а на пути ошибки копирует 72 байта в свой результат:
четыре 16-байтовых `movups` и ещё одно слово. Во второй — 16 байт стека
и копия одного указателя. Путь успеха в обеих версиях пишет только
признак и значение. В прошивке с 2–8 КБ стека разница в 64 байта на
каждом уровне `?` — это не абстракция.

</div>

<div class="box trick">

**Трюк.** `clippy` предупреждает о большой ошибке сам: линт
`result_large_err` включён по умолчанию и срабатывает, когда вариант
`Err` занимает 128 байт и больше:

```text
  |               ^^^^^^^^^^^^^^^^^ the `Err`-variant is at least 128 bytes
  |
  = help: try reducing the size of `E128`, for example by boxing large elements or replacing it with `Box<E128>`
```

Порог настраивается в `clippy.toml` (`large-error-threshold`). Для
прошивки разумно опустить его до 32–64 байт. Без кучи вместо `Box`
храните в ошибке индекс или смещение, а данные оставьте там, где они
лежали.

</div>

## #[non_exhaustive]: место для новых вариантов

Если в следующей версии драйвера появится ошибка `Overrun`, все
`match` по `DriverError` у пользователей крейта перестанут
компилироваться. Атрибут `#[non_exhaustive]` заранее запрещает им
перечислять варианты без ветки `_`:

```rust
{{#include ../../code/ch07/src/sizes.rs:non_exhaustive}}
```

Внутри крейта атрибут ничего не меняет, а снаружи (doc-тест в
`code/ch07/src/sizes.rs`):

```text
error[E0004]: non-exhaustive patterns: `_` not covered
 --> ne.rs:2:11
  |
2 |     match e {
  |           ^ pattern `_` not covered
  |
  = note: the matched value is of type `DriverError`
  = note: `DriverError` is marked as non-exhaustive, so a wildcard `_` is necessary to match exhaustively
```

Цена — пользователь больше не узнает от компилятора о новом варианте.
Для ошибок протокола, где каждый вариант требует своей реакции, иногда
честнее оставить перечисление исчерпывающим и выпускать новую мажорную
версию при его расширении.

## io::Error: ошибка в одном слове

`std::io::Error` — пример хорошо спроектированной ошибки. Она
описывает и код ОС, и вид ошибки, и произвольную ошибку пользователя, а
занимает одно машинное слово:

```rust
{{#include ../../code/ch07/src/io.rs:io}}
```

Тест `io_error_is_one_word` проверяет, что `size_of::<io::Error>()` и
`size_of::<io::Result<()>>()` равны размеру указателя. Тест
`errors_keep_os_code` открывает `/` и читает его как файл: ошибка
хранит `EISDIR` (21), тот самый код, который потерял `errno.c` во
введении. Код ОС запоминается в момент ошибки и вместе со значением
уходит вызывающему, и никакой последующий вызов его не перезапишет.

<div class="box hood">

**Под капотом: упакованный указатель.** На 64-битных платформах
`io::Error` хранит указатель, у которого два младших бита заняты под
вид содержимого: выравнивание указываемых данных не меньше 4, и эти
биты в настоящем адресе всегда нулевые. Код `0b00` — указатель на
статическое сообщение, `0b01` — указатель на `Box` с пользовательской
ошибкой, `0b10` — код ОС в старших 32 битах, `0b11` — один из
`ErrorKind` без сообщения. Так `io::Error` из системного вызова не
выделяет памяти, а `io::Result<()>` возвращается в одном регистре.
Реализация в исходниках rustc 1.97 — `library/std/src/io/error/repr_bitpacked.rs`
(в nightly 1.101 тот же файл уже лежит в `library/core`: `io::Error`
переезжает в `core`). На 32-битных целях используется обычное
перечисление.

</div>
