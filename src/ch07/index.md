# 7. Обработка ошибок и паника

## Мотивирующая проблема

В C у ошибки нет типа. Функция возвращает `-1`, `NULL` или код, а
подробности кладёт в глобальную `errno`. Три программы из
`code/ch07/c` показывают, во что это обходится. Все три собираются
`gcc -O2 -Wall -Wextra -fanalyzer` без единого предупреждения.

**Причину ошибки перезаписали.** Конфигурацию не удалось открыть, и
программа честно сообщает об этом:

```c
{{#include ../../code/ch07/c/errno.c:open_config}}
```

```console
$ ./errno
open /tmp: No such file or directory
```

`/tmp` существует. `open` вернул `EISDIR`, «это каталог», но между
`open` и `strerror` журнал вызвал `fopen` для файла, которого нет, и тот
записал в `errno` своё `ENOENT`. Код ошибки — глобальное состояние (в
многопоточной программе — состояние потока), и любой вызов библиотеки
вправе его менять, даже успешный.

**Проверку забыли.** Функция чтения датчика возвращает 0 или −1, а
значение пишет через указатель:

```c
{{#include ../../code/ch07/c/sensor.h}}
```

```c
{{#include ../../code/ch07/c/unchecked.c}}
```

Канала 7 нет, `read_sensor` вернула −1 и `t` не тронула. Программа
печатает `t = 0` — неинициализированную переменную, которой случилось
быть нулём. Компилятор молчит, пока функцию не пометить
`__attribute__((warn_unused_result))` (в примере — сборка с
`-DMUST_USE`). После этого GCC предупреждает,
причём даже о вызове с `(void)` перед ним, а clang принимает `(void)` как
явный отказ от результата. В стандарте C23 появился атрибут
`[[nodiscard]]`, но в старом коде и в большинстве заголовков его нет.

**Ошибку обработали прыжком.** Чтобы не проверять код возврата на каждом
уровне, C-программы иногда пользуются `setjmp`/`longjmp` как
исключениями:

```c
{{#include ../../code/ch07/c/longjmp.c:handle}}
```

```console
$ ./longjmp
A1: принято
B2: ошибка разбора
A3: шина занята
```

`longjmp` вернул управление в `main`, перепрыгнув через `free` и
`pthread_mutex_unlock`. Копия сообщения утекла (это находит
[LeakSanitizer][g-lsan]: `Direct leak of 64 byte(s)`), а мьютекс шины останется
захваченным до конца процесса: третье сообщение уже не обработать.
Скрипт `code/ch07/c/run.sh` проверяет все три вывода.

## Что делает Rust

- Ошибка — это значение с типом. Функция, которая может не выполниться,
  возвращает `Result<T, E>`, и получить `T`, не посмотрев на вариант,
  нельзя. Код ошибки не лежит в глобальной переменной и не может быть
  перезаписан посторонним вызовом.
- Оператор `?` передаёт ошибку вызывающему одной буквой. Это обычный
  `return`, поэтому все [деструкторы][g-destructor] выполняются: мьютекс отпускается,
  память освобождается (раздел [7.1](01-result.md)).
- Типы ошибок разных уровней связываются через `From` и цепочку `source`:
  «не удалось прочитать конфигурацию» → «ошибка в строке 5» → «значение
  не число» (разделы [7.2](02-convert.md) и [7.3](03-error-trait.md)).
- Для нарушенных инвариантов, то есть ошибок программиста, есть [паника][g-panic].
  Она [раскручивает][g-unwinding] стек, вызывая деструкторы, и останавливает поток. Её
  можно поймать на границе, но не для того, чтобы продолжать как ни в чём
  не бывало (разделы [7.5](05-panic.md)–[7.7](07-ffi.md)).
- На микроконтроллере паника заканчивается вашей функцией
  [`#[panic_handler]`][g-panic-handler]: там решается, сообщить, перезапустить или
  остановиться (раздел [7.8](08-nostd.md)).

Цена всего этого измеряется в главе так же, как в главе 6: ассемблером
и размерами. `Result` с маленькой ошибкой возвращается в регистрах, как
код возврата C. Путь без ошибки не платит за раскрутку ни одной
инструкцией, но таблицы раскрутки занимают место в файле.

## Код главы

```console
$ cargo test -p ch07 -p ch07-solutions                  # примеры и решения
$ cargo run -p ch07 --bin panics -- double              # опыты с паникой, раздел 7.5
$ cargo +nightly test --doc -p ch07                     # коды ошибок в doc-тестах
$ cargo +nightly miri test -p ch07 -p ch07-solutions    # те же тесты под Miri
$ bash code/ch07/c/run.sh                               # errno.c, unchecked.c, longjmp.c
$ cd firmware && cargo run --release -p ch07-panic --bin report   # паника на Cortex-M3
```

Числа в тексте получены на rustc 1.97.0 (LLVM 22.1.6) и nightly 1.101.0
(2026-10-21) для `x86_64-unknown-linux-gnu`, `thumbv6m-none-eabi` и
`thumbv7m-none-eabi`, GCC 13.3 и clang 18.1. Ассемблер снят командой
`cargo asm --simplify` из release-сборки.
