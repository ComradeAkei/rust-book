# 7.5. Паника

## Когда паниковать

`Result` — для ситуаций, которые программа должна пережить: нет файла,
датчик не ответил, пришёл битый кадр. *Паника* (panic) — для нарушенных
инвариантов, то есть для ошибок в самой программе: индекс за границей
массива, `unwrap` на `None`, который «не может быть `None`»,
переполнение в отладочной сборке, `unreachable!()`, который оказался
достижимым. Продолжать после такого бессмысленно: программа уже
находится в состоянии, о котором её автор не думал.

Паника не возвращает значение и не требует обработки на каждом уровне.
Она останавливает поток и сообщает о причине. Что происходит по дороге,
показывают опыты программы `code/ch07/src/bin/panics.rs`. Каждый
запускается отдельно, потому что часть из них завершает процесс:

```console
$ cargo run -q -p ch07 --bin panics -- <опыт>
```

Вывод в тексте снят с `env -u RUST_BACKTRACE`, номер в скобках после
имени потока — его идентификатор в ОС, он меняется от запуска к
запуску. Тест `code/ch07/tests/panics.rs` запускает все опыты и сверяет
строки и способ завершения.

## Раскрутка стека

```rust
{{#include ../../code/ch07/src/bin/panics.rs:loud}}
```

```rust
{{#include ../../code/ch07/src/bin/panics.rs:catch}}
```

```console
$ cargo run -q -p ch07 --bin panics -- catch

thread 'main' (18193) panicked at code/ch07/src/bin/panics.rs:29:9:
index out of bounds: the len is 3 but the index is 7
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
drop a
поймали: index out of bounds: the len is 3 but the index is 7
main завершился
```

Порядок событий:

1. Выражение `v[i]` проверило границу и вызвало панику.
2. *Хук паники* напечатал сообщение и место. Это происходит до
   раскрутки, пока стек ещё цел, поэтому трассировка
   (`RUST_BACKTRACE=1`) видит место паники.
3. Началась *раскрутка* (unwinding): кадры стека снимаются по одному, и для каждой
   живой переменной вызывается деструктор. Отсюда `drop a`.
4. `catch_unwind` остановил раскрутку и вернул `Err` с *полезной
   нагрузкой* паники: `Box<dyn Any + Send>`. Если текст сообщения
   известен при компиляции, внутри лежит `&'static str`: так у
   `panic!("литерал")`, у `None.unwrap()` и даже у `panic!("число {}", 5)`
   — литеральный аргумент компилятор подставляет в строку сам. Если текст
   собирается во время выполнения, как у выхода за границу с конкретным
   индексом, внутри `String`. Поэтому код пробует оба типа.

Без `catch_unwind` раскрутка дошла бы до начала потока. Поток
завершается, а паника главного потока завершает процесс с кодом 101.

<div class="box trap">

**Ловушка.** `catch_unwind` — не `try`/`catch`. Он нужен на границах:
чтобы паника в одном обработчике запроса не уронила весь сервер, чтобы
не выпустить раскрутку в C-код (раздел [7.7](07-ffi.md)), чтобы
тестовый фреймворк поймал упавший тест. Ловить им ожидаемые ошибки
нельзя: при `panic = "abort"` он не ловит ничего, а паника по-прежнему
печатает сообщение и выглядит для пользователя как авария.

</div>

## UnwindSafe

Замыкание для `catch_unwind` должно быть `UnwindSafe`. Ссылки `&mut T` и
ссылки на типы с внутренней изменяемостью (`Cell`, `RefCell`) этому
требованию не удовлетворяют: если паника случилась посреди изменения,
после `catch_unwind` можно увидеть объект в промежуточном состоянии. В
тесте `drop_runs_on_unwind` из `code/ch07/src/unwind.rs` проверяется
ровно такое состояние, поэтому замыкание обёрнуто в
`AssertUnwindSafe`: так программист берёт ответственность на себя.
`UnwindSafe` не влияет на безопасность памяти, это подсказка, а не
гарантия, и обойти её можно без `unsafe`.

## Хук паники

```rust
{{#include ../../code/ch07/src/bin/panics.rs:hook}}
```

```console
$ cargo run -q -p ch07 --bin panics -- hook
[станция] паника в code/ch07/src/bin/panics.rs:48: датчик 3 не отвечает

thread 'main' (18195) panicked at code/ch07/src/bin/panics.rs:50:36:
снова со стандартным хуком
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
main завершился
```

Хук вызывается для каждой паники в процессе до начала раскрутки. Его
ставят, чтобы отправить сообщение в журнал, в системный лог или на
экран устройства. `take_hook` снимает свой хук и возвращает стандартный.

## Паника в другом потоке

```rust
{{#include ../../code/ch07/src/bin/panics.rs:thread}}
```

```console
$ cargo run -q -p ch07 --bin panics -- thread

thread '<unnamed>' (18207) panicked at code/ch07/src/bin/panics.rs:129:9:
поток обработки упал, держа замок
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
join: Err("поток паниковал")
замок отравлен, данные: [1, 2, 3, 4]
main завершился
```

Паника убивает поток, а не процесс: `join` возвращает `Err`, и главный
поток решает, что делать. Раскрутка отпустила замок, но `Mutex`
запомнил, что владелец упал, держа его, — замок *отравлен*. Следующий
`lock` возвращает `Err(PoisonError)`, и данные можно забрать через
`into_inner`, осознанно приняв, что они могли остаться наполовину
изменёнными. Здесь `push` успел выполниться, и в векторе четыре
элемента. Подробнее о потоках — в главе 20.

## Двойная паника

Что, если деструктор паникует сам, пока идёт раскрутка от другой паники?

```rust
{{#include ../../code/ch07/src/bin/panics.rs:double}}
```

```console
$ cargo run -q -p ch07 --bin panics -- double

thread 'main' (18197) panicked at code/ch07/src/bin/panics.rs:69:5:
первая паника
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
drop a
drop Flusher: сброс буфера

thread 'main' (18197) panicked at code/ch07/src/bin/panics.rs:62:9:
сброс не удался
stack backtrace:
   …

thread 'main' (18197) panicked at /rustc/2d8144b7880597b6e6d3dfd63a9a9efae3f533d3/library/core/src/panicking.rs:233:5:
panic in a destructor during cleanup
thread caused non-unwinding panic. aborting.
$ echo $?
134
```

Раскрутка уже идёт, и вторую параллельную раскрутку начать нельзя: у
потока один стек и одна «текущая» паника. Rust делает то же, что C++ с
исключением из деструктора, — завершает процесс через `abort`
(SIGABRT, код 134 в shell). Трассировку стека при этом печатает всегда,
даже без `RUST_BACKTRACE` (в тексте она сокращена). Деструкторы
оставшихся значений не выполняются.

Без первой паники тот же `Flusher` ведёт себя как любая паника:
`cargo run -p ch07 --bin panics -- drop-only` печатает «сброс не
удался» и завершается с кодом 101. Опасна именно паника в деструкторе
*во время* раскрутки. Как спроектировать тип, у которого деструктору
есть что сбрасывать, но который так не упадёт, — задача
[7.D](09-tasks.md).

<div class="box trap">

**Ловушка.** Деструктор, который вызывает `unwrap` на результате
ввода-вывода, — мина. Пока всё работает, она не видна. Стоит упасть
чему-то другому, раскрутка вызовет деструктор, сеть или диск ответят
ошибкой, и вместо понятной паники с сообщением программа умрёт от
SIGABRT. `std::io::BufWriter` поэтому молча выбрасывает ошибку сброса в
`drop`, а получить её можно только явным `flush` или `into_inner`.

</div>

## #[track_caller]: виноват вызывающий

Функция-помощник с проверкой аргумента обычно паникует у себя внутри,
и сообщение указывает на неё, а не на код, который передал плохое
значение. Атрибут `#[track_caller]` переносит место паники на
вызывающего:

```rust
{{#include ../../code/ch07/src/bin/panics.rs:track}}
```

```console
$ cargo run -q -p ch07 --bin panics -- track

thread 'main' (18203) panicked at code/ch07/src/bin/panics.rs:118:13:
регистр 40 вне окна
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
```

Строка 118 — вызов `reg(std::hint::black_box(40))` в `track`, а не
`assert!` внутри `reg`. Так устроены `unwrap`, `expect` и индексация в
стандартной библиотеке: сообщение указывает на ваш код, а не на
`option.rs`.

<div class="box hood">

**Под капотом.** Цена `#[track_caller]` — скрытый аргумент. Функция
из `code/ch07/src/abi.rs`:

```rust
{{#include ../../code/ch07/src/abi.rs:track_caller}}
```

```text
x86_64:                                    thumbv7m:
ch07_reg:                                  ch07_reg:
	cmp rdi, 16                            	cmp r0, #16
	jae .LBB44_2                           	it lo
	mov rax, rdi                           	bxlo lr
	ret                                    	push {r7, lr}
.LBB44_2:                                  	mov r7, sp
	push rax                               	movw r0, :lower16:.Lanon…
	mov rdx, rsi                           	mov r2, r1
	lea rdi, [rip + .Lanon…]               	movt r0, :upper16:.Lanon…
	mov esi, 61                            	movs r1, #61
	call qword ptr [rip + core::panicking::panic_fmt@GOTPCREL]
	                                       	bl core::panicking::panic_fmt
```

У функции один параметр `n`, но использует она два регистра: во
втором (`rsi`, `r1`) приходит указатель на статическую структуру
`Location` с файлом, строкой и столбцом вызова, и она уходит в
`panic_fmt` третьим аргументом (`rdx`, `r2`). Вызывающий кладёт этот
адрес перед каждым вызовом. Если функция встроена или вызывается из
одного места, оптимизатор подставляет константу, и цена исчезает.

</div>

## panic = "abort"

```toml
[profile.release]
panic = "abort"
```

С этой настройкой паника после хука сразу вызывает `abort`. Раскрутки
нет, деструкторы не выполняются, `catch_unwind` ничего не ловит, поток
не может упасть отдельно от процесса. Зато компилятору не нужны
посадочные площадки (раздел [7.6](06-unwind.md)), и код получается
меньше. Для целей Cortex-M так всегда: в описании цели
`thumbv7m-none-eabi` стоит `"panic-strategy": "abort"`, а раскрутки
в `core` для них нет вовсе (раздел [7.8](08-nostd.md)).

<div class="box c">

**Как в C.** Ближайший аналог паники — `assert` из `<assert.h>`: печатает
выражение, файл и строку и вызывает `abort`. Отличий два. `assert`
исчезает при `-DNDEBUG`, а проверки границ и `unwrap` в Rust остаются в
release-сборке. И `abort` в C не выполняет никакой очистки, как
`panic = "abort"`, а раскрутка Rust вызывает деструкторы, как
исключения C++.

</div>
