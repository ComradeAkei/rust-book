# 7.10. Сквозной проект: ошибки протокола

В разделе [6.11](../ch06/11-project.md) у формата кадра появился тип
`FrameError` — перечисление с данными, которое можно сравнить и
напечатать через `Debug`, и только. Шаг главы 7 делает из него
полноценную ошибку для обеих сторон канала: хост пишет в журнал
понятное сообщение, прошивка решает, что делать с потоком байт дальше,
и ни одной из сторон для этого не нужен аллокатор.

## Что уже есть

```rust
{{#include ../../project/telemetry-frame/src/lib.rs:error}}
```

`decode` из главы 6 уже пользуется `ok_or` и `?`. Теперь видно, что
это такое: `ok_or` превращает `Option` в `Result` (раздел
[7.1](01-result.md)), а `?` после `Kind::try_from(kind)` проходит через
тождественную реализацию `From<FrameError> for FrameError`, которую
стандартная библиотека даёт любому типу (раздел [7.2](02-convert.md)).

## Решения, которые следуют из главы

**Сообщение — в `Display`, по одному на вариант.** Как в разделе
[7.3](03-error-trait.md): с маленькой буквы, без точки в конце и без
причины. Числа, которые будут сравнивать с дампом канала, печатаются
в шестнадцатеричном виде: `{b:#04x}` даёт `0x5a` (ширина 4 включает
префикс `0x`), `{stored:#06x}` — `0x73e5`.

```rust
{{#include ../../project/telemetry-frame/src/lib.rs:display}}
```

**`core::error::Error`, а не `std::error::Error`.** Крейт собирается в
`no_std`, а трейт с Rust 1.81 живёт в `core` (раздел
[7.2](02-convert.md)); `std::error::Error` — тот же трейт под другим
путём, так что на хосте `?` упакует `FrameError` в `Box<dyn Error>`
без всяких переходников. Реализация пустая: у ошибки разбора нет
причины, она — последнее звено любой цепочки.

**Реакция — метод, а не разбор строки.** Приёмнику нужно решить, что
делать с потоком, и решать это сравнением текста сообщения нельзя
(раздел [7.4](04-design.md)). Метод `recovery` раскладывает варианты
по четырём реакциям:

```rust
{{#include ../../project/telemetry-frame/src/lib.rs:recovery}}
```

| Ошибка | Реакция | Почему |
|---|---|---|
| `Short` | `NeedMore(need − have)` | кадр ещё идёт по проводу |
| `BadMagic`, `BadVersion`, `BadKind`, `TooLong` | `Resync` | это не начало кадра или заголовок испорчен |
| `BadCrc` | `Resync` | повреждение могло задеть поле длины, пропускать кадр по ней нельзя |
| `BadPayload` | `Drop` | CRC сошлась, длине можно верить; не подходит только содержимое |
| `BufferTooSmall` | `Reject` | возникает только в `encode`, на приёме не бывает |

`match` в `recovery` перечисляет все варианты без ветки `_`, и
`FrameError` намеренно не помечен `#[non_exhaustive]`: новая ошибка
протокола требует своей реакции, и пусть компилятор не даст забыть о
ней ни в этом методе, ни в приёмниках, которые разбирают ошибки сами
(раздел [7.4](04-design.md)). `const fn` позволяет вычислять реакцию и
в константах. [`saturating_sub`][g-saturating] вместо
вычитания защищает от `Short`, собранной вручную с `need < have`:
`decode` такой не создаёт, но с обычным вычитанием `recovery`
запаниковала бы в отладочной сборке, а в release вернула бы почти
`usize::MAX` байт ожидания.

**Контекст — отдельный тип без аллокации.** Ошибка одного кадра не
знает, где этот кадр лежал в потоке, а приёмнику и журналу это нужно.
Контекст добавляет обёртка, как `Context` в разделе
[7.3](03-error-trait.md), только вместо `String` в ней число, и вся
ошибка остаётся `Copy`:

```rust
{{#include ../../project/telemetry-frame/src/lib.rs:rx_error}}
```

`Display` у `RxError` говорит только о своём уровне, причину отдаёт
`source`. Смещение за концом потока не паникует, а даёт «кадр не
полон»: байт там действительно ещё нет.

**Ошибки маленькие.** Размеры, снятые rustc 1.97.0:

| Тип | x86_64 | thumbv7m |
|---|---|---|
| `FrameError` | 24 | 12 |
| `RxError` | 32 | 16 |
| `Frame<'_>` | 24 | 12 |
| `Result<Frame<'_>, RxError>` | 32 | 16 |

`Result` не больше самой ошибки: признак `Ok` поместился в нишу
[дискриминанта][g-discriminant] `FrameError`, у которого из 256 значений байта заняты
восемь (раздел [6.4](../ch06/04-niches.md)). До порога
`clippy::result_large_err` в 128 байт далеко. В регистрах такой
`Result` уже не помещается: это не пара скаляров, и по правилу из
раздела [7.1](01-result.md) он возвращается через память — `decode_at`
на thumbv7m получает адрес результата в `r0`, а поток и смещение в
`r1`–`r3`. Для функции, которая вызывается раз на кадр, это несколько
лишних записей в стек, не больше. Тест `p7_errors_are_small` следит
только за верхней границей: точный размер `repr(Rust)` не обещан, и тест
проходит под `-Zrandomize-layout`.

## На Cortex-M: сколько стоят сообщения

Прошивка `firmware/ch07-frame` подключает тот же крейт и разбирает поток
из двух подтверждений, у второго из которых испорчена CRC:

```rust
{{#include ../../firmware/ch07-frame/src/lib.rs:stream}}
```

Три варианта `main` отличаются только тем, что печатают об ошибке.
`quiet` — ничего, кроме строкового литерала:

```rust
{{#include ../../firmware/ch07-frame/src/bin/quiet.rs:quiet}}
```

`direct` печатает обёртку и причину, обращаясь к полю `e.error`
напрямую:

```rust
{{#include ../../firmware/ch07-frame/src/bin/direct.rs:direct}}
```

`verbose` проходит по цепочке `source`, как `report` из раздела
[7.3](03-error-trait.md), и годится для ошибки любой глубины:

```rust
{{#include ../../firmware/ch07-frame/src/bin/verbose.rs:verbose}}
```

```console
$ cd firmware
$ cargo run --release -q -p ch07-frame --bin verbose
искать маркер со следующего байта
ошибка: кадр со смещения 8 отвергнут
  причина: CRC не совпадает: в кадре 0x5555, посчитано 0x9db4
$ cargo run --release -q -p ch07-frame --bin quiet
искать маркер со следующего байта
кадр отвергнут
```

`direct` печатает то же, что `verbose`. А размеры кода (столбец `text` у
`llvm-size`, как в разделе [7.8](08-nostd.md), release, rustc 1.97.0)
на Cortex-M3 различаются почти вчетверо:

| Прошивка | Cortex-M3, `text` | Cortex-M0, `text` | Cortex-M4F, `text` |
|---|---|---|---|
| `quiet` | 2536 | 1656 | 2568 |
| `direct` | 5792 | 5340 | 5904 |
| `verbose` | 9556 | 8928 | 9704 |

Реализация `Display` в крейте прошивке ничего не стоит, пока её не
вызывают: в `quiet` нет ни одного символа `core::fmt`, компоновщик
выбросил его целиком. `direct` платит за `core::fmt` около трёх
килобайт, как `report` в разделе [7.8](08-nostd.md).

Ещё почти четыре килобайта `verbose` отдаёт за `dyn Error`. Метод
`source` возвращает `&dyn Error`, а [таблица виртуальных функций][g-vtable]
`FrameError` для трейта `Error` обязана быть полной: в ней
`description`, `cause`, `provide`, `type_id` и методы [супертрейтов][g-supertrait]
`Display` и `Debug`. Программа ни разу не печатает `{:?}`, но `llvm-nm`
находит в образе выведенный `<FrameError as Debug>::fmt` (996 байт), а с
ним `DebugStruct::field`, `PadAdapter` и `Debug` для `u8`, `u16` и
`usize`. На функцию, адрес которой лежит в таблице, есть ссылка, и
компоновщик её не выбросит.

<div class="box trap">

**Ловушка.** Обход цепочки `source` в прошивке тянет в образ `Debug`
каждого типа ошибки, до которого дотягивается `dyn Error`, даже если
отладочный вывод нигде не нужен. Где каждый килобайт на счету,
печатайте известные типы напрямую, как `direct`, или передавайте на хост
номер варианта, а текст сообщения делайте уже там. Так работает и
`defmt` (глава 27): строки форматов остаются в ELF-файле на хосте, по
проводу идут их номера и сырые аргументы. Проверки в
`firmware/run-demos.sh` следят, что `quiet` и `direct` не содержат
этих символов, а `verbose` содержит.

</div>

## Задача П7

Реализуйте шаг главы 7 в заготовке `exercises/project-frame`, где уже
решён шаг главы 6. Типы `Recovery` и `RxError` и сигнатуры там есть,
тела — `todo!()`. Сообщения `Display` должны совпадать с таблицей
буква в букву:

| Ошибка | Сообщение |
|---|---|
| `Short { need: 18, have: 5 }` | `кадр не полон: нужно 18 байт, есть 5` |
| `BufferTooSmall { need: 18, have: 12 }` | `буфер мал: нужно 18 байт, есть 12` |
| `BadMagic(0x5a)` | `неверный маркер 0x5a` |
| `BadVersion(2)` | `версия 2 не поддерживается` |
| `BadKind(9)` | `неизвестный тип кадра 9` |
| `TooLong(241)` | `нагрузка 241 байт длиннее 240` |
| `BadCrc { stored: 0x73e5, computed: 0x0a1b }` | `CRC не совпадает: в кадре 0x73e5, посчитано 0x0a1b` |
| `BadPayload` | `нагрузка не соответствует типу кадра` |
| `RxError { offset: 26, .. }` | `кадр со смещения 26 отвергнут` |

```console
$ cargo test -p project-frame p7
```

Тесты `p7_` из `tests-shared/frame.rs` проверяют:

- сообщения всех вариантов и отсутствие причины у `FrameError`;
- реакции по таблице выше, включая несогласованную `Short`, на которой
  `recovery` не должна паниковать;
- разбор потока по смещениям: `RxError` хранит смещение, `source`
  отдаёт ту же `FrameError`, и до неё можно добраться через
  `downcast_ref`;
- порчу поля длины и смещение за концом потока;
- что ошибки не больше 24 и 32 байт на x86_64.

Тесты главы 6 должны по-прежнему проходить: `cargo test -p
project-frame` без фильтра.

Когда тесты пройдут, ответьте письменно:

1. Почему при `BadCrc` нельзя пропустить кадр по его длине? Постройте
   поток из трёх кадров, в котором такой пропуск теряет целый кадр
   после испорченного, и проверьте его тестом.
2. Тест `p7_context_in_stream` портит один бит поля длины, и ошибка
   превращается в `Short` с реакцией `NeedMore(58)`: заголовок выглядит
   правильным, а CRC нельзя проверить, пока не пришла нагрузка. Сколько
   в худшем случае прождёт приёмник на 115200 бод (8N1)? Что он должен
   сделать по тайм-ауту и почему `Recovery` этого не выражает?
3. Как изменить формат кадра, чтобы порча длины обнаруживалась сразу,
   до прихода нагрузки? Чего это стоит в байтах на кадр?
4. Добейтесь, чтобы `verbose` печатал ту же цепочку через `dyn Error`,
   но выведенного `Debug` в образе не было. Проверьте результат
   `llvm-nm` и `llvm-size`. Что при этом потеряют тесты на хосте?

В главах 12–13 эти реакции соберёт парсер потока байт: он сам ищет
маркер после сбоя, ждёт продолжения кадра и сдаётся по тайм-ауту.
