# 21. Атомики и модель памяти

**Перед чтением.** Сначала нужны [потоки и общее состояние](../ch20/03-shared.md)
и различие между [Send и Sync](../ch20/02-marker.md).
Здесь мы заменяем защиту мьютексом более мелкими операциями. Проверять
придётся отдельно две вещи: неделимость изменения одной ячейки и порядок,
в котором другие потоки получают право читать связанные с ней данные.

## Мотивирующая проблема

Поток ждёт, пока другой подготовит данные, и смотрит на флаг:

```c
/* C: так писали годами — и так неправильно */
volatile int ready = 0;
int data = 0;

void producer(void) { data = 42; ready = 1; }        /* поток 1 */
void consumer(void) { while (!ready) {} use(data); }  /* поток 2 */
```

`volatile` в C и C++ не даёт ни атомарности, ни порядка: компилятор не
соврёт про сам `ready`, но вправе переставить `data = 42` и `ready = 1`
местами, а процессор — выполнить записи в своём порядке. Потребитель увидит
`ready == 1` и прочитает `data == 0`. Баг не ловится ни компилятором, ни
обычным прогоном: он выстреливает раз в миллион итераций на другом ядре.
Правильный инструмент — атомарные операции с явным *порядком памяти*
(`stdatomic.h` в C11), а не `volatile`.

Rust наследует ту же модель памяти, что C++20 и C11, но делает порядок
обязательной частью каждой операции: у атомарного типа нет «просто load» —
есть `load(Ordering)`, и выбрать порядок придётся явно. Однако компилятор
не доказывает, что выбран правильный [барьер][g-memory-barrier]: поставить
`Relaxed` там, где нужен `Acquire`, по-прежнему можно. Он проверяет
допустимость операции, а правильность передачи данных нужно обосновать
отдельно. Как это сделать, показывает [21.2](02-ordering.md).

## Что делает Rust

Глава — про то, как [без единого замка][g-lock-free] безопасно делить данные между потоками
(а на Cortex-M — между основным кодом и прерыванием,
[27.6](../ch27/06-interrupts.md)):
на атомарных операциях и явной модели памяти.

- Атомарные типы ([21.1](01-atomics.md)) — `AtomicUsize`, `AtomicBool`,
  `AtomicPtr`; `load`, `store`, `fetch_add`, `compare_exchange` и его
  `_weak`-версия — основа lock-free.
- [happens-before][g-happens-before] ([21.2](02-ordering.md)) — пара Release/Acquire как способ
  передать через одну атомарную переменную *другие* данные.
- Заборы и SeqCst ([21.3](03-fences.md)) — единый глобальный порядок, проба
  на [буфер записи][g-store-buffer], `fence` отдельно от переменной.
- Во что это компилируется ([21.4](04-hardware.md)) — [x86-TSO][g-tso] против слабой
  модели ARM, `xchg` и префикс `lock`, [кэш-когерентность][g-cache-coherence].
- Lock-free [SPSC][g-spsc] ([21.5](05-spsc.md)) — кольцевая очередь на атомарных
  индексах без [RMW][g-rmw], работает даже на Cortex-M0.
- Замки и [ABA][g-aba] ([21.6](06-locks.md)) — спинлок и [ticket lock][g-ticket-lock] из [атомиков][g-atomic],
  проблема ABA в lock-free стеке и [тегированный указатель][g-tagged-pointer] против неё.

Принцип тот же, что в [главе 20](../ch20/index.md): опасное (ручной `unsafe
impl Sync`, сырые ячейки) заперто за инвариантом с `// SAFETY`, а на
поверхности — безопасный API, где неверный порядок невозможно «забыть».

Примеры разделов 21.1–21.3 [хостовые][g-host] (потоки ОС для демонстрации гонок);
кольцевой буфер 21.5 собирается и без std — на три [цели][g-target] Cortex-M.

```console
$ cargo test -p ch21                 # атомики, порядки, заборы, SPSC, asm
$ cargo test -p ch21-solutions       # задачи A–D
```

Кодогенерацию раздела 21.4 (`xchg`, `lock`) проверяет `tests/asm.rs`;
корректность SPSC с `UnsafeCell<MaybeUninit>` — Miri на однопоточном и
малом двухпоточном тестах. Порядки памяти Miri тоже проверяет: он
исполняет программу по модели слабой памяти и ловит гонки данных — но лишь
на тех чередованиях, что выпали при данном зерне планировщика.
