# 21. Атомики и модель памяти

## Мотивирующая проблема

Поток ждёт, пока другой подготовит данные, и смотрит на флаг:

```c
/* C: так писали годами — и так неправильно */
volatile int ready = 0;
int data = 0;

void producer(void) { data = 42; ready = 1; }        /* поток 1 */
void consumer(void) { while (!ready) {} use(data); }  /* поток 2 */
```

`volatile` в C и C++ не даёт ни атомарности, ни порядка: компилятор не
соврёт про сам `ready`, но вправе переставить `data = 42` и `ready = 1`
местами, а процессор — выполнить записи в своём порядке. Потребитель увидит
`ready == 1` и прочитает `data == 0`. Баг не ловится ни компилятором, ни
обычным прогоном: он выстреливает раз в миллион итераций на другом ядре.
Правильный инструмент — атомарные операции с явным *порядком памяти*
(`stdatomic.h` в C11), а не `volatile`.

Rust наследует ту же модель памяти, что C++20 и C11, но делает порядок
обязательной частью каждой операции: у атомарного типа нет «просто load» —
есть `load(Ordering)`, и выбрать порядок придётся осознанно. Забыть барьер,
как в коде выше, здесь нельзя: `data` пришлось бы сделать атомарной, а у её
операций всегда есть `Ordering`.

## Что делает Rust

Глава — про то, как без единого замка безопасно делить данные между потоками
(а на Cortex-M — между основным кодом и прерыванием, [20](../ch20/index.md)):
на атомарных операциях и явной модели памяти.

- Атомарные типы ([21.1](01-atomics.md)) — `AtomicUsize`, `AtomicBool`,
  `AtomicPtr`; `load`, `store`, `fetch_add`, `compare_exchange` и его
  `_weak`-версия — основа lock-free.
- happens-before ([21.2](02-ordering.md)) — пара Release/Acquire как способ
  передать через одну атомарную переменную *другие* данные.
- Заборы и SeqCst ([21.3](03-fences.md)) — единый глобальный порядок, проба
  на буфер записи, `fence` отдельно от переменной.
- Во что это компилируется ([21.4](04-hardware.md)) — x86-TSO против слабой
  модели ARM, `xchg` и префикс `lock`, кэш-когерентность.
- Lock-free SPSC ([21.5](05-spsc.md)) — кольцевая очередь на атомарных
  индексах без RMW, работает даже на Cortex-M0.
- Замки и ABA ([21.6](06-locks.md)) — спинлок и ticket lock из атомиков,
  проблема ABA в lock-free стеке и тегированный указатель против неё.

Принцип тот же, что в [главе 20](../ch20/index.md): опасное (ручной `unsafe
impl Sync`, сырые ячейки) заперто за инвариантом с `// SAFETY`, а на
поверхности — безопасный API, где неверный порядок невозможно «забыть».
