# 10. Обобщения и мономорфизация

## Мотивирующая проблема

Обобщённый код на C пишут двумя способами, и оба видны в одной
программе. Первый — `qsort` из стандартной библиотеки: данные передаются
через `void *` вместе с размером элемента, а сравнение — указателем на
функцию. Второй — макрос, который подставляет тип в текст функции и
порождает отдельную копию для каждого типа. Программа `code/ch10/c/sort.c`
сортирует миллион чисел обоими способами:

```c
{{#include ../../code/ch10/c/sort.c}}
```

```console
$ gcc -O2 -Wall -Wextra -o sort sort.c
$ ./sort
qsort:          147.8 мс, упорядочен: 1
sort_uint32_t:  115.3 мс, упорядочен: 1
qsort с cmp_u16: упорядочен: 0
$ gcc -O2 -DCOUNT -o count sort.c && ./count | grep вызовов
вызовов cmp_u32: 18674574
```

Ни GCC, ни clang с `-Wall -Wextra` не предупреждают ни о чём, а
недостатков у каждого способа по нескольку.

**Сравнение через указатель не встраивается.** `qsort` собрана заранее и
лежит в libc. Что ей передадут вместо `cmp_u32`, она не знает и вызывает
компаратор по адресу на каждое сравнение: на миллионе чисел — 18,7
миллиона косвенных вызовов, чуть меньше `n · log₂ n` ≈ 19,9 миллиона.
Каждый вызов ради нескольких инструкций сравнения. Фрагмент `objdump -d
-M intel sort`:

```text
00000000000014f0 <cmp_u32>:
    14f4:	mov    ecx,DWORD PTR [rdi]          ; x = *a
    14f6:	mov    edx,DWORD PTR [rsi]          ; y = *b
    14f8:	xor    eax,eax
    14fa:	cmp    edx,ecx
    14fc:	setb   al                           ; eax = y < x
    14ff:	cmp    ecx,edx
    1501:	sbb    eax,0x0                      ; eax -= x < y
    1504:	ret
…
    11bf:	lea    rcx,[rip+0x32a]        # 14f0 <cmp_u32>
    11cc:	call   10c0 <qsort@plt>
```

В `main` адрес `cmp_u32` кладётся в `rcx`, четвёртый аргумент, и
уходит в `qsort` через таблицу PLT. Сама `qsort` из glibc 2.39
сортирует слиянием, а размер элемента узнаёт только во время работы и по
нему выбирает, как копировать элементы.

**`void *` принимает любой компаратор.** Третья сортировка передаёт
`cmp_u16` для массива `uint32_t`. Сигнатура та же, `int (*)(const void *,
const void *)`, и компилятор согласен. Компаратор читает младшие два
байта каждого числа, и массив «сортируется» по ним: результат не
упорядочен, и узнать об этом можно только проверкой.

**Макрос быстрее, но проверяется после подстановки.** `DEFINE_SORT`
порождает `sort_uint32_t`, где сравнение `LESS_NUM` встроено:

```text
0000000000001530 <sort_uint32_t>:
…
    1570:	mov    r9d,DWORD PTR [rbp+r8*4-0x4]
…
    157c:	cmp    r9d,edi              ; LESS(v[i], p) — одна инструкция
    157f:	jb     15c1 <sort_uint32_t+0x91>
…
    15df:	call   1530 <sort_uint32_t> ; единственный вызов — рекурсия
```

Но макрос — подстановка текста. Что `T` можно сравнивать через `<`,
никто не проверяет, пока макрос не развернут. Для структуры `point`
ошибка приходит изнутри тела, трижды, по разу на каждое `LESS` в нём:

```console
$ gcc -O2 -DBAD_POINT -c sort.c
sort.c: In function 'sort_point':
sort.c:64:29: error: invalid operands to binary < (have 'point' and 'point')
   64 | #define LESS_NUM(a, b) ((a) < (b))
      |                         ~~~ ^
sort.c:40:24: note: in expansion of macro 'LESS_NUM'
   40 |                 while (LESS(v[i], p))                                \
      |                        ^~~~
sort.c:73:1: note: in expansion of macro 'DEFINE_SORT'
   73 | DEFINE_SORT(point, LESS_NUM)
      | ^~~~~~~~~~~
…
```

У макроса и другие ограничения: имя функции склеивается через `##`,
поэтому `DEFINE_SORT(unsigned int, …)` не соберётся без `typedef`, а
отлаживать тело, записанное в одну логическую строку, неудобно. Скрипт
`code/ch10/c/run.sh` проверяет все эти выводы.

На микроконтроллере выбор между способами ещё жёстче. Косвенный вызов на
Cortex-M — загрузка адреса и `blx` по регистру. Предсказателя переходов
у M0, M3 и M4 нет, каждый такой переход сбрасывает конвейер, и встроить
через него ничего нельзя. Копия на каждый тип занимает flash, и
её размер приходится считать.

## Что делает Rust

Обобщения Rust устроены как макрос по скорости и как функция по
проверкам. Тело обобщённой функции проверяется один раз, по её
*ограничениям* (trait bounds), а машинный код создаётся отдельно для
каждого набора типов — это *мономорфизация*.

- Обобщённые функции и типы, методы для отдельных типов-аргументов,
  turbofish `::<>` (раздел [10.1](01-generics.md)).
- Ограничения и `where`, условные реализации, `T: 'static` (раздел
  [10.2](02-bounds.md)).
- `impl Trait` в аргументе и в результате: безымянный параметр и скрытый
  тип, в том числе в методах трейтов (раздел [10.3](03-impl-trait.md)).
- Параметры-константы: размер массива, ёмкость буфера, делитель — часть
  типа, известная при компиляции (раздел [10.4](04-const-generics.md)).
- Во что обходится мономорфизация: сколько копий в бинарнике, как их
  посчитать и как сократить внутренней необобщённой функцией (раздел
  [10.5](05-mono.md)).
- Встраивание через границу обобщения: почему замыкание встраивается, а
  указатель на функцию нет (раздел [10.6](06-inlining.md)).
- Типы-маркеры и typestate: состояние протокола или периферии в типе,
  недопустимые переходы не компилируются, а проверка ничего не стоит
  (раздел [10.7](07-typestate.md)).

Когда копий слишком много или тип известен только во время работы,
нужна таблица методов: объекты `dyn Trait` разбирает глава 11.

## Код главы

```console
$ cargo test -p ch10 -p ch10-solutions            # примеры и решения
$ cargo +nightly test --doc -p ch10               # коды ошибок в doc-тестах
$ bash code/ch10/c/run.sh                         # sort.c: qsort против макроса
$ cargo asm -p ch10 --lib --simplify ch10_cal_generic
$ cd firmware && cargo run --release -p ch10-typestate   # UART с состоянием в типе
```

Числа в тексте получены на rustc 1.97.0 (LLVM 22.1.6) и nightly 1.101.0
(2026-10-21) для `x86_64-unknown-linux-gnu` и трёх целей Cortex-M, GCC
13.3, clang 18.1 и glibc 2.39, прошивки — в QEMU 8.2.2. Ассемблер снят
командой `cargo asm --simplify` из release-сборки; для Cortex-M к ней
добавлены `--no-default-features --target <цель>`. Время сортировки от
запуска к запуску меняется на 10–20 %.
