# 10.6. Встраивание через границу обобщения

## Тип функции

Калибровка отсчётов: умножить на усиление, прибавить смещение. Функцию
калибровки можно передать двумя способами — как параметр типа и как
указатель на функцию, по образцу компаратора `qsort`:

```rust
{{#include ../../code/ch10/src/inline.rs:apply}}
```

Разница в типе `f`. У каждой функции и каждого замыкания в Rust свой
тип, и у этого типа нет значений, кроме одного: самой функции. Тип
функции `calibrate` — [тип нулевого размера][g-zst], и указателем он становится,
только если его привести к `fn(u32) -> u32`:

```rust
{{#include ../../code/ch10/src/inline.rs:closure-types}}
```

`sizes()` возвращает `[0, 8, 4]` на x86-64 и `[0, 4, 4]` на Cortex-M:
имя функции ничего не занимает, указатель занимает слово, замыкание —
столько, сколько захватило (один `u32`). `rustc` печатает тип функции
как `fn(u32) -> u32 {calibrate}`: в фигурных скобках — какая именно
функция, и она часть типа.

Поэтому `apply(v, calibrate)` мономорфизуется не «для функции из `u32` в
`u32`», а для одной `calibrate`. В копии `apply` вызов `f(*x)` — прямой
вызов известной функции, и LLVM встраивает его. Дальше обычная
оптимизация цикла, у которого видно тело:

```console
$ cargo asm -p ch10 --lib --simplify ch10_cal_generic
ch10_cal_generic:
…
.LBB13_3:
	movdqu xmm1, xmmword ptr [rdi + 4*r8]
	movdqu xmm2, xmmword ptr [rdi + 4*r8 + 16]
	movdqa xmm3, xmm1
	paddd xmm3, xmm3
	paddd xmm3, xmm1
	movdqa xmm1, xmm2
	paddd xmm1, xmm1
	paddd xmm1, xmm2
	psubd xmm3, xmm0
	psubd xmm1, xmm0
	movdqu xmmword ptr [rdi + 4*r8], xmm3
	movdqu xmmword ptr [rdi + 4*r8 + 16], xmm1
	add r8, 8
	cmp rdx, r8
	jne .LBB13_3
…
```

Восемь отсчётов за итерацию в двух регистрах [SSE2][g-sse-avx]: `x · 3` — это `x + x
+ x` (`paddd` дважды), а `+ 1` — вычитание вектора из единиц во всех
битах, то есть −1 (`pcmpeqd xmm0, xmm0` перед циклом). Вызова
`calibrate` нет. Через указатель то же самое выглядит так:

```console
$ cargo asm -p ch10 --lib --simplify ch10_cal_ptr
ch10_cal_ptr:
	lea rdx, [rip + ch10::inline::calibrate]
	jmp qword ptr [rip + ch10::inline::apply_ptr@GOTPCREL]
$ cargo asm -p ch10 --lib --simplify ch10::inline::apply_ptr
ch10::inline::apply_ptr:
…
.LBB9_2:
	mov edi, dword ptr [r15 + r12]
	call rbx
	mov dword ptr [r15 + r12], eax
	add r12, 4
	cmp r14, r12
	jne .LBB9_2
…
```

`ch10_cal_ptr` кладёт адрес `calibrate` в третий аргумент и передаёт
управление `apply_ptr`. Та зовёт функцию по адресу из `rbx` на каждый
отсчёт: ни [векторизации][g-vectorization], ни встраивания, `apply_ptr` не знает, что ей
передали. Ровно так `qsort` вызывает `cmp_u32`.

## На Cortex-M3

```console
$ cargo asm -p ch10 --lib --simplify --no-default-features --target thumbv7m-none-eabi ch10_cal_generic
ch10_cal_generic:
…
.LBB12_8:
	ldr r2, [r1, #16]!
	ldr r0, [r1, #12]
	add.w r2, r2, r2, lsl #1
	adds r2, #1
	str r2, [r1]
	ldrd r2, r3, [r1, #4]
	add.w r0, r0, r0, lsl #1
	adds r0, #1
	str r0, [r1, #12]
	add.w r0, r1, #16
	add.w r2, r2, r2, lsl #1
	cmp r0, r12
	add.w r2, r2, #1
	str r2, [r1, #4]
	add.w r2, r3, r3, lsl #1
	add.w r2, r2, #1
	str r2, [r1, #8]
	bne .LBB12_8
…
$ cargo asm -p ch10 --lib --simplify --no-default-features --target thumbv7m-none-eabi ch10::inline::apply_ptr
ch10::inline::apply_ptr:
…
.LBB8_2:
	ldr r0, [r6, #4]!
	blx r4
	subs r5, #4
	str r0, [r6]
	bne .LBB8_2
…
```

Векторных регистров у M3 нет, и LLVM разворачивает цикл вчетверо:
`add.w r2, r2, r2, lsl #1` — это `r2 + 2·r2`, умножение на три одной
инструкцией со сдвигом операнда, `adds #1` — смещение. Четыре отсчёта на
18 инструкций без единого перехода, кроме замыкающего `bne`. Вариант с
указателем — `blx r4` на каждый отсчёт, а внутри `calibrate` ещё
`push`/`pop` и возврат. Для ядра без предсказателя переходов каждый
`blx` по регистру и каждый возврат — сброс трёхступенчатого конвейера.

<div class="box c">

**Как в C.** Компилятор C тоже встраивает вызов по указателю, если видит
и функцию, которая вызывает, и сам указатель как константу: со
`static`-функцией сортировки в том же файле GCC и clang с `-O2`
справятся. `qsort` из libc собрана отдельно и лежит в разделяемой
библиотеке, и этого не произойдёт никогда, даже с `-flto`. Обобщённая
функция Rust в этом смысле всегда «в том же файле»: её MIR едет в
[метаданных крейта][g-crate-metadata], и вызывающий крейт компилирует свою копию со своим
`F`.

</div>

## `#[inline]`

Сказанное верно для обобщённых функций. Обычная функция из другого
крейта встраивается, только если её MIR попал в метаданные, а не только
машинный код. С Rust 1.75 rustc делает это сам для совсем маленьких
функций, которые ничего не вызывают. Для остальных этим управляют
атрибуты:

| Атрибут | Что делает |
|---|---|
| нет | обобщённые встраиваются через границу крейта, необобщённые — только самые маленькие листовые или при [LTO][g-lto] |
| `#[inline]` | MIR кладётся в метаданные, каждый крейт-пользователь может встроить |
| `#[inline(always)]` | просьба встраивать всегда, даже при `opt-level = 0`; LLVM может не послушаться |
| `#[inline(never)]` | не встраивать никогда; так в этой главе сохранены отдельные функции для `nm` |
| `#[cold]` | функция вызывается редко: её не встраивают, а ветки к ней LLVM уводит с горячего пути |

Небольшие необобщённые функции публичного API, которые сами что-то
вызывают, — обёртки над регистрами через `read_volatile`, `from`/`into`
с проверками — помечают `#[inline]`: автоматическое правило их не
берёт, и каждый вызов из другого крейта останется вызовом. Внутри одного крейта атрибут почти не
нужен: LLVM видит всё и решает сам. LTO (`lto = true` в [профиле][g-profile] release
прошивок этой книги) снимает границу крейтов целиком, но ценой времени
сборки.

<div class="box trap">

**Ловушка.** Встраивание — не бесплатная оптимизация. Каждое
встраивание — копия тела в месте вызова, и для большой функции с
несколькими вызывающими это рост кода, как у мономорфизации. На
микроконтроллере с 64 КиБ flash `#[inline(always)]` на функции в сотню
инструкций, вызванной из двадцати мест, дорого обходится. Атрибут нужен
там, где замер показал выигрыш, а не «на всякий случай».

</div>
