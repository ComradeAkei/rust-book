## A. Какие функции доживут до release

```rust
{{#include ../../solutions/ch00/src/a_vanish.rs:answers}}
```

| № | Функция | `cargo asm` (объектный файл) | `nm` (исполняемый файл) | Механизм |
|---|---|---|---|---|
| 1 | `crc_step` | есть | нет | Распространение констант при thin local [LTO][g-lto] |
| 2 | `checksum` | есть | есть | Данные спрятаны `black_box`, [встраивание][g-inlining] запрещено |
| 3 | `popcount` | нет | нет | Вызов без побочных эффектов, результат не нужен |
| 4 | `ch00a_exported` | есть | нет | Компоновщик выбросил неиспользуемую секцию |
| 5 | `triple` | есть | есть | Адрес функции ушёл в `black_box` |

Разберём механизмы по порядку.

**№2 и №5** — контрольные случаи. Аргумент `checksum` пропущен через
`black_box`, значит, его значение неизвестно, а встраивать тело запрещает
`#[inline(never)]`: вызов обязан остаться. У `triple` нет никаких
атрибутов, но её адрес передан в `black_box`, и `main` вызывает её через
указатель (`call rax`). Раз адрес наблюдаем снаружи, тело функции должно
существовать по этому адресу.

**№3.** `popcount(black_box(0xF0F0))`: `black_box` защищает аргумент, но
не вызов. Функция не пишет в память и всегда возвращает управление, а
результат отброшен, поэтому вызов удалён как мёртвый код, а с ним и сама
функция. Ответ на вопрос к отчёту: пропустить через `black_box`
результат, `black_box(popcount(black_box(0xF0F0)))`. `#[inline(never)]`
запрещает только встраивание, а не удаление.

**№4.** `#[unsafe(no_mangle)]` объявляет функцию видимой снаружи, и rustc
обязан сгенерировать её код: в `cargo asm` она есть. Но исполняемый файл
ничего не экспортирует, а rustc компонует его с `--gc-sections`, и
компоновщик выбрасывает секцию `.text.ch00a_exported`, на которую никто
не ссылается. Это видно напрямую:

```console
$ cargo rustc --release -p ch00 --example vanish -- -C link-arg=-Wl,--print-gc-sections 2>&1 | grep ch00a
removing unused section .../vanish-8d4056add7320c0a.vanish.d21f245c588ba667-cgu.0.rcgu.o:(.text.ch00a_exported)
$ cargo rustc --release -p ch00 --example vanish -- -C link-arg=-Wl,--no-gc-sections
$ nm -C target/release/examples/vanish | grep ch00a
0000000000042c00 T ch00a_exported
```

В разделяемой ([`cdylib`][g-crate-type]) или статической (`staticlib`) библиотеке функция
осталась бы: там экспорт — смысл существования файла.

**№1** — самый интересный случай. Аргумент `crc_step` известен, и тело
сворачивается в константу:

```text
$ cargo asm -p ch00 --example vanish vanish::crc_step
vanish::crc_step:
	mov eax, 1996959894
	ret
```

Это `0x7707_3096`, второй элемент таблицы CRC-32. Казалось бы, дальше
компилятор должен подставить константу в `main` и убрать вызов. В
обычной сборке так и происходит, а в сборке `cargo asm` вызов остаётся:

```text
$ cargo asm -p ch00 --example vanish vanish::main | grep call
	call vanish::crc_step
	call vanish::checksum
	call rax
	call qword ptr [rip + std::io::stdio::_print@GOTPCREL]
```

Причина — в ключах. `cargo asm -vv` показывает, что он собирает [крейт][g-crate] с
`-Ccodegen-units=1`. Одна [единица кодогенерации][g-codegen-unit] означает, что rustc не
запускает thin local LTO (раздел [0.2](../ch00/02-cargo.md)): объединять
нечего. Опыт с разными значениями `lto` поверх обычного [профиля][g-profile]
подтверждает связь:

| Настройка | `crc_step` в исполняемом файле |
|---|---|
| по умолчанию (16 единиц, thin local LTO) | нет |
| `lto = "off"` | есть |
| `lto = "thin"` | нет |
| `lto = true` | нет |
| `codegen-units = 1` | есть |

Механизм видно, если попросить LLVM печатать модуль после каждого
прохода межпроцедурного распространения констант (IPSCCP):

```console
$ cargo rustc --release -p ch00 --example vanish -- -Cllvm-args=-print-after=ipsccp 2> ipsccp.log
```

В обычной сборке IPSCCP выполняется дважды. В первый раз тело `crc_step`
ещё содержит цикл из восьми итераций, и проход не может знать, что
результат постоянен. Второй раз он выполняется на этапе LTO, когда тело
уже свёрнуто в `ret i32 1996959894`: проход подставляет константу в
`main`, вызов исчезает, а неиспользуемая функция удаляется. С
`-Ccodegen-units=1` второго прохода нет, и вызов остаётся. Вывод для
практики: если оптимизация зависит от того, в каком порядке LLVM
выполнит свои проходы, `cargo asm` и обычная сборка могут разойтись.
Сверяйте окончательный результат по исполняемому файлу.

| Шаг | В цепочке, байт | Отдельно, байт |
|---|---|---|
| профиль книги (`debug = true`) | 4 362 080 | |
| `debug = false` | 445 080 | 445 080 |
| `strip = true` | 342 536 | 342 536 |
| `opt-level = "z"` | 342 488 | 445 120 |
| `lto = true` | 290 208 | 376 248 |
| `codegen-units = 1` | 290 208 | 445 080 |
| `panic = "abort"` | 288 200 | 442 816 |

Что исчезает на каждом шаге:

- `debug = false` убирает 3,9 МБ отладочной информации. По `size -A`
  до этого шага в файле `.debug_str` занимала 1,89 МБ, `.debug_info` —
  1,08 МБ, `.debug_ranges` и `.debug_line` — ещё по 0,45 МБ. Почти вся она
  относится к `std`, а не к программе. Когда отладочная информация не
  нужна ни одному пакету, cargo по умолчанию ставит
  `strip = "debuginfo"`, и вырезается в том числе отладочная информация
  готовой `std`.
- `strip = true` убирает таблицу символов `.symtab` и строки `.strtab`:
  ещё 100 КБ. После этого `nm` и `cargo bloat` бесполезны.
- `opt-level = "z"` сам по себе не даёт ничего (+40 байт). Стандартная
  библиотека приходит уже скомпилированной с `opt-level = 3`, а
  собственного кода в hello world 18 байт. Ключ начинает работать
  только вместе с LTO, когда код `std` оптимизируется заново.
- `lto = true` оптимизирует программу вместе с `std` как одно целое и
  выбрасывает недостижимый код. Это главный шаг после отладочной
  информации: −52 КБ в цепочке, −69 КБ отдельно. В цепочке вклад меньше,
  потому что часть того, что убрал бы LTO, уже исчезла вместе с
  символами.
- `codegen-units = 1` ничего не меняет: с полным LTO вся программа и так
  становится одним модулем, а сам крейт крошечный.
- `panic = "abort"` экономит 2 КБ: таблицы [раскрутки][g-unwinding] и [посадочные
  площадки][g-landing-pad] (landing pads) пропадают только из кода, который
  компилируется в этой сборке. `std` по-прежнему собрана с раскруткой.

Что осталось в 288 КБ, показывает `cargo bloat` на той же сборке без
`strip`:

```console
$ cargo bloat --release -p ch00 --example hello --config nostrip.toml -n 5
```

Это разбор [DWARF][g-dwarf] (`gimli`, `addr2line`), распаковка сжатых отладочных
секций (`miniz_oxide`) и восстановление имён (`rustc_demangle`). Всё это
нужно, чтобы при [панике][g-panic] с `RUST_BACKTRACE=1` напечатать стек вызовов с
именами функций и строками. Код достижим из [обработчика паники][g-panic-handler], поэтому
LTO его не выбрасывает, а `panic = "abort"` не помогает: сообщение
печатается до вызова `abort`.

Исследовательская часть подтверждает это. Пересборка `std` с теми же
настройками (`-Zbuild-std=std,panic_abort`) даёт 253 136 байт: код `std`
впервые оптимизирован по размеру и без раскрутки. Стратегия
`immediate-abort` превращает любую панику в немедленное аварийное
завершение без сообщения, и весь код печати и символизации становится
недостижимым:

```console
$ RUSTFLAGS="-Zunstable-options -Cpanic=immediate-abort" cargo +nightly build --release \
>     -p ch00 --example hello --config solutions/ch00/tiny.toml \
>     -Zbuild-std=std,panic_abort --target x86_64-unknown-linux-gnu
$ ls -l target/x86_64-unknown-linux-gnu/release/examples/hello
-rwxr-xr-x 2 user user 15512 ... hello
```

15 512 байт, и `println!` по-прежнему работает: форматирование осталось,
пропала только печать паники.

Файл весит 4 776 байт, из них код — 266 байт в `.text`. Наша `main`
занимает 33 байта, `_start` из `crt1.o` — 38, остальное — служебные

другие). Обработчика паники в файле нет: паниковать нечему, и он
недостижим. Всё прочее — заголовки ELF и информация для динамического
компоновщика: `.dynamic`, `.dynsym`, `.rela.dyn`, `.got`, через которые
программа находит `write` и `abort` в `libc.so.6`. Ответ на вопрос к отчёту: до `main` выполняются
динамический компоновщик `ld-linux-x86-64.so.2`, который загружает libc и
заполняет таблицы, затем `_start`, который берёт `argc` и `argv` со стека
и вызывает `__libc_start_main`. Та инициализирует libc и вызывает
`main` по имени, как в любой программе на C, поэтому `main` объявлена с
`#[unsafe(no_mangle)]` и `extern "C"`. Без `std` в программе нет и
обычного для Rust `lang_start`. В программе со `std` он выполняется
между `main` из C и `main` из Rust: проверяет, что открыты дескрипторы
0–2, переводит SIGPIPE в режим «игнорировать» и ставит обработчик
переполнения стека.

## C. Сумма массива на двух архитектурах

```rust

```

```rust
{{#include ../../solutions/ch00/src/c_sum.rs:wide}}
```

Регистры. На x86_64 [срез][g-slice] приходит парой `rdi` (указатель) и `rsi`
(длина), результат `u32` возвращается в `eax`, `u64` — в `rax`. На
Cortex-M4F указатель в `r0`, длина в `r1`, `u32` возвращается в `r0`,
`u64` — в паре `r0:r1`. `Option<u32>` занимает два слова и
возвращается в двух регистрах: признак `Some` в `eax` или `r0`, значение
в `edx` или `r1`.

Основной цикл `ch00c_sum_wrapping` на x86_64:

```text
.LBB3_6:
	movdqu xmm2, xmmword ptr [rdi + rdx]
	paddd xmm1, xmm2
	movdqu xmm2, xmmword ptr [rdi + rdx + 16]
	paddd xmm0, xmm2
	add rdx, 32
	cmp rax, rdx
	jne .LBB3_6
```

`paddd` складывает четыре 32-битных числа за инструкцию, а два
независимых аккумулятора `xmm0` и `xmm1` позволяют процессору выполнять
сложения параллельно. За итерацию обрабатываются 8 элементов. После цикла
четыре дорожки сворачиваются (`pshufd`, `paddd`), а хвост меньше восьми
элементов досчитывается скалярным циклом `.LBB3_4`. [Векторизация][g-vectorization] законна,
потому что сложение по модулю 2³² ассоциативно и коммутативно:
переставлять слагаемые можно как угодно.

У `ch00c_sum_wide` в регистре `xmm` помещаются только две 64-битные
дорожки, и каждое `u32` сначала расширяется нулями (`punpckldq` с нулевым
регистром), поэтому за итерацию обрабатываются 4 элемента, вдвое меньше.

На Cortex-M4F векторизации нет ни у одной функции:

```text
.LBB3_4:
	ldr r4, [r2, #16]!
	adds r1, #4
	cmp r8, r1
	ldrd r5, r6, [r2, #4]
	add r0, r4
	ldr r3, [r2, #12]
	add r0, r5
	add r0, r6
	add r0, r3
	bne .LBB3_4
```

[SIMD][g-simd]-инструкции [ARMv7E-M][g-armv7m] (`UADD8`, `UADD16`, `SADD16` и другие) работают
с дорожками по 8 и 16 бит внутри одного 32-битного регистра. Дорожек по 32
бита у них нет, а векторного блока, как NEON у Cortex-A, у Cortex-M4F нет
совсем. Компилятор развернул цикл в четыре раза и читает пару слов одной
инструкцией `ldrd`, а хвост из 1–3 элементов обработан отдельной
цепочкой сравнений. В `ch00c_sum_wide` каждое сложение превращается в пару
`adds` и `adc`: 64-битная сумма собирается из двух 32-битных с переносом.

Вторая часть. Первая версия:

```rust
{{#include ../../solutions/ch00/src/c_sum.rs:checked_naive}}
```

```text
$ cargo asm -p ch00-solutions --lib ch00_solutions::c_sum::sum_checked_naive
ch00_solutions::c_sum::sum_checked_naive:
	shl rsi, 2
	xor eax, eax
	xor ecx, ecx
.LBB0_1:
	mov edx, ecx
	cmp rsi, rax
	je .LBB0_2
	mov ecx, dword ptr [rdi + rax]
	add rax, 4
	add ecx, edx
	jae .LBB0_1
	xor eax, eax
	ret
.LBB0_2:
	mov eax, 1
	ret
```

Компилятор сделал лучшее, что мог: проверка переполнения — это флаг
переноса после `add`, и `jae` продолжает цикл, пока переноса нет. Но
выход из цикла зависит от каждого элемента и от порядка сложений, а
векторный цикл складывает в другом порядке и узнаёт о переполнении
только в конце. Такое преобразование изменило бы результат на входах
вроде `[u32::MAX, 1, ...]`, поэтому оно запрещено.

Решение: считать точно в `u64` и проверять результат реже.

```rust
{{#include ../../solutions/ch00/src/c_sum.rs:checked}}
```

Доказательство отсутствия переполнения `u64`. Кусок содержит не больше
2³¹ элементов, каждый меньше 2³², значит, сумма куска меньше 2⁶³. Перед
прибавлением куска `total` не больше `u32::MAX` < 2³², иначе функция уже
вернула бы `None`. Итого `total` всегда меньше 2⁶³ + 2³² < 2⁶⁴. Без
кусков доказательство не прошло бы: срез из 2³³ элементов по `u32::MAX`
на 64-битной машине возможен, и его сумма больше 2⁶⁴.

Внутренний цикл на x86_64 теперь такой же, как у `ch00c_sum_wide`:

```text
.LBB1_6:
	movq xmm3, qword ptr [rdi + r10]
	movq xmm4, qword ptr [rdi + r10 + 8]
	punpckldq xmm3, xmm0
	paddq xmm2, xmm3
	punpckldq xmm4, xmm0
	paddq xmm1, xmm4
	add r10, 16
	cmp r9, r10
	jne .LBB1_6
```

Размер куска виден в начале внешнего цикла: `mov ecx, 2147483648` и
`cmovb rcx, rsi` выбирают меньшее из 2³¹ и оставшейся длины. После
каждого куска `shr rcx, 32` проверяет старшую половину суммы: не ноль —
значит, больше `u32::MAX`, и функция возвращает `None`. На срезах короче
2³¹ элементов внешний цикл выполняется один раз, и проверка стоит одну
инструкцию на весь массив.

Точка наблюдения срабатывает после инструкции, которая изменила память,
поэтому PC указывает на следующую, и сценарий печатает предыдущую
(`x/i $pc - 2`). Весь путь укладывается в 25 инструкций `Reset` из
`cortex-m-rt`:

```text
$ llvm-objdump -d --no-show-raw-insn --disassemble-symbols=Reset target/thumbv7em-none-eabihf/release/ch00-reset
00000400 <Reset>:
     400:      	bl	0xab2 <__pre_init>
     404:      	ldr	r0, [pc, #0x38]         @ __sbss
     406:      	ldr	r1, [pc, #0x3c]         @ __ebss
     408:      	movs	r2, #0x0
     40a:      	cmp	r1, r0
     40c:      	beq	0x412
     40e:      	stm	r0!, {r2}
     410:      	b	0x40a
     412:      	ldr	r0, [pc, #0x34]         @ __sdata
     414:      	ldr	r1, [pc, #0x34]         @ __edata
     416:      	ldr	r2, [pc, #0x38]         @ __sidata
     418:      	cmp	r1, r0
     41a:      	beq	0x422
     41c:      	ldm	r2!, {r3}
     41e:      	stm	r0!, {r3}
     420:      	b	0x418
     422:      	ldr	r0, [pc, #0x30]         @ CPACR = 0xE000ED88
     424:      	mov.w	r1, #0xf00000
     428:      	ldr	r2, [r0]
     42a:      	orr.w	r2, r2, r1
     42e:      	str	r2, [r0]
     430:      	dsb	sy
     434:      	isb	sy
     438:      	bl	0x518 <main>
     43c:      	udf	#0x0
```

Комментарии после `@` заменены: дизассемблер печатает там адрес
литерала и смещения переходов, а здесь вместо них подписано, какое
значение лежит в литерале (сверено по таблице символов). По порядку:

1. Ядро загрузило SP из слова 0 [таблицы векторов][g-vector-table] (`0x2000_4000`, конец
   16 КиБ ОЗУ из `memory.x`) и PC из слова 1 (`0x401`, младший бит —
   признак [Thumb][g-thumb]).
2. `__pre_init` — пустая по умолчанию функция, которую можно заменить
   атрибутом `#[pre_init]` для кода, которому нужно выполниться до
   инициализации памяти.
3. Цикл `stm r0!, {r2}` записывает нули словами от `__sbss` до `__ebss`.
   `BOOTS` лежит в `.bss` по адресу `0x2000_0004`, и мусор `0xdeadbeef`
   обнулила именно эта инструкция.
4. Цикл `ldm r2!, {r3}` / `stm r0!, {r3}` копирует `.data` из флеш-памяти
   (от `__sidata`) в ОЗУ (от `__sdata` до `__edata`). Адрес источника
   `0xd04` сценарий получил как `$r2 - 4`: `ldm` уже сдвинул указатель.
5. Запись `0xF0_0000` в CPACR открывает полный доступ к сопроцессорам
   CP10 и CP11, то есть к [FPU][g-fpu]. Барьеры `dsb` и `isb` гарантируют, что
   следующие инструкции выполнятся уже с включённым FPU.
6. `bl main` вызывает трамплин, который создаёт атрибут `#[entry]`, а тот
   вызывает функцию пользователя. Возврата из `main` быть не может, и
   после вызова стоит `udf` — неопределённая инструкция, которая вызовет
   исключение, если это всё же случится. Стек в `main` уменьшился на 8
   байт: трамплин сохранил `r7` и `lr`.

Ответ на первый вопрос к отчёту даёт таблица программных заголовков:

```console
$ llvm-readelf -l target/thumbv7em-none-eabihf/release/ch00-reset
  Type           Offset   VirtAddr   PhysAddr   FileSiz MemSiz  Flg Align
  ...
  LOAD           0x020000 0x20000000 0x00000d04 0x00004 0x00004 RW  0x10000
  LOAD           0x030004 0x20000004 0x20000004 0x00000 0x0000c RW  0x10000
```

У сегмента `.data` два адреса: `VirtAddr` `0x2000_0000` — где переменная
живёт во время работы, `PhysAddr` `0xd04` — где её начальное значение
лежит в образе и куда его записывает загрузчик (здесь QEMU, на плате —
программатор). Четыре байта `SIGNATURE` занимают место и во флеш-памяти,
и в ОЗУ. У сегмента `.bss` `FileSiz` равен нулю: нули не нужно хранить,
их пишет стартовый код, поэтому `BOOTS` в образе не занимает ни байта.
`MemSiz` `0xc` — это `BOOTS` и ещё 8 байт статических переменных
`cortex-m-semihosting`.

Второй вопрос — что будет без FPU:

```rust
{{#include ../../firmware/ch00-reset/src/bin/nocp.rs:nocp}}
```

```console
$ cargo run --release -p ch00-reset --bin nocp --target thumbv7em-none-eabihf
CPACR после Reset: 0x00f00000
FPU закрыт, складываем два f32
HardFault: PC = 0x00000556, CFSR = 0x00080000, HFSR = 0x40000000
UFSR.NOCP: инструкция сопроцессора, а сопроцессор закрыт
```

CPACR после `Reset` равен `0x00f0_0000`, как и в выводе gdb. Прошивка
закрывает сопроцессоры, и первая же инструкция FPU, `vldr s0, [sp, #12]`
по адресу `0x556`, вызывает [UsageFault][g-faults] с флагом NOCP: бит 19 в CFSR. Обработчик
UsageFault по умолчанию выключен, поэтому исключение повышается до
[HardFault][g-hardfault], о чём говорит бит 30 (`FORCED`) в HFSR. PC в кадре исключения
указывает на ту самую инструкцию `vldr`. Если бы прошивка собиралась для
`thumbv7em-none-eabi` без `hf`, инструкций FPU в ней не было бы вовсе, и
закрытый сопроцессор ничему бы не мешал.
