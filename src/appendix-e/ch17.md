# Глава 17. Низкоуровневая работа с памятью

Код решений: `solutions/ch17`. Задачи B, C и D — обычные тесты
(`cargo test -p ch17-solutions`, общий файл `tests-shared/ch17.rs`), и они
проходят под Miri в обеих моделях [алиасинга][g-aliasing]; задача C дополнительно — под
`-Zmiri-strict-provenance`. Задача A — каталог в `solutions/ch17/tests/ub.rs`:
корректные вызовы обычные тесты, UB-вызовы помечены `#[ignore]` и
проверяются `code/ch17/ub/run.sh` (каждый под Miri поодиночке), а два
не компилирующихся — `compile_fail`-[doc-тесты][g-doctest] в `solutions/ch17/src/lib.rs`.

## A. Каталог transmute

Восемь вызовов в трёх группах.

**Корректные (три).** `transmute` законен, но у каждого есть безопасная
замена из [17.4](../ch17/04-transmute.md):

- `[u8; 4]` → `u32` (`a_ok_bytes_to_u32`): размеры равны, любой образец
  валиден для `u32`. Замена — `u32::from_le_bytes`, вдобавок переносимая по
  порядку байт.
- `u32` → `[u8; 4]` (`a_ok_u32_to_bytes`): симметрично, замена —
  `to_ne_bytes`/`to_le_bytes`.
- `f32` → `u32` (`a_ok_f32_bits`): любой образец `u32` валиден. Замена —
  `f32::to_bits`; на неё прямо указывает [линт][g-lint] `unnecessary_transmutes`.

**UB (три).** Каждый создаёт значение, нарушающее [инвариант валидности][g-validity-invariant]
типа, — UB возникает уже в строке `transmute`, значение использовать не
нужно. Miri ловит все три:

- `2u8` → `bool` (`a_ub_invalid_bool`): `bool` обязан быть 0 или 1. Miri:
  «constructing invalid value of type bool: encountered 0x02, but
  expected a boolean».
- `0u8` → `NonZeroU8` (`a_ub_zero_nonzero`): 0 нарушает [нишу][g-niche]. Miri:
  «constructing invalid value of type `std::num::NonZero<u8>`: at .0.0,
  encountered 0, but expected something greater or equal to 1».
- `0x11_FFFF` → `char` (`a_ub_bad_char`): больше максимума Unicode
  `0x10_FFFF`. Miri: «constructing invalid value of type char: encountered
  0x0011ffff, but expected a valid unicode scalar value (in
  `0..=0x10FFFF` but not in `0xD800..=0xDFFF`)».

Без Miri их замечают не все и не всегда. Линт `invalid_value` ловит
только нулевой `NonZeroU8` («does not permit zero-initialization»); на
`char` rustc лишь советует `char::from_u32_unchecked` (линт
`unnecessary_transmutes`); `2u8` → `bool` он пропускает молча, и видит
его только [clippy][g-clippy] (`transmute_int_to_bool`). В каталоге эти линты
`#[allow]`-нуты — иначе он не прошёл бы clippy с `-D warnings`, и урок
«что именно пропускает `transmute`» пропал бы.

**Не компилируются (два).** Живут в doc-тестах `lib.rs`:

- `u32` → `u64` — разные размеры, `error[E0512]`. `transmute` проверяет
  равенство размеров статически; это единственное, что он проверяет.
- `&i32` → `&mut i32` — компилятор отвергает как заведомое UB (получить
  `&mut` из `&` означает изменяемый алиасинг неизменяемого).

Итог задачи: `transmute` проверяет ровно одно — равенство размеров.
Валидность, алиасинг, [время жизни][g-lifetime] он не трогает; за них отвечает автор, а
ловит их — в лучшем случае Miri, в рантайме.

## B. Разбор заголовка ELF64

Без копирования — [срез][g-slice] переосмысляется как ссылка после проверки размера и
выравнивания:

```rust
{{#include ../../solutions/ch17/src/b_elf.rs:zero_copy}}
```

Три проверки до `unsafe`: размер (буфер не короче заголовка), выравнивание
(`p % align == 0`), магия. Выравнивание обязательно именно потому, что
`Elf64Header` содержит `u64 entry` с выравниванием 8: прочитать его по
невыровненному адресу — UB (это проверяет тест `b_zero_copy_rejects_unaligned`).
А вот проверки валидности полей не нужно — все поля целые и байтовые, для
них любой образец корректен, о чём и говорит `// SAFETY`. Ссылка привязана
к времени жизни `buf` сигнатурой, поэтому использовать её после буфера
компилятор не даст.

Безопасная версия вообще не трогает ни `unsafe`, ни выравнивание:

```rust
{{#include ../../solutions/ch17/src/b_elf.rs:safe}}
```

Каждое поле собрано `from_le_bytes` из своего диапазона байт — порядок байт
задан явно (little-endian), и разбор одинаков на любой машине. Платит за это
копированием полей и разбором байт по одному; версия без копирования не
копирует ничего и возвращает ссылку внутрь буфера, но требует выравнивания и
`unsafe`. Тест `b_both_parsers_agree` проверяет, что оба дают одно и то же.

## C. Тегированный указатель

```rust
{{#include ../../solutions/ch17/src/c_tagged.rs:tagged}}
```

`Node` помечен [`#[repr(align(8))]`][g-layout], поэтому три младших бита любого его
адреса — нули, и в них помещается тег 0..8. Ключ — в `map_addr`: он меняет
только числовой адрес указателя, сохраняя его *provenance* — право
обращаться к `Node` ([16.4](../ch16/04-provenance.md)). Поэтому `ptr()`
(адрес с обнулённым тегом) несёт то же право, и разыменовать его законно, а
`tag()` читает биты через `addr()`, не претендуя на доступ к памяти.
Вариант «в лоб» — `(self.0 as usize | tag) as *const Node` — вернул бы
указатель без provenance (его адрес взят из целого), и
`-Zmiri-strict-provenance` отверг бы обращение по нему. Решение же проходит
строгий provenance именно потому, что право всё время едет с исходным
указателем.

## D. Свой тип динамического размера

```rust
{{#include ../../solutions/ch17/src/d_record.rs:record}}
```

Две вещи держат корректность. Первая — [раскладка][g-layout]: `layout` считает её ровно
так, как компилятор выводит для `#[repr(C)]` с хвостом (`Layout::new::<u32>`,
`extend` массивом, `pad_to_align`). Если бы она разошлась, `Box` при сбросе
освободил бы не тот размер. Вторая — перенос без двойного [владения][g-ownership]:
элементы `items` копируются в хвост `copy_nonoverlapping`, после чего
`set_len(0)` запрещает `Vec` их ронять (он освободит только свой буфер). И
никакого ручного `Drop`: [толстый указатель][g-fat-pointer] несёт длину `n`, drop-glue
`Box<Record<T>>` по ней сам роняет каждый элемент хвоста ровно один раз.
Свой `Drop` уронил бы их повторно — двойное освобождение. Тест
`d_record_holds_and_drops_each_once` кладёт три значения со счётчиком-дроппером
и проверяет, что после `drop(rec)` счётчик равен трём.

Сравнение с `TwoBox`:

```rust
{{#include ../../solutions/ch17/src/d_record.rs:twobox}}
```

Данных столько же, но на куче — два блока (заголовок и отдельный `Box<[T]>`)
вместо одного, и до хвоста лишнее разыменование. `Record` экономит одно
выделение и одну косвенность ценой `unsafe` при создании; `TwoBox`
безопасен и проще, но платит вторым блоком. Оба роняют каждый элемент ровно
один раз (`d_twobox_same_data`), так что разница не в корректности, а в
раскладке и числе обращений к куче.

<div class="box check">

**Ответы к «проверь себя» из [17.7](../ch17/07-tasks.md).**

1. `transmute` проверяет только равенство размеров; `u8`→`bool` проходит
   (оба 1 байт), хотя значение 2 нарушает валидность `bool`, а `u32`→`u64`
   отвергается статически — 4 байта нельзя читать как 8. Валидность не
   проверяется вовсе.
2. Версия без копирования читает `u64 entry` прямо из буфера по его адресу
   — невыровненный адрес даёт UB (нарушение выравнивания). `from_le_bytes`
   берёт байты по одному из `[u8]`, у которого выравнивание 1, и собирает
   число арифметикой — адресу буфера всё равно.
3. `map_addr` сохраняет provenance исходного указателя, меняя лишь адрес, —
   право обращаться к `Node` остаётся. `ptr as usize | tag` обратно в
   указатель рождает адрес из целого, без provenance; `-Zmiri-strict-provenance`
   запретит обращение по такому указателю.
4. Длина хвоста — в метаданных толстого указателя `Box<Record>`, не в
   памяти записи. Drop-glue по ней роняет элементы один раз; ручной `Drop`
   уронил бы их ещё раз — двойное освобождение. `TwoBox` платит за
   безопасность вторым выделением кучи и лишним разыменованием.

</div>
