# Глава 24. Процедурные макросы

Код решений: `solutions/ch24` (применения, часы, вызовы) и
`solutions/ch24-macros` (макросы). Все задачи — обычные тесты
(`cargo test -p ch24-solutions`, общий файл `tests-shared/ch24.rs`) и
снимки trybuild (`tests-shared/ch24-ui`, тесты `rustc_b_errors`,
`rustc_c_errors`, `rustc_d_errors`). Библиотека без возможности `std`
собирается на три цели Cortex-M, и решения B–D использует прошивка
`firmware/ch24-tasks`. Тесты, которые запускают cargo, rustc и trybuild,
пропускаются под Miri и в задании CI со случайной раскладкой; остальное
проходит Miri в обеих моделях алиасинга.

## A. Два раскрытия

```rust
{{#include ../../solutions/ch24/src/a_expand.rs:predicted}}
```

**`impl Debug for Point`.** `#[automatically_derived]` — пометка
сгенерированного кода; по ней, в частности, анализ мёртвого кода не
считает чтение полей в `Debug` и `Clone` использованием. Поэтому в
прошивке на типах стоит `#[expect(dead_code)]`: без него rustc
предупреждает, что поля `x` и `y` никто не читает, и прямо пишет, что
`Debug` «intentionally ignored during dead code analysis». `#[inline]` —
`fmt` маленький, и ему разрешено встраиваться в другие крейты. `Formatter`
без `<'_>` — так derive и пишет: время жизни в пути можно опустить, а линт
`elided_lifetimes_in_paths`, который требует `<'_>`, по умолчанию молчит
(рукописное `Formatter<'_>` печать раскрытия сохраняет).

Тело — не цепочка `f.debug_struct("Point").field("x", &self.x)
.field("y", &self.y).finish()`, а один вызов
`debug_struct_field2_finish`. В core есть такие помощники на 1–5 полей и
общий `debug_struct_fields_finish` на массивах; они `#[doc(hidden)]` и
нестабильны (`fmt_helpers_for_derive`), а комментарий в исходнике core
объясняет зачем: меньше кода, быстрее компиляция, меньше двоичный файл.
Встроенный derive вправе звать нестабильный API — его токены помечены
разрешением на это; процедурному макросу пользователя такого не дано.

Первая вещь, которую руками не пишут, — `&&self.y`: у последнего поля
двойная ссылка. Последнее поле структуры может быть безразмерным (`[u8]`,
`dyn Trait`), а `&[u8]` к `&dyn Debug` не приводится — у толстого
указателя нет места для второй таблицы. `&&[u8]` — тонкий указатель на
толстый, и он приводится. Derive не знает типов (раздел
[24.2](../ch24/02-syn-quote.md)), поэтому делает так всегда.

**`impl Debug for Mode`.** `match self` с эргономикой образцов:
`__self_0` — `&u8`, и снова `&__self_0` — двойная ссылка на последнее
поле. Вторая вещь — вариант без полей печатается через `write_str(f,
"Off")`, а не через `debug_tuple("Off").finish()`: результат тот же, кода
меньше. Имена `__self_0` с двумя подчёркиваниями — защита от
столкновения с именами пользователя (гигиена встроенного derive в этом
месте не нужна, но соглашение осталось).

**Переходник `#[entry]`.** `#[export_name = "main"]` — символ, который
вызывает `Reset` из cortex-m-rt после инициализации `.data` и `.bss`
([0.3](../ch00/03-asm.md)). Атрибут без `unsafe(...)`, хотя прошивка —
edition 2024: токены пришли из cortex-m-rt-macros, а это крейт 2021, и
правила применяются его ([24.4](../ch24/04-attributes.md)).
`pub unsafe extern "C"` — функцию нельзя вызвать из безопасного кода;
`#[doc(hidden)]` прячет её из документации. `static mut BOOTS` объявлен
*внутри блока* в аргументе, и `&mut BOOTS` — единственный путь к нему;
`#[allow(static_mut_refs)]` глушит линт, который в редакции 2021 —
предупреждение. Единственность ссылки гарантирует не компилятор, а
договор: `Reset` вызывает `main` один раз, а `main` не возвращается.

**Функция пользователя.** Переименована в `__cortex_m_rt_main`, `static
mut` стал параметром `BOOTS: &'static mut u32` с
`#[allow(non_snake_case)]` (имя заглавное), тип возврата `!` проверен
макросом. Отсюда `&'static mut` без `unsafe` у пользователя: `unsafe`
написал макрос, а обоснование — тот самый договор. У `#[interrupt]`
ссылка на `static mut` — просто `&mut`, без `'static`: обработчик
возвращается и вызывается снова, и ссылка, сохранённая на потом, пережила
бы его вызов (так же устроен `#[interrupt]` из
[24.4](../ch24/04-attributes.md)).

Попутно раскрытие объясняет загадку из прошивки задачи C:
`hprintln!("...", x)` раскрывается в
`hstdout_fmt(format_args!("...\n", x))` — перевод строки дописан к
строке формата через `concat!`, а строка формата, полученная из другого
макроса, не может захватывать переменные по имени (`{calls}`).

## B. Битовые поля регистра

Раскладка считается в макросе — при компиляции, один раз, — и в код
попадают уже числа:

```rust,ignore
{{#include ../../solutions/ch24-macros/src/bitfield.rs:layout}}
```

Каждая ошибка копится, и разбор продолжается: поле без `#[bits]` не
мешает проверить остальные. Спан выбран по смыслу: ширину исправляют в
литерале, тип — в типе, забытый атрибут — у имени. Для выхода за 32 бита
ошибка у литерала *первого* поля, которое пересекло край, и в тексте —
его биты (`28..36`): пользователь сразу видит, на сколько не хватило.

```rust,ignore
{{#include ../../solutions/ch24-macros/src/bitfield.rs:expand}}
```

Решения, которые стоит заметить:

- **маска во всё слово.** `(1u32 << width) - 1` при `width == 32` —
  переполнение сдвига. Макрос считает маску сам и для 32 подставляет
  `u32::MAX`; в коде пользователя такой ветки нет вовсе;
- **сообщение паники собрано заранее.** В `const fn` от форматирования
  осталось одно: `assert!(cond, "{}", s)` с единственным `&str`. Уже
  `assert!(value <= mask, "{}.{}", name, field)` — E0015 «cannot call
  non-const formatting macro in constant functions». Макрос знает имена
  структуры и поля и ширину и вставляет готовый литерал
  «Lcrh.wlen: значение не помещается в 2 бит»;
- **`const fn` с `&mut self`** — стабильны с Rust 1.83, поэтому
  `with_x` выражен через `set_x`, и константа `LCRH_8N1_FIFO` собирается
  цепочкой вызовов при компиляции;
- **спан методов — имя поля** (`quote_spanned! {fname.span()=> ...}`):
  если имя метода столкнётся с чужим (`set_x` у пользователя уже есть),
  ошибка укажет на поле;
- **`Debug` через геттеры**, а не через биты: печать показывает поля, а
  не число;
- **все пути — от `::core`**, `#[repr(transparent)]` — тип ровно `u32`, и
  его можно класть в `#[repr(C)]`-блок регистров.

Сгенерированный код — те же сдвиги и маски, что пишут руками, и в
выпускной сборке `with_wlen(3).with_fen(true)` сворачивается в константу
`0x70`.

## C. Замер времени функции

```rust,ignore
{{#include ../../solutions/ch24-macros/src/timed.rs:expand}}
```

**Охранник, а не обёртка.** Первая мысль — обернуть тело замыканием:
`let start = now(); let r = (|| тело)(); record(now() - start); r`.
`return` и `?` внутри замыкания вернут из замыкания то же значение, и
это даже работает — до первой паники: при раскрутке стека строка
`record` не выполнится, и вызов потеряется. Замыкание к тому же меняет
заимствования (аргументы захватываются), ломает `impl Trait` в
результате и мешает рекурсии. `Drop` охранника выполняется на *любом*
выходе из области видимости, в том числе при раскрутке, и тело остаётся
телом. Тест `c_panic_is_counted` ловит разницу.

**`_guard` с `mixed_site`.** Имя охранника не должно перекрывать
аргументы (тест с аргументами `guard`, `_guard` и `__guard`), и гигиена
`mixed_site` делает имя невидимым для тела. Подчёркивание глушит линт
`unused_variables`. А вот `let _ = STATS.start();` — классическая
ловушка: `_` не привязывает значение, охранник уничтожается сразу, и
замер — ноль. От неё же защищает `#[must_use]` на `Guard` с объясняющим
текстом.

**Отказы.** У `const fn` нет часов при вычислении в `const`, и
`STATS.start()` там не вызвать — ошибка всё равно была бы, но невнятная
(E0015 где-то в раскрытии). У `async fn` охранник жил бы от первого
`poll` до готовности и мерил бы время вместе с ожиданием в `.await` —
код соберётся, а цифры будут враньём. Без аргумента — ошибка со спаном
атрибута: `Error::new(Span::call_site(), ...)`; аргумент не-путь — ошибку
выдаёт syn (`expected identifier`).

**Атомики `Relaxed`.** Счётчики независимы, и ни одно другое значение не
публикуется через них, — `Relaxed` достаточно (глава 21). `fetch_max`
обновляет максимум одним вызовом: цикл CAS за нас пишет компилятор
(`lock cmpxchg` на x86-64, `ldrex`/`strex` на ARMv7-M). На ARMv6-M нет ни
того ни другого, отсюда `#[cfg(target_has_atomic = "32")]` на `Timing` — и
`cfg_attr` в прошивке. `total` в `u32` переполняется: у `HostClock` в
наносекундах — после 4,3 с суммарного времени; для долгих замеров нужен
`AtomicU64` там, где он есть.

**Часы Cortex-M.** SysTick — 24-битный счётчик вниз, поэтому
`elapsed` — `(start - end) & 0xFF_FFFF`, и замер верен, только если вызов
короче периода в 2²⁴ тактов (0,34 с на 50 МГц). CYCCNT блока DWT — 32
бита вверх на частоте ядра: переполнение через 2³² тактов (86 с на
50 МГц), разность с переносом из `Clock::elapsed` по умолчанию. Счётчик
включается двумя битами — TRCENA в DEMCR и CYCCNTENA в DWT_CTRL — и
`enable` проверяет, что бит действительно встал: в QEMU 8.2 DWT не
моделируется и читается нулём, а на Cortex-M7 запись в DWT ещё и закрыта
регистром блокировки LAR. Поэтому `enable` возвращает `bool`, а не
делает вид, что всё получилось.

## D. Регистры из файла SVD

Решение разделено на три слоя: разбор XML в модель (`Peripheral`,
`Register`, `Field`), проверки модели и генерация кода. Ошибка любого
слоя несёт место — строку и столбец узла XML или «файл целиком», или
имя периферии в вызове:

```rust,ignore
{{#include ../../solutions/ch24-macros/src/svd.rs:find}}
```

`derivedFrom` разрешается так: адрес и описание — свои, регистры и
значения по умолчанию (`size`, `access`, `resetValue`) — образца.
Значения по умолчанию наследуются от устройства к периферии и к
регистру — так их задаёт формат SVD. Числа SVD бывают десятичными, `0x…`
и двоичными `#…`:

```rust,ignore
{{#include ../../solutions/ch24-macros/src/svd.rs:number}}
```

Генерация:

```rust,ignore
{{#include ../../solutions/ch24-macros/src/svd.rs:codegen}}
```

- **промежутки** — поля `_reservedN: [u8; n]` с литералом без суффикса:
  длина массива — `usize` ([24.5](../ch24/05-testing.md));
- **проверки при компиляции** — `size_of` блока и `offset_of!` каждого
  регистра. Если в генераторе ошибка, сборка упадёт на ней, а не в
  прошивке, которая пишет мимо регистра;
- **права доступа — наличием методов.** У `Fr` нет `write`, у `Icr` нет
  `read`; ошибка пользователя — E0599 «no method named `write` found for
  struct `Fr`», и указывает она на вызов `.write`;
- **`UnsafeCell` внутри** — регистр меняется не через `&mut`, а через
  `&self`: его меняет и железо. Чтение и запись — volatile;
- **`steal`** строит ссылку из адреса через `with_exposed_provenance`
  ([16.4](../ch16/04-provenance.md)), а `from_ptr` даёт тот же блок
  поверх обычной памяти — на нём тест проверяет запись по смещениям;
- **зависимость от файла** — `const _: &[u8] = include_bytes!(путь)`
  ([24.6](../ch24/06-cost.md)).

### Сравнение со svd2rust

svd2rust 0.37.1 на том же файле (`svd2rust -i lm3s6965.svd --target
cortex-m --edition 2024`), сборка под thumbv7m-none-eabi на четырёх
ядрах, rustc 1.97, медиана трёх прогонов:

| | svd2rust | `include_svd!` |
|---|---|---|
| сгенерировано (после rustfmt) | 2014 строк | 1557 строк |
| из них без документации | 1445 | 1355 |
| чистая сборка, отладочная | 4,35 с | 4,06 с |
| чистая сборка, выпускная | 3,52 с | 3,13 с |
| крейтов в сборке | 20 | 8 |
| самый долгий крейт | syn 2 — 3,0 с | syn 3 (`full`) — 2,7 с |
| пересборка после правки крейта | 0,07 с | 0,06 с |

Строки `include_svd!` сосчитаны по выводу `-Zunpretty=expanded` без двух
строк-литералов: печать раскрытия разворачивает `include_bytes!` в
байтовую строку на 23 КБ, хотя в программу эти байты не попадают.

Цифры почти равны, и важно, *из чего* они сложены:

- **svd2rust генерирует один раз**, а результат — обычный крейт.
  Генерация в сборку не входит вовсе: 4 с — это cortex-m с зависимостями
  (embedded-hal двух версий, bare-metal, syn 2 через cortex-m-macros) и
  сам PAC за 0,18 с. В прошивке cortex-m уже есть, и PAC добавляет к
  сборке только себя;
- **`include_svd!` собирает генератор в каждой чистой сборке**: syn с
  `full`, roxmltree с memchr и сам макрос — около 1,7 с процессорного
  времени у этих трёх, не считая syn. syn 3 с `full` в прошивке уже есть
  (его требует cortex-m-rt-macros 0.7.7), а roxmltree и макрос — новые;
- **объём** почти одинаков, но по-разному распределён. У svd2rust 867
  строк — общий модуль `generic` (трейты `Readable`, `Writable`,
  `FieldWriter`…), он не растёт с числом регистров; UART1 не повторяет
  UART0, а ссылается на него: `pub use self::uart0 as uart1` и
  `pub type Uart1 = Periph<uart0::RegisterBlock, 0x4000_d000>`. У
  `include_svd!` каждый вызов порождает свой модуль целиком — `derivedFrom`
  стоило бы раскрывать так же, ссылкой;
- **машинный код одинаков.** Запись 8N1 с FIFO в LCRH и чтение CTL:

```rust,ignore
// svd2rust
u.lcrh().write(|w| unsafe { w.wlen().bits(3) }.fen().set_bit());
u.ctl().read().bits()
// include_svd!
u.lcrh.write(uart0::Lcrh::FEN.set(uart0::Lcrh::WLEN.set(0, 3), 1));
u.ctl.read()
```

```text
movs  r1, #0x70
str   r1, [r0, #0x2c]
ldr   r0, [r0, #0x30]
```

  (выпускная сборка, `llvm-objdump -d`; пролог `push {r7, lr}` у обоих).
  Вся разница API — при компиляции.

Чего `include_svd!` не умеет, а svd2rust умеет: типизированные
читатели и писатели полей (`r.wlen().bits()`, `w.fen().set_bit()`) с
перечислениями из `enumeratedValues`; `write`, который начинает с
`RESET`, а не с нуля; синглтон `Peripherals::take()` через
critical-section; перечисление прерываний и таблицу векторов
(`device.x` с `PROVIDE(UART0 = DefaultHandler);`) под возможностью `rt`;
массивы и кластеры регистров (`dim`). Первое, что стоило бы добавить, —
перечисление прерываний из элементов `<interrupt>`: тогда `include_svd!`
и `#[interrupt]` из раздела [24.4](../ch24/04-attributes.md) замкнулись бы
— список прерываний для проверки имени давал бы тот же файл.

Где граница. На настоящем файле кристалла — десятки периферий, тысячи
регистров — svd2rust порождает всё (и `--feature-peripheral`, чтобы
компилировать только нужное), а `include_svd!` — только названное, но
*разбирает файл целиком при каждой компиляции* вызывающего крейта. Для
прошивки, которую часто пересобирают, разумнее генерировать один раз —
svd2rust или `build.rs`; функциональный макрос хорош, когда описание
маленькое, своё и меняется вместе с кодом.
