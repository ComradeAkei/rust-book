# Глава 15. Коллекции и аллокация

Код решений: `solutions/ch15`. Проверка: `cargo test -p ch15-solutions`
(задачи A, C, D — `--test ch15`, задача B — `--test ch15-count`, она
ставит свой [`#[global_allocator]`][g-global-allocator]). Задачи A, C и D проходят под Miri со
[Stacked Borrows][g-stacked-borrows] и с Tree Borrows без утечек; под Miri берут меньше
итераций. Замеры — примеры `report`, `ast` и `probes` в
`solutions/ch15/examples`.

## A. Предсказать рост Vec

```rust
{{#include ../../solutions/ch15/src/a_predict.rs:solution}}
```

Предсказание повторяет логику `RawVec`: каждая операция считает новую
ёмкость и, если она изменилась, засчитывает `realloc` (или первый
`alloc`, а при сжатии до нуля — `dealloc`). Три места, где ошибаются:

- `reserve(n)` — удвоение, но не меньше `len + n`; `reserve_exact(n)` —
  ровно `len + n`. Поэтому `vec![1,2,3]` плюс `reserve(1)` даёт 6
  (удвоение), а плюс `reserve_exact(1)` — 4.
- минимальная ёмкость при первом росте зависит от размера элемента: 8
  для 1 байта, 4 до 1024 байт, 1 дальше. У [ZST][g-zst] ёмкость сразу
  `usize::MAX`, и ни одного обращения к распределителю нет никогда — для
  неё в `predict` отдельная ветка.
- `shrink_to(min)` при `len == cap`, но с ёмкостью больше `min`, зовёт
  `realloc` на тот же размер: его надо засчитать. Это проверяет тест
  `task_a_shrink_to_same_size`.

Тест `task_a_random_sequences` гоняет четыреста случайных
последовательностей против настоящего `Vec` для четырёх размеров
элемента — предсказание обязано совпасть с каждым обращением к
распределителю, которое сделает `Vec`.

## B. Аллокатор-счётчик

```rust
{{#include ../../solutions/ch15/src/b_count.rs:measure}}
```

Ключевых решений три. Счётчики — в `thread_local`, потому что
распределитель стоит на весь процесс, а тесты идут параллельно: `measure`
обязан видеть только свой поток. Доступ к ним не должен выделять память
(иначе `alloc` вызвал бы сам себя) — поэтому счётчики лежат в `Cell` с
`const`-инициализацией и без `Drop`, а обращение идёт через `try_with`
(на некоторых платформах к TLS нельзя обратиться после завершения
потока). Вложенность: `measure` сохраняет пик снаружи и отсчитывает свой
заново от текущего уровня, поэтому внешний замер видит внутренний пик.

Применён счётчик в примере `report` к решениям прошлых глав:

```console
$ cargo run --release -p ch15-solutions --example report

  v.iter().filter(|&&x| x % 3 == 0).collect::<Vec<_>>()                alloc    1, realloc  7, запрошено    4096 Б, пик   4096 Б
  ...
11.C: 1000 операций восьми типов
  Vec<Box<dyn Op>>                                                     alloc 1001, realloc  0, запрошено   20000 Б, пик  20000 Б
  Vec<Any8>                                                            alloc    1, realloc  0, запрошено    8000 Б, пик   8000 Б
...
14.C: двусвязный список из 1000 узлов
  RcList: постройка и уничтожение                                      alloc 1000, realloc  0, запрошено   56000 Б, пик  56000 Б
  ArenaList: постройка и уничтожение                                   alloc    1, realloc  8, запрошено   32768 Б, пик  32768 Б
```

Числа подтверждают выводы тех глав: `Vec<Box<dyn Op>>` — тысяча
выделений (бокс на операцию) против одного у `Vec<Any8>`; список на `Rc`
— тысяча против одного у [арены][g-arena].

## C. Bump-аллокатор для дерева

```rust
{{#include ../../solutions/ch15/src/c_bump.rs:bump}}
```

Арена хранит текущую границу и конец куска указателями (не числами —
чтобы сохранить происхождение для Miri), выдаёт выровненную память
сдвигом границы и растит куски вдвое, когда места не хватило. Типы с
[деструктором][g-destructor] она отвергает на этапе компиляции — `const {
assert!(!needs_drop::<T>()) }`, — потому что освобождает всё разом и
деструкторы не вызывает; тихо их пропустить было бы утечкой или хуже.

Пример `ast` строит дерево на миллион узлов обоими способами:

```console
$ cargo run --release -p ch15-solutions --example ast
Box:  разбор  76.1 нс, вычисление 22.9 нс, уничтожение 26.5 нс на узел; alloc 1253090, пик 25.4 МиБ, RSS 44.7 МиБ
Bump: разбор  42.2 нс, вычисление 17.7 нс, уничтожение  1.1 нс на узел; alloc 14, пик 32.0 МиБ, кусков 13 (32.0 МиБ), RSS 32.3 МиБ
```

Главный выигрыш арены — не скорость разбора (на этой ВМ она шумит:
первое касание большого `mmap`-куска даёт отказы страниц), а число
выделений (14 против 1,25 млн) и уничтожение: у `Box` это обход дерева с
`free` на каждый узел (26,5 нс/узел), у арены — сброс границы (1,1 нс/узел).
RSS арены ниже (32,3 против 44,7 МиБ): нет заголовков блоков на каждый
узел. Под `strace -c` у `box`-варианта сотни `brk`, у `bump` — десяток
`mmap`.

## D. Своя хеш-таблица и длина пробы

```rust
{{#include ../../solutions/ch15/src/d_table.rs:get}}
```

Поиск идёт от домашней ячейки сквозь надгробия до первой пустой: пустая
ячейка — сигнал, что ключа нет, а надгробие — что здесь был ключ и за ним
могут лежать другие, легшие при пробировании. Поэтому `remove` ставит
`Tomb`, а не `Empty`: `Empty` оборвал бы пробу и «потерял» ключи,
вставленные после удаляемого в ту же цепочку.

Пример `probes` заполняет таблицу случайными ключами до разных
коэффициентов загрузки:

```console
$ cargo run --release -p ch15-solutions --example probes
загрузка  средняя проба  макс
   0.30          1.21    12
   0.50          1.51    22
   0.70          2.17    98
   0.90          5.37   425
   0.95          9.77  1667
```

Средняя длина пробы растёт по формуле Кнута для успешного поиска при
линейном пробировании, `≈ (1 + 1/(1−α))/2`: при загрузке 0,9 это 5,5,
при 0,95 — 10,5. Наибольшая проба к 0,95 доходит до 1667 ячеек. Отсюда
правило `std`: [SwissTable][g-swisstable] держит загрузку не выше 7/8 и растит таблицу
заранее. Надгробия удлиняют пробу так же, как живые ключи (их всё равно
осматривают), — тест `task_d_tombstones_inflate_then_compaction_helps`
показывает, что после удаления половины ключей проба не короче, а
перехеширование её возвращает.

Почему `std::HashMap` не вырождается ни от загрузки, ни от подобранных
ключей: загрузка ограничена 7/8; [SIMD][g-simd]-группы из 16 корзин ([раздел
15.3](../ch15/03-maps.md)) делают пробу группами, а не по одной корзине;
а случайный ключ [SipHash][g-siphash] не даёт заранее подобрать ключи в одну цепочку.
Самодельная таблица не делает ни первого, ни второго, ни третьего — и
потому опасна ровно так, как `table.c` из вступления главы.
