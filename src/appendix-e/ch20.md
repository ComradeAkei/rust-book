## A. SendBox и классификация Send/Sync

```rust
{{#include ../../solutions/ch20/src/a_send.rs:solution}}
```

`SendBox` — единоличный [владелец][g-ownership] выделения (как `Box`). [Перемещение][g-move] в другой
поток передаёт владение *целиком*: второго доступа к указателю не остаётся,
поэтому `unsafe impl Send for SendBox<T> where T: Send` обоснован. А [`Sync`][g-send-sync]
ставить нельзя: `&SendBox` дал бы двум потокам общий доступ к одному `*mut
T` без синхронизации — гонка данных. `into_inner` гасит `Drop` через
`mem::forget`, иначе память освободилась бы дважды — и это ловит Miri в тесте
`a_sendbox_drops_without_leak`.

Классификация восьми типов:

| Тип | `Send` | `Sync` | Почему |
|---|:---:|:---:|---|
| `Rc<i32>` | нет | нет | счётчик ссылок неатомарный — гонка при клоне из двух потоков |
| `Arc<i32>` | да | да | атомарный счётчик; `i32: Send + Sync` |
| `Arc<Cell<i32>>` | нет | нет | `Arc<T>` требует `T: Send + Sync`, а `Cell` не `Sync` |
| `&RefCell<i32>` | нет | нет | `&T: Send` ⟺ `T: Sync`, но `RefCell` не `Sync` |
| `MutexGuard<'_, i32>` | нет | да | освобождать мьютекс обязан захвативший поток; делить `&guard` безопасно |
| `*const u8` | нет | нет | про [сырой указатель][g-raw-pointer] компилятор не знает ничего |
| `Arc<Mutex<i32>>` | да | да | `Mutex<i32>: Send + Sync` — канонический общий тип |
| `Arc<Mutex<Rc<i32>>>` | нет | нет | внутри `Rc` не `Send`, значит `Mutex<Rc<i32>>` ни `Send`, ни `Sync` |

Главный вывод: маркеры выводятся из полей, поэтому «неправильный» тип — это
всегда либо неатомарный счётчик (`Rc`), либо изменяемость через `&` (`Cell`,
`RefCell`), либо сырой указатель. Обёртка (`Arc`, `Mutex`) чинит ровно то,
что внутри неё, и не чинит того, что осталось сломанным глубже (`Rc` внутри
`Mutex`).


Текст режется на куски по числу потоков; каждый поток считает в свой
`HashMap` через [`thread::scope`][g-scoped-threads] ([срез][g-slice] строк одалживается без `Arc`), затем
локальные таблицы сливаются. Общий `Mutex<HashMap>` на каждое слово
сериализовал бы потоки — они стояли бы в очереди за замком, и параллелизм
исчез бы. Локальная таблица убирает конкуренцию с горячего пути: данные
сходятся ровно один раз, при слиянии. Тест `b_wordcount_matches_sequential`
сверяет результат с последовательным подсчётом для 1, 2, 3 и 8 потоков.

## C. Мьютекс на futex

```rust
{{#include ../../solutions/ch20/src/c_futex.rs:solution}}
```

Три состояния — ключ к экономии системных вызовов. По незанятому замку
`lock` делает один `compare_exchange(0 → 1)` и возвращается, не трогая ядро;
`unlock` видит состояние `1` (ожидающих нет) и тоже обходится без вызова.
Ядро (`futex`) зовут только при конкуренции: претендент ставит состояние `2`
(«занят, есть ожидающие») и засыпает на `FUTEX_WAIT`, а `unlock`, увидев
`2`, будит одного через `FUTEX_WAKE`. Сам вызов — инструкцией `syscall`
([19.1](../ch19/01-asm.md)) без [крейта][g-crate] libc. Тест
`c_futex_mutex_provides_mutual_exclusion` инкрементит счётчик *неатомарно*
(load+store) под замком восемью потоками: верный итог возможен только при
настоящем взаимном исключении. `strace -f -e futex` на версии со `std::sync
::Mutex` покажет ту же картину: при низкой конкуренции системных вызовов
почти нет, при высокой — пара на претендента.

## D. Перевод без взаимной блокировки

```rust
{{#include ../../solutions/ch20/src/d_deadlock.rs:solution}}
```

Наивный `transfer` берёт замки в порядке аргументов: поток, переводящий 0→3,
захватывает счёт 0, затем 3; встречный поток 3→0 — счёт 3, затем 0. Каждый
держит один замок и ждёт второй — граф ожидания образует цикл 0→3→0, и оба
потока стоят навсегда. Решение — глобальный порядок: замки всегда
захватываются по возрастанию индекса (`lo = from.min(to)`, затем `hi`),
одинаково во всех потоках, поэтому цикла в графе ожидания не бывает.
Отдельно обработан `from == to`: второй замок того же счёта — самоблокировка.
Тест `d_ordered_transfers_conserve_total_without_deadlock` гоняет встречные
переводы в восемь потоков; при неупорядоченном захвате он бы завис, а так —
завершается, и сумма счетов сохраняется.

Закрепить порядок в типах можно иерархией замков: дать каждому `Mutex`
уровень (константу-параметр) и разрешать `lock` более высокого уровня только
при наличии токена-доказательства, что более низкие уже взяты. Тогда захват
в неверном порядке не наберёт нужный токен и не скомпилируется. Так
устроен, например, крейт `lock_ordering`; крейт `tracing-mutex` решает ту
же задачу в рантайме — строит граф порядка захватов и [паникует][g-panic], если в нём
появился цикл. Для банка же достаточно упорядочить по индексу счёта.
