(`cargo test -p ch23-solutions`, общий файл `tests-shared/ch23.rs`) и

## A. Шесть раскрытий

```rust
{{#include ../../solutions/ch23/src/a_expand.rs:predicted}}
```

Вывод `rustc -Zunpretty=expanded` для тех же функций (rustc 1.97):

```rust,ignore
pub fn call1(next: &mut impl FnMut() -> i32) -> i32 {
    if next() > 3 { next() } else { 3 }
}

pub fn call2() -> (i32, i32) { ((1 + 2) * (1 + 2), 1 + 2 * 1 + 2) }

pub fn call3(mut x: i32, mut tmp: i32) -> (i32, i32) {
    let tmp = x;
    x = tmp;
    tmp = tmp;
    ;
    (x, tmp)
}

pub fn call4() -> usize { 1usize + (1usize + (1usize + 0usize)) }

pub fn call5() -> (&'static str, &'static str) {
    ("ноль", "не ноль")
}
```

Две из шести — про скобки, которых в подстановке нет. В `call2` их
вернула печать: `$x` из `square!` — узел-выражение, и чтобы текст
раскрытия значил то же, что дерево, печать берёт узел в скобки. У
`square_tt!` узла нет — токены вставлены как есть, и скобок не будет. В
`call4` то же происходит с результатом вложенного вызова: `count!(b c)`
внутри подстановки раскрывается в выражение, и это выражение — тоже
целый узел, `1usize + (…)`. Рекурсия раскрывается «справа», и скобки
показывают порядок вложенности.

`call3` — главная ловушка задачи: текст `let tmp = x; x = tmp; tmp = tmp;`
выглядит ровно как сломанный `SWAP` из C, но `tmp` в первой и последней
позиции — макросный, с другим контекстом гигиены
([23.3](../ch23/03-hygiene.md)): `-Zunpretty=expanded` контексты не
печатает, а `-Zunpretty=expanded,hygiene` — печатает. Одинокий `;` — след
точки с запятой после `swap!(x, tmp);`: макрос в позиции оператора
раскрылся в три оператора, а `;` после вызова стал пустым оператором.

`call5`: `via_expr!(0)` захватил ноль как `expr`, и для `is_zero!` это
уже непрозрачный узел, а не токен `0`. `call1` — двойное вычисление,
которое никакая гигиена не лечит.

## B. Флаги регистра

```rust
{{#include ../../solutions/ch23/src/b_flags.rs:solution}}
```

Основа — `#[repr(transparent)]` над целым: значение флагов и есть
регистр, `size_of::<Cr>()` равен `size_of::<u32>()`, и запись
`uart.CR().write(on.bits())` ничего не стоит. Константы флагов —
ассоциированные константы типа, поэтому пишутся `Cr::TXE`.

Методы — `const fn`, а операторы — тонкие обёртки над ними. Наоборот
нельзя: оператор `|` — вызов `BitOr::bitor`, обычного метода трейта, и
`const X: Cr = Cr::A | Cr::B;` на rustc 1.97 — E0015 «cannot call
non-const operator in constants». А прошивке константы нужны:
`const ON: Cr = Cr::UARTEN.union(Cr::TXE).union(Cr::RXE);` из doc-теста
модуля. `all()` — повторение `0 $(| $value)*`: одно выражение из всех
флагов, константа.

`complement` — дополнение в пределах `all()`, а не `!self.0`. У регистра
есть зарезервированные биты, и `!Cr::TXE`, записанный в CR, не должен
поднимать биты, которых в описании нет. По той же причине три варианта
`from_bits`: строгий, отбрасывающий и сохраняющий — при чтении регистра
нужен последний, иначе зарезервированные биты пропадут при
«прочитать — изменить — записать».

`Debug` идёт по таблице `FLAGS` в порядке объявления и печатает каждый
флаг, все биты которого подняты; что осталось — числом `{:#x}`. Флаг со
значением 0 пропускается — иначе он печатался бы всегда. Таблица `FLAGS` —
`&'static [(&str, Self)]`: `stringify!($flag)` даёт имя при компиляции.

Все пути — от `::core`: `::core::option::Option`, `::core::fmt::Formatter`,
`::core::ops::BitOr`. Модуль `hostile` в тестах объявляет свои `Option`,
`Result`, `core` и `fmt`; решение, где хоть один путь написан коротко,
там не скомпилируется или — хуже — построит чужой `Option`.

Право доступа — тип без значений (`enum RO {}`), и выбор методов делает
система типов: `read` есть у `Reg<T, A: Readable>`, `write` — у
`A: Writable`, `modify` — у обоих сразу. Запись в `FR` даёт E0599 с
понятной причиной — «the following trait bounds were not satisfied:
`RO: Writable`».

Разбор входа упирается в follow-set ([23.1](../ch23/01-rules.md)). Тип
регистра — `$ty:ident`, потому что после `ty` нельзя поставить `@`; для
`u8`, `u16`, `u32` это не потеря, а составной тип вроде `[u8; 4]` регистру
и не нужен. Смещение — `$off:literal`, а не `expr`: после `expr` нельзя
поставить слово доступа, а главное, литерал не даёт вызывающему вставить
своё выражение в `unsafe`-блок аксессора — ровно ловушка `take_once_bad!`
из [23.6](../ch23/06-hardware.md). Слово доступа необязательно:
`$($access:ident)?`, а выбор делает внутреннее правило `@access` — вызов
`$crate::peripheral!(@access $($access)?)` стоит прямо в позиции типа.
Расплата — диагностика: на неизвестное слово `rx` rustc 1.97 показывает
весь вызов `peripheral!`, а не слово, — ошибку нашёл вложенный вызов, и
компилятор указывает на внешний.

`steal` строит указатель из числа `BASE` через
`with_exposed_provenance_mut` ([16.4](../ch16/04-provenance.md)): на
Cortex-M нет аллокатора, который «выдал» бы эту память, и право на неё
берётся из адреса. Тесты не могут писать по 0x4000_C000, поэтому есть
второй конструктор, `at(base)`: блок регистров на обычной памяти,
выровненной под `u32`. Оба `unsafe` — с контрактом в документации: два
`steal` дают две ручки на одни регистры, и за этим следит вызывающий
(синглтоны периферии с `take()` — в [10.7](../ch10/07-typestate.md)).

Проверка выравнивания — по `const _` на регистр: `$off % align_of::<$ty>()`.
Неверное смещение — E0080 «evaluation panicked: смещение регистра не
кратно его выравниванию» с указанием на вызов.

Вывод прошивки `firmware/ch23-periph` в QEMU приведён в
[23.7](../ch23/07-tasks.md). Регистры там описаны этим макросом, флаги —
макросом из задачи B, и `Debug` печатает состояние UART0 как
`Cr(UARTEN | TXE | RXE)`.

## D. Конечный автомат

```rust
{{#include ../../solutions/ch23/src/d_fsm.rs:solution}}
```

Правила `@munch` съедают по переходу и раскладывают их в три накопителя:
конкретные переходы `[($from $ev $to) ...]`, переходы из `_`
`[($ev $to) ...]` и рёбра графа. Список состояний `[$($s)*]` едет
вместе с накопителями: он нужен, чтобы раскрыть `_ --e--> t` в рёбра из
*каждого* состояния — `$(($s $ev $to))*`. Переход `a | b --e--> c`
повторением `$($from:ident)|+` превращается в два конкретных. Когда вход
съеден, `@emit` выдаёт всё разом: `match` нельзя собрать по веткам
([23.4](../ch23/04-recursion.md)), а в накопителях к этому моменту лежат
все ветки.

Порядок веток решает приоритет: сначала все конкретные переходы, затем
все `_`, где бы `_` ни стоял во входе, — поэтому накопителей два, а не
один. Последняя ветка `_ => None` нужна, если какие-то пары не покрыты,
и недостижима, если покрыты все; `#[allow(unreachable_patterns)]` глушит
предупреждение во втором случае.

Детерминизм проверяет `const`-блок: двойной цикл по `TRANSITIONS`
сравнивает пары «источник, событие». Повтор конкретного перехода сделал
бы вторую ветку `match` недостижимой, но предупреждение
`unreachable_patterns` в коде из макроса чужого крейта компилятор не
показывает — поэтому нужна явная проверка. Сравнение вариантов —
`a as usize == b as usize`: `==` у вариантов — вызов `PartialEq::eq`, и в
`const` это та же E0015 «cannot call non-const operator», а сравнение
целых — встроенная операция.

Что получает пользователь при ошибке:

| Ошибка в описании | Диагностика rustc 1.97 | Куда указывает |
|---|---|---|
| опечатка в состоянии `Openned` | E0599 «no variant … named `Openned`» и подсказка `Opened` | точно на имя |
| опечатка в событии `Opne` | E0599, подсказка `Open` | точно на имя |
| стрелка `->` вместо `-->` | «no rules expected `->`» | точно на стрелку |
| два перехода из `Closed` по `Open` | E0080 «evaluation panicked: два перехода из одного состояния по одному событию» | на весь вызов `fsm!` |

Первые три хороши потому, что их находит не макрос, а компилятор в
сгенерированном коде или парсер образца, и токены помнят своё место.
Четвёртую находит сам макрос — точнее, `const`-код, который он
сгенерировал, — и указать на повторный переход ему нечем.

### Где граница

Замер — автомат из *n* состояний по кругу (`S0 --Next--> S1`, ...) плюс
`_ --Reset--> S0`, то есть *n* переходов. Без `#![recursion_limit]`
решение раскрывает 122 перехода; на 123-м — «recursion limit reached»:
каждый переход — уровень рекурсии, плюс несколько уровней на вход,
`@emit` и вложенные `concat!`/`assert!`. С
`#![recursion_limit = "4096"]` время проверки крейта
(`--emit=metadata`, `RUSTC_BOOTSTRAP=1 rustc -Ztime-passes`, rustc 1.97,
Intel Xeon 2,1 ГГц в контейнере сборки, один прогон):

| Переходов | Раскрытие макросов, с | Проверка типов и `const`, с | Всего, с |
|---|---|---|---|
| 200 | 0,044 | 0,20 | 0,27 |
| 400 | 0,156 | 0,81 | 1,00 |
| 800 | 0,667 | 4,55 | 5,31 |

При 25 переходах вся компиляция файла — 0,06 с (лучшее из трёх
измерений по часам). Рост квадратичный в обоих столбцах, но по разным
причинам. Раскрытие: TT-muncher на каждом шаге копирует остаток входа и
накопители, ~*n²* токенов. Проверка типов: в неё входит вычисление
`const`-блока детерминизма, двойной цикл по таблице, ~*n²*/2 сравнений.
Копия макроса без `const`-проверки на 800 переходах проходит проверку
типов за 0,03 с, а копия с проверкой — за 4,7 с: проверка и есть главная
цена.

Граница, таким образом, проходит не по числу переходов: автомат протокола
или драйвера на 10–50 переходов обходится в десятки миллисекунд. Она
проходит по тому, что нужно проверить:

- **сравнение имён.** `macro_rules!` не умеет сравнить два
  идентификатора. Детерминизм поэтому проверяется в `const` — за *n²* и
  с ошибкой на весь вызов. Процедурный макрос сложит пары в `HashSet` за
  линейное время *при раскрытии* и укажет спаном на второй переход;
- **анализ графа.** Недостижимые состояния, состояния без выхода,
  события, которые нигде не используются, — всё это требует сравнивать
  имена и обходить граф. Средствами `macro_rules!` такое не выразить, а
  `const`-код с той же целью дал бы ещё более слепую диагностику;
- **новые имена.** Склеить `Door` и `Event` в `DoorEvent`, перевести
  `Timeout` в `TIMEOUT` или `timeout` нельзя — поэтому оба перечисления
  задаёт пользователь;
- **длинные описания.** Больше ~120 переходов требуют
  `#![recursion_limit]` у *вызывающего* крейта, а время растёт как *n²*.

Процедурный макрос стоит отдельного крейта типа `proc-macro` и сборки
`syn` и `quote` на хосте — один раз на чистую сборку; эту цену глава 24
измерит. Пока описание укладывается в повторение и рекурсию, а проверки —
в то, что компилятор и так сделает над сгенерированным кодом, достаточно
`macro_rules!`; когда макросу нужно *понимать* вход — пора в главу 24.
