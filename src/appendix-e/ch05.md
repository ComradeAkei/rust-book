## A. Элизия вручную

```rust
{{#include ../../solutions/ch05/src/a_elision.rs:answers}}
```

Простые случаи — a1, a2, a4, a6 и a7.

- a1 и a2 — правило 2: у входа одно время жизни, и выход берёт его.
  `sep: char` в a2 не ссылка и в счёт не идёт. Результат a2 — кортеж из
  двух ссылок, и обе получают одно `'a`.
- a4 — правило 1: каждая пропущенная ссылка на входе получает свой
  параметр, в том числе ссылка внутри `Vec<&str>`. Итого три параметра.
  Выход `usize` ссылок не содержит, связывать его не с чем.
- a6 и a7 — правило 3: если есть `&self` или `&mut self`, выход берёт его
  время жизни, сколько бы ещё ссылок ни было на входе. В a7 `key`
  получает своё `'b` и с результатом не связан — так и надо: результат
  смотрит в таблицу, а не в ключ.
- a3 — две ссылки на входе и нет `self`: ни одно правило не применимо,
  E0106. Исправление — `fn pick<'a>(a: &'a [u8], b: &'a [u8]) -> &'a [u8]`,
  но это уже решение программиста, а не элизии.

Подводят a5 и a8.

**a5.** В `Box<dyn Fn(&str) -> bool>` два пропуска, и правила элизии
функций не действуют ни на один.

1. `Fn(&str)` — сокращённая запись границы `for<'b> Fn(&'b str)`
   (раздел [5.5](../ch05/05-hrtb.md)). Её время жизни не связано с
   параметрами `make_filter`: замыкание принимает строку любого времени
   жизни.
2. У `dyn Trait` без явной границы время жизни по умолчанию берётся из
   окружающего типа: в `&'x dyn Trait` это `'x`, а в `Box<dyn Trait>`
   ограничений нет, и граница — `'static`. Правило 2 его не трогает,
   хотя ссылка на входе одна.

Отсюда ответ `Box<dyn for<'b> Fn(&'b str) -> bool + 'static>`. Тело с этим
согласно: префикс копируется в `String`, и замыкание ничего не
заимствует. Два типичных неверных ответа тест ловит на второй проверке,
`back_make_filter` с исходной сигнатурой:

```text
error[E0308]: mismatched types
 --> a5.rs:7:59
  |
7 | pub fn back1(prefix: &str) -> Box<dyn Fn(&str) -> bool> { stud1(prefix) }
  |                                                           ^^^^^^^^^^^^^ one type is more general than the other
  |
  = note: expected trait object `dyn for<'a> Fn(&'a str) -> bool`
             found trait object `dyn Fn(&str) -> bool`
```

Это ответ `Box<dyn Fn(&'a str) -> bool + 'static>`: замыкание, которое
принимает строки только одного времени жизни `'a`, не заменит замыкание
для любых строк. Первую проверку этот ответ проходит: обратное
приведение, от `dyn for<'b> Fn(&'b str)` к `dyn Fn(&'a str)`, разрешено,
как у указателей на функции. Ответ `Box<dyn for<'b> Fn(&'b str) -> bool +
'a>` (граница от входа, по аналогии с правилом 2) отвергается так:

```text
error: lifetime may not live long enough
  --> a5.rs:10:59
   |
10 | pub fn back2(prefix: &str) -> Box<dyn Fn(&str) -> bool> { stud2(prefix) }
   |                      -                                    ^^^^^^^^^^^^^ returning this value requires that `'1` must outlive `'static`
   |                      |
   |                      let's call the lifetime of this reference `'1`
```

Оба вывода сняты с файла, который повторяет устройство теста: исходная
функция, `stud` с ответом и `back` с исходной сигнатурой.

**a8.** У `Parser<'s>` есть своё время жизни, и хочется ответить
`Option<&'s str>`. Но правило 3 берёт время жизни `&mut self`, а не
параметр структуры: `fn next_token<'a>(&'a mut self) -> Option<&'a str>`.
Здесь элизия угадала верно: слово лежит в `self.word`, который следующий
вызов перепишет, и держать его дольше заимствования парсера нельзя. Это
одалживающий итератор из раздела [5.6](../ch05/06-gat.md). Ответ с `'s`
не пройдёт первую проверку: `stud_next_token` пытается отдать на `'s`
данные, заимствованные на время вызова. Если бы парсер отдавал срезы
`src` без перевода в нижний регистр, `-> Option<&'s str>` пришлось бы
писать явно, и тогда он мог бы стать обычным `Iterator`, как лексер из
задачи B.

## B. Токенизатор без выделения памяти

```rust
{{#include ../../solutions/ch05/src/b_lexer.rs:lexer}}
```

Главное решение — где хранится время жизни. `Lexer<'a>` держит
`rest: &'a str`, остаток текста. Методы берут `&mut self`, но отдают
`&'a str`: `self.rest` — значение типа `&'a str`, его можно скопировать из
структуры, и срезы копии живут `'a`, а не столько, сколько заимствование
лексера:

```rust
{{#include ../../solutions/ch05/src/b_lexer.rs:next_line}}
```

Поэтому `Item = Result<Token<'a>, LexError>` от заимствования лексера не
зависит, `Lexer` — обычный `Iterator`, и тест собирает лексемы в `Vec`
через `collect`. `Normalize` из раздела 5.6 так не может: он отдаёт свой
буфер, а не текст.

Ловушка — пропустить `'a` в сигнатуре `next_line`. Правило 3 привяжет
результат к `&mut self`, строка будет держать лексер, и цикл в `next` не
скомпилируется:

```text
error[E0499]: cannot borrow `*self` as mutable more than once at a time
  --> b_lexer.rs:69:24
   |
61 | impl<'a> Iterator for Lexer<'a> {
   |      -- lifetime `'a` defined here
...
69 |             let line = self.next_line()?;
   |                        ^^^^ `*self` was mutably borrowed here in the previous iteration of the loop
70 |             if let Some(r) = self.lex_line(line) {
   |                              ------------------- argument requires that `*self` is borrowed for `'a`
```

Сообщение говорит о двойном `&mut`, но причина — в сигнатуре: `lex_line`
отдаёт `Token<'a>`, значит, `line` должна жить `'a`, а с пропущенным
временем жизни она заимствует `*self` на весь `'a`. Когда ошибка
заимствования указывает на `'a` из `impl`, ищите метод, у которого
элизия связала результат не с тем входом.

Остальное — аккуратный разбор строки, весь на срезах:

- `lex_line` отрезает от строки префиксы через `strip_prefix`,
  `split_at`, `trim_start`; каждый результат — срез той же строки.
- Ключ отдаётся сразу, значение кладётся в `pending: Option<Token<'a>>` и
  выдаётся следующим вызовом `next`. Очередь из одного элемента не
  требует выделения памяти.
- `comment_start` ищет `#` или `;` в начале значения или после пробела
  (правило 5), `garbage` проверяет остаток после `]` и закрывающей
  кавычки (правила 3 и 6).
- Столбец ошибки считается от хвоста строки `at`, который начинается с
  ошибочного символа: `line.len() - at.len()` — байтовое смещение, а
  `chars().count()` префикса переводит его в символы. Счёт линейный, но
  только на пути ошибки.

Размеры на x86_64 (rustc 1.97): `Token` — 24 байта, тег и `&str`.
`Result<Token, LexError>` — тоже 24: `Err` занимает свободное значение
тега `Token`, и `LexError` (12 байт) помещается рядом с ним. `Lexer` — 48
байт. Тест `zero_copy_and_zero_allocations` подменяет распределитель
счётчиком, разбирает 2000 секций и проверяет, что выделений не было и
каждый срез лежит внутри исходного текста по адресу.

## C. Таблица вариантности

### Часть 1

```rust
{{#include ../../solutions/ch05/variance/covariant.rs}}
```

`builtin` имеет тип `&'a Vec<&'static str>`, а возвращается как
`&'a Vec<&'a str>`. Подстановка проходит по цепочке: `&'static str`
годится вместо `&'a str`, `Vec<T>` ковариантен по `T`, `&'a T` —
тоже. Ковариантность здесь нужна дважды, на `Vec` и на внешней ссылке.
Любой пример, где длинное время жизни молча становится коротким,
годится; вложенный `Vec` выбран ради части 2: в него есть куда вставить
`Cell`.

### Часть 2

```rust
{{#include ../../solutions/ch05/variance/cell.rs}}
```

```text
error: lifetime may not live long enough
  --> variance/cell.rs:12:26
   |
 8 | pub fn choose<'a>(
   |               -- lifetime `'a` defined here
...
12 |     if user.is_empty() { builtin } else { user }
   |                          ^^^^^^^ returning this value requires that `'a` must outlive `'static`
   |
   = note: requirement occurs because of the type `Cell<&str>`, which makes the generic argument `&str` invariant
   = note: the struct `Cell<T>` is invariant over the parameter `T`
```

`Cell` позволяет писать через разделяемую ссылку, поэтому тип внутри
неё ведёт себя как за `&mut`: инвариантен. Вот программа, которая
получила бы висячую ссылку, если бы `choose` компилировалась:

```rust,ignore
let builtin = vec![Cell::new("uart")];            // Vec<Cell<&'static str>>
{
    let name = String::from("spi");
    choose(&Vec::new(), &builtin)[0].set(&name);  // в builtin теперь &name
}                                                 // name освобождена
println!("{}", builtin[0].get());                 // &'static str на кучу после free
```

Для `builtin` элемент по-прежнему `&'static str`, и ничто не мешает
хранить его хоть до конца программы. Тот же отказ получит
`&'a mut Vec<&'static str>` → `&'a mut Vec<&'a str>`: через `&mut` можно
сделать `push(&name)`.

### Часть 3

```rust
{{#include ../../solutions/ch05/src/c_variance.rs:answers}}
```

Правило для составных типов: вариантность по `'a` вычисляется по всем
местам, где `'a` встречается. Ковариантное место в ковариантном —
ковариантно, контравариантное в контравариантном — ковариантно (минус
на минус), любое место внутри инвариантного — инвариантно, а если `'a`
стоит в местах разной вариантности — инвариантно.

- 1, 4 — ссылка и `*const` ковариантны по всему.
- 2 — частая ошибка — ответ «инвариантен». `&'a mut T` инвариантен по
  `T`, но по своему времени жизни ковариантен: укоротить срок
  заимствования всегда безопасно. Здесь `T = u8`, и от `'a` не зависит.
- 3 — `'a` стоит и снаружи (ковариантно), и в `T` у `&mut T`
  (инвариантно). Итог — инвариантен. Это тип, из-за которого
  «самые загадочные ошибки» из программы курса. Если функция принимает
  `&'a mut &'a str`, а `s: &str` живёт до конца блока, то после
  `f(&mut s)` переменная заимствована до конца жизни своего значения, и
  следующий `println!("{s}")` — E0502: укоротить внутреннее `'a`
  нельзя, и внешнее заимствование растягивается до него.
- 5, 6 — `*mut T` и `Cell<T>` инвариантны по `T`, как `&mut T`. Для
  `Cell` это `UnsafeCell<T>` внутри.
- 7 — аргумент функции. Функция, которая принимает короткие ссылки,
  примет и длинные, поэтому годится там, где ждут функцию для длинных:
  `fn(&'short u8)` можно передать вместо `fn(&'long u8)`. Направление
  подстановки обратное, чем у ссылок, — контравариантен.
- 8 — аргумент аргумента. `fn(fn(&'a u8))` вызывает переданную функцию,
  передавая ей `&'a u8`, — то есть *отдаёт* ссылки, как возвращаемое
  значение. Два раза контравариантно — ковариантно.
- 9 — `Box<T>` ковариантен, но `dyn Fn(&'a u8)` — это
  `dyn Fn<(&'a u8,), Output = ()>`, и параметры трейта у `dyn`
  инвариантны. Указатель на функцию той же сигнатуры (строка 7)
  контравариантен, а объект трейта — нет. Если `'a` не нужно, пишут
  `Box<dyn Fn(&u8)>`, то есть `for<'b>`, и от внешнего времени жизни тип
  не зависит вовсе.
- 10 — `str::Lines<'a>` внутри хранит `SplitInclusive<'a, char>`, а там —
  поле типа `<char as Pattern>::Searcher<'a>`. Проекция ассоциированного
  типа инвариантна по своим параметрам: компилятор не знает, что за тип
  за ней стоит. `Chars<'a>`, где внутри срезовый итератор, ковариантен.
  Отсюда заметки об инвариантности `Normalize` в разделе
  [5.6](../ch05/06-gat.md).

## D. Окна `&mut [T]`

### Часть 1

```rust

```

```text
error: lifetime may not live long enough
  --> windows/iterator.rs:26:9
   |
16 | impl<'s, T> Iterator for WindowsMut<'s, T> {
   |      -- lifetime `'s` defined here
...
22 |     fn next(&mut self) -> Option<&'s mut [T]> {
   |             - let's call the lifetime of this reference `'1`
...
26 |         Some(w) // окно заимствует `*self` только на время этого вызова
   |         ^^^^^^^ method was supposed to return data with lifetime `'s` but it is returning data with lifetime `'1`
```

`self.slice.get_mut(..)` перезаимствует срез через `&'1 mut self`, и
окно живёт `'1`. Отдать его на `'s` можно было бы, только забрав срез из
итератора. Так пишется `chunks_mut` без `unsafe`: `mem::take` забирает
срез из `self`, `split_at_mut` отрезает кусок, а хвост, которого кусок
не касается, возвращается в итератор. Для окон это невозможно:
следующее окно делит элементы с текущим, и программа из комментария
получила бы два `&mut` на `v[1]`. В стандартной библиотеке нет
`windows_mut` именно поэтому.

### Часть 2


`next` с `&mut self` и `Item<'_>` по правилу 3 — тот же `get_mut`, что в
части 1, но теперь сигнатура разрешает окну жить ровно `'1`. Детали:

`despike`:

```rust
{{#include ../../solutions/ch05/src/d_windows.rs:despike}}
```

`abs_diff` возвращает `u32`, и разность `i32::MAX - i32::MIN` = 2³² − 1
в него помещается. Наивное `(w[1] - w[0]).abs()` в отладочной сборке
паникует на переполнении, а в release разность заворачивается в −1, и
`abs` молча даёт 1.

Видимость исправления проверяет случай `[0, 50, 0, 50, 0]` в тесте
`despike_samples`. Решение, которое читает исходные значения (копия в
`Vec` и цикл по индексам), видит второе окно как `[50, 0, 50]` и
«исправляет» ноль: получается `[0, 0, 50, 0, 0]` и три исправления вместо
двух. Одалживающий итератор даёт окну актуальные значения, потому что
пишет на месте.

Абстракция ничего не стоит. Вот `despike` на x86_64:

```text

	cmp rsi, 3
	jb .LBB3_1
	mov ecx, 2
	xor eax, eax
.LBB3_4:
	mov r8d, dword ptr [rdi + 4*rcx - 8]
	cmp r8d, dword ptr [rdi + 4*rcx]
	jne .LBB3_5
	mov r9d, dword ptr [rdi + 4*rcx - 4]
	mov r10d, r9d
	sub r10d, r8d
	mov r11d, r8d
	sub r11d, r9d
	cmovl r11d, r10d
	cmp r11d, edx
	jbe .LBB3_5
	mov dword ptr [rdi + 4*rcx - 4], r8d

.LBB3_1:

```

Итератор, `Option` и `get_mut` растворились в цикле по индексу `rcx`:
окно — это `[rdi + 4*rcx - 8]`, `[rdi + 4*rcx - 4]` и `[rdi + 4*rcx]`.
Проверок границ и вызовов паники нет: длина окна 3 известна, а условие
выхода из цикла совпало с условием `get_mut`. `assert!(size > 0)`
исчез, потому что `size` — константа 3. `abs_diff` — две разности и
`cmovl`. На `thumbv7m-none-eabi` и `thumbv6m-none-eabi` вызовов паники
тоже нет; на Cortex-M3 LLVM развернул цикл по четыре окна.
