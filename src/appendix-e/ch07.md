## A. Шесть цепочек ?

```rust
{{#include ../../solutions/ch07/src/a_chains.rs:answers}}
```

Ключ ко всем шести фрагментам: `?` на `Result<T, E>` в функции,
возвращающей `Result<U, F>`, вызывает ровно один `From::from(E) -> F`
(раздел [7.1](../ch07/01-result.md)). Значит, для каждого `?` нужна одна
реализация `From<E> for F`, своя или стандартная.

- **a1** собирается. Все три ошибки превращаются в `Box<dyn Error>`
  стандартными реализациями: `io::Error` и `ParseIntError` — общей
  `impl<E: Error> From<E> for Box<dyn Error>`, а `&str` из `ok_or` —
  отдельной `From<&str> for Box<dyn Error>`.
- **a2**: для второго `?` нет `From<ParseIntError> for ConfigError`.
  Компилятор сам подсказывает, какой `From` у типа есть:

  ```text
  error[E0277]: `?` couldn't convert the error to `ConfigError`
    --> a2.rs:17:37
     |
  17 |     let b: u32 = text.trim().parse()?;
     |                              -------^ the trait `From<ParseIntError>` is not implemented for `ConfigError`
  ...
  help: the trait `From<ParseIntError>` is not implemented for `ConfigError`
        but trait `From<std::io::Error>` is implemented for it
  ```

  В ответе реализация отображает ошибку в `Range(0)`, чтобы не менять
  перечисление; в настоящем коде честнее добавить вариант
  `Parse(ParseIntError)`.
- **a3** не исправить никакой реализацией. `?` на `Option` в функции,
  возвращающей `Result`, требует `FromResidual<Option<Infallible>> for
  Result<u8, String>`: [трейт][g-trait] нестабилен, а оба типа чужие, так что
  [правило сироты][g-orphan-rule] запретило бы такую реализацию в любом случае. Нужен
  другой код, и компилятор его называет:

  ```text
  error[E0277]: the `?` operator can only be used on `Result`s, not `Option`s, in a function that returns `Result`
   --> a3.rs:3:26
    |
  3 |     let ch = frame.get(2)?;
    |                          ^ use `.ok_or(...)?` to provide an error compatible with `Result<u8, String>`
  ```

- **a4**: `From` не транзитивен. Есть `io::Error → ConfigError` и
  `ConfigError → AppError`, но `?` вызывает один `From::from` и цепочку
  из двух не ищет. Нужна прямая реализация `From<io::Error> for
  AppError` (или `load(path).map_err(ConfigError::from)?` на месте).
- **a5** собирается: `TryFromSliceError` реализует `Error`, а для
  `String` есть `From<String> for Box<dyn Error + Send + Sync>`.
  `Err(…)?` — идиома безусловного раннего возврата с преобразованием.
- **a6**: не хватает не `From`, а самого `Error`. [Общая реализация][g-blanket-impl]
  `From<E> for Box<dyn Error>` требует `E: Error`, а у `SensorFault` есть
  только `Debug` и `Display`:

  ```text
  error[E0277]: `?` couldn't convert the error: `SensorFault: std::error::Error` is not satisfied
  ...
     = note: required for `Box<dyn std::error::Error>` to implement `From<SensorFault>`
  ```

  Пустой `impl Error for SensorFault {}` закрывает вопрос: все методы
  трейта имеют реализации по умолчанию.

## B. Иерархия ошибок конфигурации

Ключевые решения.

- **Обёртка над чужой ошибкой.** `LexError` объявлен в [крейте][g-crate] решений
  главы 5, и реализовать для него `Display` или `Error` здесь не даёт
  правило сироты. Отсюда `SyntaxError(LexError)` — это ответ на первый
  вопрос «Проверь себя» после задач.
- **Куча там, где без неё никак.** `SemanticError` с двумя `String`
  занимает 48 байт. Положи его в `ConfigError` по значению — и вся
  ошибка займёт 56 байт (проверено копией типа), больше лимита в 40.
  С `Box` в `Semantic` и в рекурсивном `InFile` (без `Box` рекурсивный
  тип не имеет конечного размера, E0072) `ConfigError` занимает ровно
  40: самые большие варианты — путь (24 байта) и указатель (8).
  `io::Error` — одно слово (раздел [7.4](../ch07/04-design.md)).
- **Сообщения без причины.** Каждый `Display` говорит только о своём
  уровне, причину отдаёт `source`; тест сверяет, что ни одно звено не
  повторяет текст следующего.

## C. Цена раскрутки и цена Result

### Часть 1

```rust
{{#include ../../solutions/ch07/src/c_cost.rs:sizes}}
```

`panic = "abort"` уменьшает файл на 0,7 %, хотя многие ждут разницы в
разы. Причина в том, где собиралась стандартная библиотека: `std`
поставляется готовой, собранной с `panic = "unwind"`, и её [посадочные
площадки][g-landing-pad] и таблицы остаются в программе. [Профиль][g-profile] меняет только код
нашего крейта, и `.gcc_except_table` из 11 140 байт теряет 156.

Чтобы выигрыш стал заметным, `std` надо пересобрать (nightly,
`-Zbuild-std`) и убрать то, что тянет за собой сама [паника][g-panic]:

```console
$ cargo +nightly build --release --target x86_64-unknown-linux-gnu \
    -Zbuild-std=std,panic_abort --config 'profile.release.panic="abort"'
$ RUSTFLAGS="-Zunstable-options -Cpanic=immediate-abort" \
    cargo +nightly build --release --target x86_64-unknown-linux-gnu \
    -Zbuild-std=std,panic_abort
```

| Сборка | Файл | `.text` | `.eh_frame` | `.eh_frame_hdr` | `.gcc_except_table` |
|---|---|---|---|---|---|
| unwind | 462 096 | 260 611 | 22 008 | 4 412 | 11 140 |
| abort | 458 880 | 259 059 | 21 684 | 4 364 | 10 984 |
| build-std, abort | 475 784 | 261 250 | 27 916 | 4 636 | нет |
| build-std, immediate-abort | 66 504 | 26 244 | 4 656 | 868 | нет |

Первые две строки — rustc 1.97.0, последние две — nightly 1.101.0 от
2026-10-21. Пересобранная с `abort` библиотека теряет
`.gcc_except_table` целиком, но файл не уменьшается: `.eh_frame`
остаётся, потому что у [цели][g-target] `x86_64-unknown-linux-gnu` в описании
(`rustc +nightly -Zunstable-options --print target-spec-json`) стоит
`"default-uwtable": true`. Таблицы [раскрутки][g-unwinding] строятся для каждой
функции и без паник: по ним идут трассировка стека, отладчик и
профилировщик.

Основная масса `.text` — вовсе не раскрутка. Разбор символов сборки
`unwind` (`nm -S` по функциям, сгруппированным по крейтам):

| Крейт | Байт `.text` | Доля |
|---|---|---|
| `gimli` (разбор [DWARF][g-dwarf]) | 139 381 | 54 % |
| `rustc_demangle` | 21 188 | 8 % |
| `core::fmt` | 15 948 | 6 % |
| `alloc` | 11 918 | 5 % |
| `miniz_oxide` (сжатые отладочные секции) | 9 577 | 4 % |
| остальное | 61 350 | 23 % |

Стандартный [хук паники][g-panic-hook] умеет печатать трассу стека с именами функций и
строками (`RUST_BACKTRACE=1`), и для этого программа носит с собой
разборщик DWARF, деманглер и распаковщик. `immediate-abort` убирает хук
вместе со всем, что он тянет, и `.text` сжимается в десять раз; после
`strip` файл занимает 42 624 байта.

### Часть 2

```rust
{{#include ../../solutions/ch07/src/c_cost.rs:scale}}
```

Ассемблер (rustc 1.97.0, x86_64, `cargo asm --simplify`):

```text
ch07c_scale:
	mov eax, edi
	xor ecx, ecx
	mul esi
	mov edx, eax
	seto cl
	mov eax, ecx
	ret

ch07c_scale_code:
	mov rcx, rdx
	mov eax, edi
	mul esi
	jo .LBB23_1
	mov dword ptr [rcx], eax
	xor eax, eax
	ret
.LBB23_1:
	mov eax, -1
	ret
```

`Result<u32, Overflow>` — пара скаляров: признак в `eax`, значение в
`edx` (раздел [7.1](../ch07/01-result.md)). Версия в стиле C пишет
результат в память по указателю из `rdx`. Тела циклов сумм:

```text
; sum_result
.LBB6_3:
	mov edi, dword ptr [r12 + rbx]
	mov esi, ebp
	call r13
	test al, 1
	jne .LBB6_4
	mov eax, edx
	add r14, rax
	add rbx, 4
	cmp r15, rbx
	jne .LBB6_3

; sum_code
.LBB7_3:
	mov edi, dword ptr [r12 + r13]
	mov dword ptr [rsp + 12], 0
	mov esi, ebp
	lea rdx, [rsp + 12]
	call rbx
	test eax, eax
	jne .LBB7_6
	mov eax, dword ptr [rsp + 12]
	add r14, rax
	add r13, 4
	cmp r15, r13
	jne .LBB7_3
```

`?` в цикле стал одной проверкой `test al, 1` с переходом на выход. У
версии с кодом на каждый отсчёт три лишних обращения к памяти:
обнуление `v` в стеке, запись внутри `ch07c_scale_code` и чтение после
вызова. По времени разницы почти нет: минимум из 15 прогонов по сто
проходов миллиона отсчётов — 1,3–1,7 мс у обеих сумм на Xeon 2,8 ГГц в
облачной машине, разница в пределах шума. Запись и чтение одного
адреса подряд процессор обслуживает пересылкой из [буфера записи][g-store-buffer], а
главная цена — сам вызов.

Без `#[inline(never)]` (копия `c_cost.rs` без этих атрибутов) обе
функции [встраиваются][g-inlining] в циклы, `v` перестаёт утекать по указателю и
живёт в регистре, и циклы получаются одинаковыми:

```text
.LBB0_3:
	mov eax, r8d
	mul dword ptr [rdi + r10]
	jo .LBB0_4
	mov eax, eax
	add rcx, rax
	add r10, 4
	cmp rsi, r10
	jne .LBB0_3
```

[Векторизации][g-vectorization] нет ни там, ни там: досрочный выход при переполнении
делает итерации зависимыми. Вывод: `Result` не дороже кода возврата, а
через границу вызова, которую оптимизатор не видит насквозь, — даже
дешевле.

### Часть 2

```rust
{{#include ../../solutions/ch07/src/d_writer.rs:buffered}}
```

Ключевые решения.

- **`Option<S>` вместо `S`.** `finish` должна отдать приёмник
  вызывающему, но [переместить][g-move] поле из типа с `Drop` нельзя: деструктор
  потом получил бы структуру без поля.

  ```text
  error[E0509]: cannot move out of type `Buffered<S>`, which implements the `Drop` trait
   --> e0509.rs:4:32
    |
  4 |     pub fn finish(self) -> S { self.sink }
    |                                ^^^^^^^^^
    |                                |
    |                                cannot move out of here
    |                                move occurs because `self.sink` has type `S`, which does not implement the `Copy` trait
  ```

  `take()` оставляет на месте `None`, и деструктору после `finish`
  нечего делать. `finish` принимает `self` по значению, потому что
  после неё объекта не должно остаться: компилятор запретит писать в
  `Buffered`, у которого забрали приёмник.
- **Деструктор не паникует сам и не даёт паниковать приёмнику.**
  Ошибку `flush` некому вернуть, и она теряется; кому она важна,
  вызывает `finish`. Во время раскрутки (`thread::panicking()`) приёмник
  не трогаем совсем: паника из `send` там означала бы abort.
- **Флаг `poisoned`.** Если `send` запаниковал, а панику поймали
  `catch_unwind` и `Buffered` пережил её, состояние приёмника неизвестно.
  Флаг ставится перед вызовом и снимается после, так что после паники
  он остаётся поднятым, и деструктор, вызванный уже вне раскрутки,
  приёмник не тронет. Тесты этот случай не проверяют, но без флага он
  превратился бы во вторую панику из того же `send`.
- **Приёмник, нарушивший контракт.** `Ok(0)` зациклил бы сброс, а
  число больше остатка вывело бы срез за границу буфера. Первое
  превращается в `SinkError::Full` с данными в буфере, второе
  обрезается до остатка.

Сравнение с `std::io::BufWriter` (исходник `library/std/src/io/buffered/bufwriter.rs`
в rustc 1.97.0):

```rust,ignore
impl<W: ?Sized + Write> Drop for BufWriter<W> {
    fn drop(&mut self) {
        if !self.panicked {
            // dtors should not panic, so we ignore a failed flush
            let _r = self.flush_buf();
        }
    }
}
```

Флаг `panicked` устроен как наш `poisoned`: поднимается вокруг вызовов
внутреннего писателя. Ошибку сброса в `drop` `BufWriter` тоже молча
теряет, а узнать о ней можно, только сбросив буфер раньше: явным
`flush` или через `into_inner`, которая, как `finish`,
при ошибке возвращает сам `BufWriter` вместе с ней. Отличие в том, что `BufWriter` не
смотрит на `thread::panicking()` и сбрасывает буфер и во время
раскрутки чужой паники: если внутренний писатель в этот момент
запаникует, процесс завершится через abort.

## П7. Ошибки протокола

Эталон — крейт `project/telemetry-frame`, разобранный в разделе
[7.10](../ch07/10-project.md). Ответы на вопросы:

1. После `BadCrc` поле длины — часть испорченных данных. Поток
   `ACK, ACK с длиной 0 → 10, MEAS, ACK` (в длине второго кадра
   инвертированы два бита): `decode_at(…, 8)` берёт нагрузкой первые 10
   байт измерения и получает `BadCrc`. Пропуск по длине перепрыгивает на
   смещение 26, в середину измерения, и цикл, который пропускает кадры
   по длине, принимает только `[(0, Ack), (34, Ack)]`: измерение
   потеряно. `Resync` сдвигается на байт, находит маркер со смещения 16
   и принимает `[(0, Ack), (16, Measurement), (34, Ack)]`.
2. Наибольшая длина нагрузки 240 байт, поэтому после целого заголовка
   приёмник ждёт не больше 240 байт. На 115200 бод при 8N1 байт занимает
   10 битовых интервалов, 11 520 байт в секунду, и 240 байт приходят за
   20,8 мс. По тайм-ауту приёмник должен сделать то же, что при `Resync`:
   отбросить первый байт и искать маркер дальше. `Recovery` зависит
   только от ошибки, а тайм-аут — от времени, которого у функции разбора
   нет: решение принимает приёмник с часами (главы 12–13, а на
   микроконтроллере — таймер, главы 26–27).
3. Дать заголовку собственную контрольную сумму, например CRC-8 по
   байтам 0..6. Порча длины обнаружится, как только придёт заголовок.
   Цена — байт на кадр, для подтверждения из 8 байт это 12,5 %. Общая
   CRC-16 по кадру остаётся и защищает нагрузку.
4. Реализовать `Debug` для `FrameError` вручную через `Display`:

   ```rust,ignore
   impl fmt::Debug for FrameError {
       fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
           fmt::Display::fmt(self, f)
       }
   }
   ```

   `verbose` на Cortex-M3 сжимается с 9556 до 6052 байт (столбец
   `text`), всего на 260 байт больше `direct`, а `llvm-nm` находит
   `<FrameError as Debug>::fmt` в 12 байт вместо выведенного в 996. Тесты на [хосте][g-host]
   теряют структурный вывод: `assert_eq!` при падении печатает
   сообщение, а не `Short { need: 18, have: 5 }`. Если это мешает,
   выведенный `Debug` можно оставить для хоста
   (`#[cfg_attr(not(target_os = "none"), derive(Debug))]`), а ручной
   включать только для целей без ОС.
