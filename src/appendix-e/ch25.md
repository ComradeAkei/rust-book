# Глава 25. Вычисления при компиляции

Код решений: `solutions/ch25`. Все задачи — обычные тесты (`cargo test
-p ch25-solutions`, общий файл `tests-shared/ch25.rs`). Библиотека —
`no_std` и собирается на три цели Cortex-M. Тесты `rustc_*` запускают
закреплённые rustc и cargo; они пропускаются под Miri и в задании CI со
случайной раскладкой, остальное проходит Miri.

## A. Шесть объявлений

```rust,ignore
{{#include ../../solutions/ch25/src/a_sections.rs:answers}}
```

```console
$ llvm-nm a.o
00000000 D BOOTS
00000000 D CALIB
00000000 B EVENTS
00000000 R GAINS
00000000 B SCRATCH
00000000 R ZEROS
```

Секцию выбирают два вопроса по порядку. Первый: можно ли объект менять
после запуска? `static` без `mut` и без внутренней изменяемости менять
нельзя, и ему место в неизменяемой секции — во flash. Второй, только для
изменяемых: начинается ли объект с нулей? Тогда `.bss`, иначе `.data`.

Ловушка — `ZEROS`. Правило «нули — в `.bss`» из C верно только для
*изменяемых* объектов: `.bss` — область ОЗУ, которую код запуска
обнуляет, и она записываемая. Неизменяемый массив нулей rustc кладёт в
`.rodata`, как любой другой неизменяемый `static`: 64 байта flash вместо
64 байт ОЗУ. В C так же: `static const uint32_t zeros[16];` (без
инициализатора, то есть нули) arm-none-eabi-gcc 13.2 кладёт в
`.rodata`, а `static uint32_t zb[16];` — в `.bss`.

`BOOTS` и `EVENTS` — атомики: тип с внутренней изменяемостью, и
неизменяемый `static` всё равно меняется через `&self`. Поэтому оба — в
ОЗУ, а дальше решает начальное значение: 1 — `.data`, 0 — `.bss`.
`SCRATCH` и `CALIB` — `static mut`, тот же выбор по значению.

Имена секций — с суффиксом объекта: `llvm-objdump -t` показывает
`.rodata.GAINS`, `.data.CALIB`. Это входные секции, по одной на объект
(`-fdata-sections` в терминах gcc, у rustc так всегда), и скрипт
компоновки собирает их в выходные `.rodata`, `.data`, `.bss` (раздел
[8.8](../ch08/08-sections.md)).

## B. CRC-32 и синус без build.rs

```rust,ignore
{{#include ../../solutions/ch25/src/b_crc.rs:crc32}}
```

Таблица — та же, что у zlib: `CRC32_TABLE[1] = 0x77073096`,
`CRC32_TABLE[255] = 0x2D02EF8D` (тест `b_crc32_table`), а `crc32`
сверен с побитовым вариантом на всех одно- и многих двухбайтовых входах
и на 3000 байтах данных. `crc32` — `const fn`, поэтому `CHECK` — тоже
вычисление при компиляции, а не просто литерал: проверка при сборке
защищает и таблицу, и цикл.

```rust,ignore
{{#include ../../solutions/ch25/src/b_crc.rs:sine}}
```

Синус — ряд Тейлора до x¹⁹. На отрезке [0, π/2] первый отброшенный член
x²¹/21! не больше (π/2)²¹ / 21! ≈ 2,6 · 10⁻¹⁶, а ряд знакочередующийся,
так что ошибка ряда не больше этого члена — порядка последнего разряда
`f64`, как и ошибки округления при суммировании. После умножения на 32767
это около 10⁻¹¹ — бесконечно далеко от границы округления, если только
значение не попадает почти точно на `k + 0,5`. Таких точек в таблице нет, и тест
`b_sine_matches_build_rs` подтверждает: все 257 значений совпали с
таблицей `build.rs` из задачи 8.B бит в бит.

Округление: значения неотрицательны, и `(y + 0.5) as i16` — то же, что
`y.round()`. `as` из `f64` в целое отбрасывает дробную часть и в
константах работает так же, как при выполнении.

**`build.rs` против `const fn`.** Плюсы `const fn`: нет второго языка
(сценарий сборки — та же Rust, но другая программа со своим `main` и
вводом-выводом), нет сгенерированного файла, функцию можно вызвать из
теста, и она работает и при выполнении. Ошибка в формуле видна в
исходнике рядом с таблицей, а не в генераторе.

Минусы — скорость и возможности. Интерпретатор констант медленнее
машинного кода на порядки. Та же `sine_table` на 4096, 16 384 и 65 536
элементов (rustc 1.97, x86-64, `--emit metadata`) вычисляется за 0,19,
0,57 и 2,1 секунды — и это при каждой пересборке крейта, а не однажды.
`build.rs` построил бы таблицу на 64 Ки за миллисекунды, и cargo не
перезапускает его, пока не изменились его входы. Кроме того, `build.rs`
может читать файлы (таблица из CSV датчика, SVD), звать библиотеки и
`f64::sin`. `build.rs` нужен, когда входные данные — файл, когда
вычисление требует `std` или стороннего крейта, когда таблица большая.

## C. ip!

```rust,ignore
{{#include ../../solutions/ch25/src/c_ip.rs:parse}}
```

Разбор — конечный автомат на `while` без `for`, итераторов и `?`
(раздел [25.2](../ch25/02-const-fn.md)). Лишний шаг при `i == b.len()`
закрывает последний октет тем же кодом, что и точка, — без дублирования
после цикла. Проверка `value > 255` на каждой цифре держит `value` не
больше 2559: переполнения нет при любой длине строки.

Ведущий ноль: «0» — октет, «00» и «01» — нет. Условие `digits == 1 &&
value == 0` срабатывает на второй цифре, если первая была нулём. Тест
`c_parse` сверяет каждый случай с `str::parse::<Ipv4Addr>` — разбор `std`
тоже отвергает ведущие нули, именно из-за восьмеричного прочтения в
`inet_aton`.

```rust,ignore
{{#include ../../solutions/ch25/src/c_ip.rs:fail}}
```

`fail` возвращает `!` — тип, у которого нет значений, — и потому
подходит в обе ветки `match` в `ipv4`. Сообщение — литерал на каждый
вариант: `panic!("{}", …)` в константе — E0015.

```rust,ignore
{{#include ../../solutions/ch25/src/c_ip.rs:macro}}
```

Весь смысл макроса — в блоке `const`. Без него `ip!("10.0.0.300")` в
теле функции — обычный вызов `ipv4` при выполнении и паника в поле. С
ним — ошибка сборки:

```text
error[E0080]: evaluation panicked: IPv4: октет больше 255
 --> c_range.rs:1:42
  |
1 | pub fn server() -> core::net::Ipv4Addr { sut::ip!("10.0.0.300") }
  |                                          ^^^^^^^^^^^^^^^^^^^^^^ evaluation of `server::{constant#0}` failed inside this call
  |
note: inside `ipv4`
 --> solutions/ch25/src/c_ip.rs:88:19
  |
88 |         Err(e) => e.fail(),
  |                   ^^^^^^^^
note: inside `IpError::fail`
```

Но только при сборке: `cargo check` и пробы с `--emit metadata` ошибку
в блоке `const` внутри функции не видят (раздел
[25.3](../ch25/03-checks.md)). Поэтому `rustc_c_macro` собирает пробы
`--emit link`. Хотите, чтобы ловил и `cargo check`, — кладите адреса в
свободные константы: `const GATEWAY: Ipv4Addr = ip!("…");`.

`$s:literal` вместо `$s:expr` — договор: адрес написан в месте вызова.
С `$s:expr` макрос принял бы и имя строковой константы, а переменную
`let` отверг бы ошибкой E0435 «attempt to use a non-constant value in a
constant». С `literal` переменная — «no rules expected `s`». Обе ошибки
указывают на аргумент, так что выбор — о том, что считать допустимым
вводом, а не о качестве сообщения.

## D. Бюджет ОЗУ

```rust,ignore
{{#include ../../solutions/ch25/build.rs:build}}
```

Путь к `memory.x` — от `CARGO_MANIFEST_DIR`: текущий каталог сценария
сборки — каталог пакета, но опираться на это хуже, чем на явный путь.
Три строки `rerun-if-…` — договор с cargo: без `rerun-if-changed` на
`memory.x` правка карты памяти не пересобрала бы крейт, а без
`rerun-if-env-changed` смена `CH25_RAM_BUDGET` не перезапустила бы
сценарий. При первой же строке `rerun-if-…` cargo перестаёт следить за
всеми файлами пакета, поэтому `build.rs` указан явно (раздел
[8.5](../ch08/05-build-rs.md)).

```rust,ignore
{{#include ../../solutions/ch25/src/d_budget.rs:parse}}
```

`env!` — строка при компиляции; `parse_budget` превращает её в число в
константе. Ошибка в переменной («12K») — паника при вычислении `BUDGET`,
то есть ошибка сборки с текстом «CH25_RAM_BUDGET: не десятичное число».

```rust,ignore
{{#include ../../solutions/ch25/src/d_budget.rs:check}}
```

Вторая проверка — приём для числа в сообщении. Тип константы — `[(); 0]`,
а значение — массив длины `USED - BUDGET` (с насыщением, чтобы при
запасе не было переполнения). Если длины не совпали, проверка типов
печатает обе:

```text
error[E0080]: evaluation panicked: буферы драйверов не помещаются в бюджет ОЗУ
  --> solutions/ch25/src/d_budget.rs:76:15
   |
76 | const _: () = assert!(USED <= BUDGET, "буферы драйверов не помещаются в бюджет ОЗУ");
   |               ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ evaluation of `d_budget::_` failed here

error[E0308]: mismatched types
  --> solutions/ch25/src/d_budget.rs:80:20
   |
80 | const _: [(); 0] = [(); USED.saturating_sub(BUDGET)];
   |          -------   ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ expected an array with a size of 0, found one with a size of 3936
   |          |
   |          expected because of the type of the constant
```

Буферы занимают 768 + 2048 + 4096 + 1024 = 7936 байт, бюджет по
умолчанию — 16 КиБ − 4 КиБ = 12 288, запас 4352 байта. Журнал на 8 КиБ
ещё помещается (12 032 байта), а на 12 КиБ — нет, и вторая ошибка
скажет, что не хватило 3840 байт. `[(); N]` ничего не занимает: `()` — тип нулевого размера.

Размеры берутся из типов через `size_of`, а не пишутся числами:
поменяли `[u8; 4096]` на `[u8; 8192]` — изменилась и проверка. На
настоящей прошивке так считают только то, что программист объявил
сам; полный расход ОЗУ знает компоновщик, и последнюю проверку делает
он. `static mut LOG: [u8; 20000]` в прошивке `ch25-flash` даёт ошибку
компоновки:

```text
rust-lld: error: section '.bss' will not fit in region 'RAM': overflowed by 3628 bytes
```

Но это уже после компиляции всего крейта и всех зависимостей, и в
сообщении — секция, а не драйвер, который её раздул.
