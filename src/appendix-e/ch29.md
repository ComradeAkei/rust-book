`kfree` или лестница `goto`, и о ней надо помнить на каждом новом выходе.

lockdep проверяет это на выходе из системного вызова: в ядре мьютекс
можно держать сколько угодно, но вернуться с ним в пространство

останется захваченным: следующий `sensor_last` из любого процесса
уснёт в `mutex_lock` навсегда.

охранник `guard` отпускает мьютекс в `Drop` на любом выходе из функции,
и на `return Err(…)` тоже.

Класс блокировки в C — место `mutex_init`, имя — его аргумент

Ответы на вопросы. **Исключены типами** три ошибки: утечка на пути ошибки
(владение и `Drop`), обращение после освобождения (перемещение и E0382),
забытый `unlock` (охранник). **В oops** превратилась запись за конец:
проверка границы во время выполнения. Oops здесь лучше, потому что запись
не случилась: C молча портит соседний объект kmalloc-32, и без KASAN это
всплывёт потом и в чужом коде. А KASAN главы — generic, по документации
ядра — режим «intended for debugging» с «significant performance and
memory overheads»; в рабочих ядрах x86 его нет. Rust останавливает поток
выполнения в той же строке, с файлом и номером строки в журнале, в любом
ядре. Цена тоже видна: утечки после паники, `insmod` убит, ядро
помечено `D`.

**Остались** две ошибки. Сон под спин-блокировкой — свойство контекста
выполнения: можно ли спать, зависит от того, кто и под чем вызвал
функцию, а это значение счётчика вытеснения во время выполнения. В
`fsleep` об этом — только строка документации: «This function can only
be used in a nonatomic context». Порядок блокировок — свойство всей
программы: каждая функция по отдельности верна, ошибка — в паре
вызовов, а типы смотрят на одну функцию за раз. Чтобы увидеть обе
ошибки, нужно знать, кто кого вызывает и под какими блокировками, —
это знает lockdep во время выполнения, а не компилятор.

**Зачем Rust, если есть KASAN и lockdep.** Отладочное ядро нашло все шесть
ошибок C — но только потому, что модули вызывали фрагменты так, чтобы
ошибка сработала. Путь ошибки (фрагменты 1 и 3) в обычном тесте не
выполняется никогда, а отладочное ядро видит только выполненный код. Ещё
оно медленное и прожорливое, и даже на нём понадобились уловки: отдельная
загрузка на фрагмент, `slub_debug=U`, два прохода kmemleak. Rust закрывает
первые три ошибки на всех путях, включая невыполненные, и пятую — в любом
ядре. А четвёртую и шестую по-прежнему ловят lockdep и
`CONFIG_DEBUG_ATOMIC_SLEEP` — Rust их не заменяет.

## B. Число Фибоначчи из параметра

```rust,ignore
{{#include ../../solutions/ch29/modules/ch29_b.rs:fib}}
```

`checked_add` и `?` по `Option`: первое переполнение — `None`. Цикл
делает `n - 1` сложений и останавливается на F(n), поэтому F(93)
считается, хотя F(94) уже не помещается. Сеанс:

```text
# insmod /lib/ch29_b.ko
info:   ch29_b: fib(10) = 55
# rmmod ch29_b
info:   ch29_b: выгружен
…
# insmod /lib/ch29_b.ko n=93
info:   ch29_b: fib(93) = 12200160415121876738
# rmmod ch29_b
info:   ch29_b: выгружен
# insmod /lib/ch29_b.ko n=94
insmod: Value too large for defined data type (os error 75)
err:    ch29_b: fib(94) не помещается в u64
# grep ch29_b /proc/modules
```

Ответы на вопросы. **Обычный `+`** переполнился бы на F(94), и ядро
главы, собранное с `CONFIG_RUST_OVERFLOW_CHECKS=y` (по умолчанию
включено), запаниковало бы: «attempt to add with overflow», дальше —
oops, как у команды `overflow` в разделе [29.9](../ch29/09-oops.md).
Программа в пространстве пользователя с `--release` собрана без
проверок переполнения и молча напечатала бы F(94) по модулю 2⁶⁴ —
1293530146158671551 вместо 19740274219868223167. Для ядра выбор по
умолчанию разумен: неверное число здесь — чаще всего размер буфера или
индекс, и тихий перенос опаснее паники.

**Модуль с ошибкой в `init`.** `init` вернул `EOVERFLOW`, и
`do_init_module` идёт по пути ошибки: модуль переходит в состояние
`GOING`, уведомления, `free_module`. Тот убирает каталог
`/sys/module/ch29_b` (`mod_sysfs_teardown`), освобождает память
параметров (`destroy_params`), вынимает модуль из списка модулей — а
`/proc/modules` и есть этот список — и освобождает всю его память,
код и данные (`free_mod_mem`). Сам модуль на Rust ничего не выделил:
`Fib` не создан, ронять нечего. Выдели он что-нибудь до `return Err`,
это уронил бы компилятор, как в фрагменте 1 задачи A.

Ответы на вопросы. **Строк больше** — на разбор и форматирование: в C
это `kstrtou64_from_user` и `scnprintf`, а в Rust — 15 и 16 строк.
Без них модуль на Rust короче эталона, 86 строк против 90: у него нет

`misc_deregister` — это делают `#[vtable]` и `Drop`. **Выходы по
ошибке** в Rust видны все, потому что каждый — `?` или `Err(…)` в
тексте. В C пять строк, но путей больше: `kstrtou64_from_user` сама
возвращает `-EFAULT`, `-EINVAL` и `-ERANGE`, `simple_read_from_buffer` —
`-EFAULT`, и они уходят наружу через `return ret` неназванными.

**На дисциплине в эталоне** держится вот что:

- `counter` защищён `counter_lock` только по соглашению — ничто в
  типах их не связывает, и чтение `counter` без мьютекса компилируется;
- `mutex_unlock` перед `return -EOVERFLOW` — ручной, его легко
  потерять при правке (фрагмент 3 задачи A);
- `file->private_data` — `void *`, и что там `struct reader`, знает
  только программист; в Rust тип указателя — `Self::Ptr`, и
  `kiocb.file()` возвращает `&Reader`;
- `kfree` и `mutex_destroy` в `release` — парные к `open`; в Rust это
  `Drop` у `Pin<KBox<Reader>>`;
- `mutex_init` до первого `mutex_lock`: в Rust нет способа получить
  `Reader` с неинициализированным мьютексом — `try_pin_init!` отдаёт
  значение только целиком;
- `r->len` не больше `sizeof(r->text)`, потому что так обещает
  `scnprintf`; в Rust срез `snap.text[..snap.len]` проверяется;
- `__user` у указателей видит только sparse, не компилятор; модуль на
  Rust указателя пользователя не получает вовсе.

Одно правило не держат ни типы, ни компилятор, в обоих модулях оно —
дисциплина: порядок блокировок, `snap` раньше `COUNTER` (фрагмент 6
задачи A).

**Отдельный мьютекс снимку** нужен, потому что одно открытие — это
одна `struct file`, а не один процесс. Её делят процессы после `fork`,
дескрипторы после `dup`, все потоки процесса, и её можно передать
через сокет с `SCM_RIGHTS`. Два одновременных `read` по одной `struct
file` ядро не упорядочивает: `f_pos_lock` берётся только для обычных
файлов и каталогов (`FMODE_ATOMIC_POS` в `fs/open.c`), а `pread` позицию
файла не трогает вовсе. Rust не дал бы забыть: `read_iter` получает
`&Reader` — общую ссылку, `MiscDevice::Ptr` обязан быть `Send + Sync`, и
изменить снимок можно только через тип с внутренней изменяемостью,
который `Sync`, — мьютекс.

  статическая строка `c"…"`;

- статика группы и атрибутов живёт, пока модуль загружен, а `Drop`
  снимает kobject и его файлы раньше, чем ядро освободит память модуля:
  после удаления файла sysfs не вызывает его `show` и `store`, а
  начатые вызовы удаление дожидается (`kernfs_drain`);
- `kobject_put` — ровно один раз на ссылку из

(`tools/memory-model/Documentation/explanation.txt`) это гонка данных: два
обращения к одному месту на разных процессорах, одно из них — запись и

Проверки:

- переходник сравнивает `data_source` у `iov_iter` с `ITER_DEST` —
  `assert_eq!` в `IovIterDest::from_raw`, с вызовом
  `core::panicking::assert_failed` на случай неравенства;
- `ki_pos` отрицательная — `EINVAL` (`usize::try_from`), `js` в коде;
- `ki_pos + n` — с проверкой переполнения, два вызова
  `panic_const_add_overflow`;
- `n == 0` при непустом источнике — `EFAULT`.

Абстракции, которые не встроились:

- вызовы `<kernel::error::Error>::to_errno` в переходнике и
  `AtomicRepr<i32>::as_ptr` в теле — мелкие функции крейта `kernel`,
  оставшиеся вызовами при `-Os`;
- `rust_helper_mutex_assert_is_held` — функция C, которая в ядре без
  lockdep пуста (`lockdep_assert_held`), но вызывается: конструктор
  охранника `Guard::new` проверяет, что мьютекс захвачен;
- `rust_helper_atomic_read_acquire` — чтение атомика, в C это
  встроенная функция, а из Rust — вызов переходника.

Разная работа:

- модуль на Rust на каждом `read` читает параметр `simple` —
  выбор между `simple_read_from_buffer` и своим путём (раздел
  [29.7](../ch29/07-chardev.md)). Значение параметра — в `SetOnce`, и
  `value()` сначала читает с `Acquire` его состояние, задан ли параметр
  при загрузке, потом берёт значение или умолчание;
- путь копирования свой: срез, `is_empty`, `copy_to_iter`, обновление
  позиции, — а у C всё это внутри `simple_read_from_buffer`, вне
  модуля;
- и мимо модуля: у C в таблице `.read`, а абстракция Rust даёт
  `.read_iter`, и `vfs_read` идёт через `new_sync_read` (она встроена в
  `vfs_read`): заполняет `struct kiocb` и `iov_iter` на стеке. Эту
  работу не видно ни в инструкциях модуля, ни в трассе.

**С `-O2` вместо `-Os`.** Проверено сборкой: то же ядро с
`CONFIG_CC_OPTIMIZE_FOR_PERFORMANCE=y` (Rust получает
`-Copt-level=2`, C — `-O2`) и те же два модуля. `notes_read` — те же
27 инструкций. Переходник — 24 вместо 27, тело — 88 вместо 86: вызовы
`to_errno` и `AtomicRepr::as_ptr` исчезли — эти функции встроились, —
а инструкций почти не убавилось, и в сумме 112 против 113. Остались:

- два вызова `rust_helper_*`: переходники — отдельный объектный файл
  C, `rust/helpers/helpers.o`, и способа встроить их в код Rust в ядре
  7.0 нет;
- все проверки: они — часть смысла программы, оптимизатор вправе
  убрать проверку, только если докажет, что она не сработает, а
  `ki_pos` приходит от пользователя;
- разная работа — параметр, свой путь копирования, `new_sync_read`.

Порядок величин от уровня оптимизации не зависит: C отдаёт работу
одной функции ядра, Rust делает её у себя — с проверками и через
переходники.
