# 28. Системное программирование под Linux

## Мотивирующая проблема

Программа на C под Linux говорит с ядром через системные вызовы, и у
каждого вызова свои правила, которые компилятор не проверяет:

- **ошибка — это −1 и `errno`.** Глобальная (на самом деле локальная
  для потока) переменная, которую затирает любой следующий вызов, даже
  `close` на пути ошибки. Забыть проверить результат — обычное дело;
  компилятор не скажет ни слова;
- **дескриптор — просто `int`.** Его надо закрыть на каждом пути выхода
  из функции, и ровно один раз. Утечка дескриптора не видна, пока
  процесс не упрётся в предел; двойной `close` закрывает чужой файл,
  если номер успел достаться другому потоку;
- **`fork` в многопоточной программе.** Ребёнок получает копию памяти с
  мьютексами, захваченными потоками, которых у него нет. Первый же
  `malloc` в ребёнке может зависнуть навсегда;
- **обработчик сигнала выполняется посреди любой инструкции.** `printf`
  или `malloc` в нём — взаимная блокировка или испорченный буфер раз в
  неделю;
- **`EINTR`.** Сигнал прерывает `read`, и каждый цикл чтения обязан это
  пережить;
- **`mmap` отдаёт указатель.** Сколько он живёт, можно ли писать и что
  будет, если файл укоротят, — знает только программист.

## Что делает Rust

Rust не добавляет ядру новых вызовов. Меняется то, что о них знают
типы.

- **Ошибка — значение.** `io::Result<T>` возвращает код ошибки вместе с
  результатом; его нельзя прочитать «не тот» и нельзя забыть: `?` или
  явный `match`. rustix и nix делают так же для вызовов, которых нет в
  std.
- **Дескриптор во владении.** `OwnedFd` закрывает дескриптор в `Drop` —
  на каждом пути, включая `?` и панику; `BorrowedFd<'a>` не переживёт
  владельца. Создать владельца из голого номера — `unsafe`: это и есть
  место, где можно ошибиться.
- **`fork` — `unsafe`.** Обычный запуск программы, `Command`, идёт через
  `posix_spawn` и не копирует память. Код в ребёнке до `exec` — только
  через `unsafe fn pre_exec`, и правила для этого кода написаны в его
  документации.
- **Сигналы.** В std их нет совсем, кроме одного решения до `main`:
  игнорировать SIGPIPE. Обработчик через nix — `unsafe`, а `signalfd`
  превращает сигнал в чтение дескриптора и уводит его из обработчика в
  обычный код.
- **`mmap` — `unsafe` конструктор с контрактом.** Отображение становится
  значением с `Drop`, а срез из него живёт не дольше отображения.

Глава идёт от вызова к системе: цена вызова и четыре уровня обёрток,
дескрипторы, процессы, сигналы, память и страницы, epoll, файлы /proc.
В конце — шаг сквозного проекта: журнал кадров станции на `mmap` и демон,
который пишет в него и правильно обрабатывает сигналы.

## Код главы

Библиотека — `code/ch28`: по модулю на раздел и программы в `src/bin`.
Опыты, которые меняют обработчики сигналов, делают `fork` или считают
страничные сбои всего процесса, — отдельные программы: тест запускает
каждую в своём процессе и сверяет вывод с текстом. Тесты из
`tests/strace.rs` запускают программы под strace; без strace они
пропускаются. Пример на C — `code/ch28/c`. Задачи — в `exercises/ch28` и
`solutions/ch28`.

```console
$ cargo test -p ch28                       # модули, программы, демон журнала, strace
$ cargo run -p ch28 --bin layers           # раздел 28.1
$ cargo run -p ch28 --release --bin syscost
$ bash code/ch28/c/run.sh                  # copy.c: GCC, clang, valgrind
$ cargo test -p ch28-solutions             # задачи A–D
```

Крейты — libc 0.2.191, rustix 1.1.5 и nix 0.31.3. Вывод снят с rustc
1.97.0 на x86-64: ядро 6.18 в виртуальной машине Firecracker, glibc 2.39,
strace 6.8, четыре процессора Xeon на 2,1 ГГц. Времена и счётчики
страничных сбоев зависят от ядра и машины: в CI (Ubuntu 24.04) они
другие, и тесты сверяют их с запасом, а точные строки — только там, где
вывод от машины не зависит.
