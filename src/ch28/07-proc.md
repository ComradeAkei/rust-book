# 28.7. /proc и /sys

<div class="box ref">

**Справка: файлы, которых нет.** `/proc` и `/sys` — не диски, а
интерфейсы ядра в виде файлов. Содержимое файла ядро генерирует в
момент чтения: `/proc/self/maps` — по таблице отображений процесса,
`/proc/self/status` — по полям задачи. `/proc/PID/…` — сведения о
процессе (`self` — ссылка на свой), `/proc/meminfo`, `/proc/cpuinfo` —
о машине. `/sys` устроен строже: один файл — одно значение, и файлы
отражают объекты ядра — устройства, драйверы, параметры подсистем;
многие из них можно писать, чтобы менять настройки.

</div>

## Файлы без размера

```rust,ignore
{{#include ../../code/ch28/src/bin/procfs.rs:sizes}}
```

```console
$ cargo run -q -p ch28 --bin procfs -- sizes
/proc/self/maps                  stat:     0, прочитано:  3175
/proc/self/status                stat:     0, прочитано:  1424
/sys/devices/system/cpu/online   stat:  4096, прочитано:     4
```

Размер файлов `/proc` по `stat` — ноль: ядро не знает его, пока не
сгенерирует текст. У файлов `/sys` размер — 4096, страница, хотя в
`online` всего 4 байта, `0-3\n`. Правило одно: такие файлы читают до
конца — до `read`, вернувшего 0, — и никогда не выделяют буфер по
`metadata().len()`. `fs::read` и `read_to_string` так и делают: размер из
`statx` для них только подсказка ёмкости, а читают они до конца потока.
Тест `proc_files_have_no_size`.

## /proc/self/maps без копий

Строка maps — одно отображение адресного пространства:

```rust,ignore
{{#include ../../code/ch28/src/procfs.rs:region}}
```

Разбор держится на трёх деталях формата, которые проверяет тест
`parses_file_anonymous_and_named_lines`. Первые пять полей разделены
одним пробелом, а перед путём ядро добивает пробелами до колонки. У
безымянной анонимной памяти строка кончается пробелом после inode — пути
нет совсем. А сам путь может содержать пробелы: `/tmp/a b (deleted)`.
Поэтому `splitn(6, ' ')`, а не `split_whitespace`: шестой кусок — всё,
что осталось от строки, с ведущими пробелами, которые снимает
`trim_start`.

`Region<'a>` заимствует путь из строки, и разбор ничего не выделяет:
`regions(maps)` — итератор по строкам, `region_of` — первое отображение,
содержащее адрес. Программа `procfs maps` находит, где у неё лежат код,
куча, анонимное отображение, стек и vDSO:

```rust,ignore
{{#include ../../code/ch28/src/bin/procfs.rs:maps}}
```

```console
$ cargo run -q -p ch28 --bin procfs -- maps
имя для анонимной памяти: Invalid argument (os error 22)
код main   r-xp    356 КиБ  procfs
Box        rw-p    132 КиБ  [heap]
журнал     rw-p   1036 КиБ  (без имени)
локальная  rw-p    144 КиБ  [stack]
           r-xp      8 КиБ  [vdso]
всего отображений: 30
```

Код — исполняемое отображение файла программы, `Box` — в `[heap]`,
области `brk`, локальная переменная — в `[stack]`. Отображение на 1 МиБ
стало 1036 КиБ: ядро склеило его с соседним анонимным отображением с
теми же правами — это видно и в тесте `own_mapping_is_found_by_address`,
который поэтому проверяет «не меньше». Восемь килобайт `[vdso]` — те
самые, через которые `Instant::now` обходится без системного вызова
(раздел [28.1](01-syscalls.md)). Тест `proc_maps_of_own_process`.

Первая строка — неудача, и честная:

```rust,ignore
{{#include ../../code/ch28/src/procfs.rs:name}}
```

`PR_SET_VMA_ANON_NAME` даёт анонимной памяти имя, и в maps вместо пустого
пути появляется `[anon:ch28-journal]`. Аллокатор или среда выполнения
могут подписать так свои арены, и в отчёте о памяти процесса будет видно,
чья она. Но это — опция сборки ядра, `CONFIG_ANON_VMA_NAME`, и ядро этой
машины собрано без неё: `EINVAL`. Тест `named_mapping_if_supported`
проверяет имя, если ядро его приняло.

## status: память процесса

```rust,ignore
{{#include ../../code/ch28/src/procfs.rs:status}}
```

```rust,ignore
{{#include ../../code/ch28/src/bin/procfs.rs:rss}}
```

```console
$ cargo run -q -p ch28 --bin procfs -- rss
в начале:            VmRSS    2.1 МиБ
после mmap 64 МиБ:   VmRSS    2.2 МиБ
после касания:       VmRSS   66.2 МиБ
после munmap:        VmRSS    2.2 МиБ
пик, VmHWM:          67656 kB
```

`VmRSS` — сколько памяти процесса сейчас в RAM. `mmap` на 64 МиБ её не
меняет: страниц ещё нет (раздел [28.5](05-mmap.md)). Касание каждой
страницы — плюс 64 МиБ, `munmap` — минус. `VmHWM` — пик за всю жизнь
процесса. Тест `rss_follows_touched_pages` проверяет приращения с
запасом. Тот же счётчик в библиотеке мерить нельзя: тесты одного
двоичного файла идут потоками одного процесса, и соседний тест меняет
`VmRSS` в любой момент. Поэтому опыт — отдельная программа.

## Процессоры

У списков процессоров в ядре один формат на всё:
`/sys/devices/system/cpu/online`, `Cpus_allowed_list` в status,
`cpuset.cpus` в cgroup — `0-3,8,10-11`:

```rust,ignore
{{#include ../../code/ch28/src/procfs.rs:cpus}}
```

```rust,ignore
{{#include ../../code/ch28/src/bin/procfs.rs:cpus}}
```

```console
$ cargo run -q -p ch28 --bin procfs -- cpus
в сети (/sys):              [0, 1, 2, 3]
разрешены потоку (status):  [0, 1, 2, 3]
available_parallelism:      4
```

Здесь все три числа совпадают, но в общем случае это три разных
вопроса. В сети — сколько процессоров у машины. Разрешены — маска
привязки потока (`taskset`, `sched_setaffinity`). А
`thread::available_parallelism` учитывает ещё и квоту cgroup: контейнер
с `--cpus=2` на 64-ядерной машине увидит 2 — и пул потоков, который
берёт число рабочих потоков отсюда (так по умолчанию делают rayon и
tokio), не создаст шестьдесят четыре.

<div class="box trap">

**Ловушка: /proc/PID — гонка с номером.** Номер процесса освобождается,
когда родитель забрал статус, и может достаться новому процессу. Код,
который нашёл процесс в `/proc`, а потом читает `/proc/PID/status` или
шлёт ему `kill`, может обратиться к другому процессу. Надёжно — через
`pidfd_open` (ядро 5.3): дескриптор на конкретный процесс, который не
спутать с новым, и `pidfd_send_signal` вместо `kill`. В std у дочернего
процесса это `std::os::linux::process::ChildExt::pidfd` (нестабильно).

</div>
