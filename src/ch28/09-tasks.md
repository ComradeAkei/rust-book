# 28.9. Задачи

Все задачи решаются кодом. Заготовки — в `exercises/ch28`, тесты, общие
для заготовок и решений, — в `tests-shared/ch28.rs`. Заготовки
собираются как есть: функции с `todo!()` паникуют только при вызове.
Программы `ch28-ops` (операции задачи A), `ch28-shell` и `ch28-search`
уже написаны и зовут ваши функции.

$ cargo test -p ch28-exercises            # все задачи
$ cargo test -p ch28-exercises c_         # одна задача
$ cargo test -p ch28-solutions            # эталон
$ cargo run -p ch28-exercises --bin ch28-shell

## B. ls -la без std::fs

Повторите вывод `ls -la` одного каталога, не трогая `std::fs`: записи
каталога — `getdents64` через `rustix::fs::RawDir`, сведения о файле —
`statat` с `AtFlags::SYMLINK_NOFOLLOW`, цель ссылки — `readlinkat`,
имена владельцев — из `/etc/passwd` и `/etc/group`, прочитанных через
`rustix::fs::openat` и `read`.

```rust,ignore
{{#include ../../exercises/ch28/src/b_ls.rs:list}}
```

- Записи — включая `.` и `..`, в порядке байтов имени: так сортирует
  `ls` при `LC_ALL=C`;
- права — десять символов, с `s`/`S` для setuid и setgid и `t`/`T` для
  sticky на месте `x`: строчная — бит x есть, прописная — нет;
- время — `ГГГГ-ММ-ДД ЧЧ:ММ` в UTC, переводить дни в дату придётся самим;
- колонки выровнены по самой длинной записи: числа вправо, имена
  владельцев — влево;
- первая строка — `total N`, где N — сумма `st_blocks` в килобайтах;
- у ссылки после имени — ` -> цель`.

Тест `b_ls_matches_gnu_ls` строит каталог со всеми видами записей —
файлы с разными правами, setuid, жёсткая ссылка, каталог со sticky,
ссылка на файл и висячая ссылка, FIFO, имя с пробелом и кириллицей, —
ставит им известное время и сравнивает ваш вывод с выводом
`LC_ALL=C TZ=UTC ls -la --time-style='+%Y-%m-%d %H:%M'` байт в байт.
`b_ls_of_missing_dir_is_an_error` ждёт ошибку, а не пустой список.
Устройства (`b`, `c`) в задачу не входят.

Вопросы к отчёту. Почему `ls -la` показывает про ссылку сведения о самой
ссылке, а не о файле, на который она указывает, — и что изменится без
`SYMLINK_NOFOLLOW`? Почему `total` — не сумма размеров? Когда имена
владельцев из `/etc/passwd` разойдутся с тем, что напечатает `ls`?

Сообщения, которые проверяют тесты, перечислены в документации модуля
`exercises/ch28/src/c_shell.rs`: `ch28-shell: [код N]`,
`ch28-shell: [сигнал SIGINT]`, `ch28-shell: имя: команда не найдена`,
`[pgid]` для фонового задания. Условия:

- каждое задание — своя группа процессов: все стадии конвейера в группе
  первой (`Command::process_group`);
- статус задания — статус последней стадии; убитая сигналом — 128 +
  номер, как в sh;
- если stdin — терминал, оболочка в своей группе, игнорирует SIGINT,
  SIGQUIT, SIGTSTP, SIGTTIN и SIGTTOU, отдаёт терминал группе задания
  переднего плана (`tcsetpgrp`) и забирает обратно, когда задание
  кончилось. Ctrl-C прерывает задание, а не оболочку;
- оболочка не ждёт фоновое задание и сообщает `[pgid] готово`, когда
  оно кончилось.

Тесты запускают `ch28-shell` со сценарием на stdin:
`c_pipelines_and_redirects`, `c_statuses_and_errors`,
`c_builtin_cd_changes_the_shell_itself`, `c_background_job_does_not_block`.
Разбор строки проверяют `c_parse_pipelines_redirects_and_quotes` и
`c_parse_errors`. А `c_ctrl_c_interrupts_only_the_job` открывает
псевдотерминал, запускает оболочку в новом сеансе с этим терминалом
как управляющим, даёт ей `sleep 30` и шлёт в терминал байт 0x03 — Ctrl-C.
Ждёт `ch28-shell: [сигнал SIGINT]`, новую подсказку, ответ на
`echo жив` и код 3 после `exit 3`.

Подсказки. Справка о группах и терминале — в разделе
[28.3](03-processes.md). Каналы — `rustix::pipe::pipe_with(CLOEXEC)` и
`Stdio::from(OwnedFd)`. Игнорирование SIGINT ребёнок унаследует (раздел
[28.4](04-signals.md)) — возвращать сигналы к умолчанию придётся в
`pre_exec`.

Вопросы к отчёту. Что будет, если оболочка не закроет свои копии концов
канала после запуска стадий? Почему `tcsetpgrp` для задания зовут и
оболочка, и сам ребёнок в `pre_exec`? Зачем оболочке игнорировать
SIGTTOU, если она никогда не пишет в терминал из фона?

## D. Поиск в большом файле: read против mmap

Найдите строку в файле на несколько гигабайт тремя способами: `read` в
буфер, `mmap`, `mmap` с `madvise(MADV_HUGEPAGE)`.

```rust,ignore
{{#include ../../exercises/ch28/src/d_search.rs:api}}
```

`find_read` возвращает смещение первого вхождения от начала файла. Игла
может лечь на границу двух чтений — значит, хвост буфера надо перенести.
`find_mmap` обходится без копий: срез отображения и есть файл. Тесты:
`d_read_and_mmap_agree_with_naive_search` — 20 000 байт из алфавита
`abc`, шесть игл, буферы от 1 до 4096 байт; `d_needle_across_buffer_boundary`
— игла начинается за 3 байта до конца первого буфера;
`d_empty_file_and_long_needle` — пустой файл и игла длиннее файла.

Потом замер. Программа `ch28-search` создаёт файл и меряет все три
способа дважды: с холодным кэшем — страницы файла выгнаны через
`posix_fadvise(POSIX_FADV_DONTNEED)` — и с тёплым:

```rust,ignore
{{#include ../../exercises/ch28/src/bin/ch28-search.rs:measure}}
```

```console
$ cargo run -q -p ch28-exercises --release --bin ch28-search -- gen /var/tmp/hay 2048
$ cargo run -q -p ch28-exercises --release --bin ch28-search -- run /var/tmp/hay
```

Файл на 2 ГиБ, игла `иголка-в-стоге` — в последней строке. Каталог
выберите на настоящем диске: в `/tmp` на tmpfs файл и так в памяти, и
холодного кэша не будет.

Вопросы к отчёту — объясните разницу во времени через страничные сбои и
TLB. Сколько сбоев у `mmap` и сколько страниц в файле; сколько байт
ядро отображает за один сбой? Почему у `read` сбоев почти нет, хотя он
тоже трогает каждую страницу кэша? Что быстрее с тёплым кэшем — копия в
`read` или сбои и промахи TLB у `mmap`? Как огромные страницы меняют
число сбоев и записей TLB, и почему с холодным кэшем они могут
оказаться медленнее обычных? Если на вашей машине есть доступ к PMU,
проверьте объяснение через `perf stat -e dTLB-load-misses`.
