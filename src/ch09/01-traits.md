# 9.1. Трейт и его реализации

## Определение трейта

Трейт перечисляет, что тип должен уметь. Датчики из введения в Rust
описываются так:

```rust
{{#include ../../code/ch09/src/sensor.rs:trait}}
```

Метод без тела, `read`, *обязательный*: каждый тип, реализующий
`Sensor`, обязан его написать. Методы с телом, `name` и `average`,
получают *реализацию по умолчанию*, которую тип может принять или
заменить своей. Метод по умолчанию вправе вызывать другие методы трейта:
`average` ничего не знает о конкретном датчике и пользуется только
`read`. Первый параметр, `&self` или `&mut self`, — получатель, как
`void *ctx` в C, только типизированный. Данных в трейте нет: он
описывает поведение, а поля остаются в типах.

## Реализации

Блок `impl Sensor for Тип` — реализация трейта для типа:

```rust
{{#include ../../code/ch09/src/sensor.rs:impls}}
```

`Thermo` заменил `name`, `Counter` оставил реализацию по умолчанию и
будет называться «датчик». Пропустить обязательный метод нельзя:

```rust
impl Sensor for Silent {}
```

```text
error[E0046]: not all trait items implemented, missing: `read`
 --> e0046.rs:3:1
  |
3 | impl Sensor for Silent {}
  | ^^^^^^^^^^^^^^^^^^^^^^ missing `read` in implementation
  |
  = help: implement the missing item: `fn read(&mut self) -> i32 { todo!() }`
```

Это та самая ошибка, которую в C допустил инициализатор `counter_ops`,
только найдена она при компиляции. Сигнатуры тоже сверяются: метод с
другим типом получателя или результата — ошибка E0053, а не
неопределённое поведение при вызове через неправильно приведённый
указатель.

<div class="box c">

**Как в C.** Пара `struct sensor_ops` + `void *ctx` разделяет то, что в
Rust живёт вместе: таблица описывает методы, контекст — данные, и связь
между ними держится на честном слове. В Rust реализация привязана к
типу, а получатель имеет тип `&mut Thermo`, поэтому подать
`thermo_read` данные счётчика невозможно. Таблицы указателей при этом
нет вовсе: какую функцию вызвать, компилятор решает по типу.

</div>

## Три записи одного вызова

Метод трейта — обычная функция, у которой получатель стоит первым
аргументом. Три вызова ниже — один и тот же вызов:

```rust
{{#include ../../code/ch09/src/sensor.rs:ufcs}}
```

Запись через точку короче, но работает, только если трейт виден в
текущей области: `use ch09::sensor::Sensor;`. Без `use` компилятор
ответит E0599 и подскажет, какой трейт импортировать. Полная форма
`<Thermo as Sensor>::read` нужна, когда одно имя есть у нескольких
трейтов:

```text
error[E0034]: multiple applicable items in scope
 --> e0034.rs:6:35
  |
6 | pub fn f() -> &'static str { Both.name() }
  |                                   ^^^^ multiple `name` found
  |
note: candidate #1 is defined in an impl of the trait `Sensor` for the type `Both`
…
note: candidate #2 is defined in an impl of the trait `ch09::supertrait::Named` for the type `Both`
…
help: disambiguate the method for candidate #1
  |
6 - pub fn f() -> &'static str { Both.name() }
6 + pub fn f() -> &'static str { Sensor::name(&Both) }
…
```

Тип `Both` реализует и `Sensor`, и `Named` из раздела
[9.3](03-supertraits.md), и у обоих трейтов есть `name`. Компилятор не
выбирает за программиста, а требует уточнить. В C две таблицы с полем
`name` просто разные структуры, и такой вопрос не возникает, но и
выбрать по ошибке не ту таблицу ничто не мешает.

## Обобщённая функция

Трейт становится интерфейсом, когда функция принимает любой тип, который
его реализует:

```rust
{{#include ../../code/ch09/src/sensor.rs:generic}}
```

`S: Sensor` — *ограничение трейта* (trait bound): внутри функции у `s`
доступны методы `Sensor` и ничего больше. Компилятор не создаёт одну
`poll_twice` на все типы. Для каждого типа, с которым её вызвали, он
делает отдельную копию, где `S` заменён настоящим типом, — это
*мономорфизация*, и подробно её разбирает глава [10](../ch10/index.md). В копии для
`Thermo` вызов `read` прямой, и его можно встроить:

```console
$ cargo asm -p ch09 --lib --simplify ch09_poll_thermo
ch09_poll_thermo:
	mov eax, dword ptr [rdi]
	add eax, eax
	ret
$ cargo asm -p ch09 --lib --simplify --no-default-features --target thumbv7m-none-eabi ch09_poll_thermo
ch09_poll_thermo:
	push {r7, lr}
	mov r7, sp
	ldr r0, [r0]
	lsls r0, r0, #1
	pop {r7, pc}
```

От двух вызовов `read` осталась одна загрузка и удвоение. Компилятор
видит тело `Thermo::read`, знает, что оно ничего не пишет, и читает
`raw` один раз. Сравните с семью инструкциями C, где таблица
перечитывается перед каждым вызовом.

`Counter::read` помечена `#[inline(never)]`, чтобы показать, как
выглядит невстроенный вызов метода трейта:

```console
$ cargo asm -p ch09 --lib --simplify --no-default-features --target thumbv7m-none-eabi ch09_poll_counter
ch09_poll_counter:
	push {r4, r5, r7, lr}
	add r7, sp, #8
	mov r4, r0
	bl <ch09::sensor::Counter as ch09::sensor::Sensor>::read
	mov r5, r0
	mov r0, r4
	bl <ch09::sensor::Counter as ch09::sensor::Sensor>::read
	add r0, r5
	pop {r4, r5, r7, pc}
```

`bl` с именем функции — прямой вызов, адрес записан в самой инструкции.
На x86-64 тот же код выглядит иначе:

```console
$ cargo asm -p ch09 --lib --simplify ch09_poll_counter
ch09_poll_counter:
	push rbp
	push r14
	push rbx
	mov rbx, rdi
	mov r14, qword ptr [rip + <ch09::sensor::Counter as ch09::sensor::Sensor>::read@GOTPCREL]
	call r14
	mov ebp, eax
	mov rdi, rbx
	call r14
	add eax, ebp
	pop rbx
	pop r14
	pop rbp
	ret
```

Это не диспетчеризация по типу. Для Linux на x86-64 rustc собирает
позиционно-независимый код, и адрес функции из другой единицы
компоновки берёт из таблицы GOT, которую заполняет загрузчик. Функция
одна и известна при компиляции, поэтому адрес загружен в `r14` один раз
на оба вызова. На Cortex-M позиционно-независимого кода нет, и там
вызов прямой.

| | C, `ops->read(ctx)` | Rust, `S: Sensor` |
|---|---|---|
| Какую функцию вызвать | решает указатель во время работы | решает тип при компиляции |
| Вызов | косвенный, таблица перечитывается | прямой или встроенный |
| Забытый метод | NULL, падение при вызове | E0046 при компиляции |
| Чужие данные | `void *` принимает что угодно | получатель `&mut Thermo` |
| Цена | одна копия кода | копия кода на каждый тип |

Последняя строка — честная цена: три типа датчиков дадут три копии
`poll_twice`. Для маленьких функций это выгодно, их всё равно встраивают,
а для больших превращается в рост прошивки. Как с этим жить, разбирает
глава 10, а когда нужна именно таблица указателей — глава 11.

<div class="box hood">

**Под капотом.** Метод по умолчанию тоже мономорфизуется: `average` для
`Thermo` и для `Counter` — две разные функции, и в каждой вызов `read`
прямой. Метод по умолчанию — не функция «базового класса», которую
вызывают все, а шаблон, который компилятор подставляет в каждую
реализацию, где его не заменили.

</div>

<div class="box trap">

**Ловушка.** Метод по умолчанию видит только то, что объявлено в
трейте. `average` не может обратиться к `self.raw`, даже если все
нынешние датчики хранят отсчёт в поле `raw`: тип `Self` внутри трейта
неизвестен. Если методу по умолчанию нужны данные, трейт должен дать к
ним доступ обязательным методом, как `read`.

</div>

<div class="box check">

**Проверь себя.** Что вернёт `Counter { total: 10, last: 4 }.average(4)`
и почему не 6? Почему в `ch09_poll_thermo` одна загрузка, а не две, а в
`poll_twice` из C — две загрузки `s->ops`? Что изменится в ассемблере
`ch09_poll_counter`, если убрать `#[inline(never)]`?

</div>
