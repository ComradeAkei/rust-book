# 9.2. Ассоциированные типы и константы

## Ассоциированный тип

Кроме методов, трейт может требовать от реализации тип. АЦП выдаёт
12-разрядный отсчёт, акселерометр — три оси сразу, и общий трейт
источника не знает заранее, каким будет отсчёт:

```rust
{{#include ../../code/ch09/src/assoc.rs:source}}
```

`type Sample` — *ассоциированный тип* (associated type): каждая реализация называет свой,
а ограничения `Copy + Default` действуют на любой выбор. Обобщённый код
пишет `S::Sample` и получает тип отсчёта из реализации: `fill` для `Adc`
принимает `&mut [u16]`, для `Accel` — `&mut [[i16; 3]]`. Вызывающему
ничего уточнять не нужно, `let x = adc.sample()` даёт `u16`.

## Ассоциированный тип или параметр трейта

То же можно попробовать записать параметром трейта:

```rust
{{#include ../../code/ch09/src/assoc.rs:source-of}}
```

Разница в числе реализаций. Ассоциированный тип — *выход*: для данного
типа реализация `Source` одна, и `Sample` определён однозначно.
Параметр — *вход*: `SourceOf<u16>` и `SourceOf<u32>` — два разных трейта,
и `Adc` реализует оба. Тогда из одного вызова не понять, какой нужен:

```text
error[E0283]: type annotations needed
 --> e0283.rs:2:49
  |
2 | pub fn f() { let mut adc = Adc { next: 7 }; let x = adc.get(); }
  |                                                 ^       --- type must be known at this point
  |
  = note: multiple `impl`s satisfying `Adc: SourceOf<_>` found in the `ch09` crate:
          - impl SourceOf<u16> for Adc;
          - impl SourceOf<u32> for Adc;
help: consider giving `x` an explicit type
```

С подсказкой `let x: u32 = adc.get();` или `SourceOf::<u32>::get(&mut
adc)` всё компилируется. Правило выбора простое: если у типа должна
быть ровно одна реализация, тип отсчёта — ассоциированный; если
реализаций может быть несколько для разных типов, это параметр. В
стандартной библиотеке `Iterator::Item` — ассоциированный тип
(итератор выдаёт что-то одно), `From<T>` — параметр (`u32` строится и
из `u8`, и из `u16`), а у `Add<Rhs>` есть и то и другое: правый операнд
— вход, `type Output` — выход.

## Ассоциированные константы

Трейт может требовать и константу. Регистры периферии описываются
адресом, который известен при компиляции:

```rust
{{#include ../../code/ch09/src/assoc.rs:register}}
```

Каждый регистр SysTick — отдельный тип без полей, а его адрес и имя —
константы реализации. В разделе [6.9](../ch06/09-registers.md) регистры
PL011 описывала структура `repr(C)`, наложенная на карту памяти: там
смещения задаёт раскладка, а адрес блока — указатель. Структура удобна
для блока регистров, идущих подряд. Тип на регистр удобен, когда
драйвер должен требовать конкретный регистр в сигнатуре, а свойства
регистра — адрес, доступ на чтение и запись, значение после сброса —
проверять при компиляции; задача [9.B](08-tasks.md) доводит этот подход
до драйвера того же PL011. `Reg<R>` хранит только `PhantomData<R>`, поэтому
`size_of::<Reg<SystCsr>>()` равен нулю: значение такого типа ничего не
занимает, всё знание о регистре в типе. Методы `read` и `write` берут
адрес из `R::ADDR`.

Константа `ALIGNED` проверяет выравнивание адреса. Она ассоциирована с
`Reg<R>`, то есть вычисляется отдельно для каждого `R`, и только когда
её используют: строка `let () = Self::ALIGNED;` в `read` и `write`
заставляет компилятор вычислить её для каждого регистра, к которому
программа обращается. Регистр с невыровненным адресом объявить можно,
а обратиться к нему — нет:

```text
error[E0080]: evaluation panicked: адрес регистра не выровнен на 4
  --> …/library/core/src/panic.rs:62:9
   |
62 |         $crate::panicking::panic_fmt($crate::const_format_args!($($t)+));
   |         ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ evaluation of `ch09::assoc::Reg::<Bad>::ALIGNED` failed here
…
note: the above error was encountered while instantiating `fn Reg::<Bad>::write`
 --> e0080.rs:7:23
  |
7 | pub fn f() { unsafe { Reg::<Bad>::write(0) } }
  |                       ^^^^^^^^^^^^^^^^^^^^
```

Сообщение на русском — строка из `assert!`: константное вычисление
паникует так же, как обычный код, только паника превращается в ошибку
компиляции.

<div class="box trap">

**Ловушка.** Это ошибка *после мономорфизации*: компилятор находит её,
когда создаёт машинный код для `Reg::<Bad>::write`. `cargo check` машинный
код не создаёт и пропустит её молча, `cargo build` остановится. Обобщённая
функция, которую никто не вызвал, тоже не проверяется: если обращение к
`Reg::<Bad>` лежит в `fn f<T>()` без единого вызова, сборка пройдёт.
Проверка срабатывает ровно там, где регистр действительно используется,
и это скорее достоинство, но в CI нужен `cargo build`, а не только
`cargo check`.

</div>

<div class="box hood">

**Под капотом.** Начиная с Rust 1.79 ту же проверку можно записать
прямо в теле метода константным блоком: `const { assert!(R::ADDR % 4 ==
0, "…") }`. Блок вычисляется при мономорфизации так же, как
ассоциированная константа. Константа в `impl` удобна, когда проверку
используют несколько методов: она пишется один раз.

</div>

## Константа в машинном коде

Функция запуска таймера пишет три регистра:

```rust
{{#include ../../code/ch09/src/assoc.rs:systick}}
```

```console
$ cargo asm -p ch09 --lib --simplify --no-default-features --target thumbv7m-none-eabi ch09_systick_start
ch09_systick_start:
	push {r7, lr}
	mov r7, sp
	movw r1, #57360
	movt r1, #57344
	str r0, [r1, #4]
	movs r0, #0
	str r0, [r1, #8]
	movs r0, #5
	str r0, [r1]
	pop {r7, pc}
```

От трейта, `PhantomData` и обобщённых методов не осталось ничего.
`movw`/`movt` собирают в `r1` число 0xE000_E010 из двух половин (57344 —
это 0xE000, 57360 — 0xE010), адрес `SYST_CSR`. Остальные два регистра
компилятор адресует смещениями `#4` и `#8` от того же `r1`: он знает все
три константы и заметил, что они идут подряд. Порядок записей — RVR,
CVR, CSR — тот же, что в исходнике: `write_volatile` запрещает их
переставлять. На других целях константа выглядит по-своему:

```console
$ cargo asm -p ch09 --lib --simplify --no-default-features --target thumbv6m-none-eabi ch09_systick_start
ch09_systick_start:
	push {r7, lr}
	add r7, sp, #0
	ldr r1, .LCPI10_0
	str r0, [r1, #4]
	movs r0, #0
	str r0, [r1, #8]
	movs r0, #5
	str r0, [r1]
	pop {r7, pc}
.LCPI10_0:
$ cargo asm -p ch09 --lib --simplify ch09_systick_start
ch09_systick_start:
	mov eax, 3758153744
	mov dword ptr [rax + 4], edi
	mov dword ptr [rax + 8], 0
	mov dword ptr [rax], 5
	ret
```

У Cortex-M0 нет `movw` и `movt`, поэтому 32-разрядная константа лежит
в литеральном пуле сразу за функцией, и `ldr` загружает её относительно
`pc`. Сам пул `--simplify` прячет вместе с остальными директивами; без
этого флага за меткой `.LCPI10_0` видна строка `.long 3758153744`, то
есть 0xE000_E010. На x86-64 адрес — непосредственный операнд `mov`. Во всех трёх
случаях это ровно тот код, который дал бы `#define` в C: адрес
известен при компиляции, а проверки типов и выравнивания уже пройдены
и в машинный код не попали.

<div class="box c">

**Как в C.** Обычная запись регистра в C —
`#define SYST_CSR (*(volatile uint32_t *)0xE000E010)`. Машинный код тот
же, но у макроса нет типа: функция не может потребовать «дай мне
регистр SysTick», любой адрес пишется так же, как любой другой, а
проверку выравнивания придётся поставить `_Static_assert` рядом с
каждым `#define` вручную. В Rust регистр — тип, свойства регистра —
константы трейта, а проверка написана один раз для всех.

</div>

## SysTick в QEMU

Прошивка `firmware/ch09-systick` запускает таймер через те же типы и
ждёт трёх периодов по флагу COUNTFLAG:

```rust
{{#include ../../firmware/ch09-systick/src/main.rs:main}}
```

```console
$ cd firmware && cargo run --release -q -p ch09-systick
SYST_CSR по адресу 0xe000e010
SYST_RVR по адресу 0xe000e014
SYST_CVR по адресу 0xe000e018
SYST_RVR = 99999
SysTick: 3 периода по 100000 тактов отсчитаны
```

Вывод одинаков на Cortex-M3, M0 и M4F, его проверяет
`firmware/run-demos.sh`. SysTick описан в архитектуре ARMv7-M и есть в
каждом Cortex-M3 и M4. В ARMv6-M он необязателен, и у настоящего
nRF51 с микроплаты micro:bit его нет; QEMU моделирует его на всех
трёх платах, поэтому прошивка проходит и там.
