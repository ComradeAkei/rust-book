## A. Где будет таблица

Пять `match` лежат в `code/ch02/src/task_a.rs`:

```rust
{{#include ../../code/ch02/src/task_a.rs:list}}
```

Для каждой функции предскажите, во что LLVM превратит `match` в
release-сборке для x86_64, и запишите ответы в
`exercises/ch02/src/a_tables.rs`. Варианты — из перечисления
`ch02::task_a::Lowering`: таблица переходов (`JumpTable`), таблица
значений в памяти (`MemoryTable`), значения, упакованные в константу и
извлекаемые сдвигом (`RegisterTable`; битовая маска из раздела
[2.5](05-lowering.md) — её частный случай с однобитными значениями),
формула без таблиц и переходов (`Formula`) и сравнения (`Compares`). К
каждому ответу добавьте комментарий: почему именно так. Не заглядывайте
в ассемблер, пока не запишете все пять, потом запустите
`cargo test -p ch02-exercises task_a`. Тест соберёт файл сам, определит
способ по инструкциям и для каждой ошибки покажет код функции:

```text
№3 ch02a_uart_reg       ваш ответ: Compares, на самом деле: ...
```

Тест компилирует тем rustc, который выбрал cargo, а способ зависит от
версии LLVM. Разборы написаны для 1.97.0 из `rust-toolchain.toml`.

Вторая часть — пороги. LLVM строит таблицу переходов, только если веток
достаточно много и значения достаточно плотные. Плотность — это число
веток, делённое на размах значений: ветки 0, 1, 2 и 9 дают 4 / 10 = 40 %.
Найдите опытом три числа и запишите их в тот же файл:

- `MIN_CASES` — наименьшее число веток (не считая `_`), при котором
  таблица переходов вообще возможна;
- `MIN_DENSITY` — наименьшую плотность в процентах при `opt-level` 2 и 3;
- `MIN_DENSITY_SIZE` — то же при оптимизации размера, `opt-level = "s"`
  и `"z"`.

Опыты удобно ставить в своём маленьком крейте: функция с нужными
ветками, у каждой из которых свой код (иначе получится таблица значений,
а не переходов), и

```console
$ cargo asm --lib имя_функции
$ cargo asm --lib --config 'profile.release.opt-level="s"' имя_функции
```

Тест `density_thresholds` проверит ваши пороги на ста с лишним функциях
с тремя и четырьмя ветками и размахом от 3 до 60 при `opt-level` 3 и `"s"` и
покажет первые расхождения.

В отчёте ответьте: почему `ch02a_method` не стала таблицей значений, хотя
каждая её ветка только возвращает константу? Затем снимите ассемблер тех
же пяти функций для `thumbv7m-none-eabi` и `thumbv6m-none-eabi`. Где
способ отличается от x86_64 и почему?

## B. Декодер Thumb

Инструкции Cortex-M0 (ARMv6-M) — 16-битные слова, кроме `bl` и
нескольких системных. Напишите декодер подмножества: MOV, ADD, SUB, B и
LDR в кодировках, перечисленных в `code/ch02/src/thumb.rs`:

```rust
{{#include ../../code/ch02/src/thumb.rs:insn}}
```

В описании каждого варианта — битовая маска: буквы обозначают поля, `0` и
`1` — фиксированные биты. Напишите функцию
`decode(hw: u16) -> Option<Insn>` в `exercises/ch02/src/b_thumb.rs`
одним `match` по старшим битам слова, уточняя кодировку охранными
условиями и вложенными `match`. Всё, что не входит в подмножество, —
`None`, в том числе `udf` и `svc`, которые занимают значения условия
1110 и 1111 в кодировке `b<c>`. Печать инструкции в синтаксисе
`llvm-objdump` уже написана: это `Display` для `Disasm { insn, addr }`.

Тест сверяет ваш декодер с дизассемблером. Готовый корпус
`tests-shared/ch02-thumb.txt` — 67 краевых кодировок (наибольшие
смещения, `sp` и `pc` в регистровых полях, `udf`, `svc`) и все различные
16-битные слова из вывода `llvm-objdump -d` прошивки `ch06-uart`,
собранной для Cortex-M0.
Каждая 16-битная инструкция корпуса проверяется: инструкции подмножества
ваш декодер должен напечатать слово в слово, остальные — отвергнуть.
Второй тест собирает все прошивки из `firmware/` для Cortex-M0 и проверяет
декодер на их дизассемблере. Ему нужен `llvm-objdump` (пакет `llvm` или
`rustup component add llvm-tools`, приложение [D](../appendix-d.md)), и
он запускается отдельно:

```console
$ cargo test -p ch02-exercises task_b
$ cargo test -p ch02-exercises task_b -- --ignored --nocapture
```

В отчёте ответьте: какая доля инструкций ваших прошивок попала в
подмножество (тест с `--nocapture` печатает оба числа)? Какие кодировки
подмножества компилятор не использовал ни разу? Во что LLVM скомпилировал
ваш `match` по старшим пяти битам: в таблицу переходов на 32 элемента или
во что-то другое?

## C. Лексер

Мини-язык команд станции телеметрии состоит из таких токенов:

- пробелы ` `, `\t`, `\r`, `\n` и комментарии `// …` до конца строки и
  `/* … */` без вложенности — пропускаются;
- идентификаторы `[A-Za-z_][A-Za-z0-9_]*`;
- целые `[0-9][0-9_]*`, `0x[0-9a-fA-F_]+`, `0b[01_]+`, в каждом хотя бы
  одна цифра после префикса, значение помещается в `u64`; сразу за числом
  не может стоять буква, цифра или `_`;
- строки `"…"` без перевода строки внутри, с экранированием `\\`, `\"`,
  `\n`, `\t`, `\0`, `\xHH`;
- операторы `->` `==` `!=` `<=` `>=` `<<` `>>` `&&` `||` и
  `+ - * / % = < > & | ! ( ) { } [ ] , ; . :`, всегда самый длинный из
  подходящих.

Типы токенов и ошибок даны в `code/ch02/src/lexer.rs`:

```rust
{{#include ../../code/ch02/src/lexer.rs:types}}
```

Напишите две функции с одной сигнатурой
`fn(&str) -> Result<Vec<Token>, LexError>`:

1. `lex` в `exercises/ch02/src/c_lexer.rs` — конечный автомат. Один цикл
   `loop` с меткой читает вход по байту, `match` по состоянию решает, что
   делать с байтом. Байт, который закончил токен, но сам ему не
   принадлежит (пробел после идентификатора), разбирается заново из
   начального состояния через `continue` с меткой. Без регулярных
   выражений и без заглядывания вперёд.
2. `lex_regex` в `exercises/ch02/src/c_regex.rs` — тот же лексер на крейте
   `regex`.

Ошибка — первая встреченная, с тем смещением, которое описано у её
варианта. Тесты проверяют написанные вручную примеры, двадцать ошибочных
входов, триста случайных программ из `ch02::lexer::generate` с заранее
известным разбором и, наконец, две тысячи испорченных программ, на
которых оба лексера обязаны ответить одинаково, вплоть до смещения
ошибки. Затем сравните скорость:

```console
$ cargo run -p ch02-exercises --release --example lexbench
```

Пример разбирает случайную программу из полумиллиона токенов (около
8 МБ) обоими лексерами и печатает время и пропускную способность.

В отчёте ответьте: во сколько раз различаются лексеры и почему? Где
`regex` тратит время, которого нет у автомата? Можно ли ускорить
версию на регулярных выражениях, не отказываясь от них?

## D. Взаимная блокировка в одну строку

В `exercises/ch02/src/d_deadlock.rs` объявлен кэш `Mutex<Option<u32>>` и
пять функций. Каждая делает одно и то же: если кэш пуст, записывает туда
`FRESH` и возвращает его, иначе возвращает то, что лежит в кэше. Каждая
проверяет кэш своей конструкцией и захватывает мьютекс выражением
`cache.lock().unwrap()` прямо в ней, без переменной:

| Функция | Проверка | Запись |
|---|---|---|
| `via_if` | `if cache.lock().unwrap().is_none()` | в ветке `if` |
| `via_if_let` | `if let Some(v) = *cache.lock().unwrap()` | в `else` |
| `via_match` | `match *cache.lock().unwrap()` | в ветке `None` |
| `via_let_else` | `let Some(v) = *cache.lock().unwrap() else { … }` | в `else` |
| `via_while_let` | `while let None = *cache.lock().unwrap()` | в теле цикла |

Файл компилируется дважды: в крейте `ch02-exercises` (edition 2024) и в
`ch02-exercises-2021` (edition 2021) через атрибут `#[path]`. Поэтому
синтаксис в нём должен быть общим для обеих редакций: цепочки
`if let ... &&` не годятся.

1. Напишите пять функций.
2. Не запуская тестов, заполните `HANGS_2021` и `HANGS_2024`: зависнет ли
   каждая функция на пустом кэше в каждой редакции.
3. Запустите обе проверки. Тест вызывает функцию в отдельном потоке и
   считает её зависшей, если за полсекунды она не вернулась, а мьютекс
   остался захвачен. Он же проверяет, что ваши предсказания отвечают на
   вопросы задачи: есть функция, которая виснет в 2021 и не виснет в
   2024, и есть функция, которая виснет в обеих.
4. Напишите `fixed` — функцию с тем же поведением, которая не виснет ни в
   одной редакции.
5. Уберите `#[allow(clippy::correctness)]` в
   `exercises/ch02-2021/src/lib.rs` и запустите [clippy][g-clippy] для обоих крейтов,
   затем ещё раз с дополнительной проверкой:

   ```console
   $ cargo clippy -p ch02-exercises -p ch02-exercises-2021
   $ cargo clippy -p ch02-exercises -p ch02-exercises-2021 -- -W clippy::significant_drop_in_scrutinee
   ```

В отчёте для каждой функции объясните результат через области
временных значений из раздела [2.6](06-temporaries.md). Какие из ваших
функций нашёл каждый анализатор, где он промолчал и где ошибся? Чем
`fixed` лучше остальных, даже когда они не виснут, если кэш заполняют
несколько потоков сразу?
