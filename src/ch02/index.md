# 2. Выражения, управление потоком, сопоставление с образцом

## Мотивирующая проблема

Обработчик команд на C, в котором две ошибки, обычные для `switch`:

```c
{{#include ../../code/ch02/c/switch.c}}
```

```console
$ gcc -O2 switch.c && ./a.out                       # GCC 13.3, x86_64
mode_name(MODE_SLEEP) = ?
reply_len(0x01) = 8
```

Режим `MODE_SLEEP` добавили в перечисление, а `mode_name` не поправили, и
функция молча возвращает `"?"`. В `reply_len` после `len = 4;` забыт
`break`, выполнение проваливается в следующую ветку, и ответ на запрос
статуса получает длину 8 вместо 4. Обе ошибки компилятор видит, но
промолчит, пока его не попросят:

```console
$ gcc -O2 -Wall -Wextra switch.c
switch.c: In function 'mode_name':
switch.c:11:5: warning: enumeration value 'MODE_SLEEP' not handled in switch [-Wswitch]
   11 |     switch (m) {
      |     ^~~~~~
switch.c: In function 'reply_len':
switch.c:25:13: warning: this statement may fall through [-Wimplicit-fallthrough=]
   25 |         len = 4;
      |         ~~~~^~~
switch.c:26:5: note: here
   26 |     case 0x02: /* версия; в ветке выше забыт break */
      |     ^~~~
```

`-Wswitch` входит в `-Wall`, а `-Wimplicit-fallthrough` у GCC только в
`-Wextra`. Clang 18 не предупреждает о провале ни с `-Wall`, ни с
`-Wextra`: флаг нужно включать по имени. И это предупреждения, а не
ошибки: сборка проходит. Достаточно добавить в `switch` ветку `default`, и
`-Wswitch` замолкает навсегда: о новом значении перечисления сообщит
только `-Wswitch-enum`, которого нет ни в `-Wall`, ни в `-Wextra`.
Наконец, в C переменная типа `enum mode` может хранить любое значение
целого типа, на котором основано перечисление, а не только перечисленные,
так что даже полный `switch` не гарантирует, что одна из веток
выполнится.

## Что делает Rust

- `match` обязан покрыть все значения. Пропущенный вариант — ошибка
  компиляции E0004, и новый вариант перечисления ломает сборку в каждом
  `match`, где его не учли (если там нет ветки `_`).
- Провала между ветками нет. Ветка — одно выражение, а несколько значений
  объединяются в одной ветке через `|` и диапазоны.
- Значение перечисления всегда одно из объявленных: создать `Mode` со
  значением 7 нельзя без `unsafe`, а такое значение — неопределённое
  поведение (раздел [6.3](../ch06/03-enums.md)).
- `match`, `if`, `loop` и блоки — выражения со значением. Тернарный
  оператор и расширения вида `({ ... })` из GCC не нужны.
- [Образцы][g-pattern] разбирают [срезы][g-slice], кортежи и структуры: разбор кадра протокола
  записывается без арифметики индексов.

В машинный код `match` превращается теми же способами, что и `switch`:
[таблицей переходов][g-jump-table], деревом сравнений, битовой маской, а иногда формулой
без единого перехода. Какой способ выберет LLVM, зависит от значений в
ветках, и раздел [2.5](05-lowering.md) показывает каждый на x86_64 и на
Cortex-M.

```console
$ cargo test -p ch02 -p ch02-solutions -p ch02-solutions-2021   # примеры и решения
$ cargo asm -p ch02 --lib ch02_exec 0                           # таблица переходов из раздела 2.5
$ cargo run -p ch02 --release --example dispatch                # цена ошибки предсказателя
$ cargo +nightly miri run -p ch02 --example unreachable         # Miri и нарушенное assert_unchecked
$ gcc -O2 -Wall -Wextra code/ch02/c/switch.c && ./a.out         # switch из введения
$ bash code/ch02/c/run.sh                                       # его вывод и предупреждения GCC и clang
```

Числа в тексте получены на rustc 1.97.0 (LLVM 22.1.6) для
`x86_64-unknown-linux-gnu`, `thumbv6m-none-eabi` (Cortex-M0) и
`thumbv7m-none-eabi` (Cortex-M3), GCC 13.3 и clang 18.1. Ассемблер снят
командой `cargo asm` из release-сборки без директив отладочной
информации, если не сказано иное.
