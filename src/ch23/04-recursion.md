# 23.4. Рекурсия и TT-muncher

Повторение умеет одно: пройти по однородному списку вперёд и выдать по
куску на элемент. Развернуть список, сложить числа, разобрать вход, где
элементы бывают разных видов, — нельзя. Для этого у макроса есть
**рекурсия**: подстановка может содержать вызов того же макроса с другими
аргументами, и компилятор раскроет и его.

## Внутренние правила и накопитель

Разворот списка — классический пример:

```rust
{{#include ../../code/ch23/src/recursion.rs:reverse}}
```

На каждом шаге первый токен входа переезжает в *начало* накопителя
`[...]`; когда вход кончился, накопитель выдаётся массивом.
`reverse!(1 2 3)` раскрывается в цепочку

```text
reverse!(1 2 3)
reverse!(@acc [] 1 2 3)
reverse!(@acc [1] 2 3)
reverse!(@acc [2 1] 3)
reverse!(@acc [3 2 1])
[3, 2, 1]
```

(тест `reverse_list`). Правила с `@acc` — **внутренние**: снаружи их не
зовут, а `@` в начале — буквальный токен, с которым не начинается ни
один разумный пользовательский вызов. Внутренние правила стоят *выше*
внешнего: внешнее правило `($($items:tt)*)` совпадает с чем угодно, в
том числе с `@acc [...] ...`, и, стоя первым, перехватывало бы
рекурсивные вызовы. Буквальный `@` сравнивается без парсера фрагментов,
так что несовпавшее внутреннее правило честно уступает следующему
(отката нет только *внутри* разбора фрагмента — [23.1](01-rules.md)).

Накопитель — главный приём рекурсивных макросов. Подстановка не может
выдать «половину» конструкции и дописать вторую половину позже: каждый
вызов макроса раскрывается в законченную синтаксическую единицу. Поэтому
промежуточный результат копят в аргументе и выдают одним куском в конце.
Особенно больно это для `match`: макрос не может раскрыться в ветку
`match`, только во всё выражение целиком:

```text
error: macro expansion ignores `=>` and any tokens following
 --> e6.rs:2:33
  |
2 |     ($p:pat => $e:expr) => { $p => $e };
  |                                 ^^
...
5 |     match x { arm!(0 => 1), _ => 2 }
  |               ------------ caused by the macro expansion here
  |
  = note: the usage of `arm!` is likely invalid in pattern context
  = note: macros cannot expand to match arms
```

Макрос конечного автомата из задачи D ([23.7](07-tasks.md)) копит ветки
`match` в трёх накопителях и выдаёт функцию перехода целиком.

## TT-muncher

Регистр управления UART — 16 полей разной ширины, часть битов
зарезервирована. Хочется описать его списком «имя: ширина» и получить
методы чтения полей с правильными сдвигами. Повторение не справится по
двум причинам: смещение поля — сумма ширин *перед* ним, а поля бывают
двух видов — именованные и `_`, для которых метода нет. Решение — разбор
по одному полю за шаг, **TT-muncher** («пожиратель деревьев токенов»):

```rust
{{#include ../../code/ch23/src/recursion.rs:fields}}
```

Каждое правило `@munch` «откусывает» от входа одно поле и зовёт макрос
на остаток `$($rest)*`. Смещение копится в накопителе `[$($off)*]` — не
числом, а *выражением*: `macro_rules!` не умеет складывать, но умеет
дописать `+ 1` к токенам `0 + 1 + 1`, а сложение выполнит компилятор при
вычислении константы. Метод `txe` получает сдвиг
`0 + 1 + 1 + 1 + 4 + 1` = 8 — бит TXE регистра UARTCR из главы 6. Когда
вход кончился, последнее правило проверяет, что сумма ширин равна
ширине регистра: `const _: () = assert!(...)` — ошибка компиляции, если
кто-то ошибся в описании. Тест `register_fields` читает поля значения
0x301 (`UARTEN | TXE | RXE`) и отдельные биты RTSEN и CTSEN.

Образец остатка `$(, $($rest:tt)*)?` — «запятая и что угодно после неё, или
ничего»: так последнее поле можно писать и с запятой, и без.

<div class="box c">

**Как в C.** Битовые поля C (`struct { unsigned uarten : 1; ... }`)
выглядят так же, но порядок бит внутри слова, выравнивание и ширина
доступа — на усмотрение компилятора (C17, 6.7.2.1), поэтому для регистров
их избегают и пишут маски руками: `#define UARTCR_TXE (1u << 8)`.
`fields!` генерирует именно маски и сдвиги — порядок задан явно, а сумма
ширин проверена.

</div>

## Предел рекурсии

Каждый рекурсивный вызов — ещё один уровень вложенности раскрытия, и
уровней по умолчанию не больше 128. Это ограничение не на «бесконечную»
рекурсию, а на любую глубокую: TT-muncher на длинном входе упирается в
него так же, как бесконечный цикл. `count_rec!` из [23.2](02-repeat.md)
на 127 аргументах работает, на 128 — нет:

```text
error: recursion limit reached while expanding `count_rec!`
 --> r1.rs:3:43
  |
3 | ...$($tail:tt)*) => { 1usize + count_rec!($($tail)*) };
  |                                ^^^^^^^^^^^^^^^^^^^^^
  |
  = help: consider increasing the recursion limit by adding a `#![recursion_limit = "256"]` attribute to your crate (`r1`)
```

Предел поднимает атрибут `#![recursion_limit = "256"]` — у крейта,
*который вызывает* макрос, а не у того, где макрос определён: пределы
считаются при раскрытии. Оба случая — doc-тесты модуля `recursion.rs`.
Хвостовая рекурсия не помогает: уровень раскрытия засчитывается каждому
вложенному вызову, даже последнему в подстановке. Макрос автомата из
задачи D тратит по уровню на переход, и без атрибута раскрывает не больше
122 переходов (замер в [приложении E](../appendix-e/ch23.md)).

<div class="box trap">

**Ловушка — квадратичная цена.** На каждом шаге TT-muncher передаёт
остаток входа и накопители целиком, то есть копирует их. На входе из
*n* элементов это порядка *n²* токенов. Для описания регистра из 16 полей
это незаметно; для автомата из 800 переходов раскрытие одно занимает
0,6 секунды (приложение E). Где рекурсия не нужна, хватает повторения —
`count!` из [23.2](02-repeat.md) считает без неё.

</div>

<div class="box trick">

**Трюк — где ставить запятые.** Правило, которое съедает элемент вместе с
запятой после него, делает запятую обязательной; правило «элемент, затем
необязательные запятая и остаток» — `$x ... $(, $($rest:tt)*)?` —
разрешает и висячую запятую, и её отсутствие. Альтернатива —
нормализовать вход заранее: внешнее правило дописывает запятую в конец, а
внутренние всегда её ожидают.

</div>

<div class="box check">

**Проверка.** `reverse_list` и `register_fields`; doc-тесты модуля
`recursion.rs` — предел рекурсии на 128 аргументах, тот же вызов с
`#![recursion_limit = "256"]` и ветка `match` из макроса. Проверка суммы
ширин — `const`: копия описания `UartCr` с `_: 15` вместо `_: 16` на
rustc 1.97 даёт E0080 «evaluation panicked: сумма ширин полей не равна
ширине регистра».

</div>
