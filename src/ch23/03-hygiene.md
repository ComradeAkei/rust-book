# 23.3. Гигиена и `$crate`

Третья ловушка из введения — `SWAP(x, tmp)`: макрос заводит свою
переменную `tmp`, и она затеняет переменную вызывающего с тем же именем.
Тот же макрос в Rust:

```rust
{{#include ../../code/ch23/src/hygiene.rs:swap}}
```

`swap!(x, tmp)` меняет значения местами (тест
`swap_with_variable_named_tmp`): `(1, 2)` становится `(2, 1)`. Хотя после
подстановки текст выглядит точно как сломанный C — `let tmp = x; x = tmp;
tmp = tmp;`, — работает он правильно. Значит, имя в Rust — не только
текст.

## Имя и контекст

У каждого идентификатора, кроме написания, есть **синтаксический
контекст** (syntax context) — отметка, из какого раскрытия макроса он
пришёл. Два `tmp` с разными контекстами — разные имена. Контексты можно
увидеть: флаг `-Zunpretty=expanded,hygiene` печатает раскрытие с номерами.
Для функции `call(mut x, mut tmp)`, которая зовёт `swap!(x, tmp)`
(`code/ch23/expanded/swap.rs`, rustc 1.97):

```rust,ignore
{{#include ../../code/ch23/expanded/swap.out.rs:19:28}}
```

```text
{{#include ../../code/ch23/expanded/swap.out.rs:37:42}}
```

Число до `#` — номер символа в таблице строк (`2353` — это `tmp`), после
`#` — контекст. `tmp /* 2353#4 */` пришёл из тела макроса: контекст `#4`
отмечен раскрытием `swap!`. `tmp /* 2353#0 */` — параметр функции,
контекст корневой. В строке `tmp#0 = tmp#4` справа — макросный
временный, слева — переменная вызывающего, и путаницы нет. Тест
`rustc_swap_hygiene_expansion` сверяет этот снимок с выводом закреплённого
rustc; номера — внутренняя деталь версии, поэтому в задании CI с nightly
он пропускается.

## Что прячет гигиена, а что — нет

Отметка `SemiOpaque` у контекста `#4` — это и есть правило `macro_rules!`,
**смешанная гигиена** (mixed-site hygiene):

- **локальные переменные, метки циклов и `$crate`** разрешаются там, где
  макрос *определён*. Макрос не видит локальную переменную вызывающего,
  если её не передали аргументом, и не затеняет её;
- **всё остальное** — функции, типы, модули, константы, статики, другие
  макросы, поля и методы — разрешается там, где макрос *вызван*.

Первая половина — в doc-тесте модуля `hygiene.rs`:

```rust,ignore
macro_rules! plus_one {
    () => { x + 1 };
}
let x = 1;
let _ = plus_one!();
```

```text
error[E0425]: cannot find value `x` in this scope
 --> e4.rs:2:13
  |
2 |     () => { x + 1 };
  |             ^ not found in this scope
3 | }
4 | fn main() { let x = 1; let _ = plus_one!(); }
  |                                ----------- in this macro invocation
  |
help: an identifier with the same name exists, but is not accessible due to macro hygiene
```

Зато макрос, определённый внутри функции *после* `let base = 10`, видит
`base`: имя разрешается в месте определения, а там `base` уже есть (тест
`local_defined_before_macro_is_visible`).

Вторая половина — элементы. Функция и тип, порождённые макросом, видны
вызывающему — так и задумано, иначе макрос не мог бы ничего объявить:

```rust
{{#include ../../code/ch23/src/hygiene.rs:items}}
```

`read_temperature()` и `Temperature(215)` доступны снаружи (тест
`items_are_visible`). Обратная сторона — столкновения. Макрос, который
заводит вспомогательную функцию с фиксированным именем, нельзя вызвать
дважды в одном модуле:

```text
error[E0428]: the name `helper` is defined multiple times
 --> e5.rs:2:13
  |
2 |     () => { fn helper() -> u32 { 42 } };
  |             ^^^^^^^^^^^^^^^^^^
  |             |
  |             `helper` redefined here
  |             previous definition of the value `helper` here
```

<div class="box trap">

**Ловушка — гигиена не распространяется на функции и типы.** Помощник,
порождённый макросом, живёт в пространстве имён вызывающего. Три выхода:
имена задаёт вызывающий (как `sensor!(Temperature, read_temperature, ...)`);
помощник прячется в анонимную константу `const _: () = { ... };` или в
модуль; помощник объявлен один раз рядом с макросом и вызывается по пути
`$crate::...` (ниже).

</div>

## Пути, которые нельзя подменить

Раз пути разрешаются у вызывающего, `Option::Some` в теле макроса — это
тот `Option`, который виден *там*:

```rust
{{#include ../../code/ch23/src/hygiene.rs:paths}}
```

В модуле `shadow` вызывающий завёл свой `Option` с вариантами `Some` и
`Absent` — в коде протоколов такое бывает. `some_fragile!(1)` молча
построил *его* `Option`, а не стандартный: функция `fragile` возвращает
`shadow::Option<u8>` и компилируется (тест `fragile_path_is_captured`).
`some_robust!` пишет путь от корня — `::core::option::Option::Some`. Ведущие
`::` означают «внешний крейт», и модуль или тип с именем `core` у
вызывающего на путь не влияет. Отсюда правило для макросов, которые
раскрываются в чужом коде: **все пути — полные, от `::core`** (или
`::alloc`, `::std`, если крейт их требует). `::core` есть и в `no_std`, так
что макрос годится для прошивки. Задача B ([23.7](07-tasks.md)) проверяет
это модулем `hostile`, где переопределены `Option`, `Result` и модуль
`core`.

## `$crate`

Макросу нужен его собственный помощник — функция из того же крейта. Путь
`crate::...` не годится: у вызывающего `crate` — *его* крейт. Имя крейта
тоже: вызывающий мог переименовать зависимость в `Cargo.toml`. Для этого
есть специальная метапеременная `$crate` — путь к крейту, где макрос
определён:

```rust
{{#include ../../code/ch23/src/hygiene.rs:dollar_crate}}
```

Помощник `__checked_add` публичный — иначе вызывающий не смог бы к нему
обратиться, — но скрыт из документации `#[doc(hidden)]`, а имя с двумя
подчёркиваниями намекает «не звать напрямую». Так устроена и
стандартная библиотека: `panic!("x")` раскрывается в
`::core::panicking::panic_fmt(format_args!("x"))`, а `vec![1, 2]` — в
вызов `::alloc::boxed::box_assume_init_into_vec_unsafe(...)` (rustc 1.97,
`-Zunpretty=expanded`; `$crate` печатается путём от корня). Обеих функций
нет в документации, звать их напрямую нельзя — они нестабильны, — а макрос
может. Тесты `dollar_crate_path` и `dollar_crate_checks` вызывают
`add_checked!` и ловят [панику][g-panic] переполнения.

<div class="box c">

**Как в C.** Гигиены нет вовсе. Защищаются соглашениями: имена вида
`_tmp_` или `__swap_tmp`, склейка с номером строки
(`tmp##__LINE__`) или `__COUNTER__` из расширений GCC и clang. Ни одно
соглашение не защищает от вызывающего, который случайно выбрал то же имя;
`-Wshadow` хотя бы предупреждает. Полных путей тоже нет: макрос из
заголовка вызывает `memcpy`, и если в единице трансляции `memcpy` —
макрос или своя функция, вызовется она.

</div>

<div class="box hood">

**Под капотом.** Контекст `SemiOpaque` — смешанная гигиена `macro_rules!`.
[Процедурные макросы][g-proc-macro] ([24.3](../ch24/03-spans.md)) получают выбор: [`Span::call_site()`][g-span] —
полностью «прозрачные» имена, как будто их написал вызывающий, а
`Span::mixed_site()` — то же правило, что у `macro_rules!`. Будущие
макросы `macro` (декларативные макросы 2.0, нестабильны) по умолчанию
полностью гигиеничны: и функции из их тела не видны снаружи.

</div>
