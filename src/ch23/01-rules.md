# 23.1. macro_rules!: правила и фрагменты

Декларативный макрос — список **правил**. У каждого правила есть образец
(matcher) и подстановка (transcriber):

```rust,ignore
macro_rules! имя {
    (образец 1) => { подстановка 1 };
    (образец 2) => { подстановка 2 };
}
```

Вызов `имя!(...)` сопоставляется с правилами сверху вниз; побеждает первое
подошедшее, и вызов заменяется его подстановкой. Скобки вызова — `()`,
`[]` или `{}` — равноправны; принято `vec![...]` для «коллекций», `{}` для
макросов, порождающих элементы, `()` для остального. Вызов в позиции
элемента с `()` или `[]` заканчивается `;`, с `{}` — нет.

Образец состоит из обычных токенов, которые должны совпасть буквально, и
**метапеременных** `$имя:вид`: вид (fragment specifier) говорит, какой
кусок синтаксиса захватить. В подстановке `$имя` вставляет захваченное.

## Двойное вычисление

Начнём с переноса `MAX` из введения:

```rust
{{#include ../../code/ch23/src/basics.rs:max}}
```

`max_twice!(next(), 3)` раскрывается в `if next() > 3 { next() } else { 3 }`
— ровно как в C. Тест `max_twice_evaluates_twice` это фиксирует: результат
20 и два вызова `next`. Гигиена и деревья токенов здесь ни при чём:
выражение подставлено дважды и вычисляется дважды. Правильный макрос
вычисляет каждый аргумент один раз — привязывает значения к именам.
`match`, а не `let`, — по образцу `assert_eq!` из стандартной библиотеки:
временное значение из выражения `match` живёт до конца оператора, где
стоит вызов, а из инициализатора `let` — только до конца этого `let`.
Поэтому `*max_once!(&Vec::from([1, 5])[1], &3)` равно 5, а тот же вызов
макроса на `let` не компилируется: «temporary value dropped while
borrowed», E0716 (doc-тест в `code/ch23/src/basics.rs`). Имена
`a` и `b` внутри макроса не столкнутся с такими же у вызывающего — это
гигиена ([23.3](03-hygiene.md)), и тест `max_once_evaluates_once` зовёт
`max_once!(b, a)` с переменными `a` и `b`.

<div class="box c">

**Как в C.** Тот же приём в GCC — выражение-оператор:
`#define MAX(a, b) ({ __typeof__(a) _a = (a); __typeof__(b) _b = (b); _a > _b ? _a : _b; })`.
Это расширение GNU, а не стандарт C; имена `_a` и `_b` по-прежнему могут
столкнуться с именами вызывающего (`MAX(_a, 1)`). В Rust блок — обычное
выражение, а столкновение исключено.

</div>

## `expr` против `tt`

Вторая ловушка — приоритет:

```rust
{{#include ../../code/ch23/src/basics.rs:square}}
```

`square!(1 + 2)` равно 9: фрагмент `expr` — уже разобранное выражение,
узел дерева. Подставленный, он остаётся одним операндом, как будто взят в
скобки; `rustc -Zunpretty=expanded` так и печатает раскрытие:
`(1 + 2) * (1 + 2)`. `square_tt!` захватывает **деревья токенов** (`tt`) —
отдельные токены или группы в скобках — и подставляет их как есть:
`1 + 2 * 1 + 2`, то есть 5, как `SQUARE` в C. Вид `tt` — самый гибкий и
самый «текстовый»; в задаче A ([23.7](07-tasks.md)) вы предскажете оба
раскрытия до запуска компилятора.

## Виды фрагментов

Макрос `frag!` захватывает фрагмент каждого вида и показывает
`stringify!`, что именно захвачено:

```rust
{{#include ../../code/ch23/src/basics.rs:fragments}}
```

| Вид | Что захватывает | Пример (тест `observed_fragment_texts`) |
|---|---|---|
| `ident` | имя или ключевое слово-идентификатор | `uart0` |
| `literal` | литерал, в том числе с `-` впереди | `-1`, `"текст"`, `0x18` |
| `expr` | выражение | `1 + 2 * x` |
| `ty` | тип | `Vec<u8>` |
| `path` | путь в стиле типа | `::core::mem::size_of::<u32>` |
| `pat` | образец, с альтернативами `\|` | `Some(x) \| None` |
| `pat_param` | образец без `\|` на верхнем уровне (`pat` редакции 2018) | `Some(x)` |
| `block` | блок в фигурных скобках | `{ 1 }` |
| `stmt` | оператор без завершающей `;` | `let x = 1` |
| `item` | элемент: функция, структура, `impl`… | `struct S;` |
| `lifetime` | время жизни | `'a` |
| `vis` | модификатор видимости, возможно пустой | `pub(crate)` |
| `meta` | содержимое атрибута | `derive(Debug)` |
| `tt` | одно дерево токенов | `[a b]` |

Текст `stringify!` — наблюдение, а не гарантия: формат печати не обещан.
Пример — `literal`: `frag!(literal -1)` на rustc 1.97 печатает `-1`, а
nightly того же времени — `- 1`. Поэтому тест
`literal_fragment_accepts_minus` проверяет *значение*: `$x:literal`
захватывает `-1` целиком, хотя в языке это унарный минус перед литералом.

Две тонкости видов, которые встречаются на практике:

- `vis` может совпасть с пустотой, но только перед следующим токеном:
  `frag!(vis fn)` даёт пустую строку, а `frag!(vis)` без `fn` — ошибку
  «unexpected end of macro invocation». Поэтому в образце `frag!` после
  `$x:vis` стоит `fn`;
- в редакции 2024 `expr` совпадает и с `const { ... }`, и с `_`;
  прежнее поведение сохранено во фрагменте `expr_2021` (тест
  `expr_fragment_edition_2024`). Такие изменения грамматики и есть причина
  ограничений из следующих двух пунктов.

## Отката нет

Захваченный фрагмент разбирает настоящий парсер языка. Если парсер
фрагмента начал разбор и споткнулся, следующее правило *не* пробуется —
это ошибка компиляции:

```rust,ignore
macro_rules! first {
    ($e:expr) => { "expr" };
    ($i:ident +) => { "ident +" };
}
let _ = first!(a +);
```

```text
error: expected expression, found end of macro arguments
 --> e1.rs:5:31
  |
2 |     ($e:expr) => { "expr" };
  |      ------- while parsing argument for this `expr` macro fragment
...
5 | fn main() { let _ = first!(a +); }
  |                               ^ expected expression
```

`a +` начинается как выражение, и парсер `expr` взялся за него. Второе
правило подошло бы, но до него дело не дошло. Отсюда правило порядка:
**частные правила — выше общих**, и особенно выше правил, начинающихся с
фрагмента `expr`, `ty` или `pat`. Буквальные токены сравниваются без
парсера, поэтому правило, которое не совпало на буквальном токене, честно
уступает следующему — на этом держатся внутренние правила `@имя`
([23.4](04-recursion.md)). Пример лежит в документации модуля
`code/ch23/src/basics.rs` doc-тестом `compile_fail`.

## Что может идти после фрагмента

Граница выражения зависит от грамматики: если бы после `$a:expr` можно
было поставить `+`, то где кончается `$a` в `1 + 2 + 3`? И что станет с
макросами, когда в язык добавят новый оператор? Поэтому за некоторыми
видами разрешены только определённые токены — **follow-set**:

```rust,ignore
macro_rules! bad {
    ($a:expr + $b:expr) => {};
}
```

```text
error: `$a:expr` is followed by `+`, which is not allowed for `expr` fragments
 --> e2.rs:2:14
  |
2 |     ($a:expr + $b:expr) => {};
  |              ^ not allowed after `expr` fragments
  |
  = note: allowed there are: `=>`, `,` or `;`
```

| После вида | Разрешены |
|---|---|
| `expr`, `stmt` | `=>` `,` `;` |
| `pat` | `=>` `,` `=` `if` `in` |
| `pat_param` | `=>` `,` `=` `\|` `if` `in` |
| `ty`, `path` | `=>` `,` `=` `\|` `;` `:` `>` `>>` `[` `{` `as` `where`, фрагмент `block` |
| `vis` | `,`, идентификатор, начало типа, фрагменты `ident`, `ty`, `path` |
| остальные | что угодно |

Ограничение проверяется при *определении* макроса, а не при вызове.
Обходят его тремя способами: разделитель из списка (`$a:expr, $b:expr`),
более узкий вид (`$off:literal`, `$name:ident`) или `tt`. Задача C
([23.7](07-tasks.md)) упирается в это: в `DR: u32 @ 0x00` после типа
стоит `@`, которого нет в follow-set `ty`, поэтому тип регистра
захватывается как `ident`. А `|` после `pat` запрещён потому, что с
редакции 2021 сам `pat` включает альтернативы: разделять образцы
символом `|` можно только после `pat_param`, его и предложит компилятор.

## Захваченное непрозрачно

Фрагмент, захваченный как `expr` (а также `ty`, `pat`, `path`, `stmt`,
`block`, `item`, `meta`, `literal`… — все, кроме `ident`, `lifetime` и
`tt`), передаётся дальше одним **непрозрачным** узлом. Другой макрос
сможет захватить его своим фрагментом того же вида или как один `tt`, но
сравнить с буквальными токенами — нет:

```rust
{{#include ../../code/ch23/src/basics.rs:opaque}}
```

`is_zero!(0)` и `via_tt!(0)` дают «ноль», а `via_expr!(0)` — «не ноль»:
внутри `via_expr!` ноль стал узлом-выражением, и образец `(0)` с ним не
совпадает (тест `captured_expr_is_opaque`). Так же ведут себя `literal` и
`ty`, а `ident` проходит насквозь: тест `which_fragments_are_opaque`
передаёт `0` через `$l:literal` и `uart` через `$i:ident` и `$t:ty`.

<div class="box trap">

**Ловушка — разбор в два этапа.** Макрос-обёртка, который захватывает
аргументы как `expr` и передаёт их макросу с буквальными образцами,
незаметно ломает этот второй макрос: все аргументы падают в правило «по
умолчанию». Если вложенному макросу нужно смотреть на токены, обёртка
должна захватывать `tt` или `$($t:tt)*`. Обратное тоже верно: захватить
`expr`, чтобы *защитить* выражение от разбора по частям, — законный приём.

</div>

<div class="box hood">

**Под капотом.** Раскрытие идёт раньше разрешения имён и проверки типов:
компилятор разбирает файл в токены, находит вызовы макросов, раскрывает
их — возможно, в новые вызовы, — и только потом строит полное
синтаксическое дерево и проверяет его. Поэтому макрос не знает типов
своих аргументов: `$x:expr` — «что-то похожее на выражение», а не «число».
Ошибка типа в раскрытом коде указывает на токены аргумента, из которых он
получился, — диагностика помнит происхождение каждого токена.

</div>
