# 25.2. const fn

## Делитель UART при компиляции

<div class="box ref">

**Справка: делитель скорости PL011.** UART отсчитывает биты по
тактовому сигналу UARTCLK, деленному на 16 · BAUDDIV. Делитель дробный:
целая часть пишется в регистр `UARTIBRD` (16 бит), дробная — в
`UARTFBRD` в шестьдесят четвёртых долях (6 бит). При 16 МГц и 115200
бод BAUDDIV = 16 000 000 / (16 · 115 200) = 8,6806, то есть IBRD = 8 и
FBRD = round(0,6806 · 64) = 44. Настоящая скорость получается чуть
другой, и две стороны линии расходятся; больше 2–3 % — и приёмник
начинает путать биты. Тот же блок стоит в lm3s6965 из QEMU и во многих
других микроконтроллерах.

</div>

Обычно этот расчёт делают на калькуляторе и пишут в код готовые 8 и 44.
Поменялась частота кварца — и кто-то должен вспомнить, что числа надо
пересчитать. В Rust расчёт — функция:

```rust
{{#include ../../code/ch25/src/const_fn.rs:divisor}}
```

`const fn` — обычная функция с одним дополнительным свойством: её
вызов может стоять там, где нужно значение при компиляции. `UART0` —
константа, и `uart_divisor(16_000_000, 115_200)` вычисляет компилятор.
Тест `divisors` проверяет результат: `Divisor { ibrd: 8, fbrd: 44,
error_ppm: -799 }`, скорость на 0,08 % ниже заданной. В прошивке из
раздела [25.6](06-flash.md) эти 8 и 44 записываются в регистры UART0 и
читаются обратно, а кода деления в ней нет: в машинный код попали только
два числа.

Если параметры недостижимы, паника при вычислении константы — ошибка
компиляции с текстом паники:

```text
error[E0080]: evaluation panicked: UART: делитель меньше 1, скорость недостижима при этой частоте
 --> fast.rs:4:43
  |
4 | pub const FAST: ch25::const_fn::Divisor = uart_divisor(12_000_000, 921_600);
  |                                           ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ evaluation of `FAST` failed inside this call
  |
note: inside `uart_divisor`
 --> code/ch25/src/const_fn.rs:97:8
```

Сменили кварц на 12 МГц и подняли скорость до 921 600 бод — сборка
остановилась на строке с константой, а не прошивка в поле на молчащем
UART.

<div class="box c">

**Как в C.** Тот же расчёт препроцессором — макросы и `#if`:

```c
{{#include ../../code/ch25/c/divisor.c:divisor}}
```

```text
divisor.c:17:2: error: #error "UART: делитель меньше 1, скорость недостижима при этой частоте"
```

Работает, пока хватает целой арифметики `#if`: без типов, без
`sizeof`, без функций, без отладки — `printf` в препроцессор не
вставить. Проверка ошибки скорости в процентах — ещё одно выражение из
макросов. А в Rust `uart_divisor` можно вызвать из теста и посмотреть
результат, как у любой функции.

</div>

## Та же функция при выполнении

`const` в объявлении функции не значит «вычисляется при компиляции». Он
значит «*может* вычисляться при компиляции». Вне константного контекста
это обычный вызов:

```rust
{{#include ../../code/ch25/src/const_fn.rs:runtime}}
```

Частота тактирования иногда известна только при запуске — после
настройки PLL. Тогда та же функция считает делитель на процессоре, а её
паника — обычная паника: тест `too_fast_panics_at_runtime`. Одна функция,
одна логика проверок, два режима, и выбирает режим место вызова, а не
функция. Оптимизатор, конечно, может сам свернуть вызов с константными
аргументами, но это его право, а не обещание: вычисление при компиляции
гарантирует только константный контекст.

## Что умеет интерпретатор

Тело `const fn` при компиляции выполняет интерпретатор, встроенный в
rustc. Он работает с [промежуточным представлением][g-ir] [MIR][g-mir] и умеет почти всё,
что не требует внешнего мира: целую и (с Rust 1.82) плавающую
арифметику, `if`, `match`, `loop` и `while`, `let mut`, массивы и
структуры, вызовы других `const fn`, панику и (с 1.83) `&mut`:

```rust
{{#include ../../code/ch25/src/const_fn.rs:mut-ref}}
```

`fill` получает `&mut [u8]` на массив, который строит `byte_classes`.
До 1.83 приходилось писать всё в одной функции или передавать массив по
значению и возвращать обратно.

Чего нет — всё, что сводится к вызову методов [трейтов][g-trait]. Цикл `for` — это
`IntoIterator::into_iter` и `Iterator::next`:

```text
error[E0015]: cannot use `for` loop on `&[u32]` in constant functions
 --> forl.rs:3:14
  |
3 |     for x in a {
  |              ^
  |
  = note: calls in constant functions are limited to constant functions, tuple structs and tuple variants
```

Оператор `?` — трейт `Try`:

```text
error[E0658]: `?` is not allowed on `Option<&u8>` in constant functions
 --> q.rs:2:13
  |
2 |     let x = a.first()?;
  |             ^^^^^^^^^^
```

Операторы над [обобщённым][g-generic] типом — `PartialEq::eq`, `Add::add`:

```text
error[E0015]: cannot call non-const operator in constant functions
 --> eq.rs:2:5
  |
2 |     a == b
  |     ^^^^^^
```

Поэтому код `const fn` выглядит как C девяностых: `while` с индексом,
явные `return`, `match` вместо `?`. Трейты в константах — нестабильная
возможность `const_trait_impl`, над которой идёт работа; на stable
1.97 её нет.

Плавающая точка разрешена, а математических функций нет: `sqrt`, `sin`,
`exp` — не операторы языка, а функции библиотеки, и константными их на
stable 1.97 не сделали (у `sin` и `exp` результат к тому же зависит от
реализации libm и может отличаться в последнем бите).

```text
error[E0015]: cannot call non-const method `f64::<impl f64>::sqrt` in constants
 --> sqrt.rs:1:31
  |
1 | pub const ROOT2: f64 = 2.0f64.sqrt();
  |                               ^^^^^^
```

Нет в `core` и `f64::round`: в `std` она константная с Rust 1.90, а
библиотеке без `std` и с *MSRV* (minimum supported Rust version — самой
старой версией компилятора, которую [крейт][g-crate] обещает поддерживать) 1.85
округление приходится писать самой. Для перевода коэффициентов фильтра в
формат Q15 этого хватает:

```rust
{{#include ../../code/ch25/src/const_fn.rs:float}}
```

В прошивке без [FPU][g-fpu] (Cortex-M0, M3) `FILTER` — четыре числа `i16`, и
ни одной операции с плавающей точкой: её выполнил компилятор на машине
сборки. Синус для таблицы — ряд Тейлора, задача [25.B](08-tasks.md).

<div class="box trap">

**Ловушка: бесконечный цикл.** Интерпретатор не знает, кончится ли
цикл. Через пару секунд работы срабатывает запрещающая проверка:

```text
error: constant evaluation is taking a long time
  --> spin.rs:5:13
   |
 5 |         x = x.wrapping_mul(6364136223846793005).wrapping_add(1);
   |             ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
   |
   = note: this lint makes sure the compiler doesn't get stuck due to infinite loops in const eval.
           If your compilation actually takes a long time, you can safely allow the lint
   = note: `#[deny(long_running_const_eval)]` on by default
```

Это не ограничение на число шагов, а страховка от зависания: настоящее
долгое вычисление можно разрешить `#[allow(long_running_const_eval)]`.
Но интерпретатор медленнее машинного кода на порядки, и таблица из
миллиона элементов — повод вспомнить `build.rs` (раздел
[8.5](../ch08/05-build-rs.md)).

</div>

<div class="box hood">

**Под капотом.** *Интерпретатор констант* (CTFE, compile-time function
evaluation) — тот же движок, на котором построен Miri (раздел
[0.5](../ch00/05-checks.md)). Он исполняет MIR, отслеживая каждый байт
памяти: выход за границу массива, чтение неинициализированной памяти,
переполнение в арифметике с проверкой при вычислении константы — ошибка
компиляции, а не неопределённое поведение. Поэтому `const fn` может быть
`unsafe` и работать с [сырыми указателями][g-raw-pointer], но UB в ней компилятор поймает
при вычислении константы. Не поймает при выполнении — там та же функция
компилируется в обычный машинный код.

</div>
