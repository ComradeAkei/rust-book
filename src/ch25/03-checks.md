# 25.3. Проверки при компиляции

## const _: () = assert!(…)

Константа с именем `_` — вычисление ради побочного эффекта: значение
никому не нужно, а паника при вычислении — ошибка сборки. Получается
аналог `_Static_assert` из C11:

```text
error[E0080]: evaluation panicked: буферы не помещаются
 --> used.rs:2:15
  |
2 | const _: () = assert!(USED <= 12_288, "буферы не помещаются");
  |               ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ evaluation of `_` failed here
```

Приём уже встречался в разделе [6.2](../ch06/02-repr-c.md); здесь —
что он умеет. Отличие от C — в условии. `_Static_assert` принимает только
целочисленное константное выражение: `sizeof`, перечисления, литералы.
Условие `assert!` в константе — любой код, который умеет интерпретатор
из раздела [25.2](02-const-fn.md): цикл по таблице, вызов `const fn`,
`size_of` и `offset_of!`.

## Раскладка совпадает с C

Заголовок записи журнала читает и загрузчик на C. Его описание в
C-заголовке — договор, и Rust-сторона должна его соблюдать:

```rust
{{#include ../../code/ch25/src/checks.rs:layout}}
```

`size_of`, `align_of` и `offset_of!` (Rust 1.77) — константные, и
проверка стоит рядом с типом. Переставили поля, сменили `u16` на `u32`,
забыли `repr(C)` — сборка остановится здесь, а не загрузчик на разборе
журнала. Тот же приём для регистровых блоков — раздел
[6.9](../ch06/09-registers.md), а derive из главы 24 порождает такие
проверки сам.

## Инвариант таблицы

Таблица порогов аварийных уровней ищется делением пополам, а
`partition_point` верен, только если пороги строго возрастают:

```rust
{{#include ../../code/ch25/src/checks.rs:invariant}}
```

Константа читает `static` (раздел [25.1](01-consts.md)), `const fn`
проверяет инвариант циклом, и таблицу больше нельзя испортить незаметно:
вставили порог не на своё место — сборка упала с текстом «THRESHOLDS:
пороги должны возрастать». Проверка ничего не стоит при выполнении: ни
одной инструкции в прошивке.

Сообщение в `assert!` константы — только литерал. Число в текст не
подставить: форматирование — это вызов `Display::fmt`, метода трейта, а
трейтов в константах нет.

```text
error[E0015]: cannot call non-const formatting macro in constants
 --> fmt.rs:3:5
  |
3 |     panic!("занято {} байт", USED)
  |     ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
```

Как всё же показать число при ошибке — задача [25.D](08-tasks.md).

## Проверка в обобщённом коде

Пул ячеек хранит занятость битами одного `u32`, и ячеек не может быть
больше 32. Ёмкость — параметр типа:

```rust
{{#include ../../code/ch25/src/checks.rs:generic}}
```

Блок `const { assert!(…) }` внутри `new` зависит от `N`, и вычисляется
он для каждого `N`, с которым функцию вызвали, — при мономорфизации
(раздел [10.4](../ch10/04-const-generics.md)):

```text
error[E0080]: evaluation panicked: ёмкость Pool — не больше 32: занятость хранится в u32
  = note: evaluation of `ch25::checks::Pool::<40>::new::{constant#0}` failed here
 --> code/ch25/src/checks.rs:102:12
...
note: the above error was encountered while instantiating `fn Pool::<40>::new`
 --> pool.rs:2:20
  |
2 |     let mut pool = ch25::checks::Pool::<40>::new();
  |                    ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
```

Ошибка показывает обе стороны: проверку в библиотеке и вызов, который
её нарушил. `Pool::<32>` собирается и работает (тест `pool`).

## Когда компилятор вычисляет константу

Не все константы вычисляются в один момент, и это видно на одном
фрагменте с тремя случаями:

```rust
{{#include ../../code/ch25/fragments/when.rs:when}}
```

Тест `tests/eval.rs` собирает каждый случай дважды: с `--emit metadata`
— так работает `cargo check` — и с `--emit link`, как `cargo build`.

| Случай | `cargo check` | `cargo build` |
|---|---|---|
| свободная константа `LIMIT` | E0080 | E0080 |
| `const { … }` в обычной функции | собирается | E0080 |
| `const { … }` в обобщённой функции без вызова | собирается | собирается |

Свободную константу компилятор вычисляет всегда, даже если её никто не
использует: это гарантия Reference. Блок `const` в теле функции rustc
1.97 вычисляет при сборке — и в ветке `if false`, и в функции, которую
никто не вызывает, — но не при проверке. Reference обещает только, что
блок, который исполняется, будет вычислен, а момент оставляет
компилятору, поэтому средняя строка — наблюдение (тест
`rustc_observed_inline_const_fails_only_build`).

<div class="box trap">

**Ловушка.** «`cargo check` прошёл» не значит «соберётся». Проверки в
блоках `const` внутри функций и в обобщённом коде срабатывают только при
настоящей сборке. Если проверка должна ловиться и в редакторе, и в
`cargo check` — делайте её свободной константой `const _: () = …`, как
`LogHeader` выше. CI, который ограничивается `cargo check` и `clippy`,
такие ошибки пропустит.

</div>

## compile_error! вместо #error

Проверка, что целевая платформа вообще подходит, — не вычисление, а
условная компиляция:

```rust
{{#include ../../code/ch25/src/checks.rs:cfg}}
```

`compile_error!` — ошибка с текстом, как `#error`, а условие — `cfg`
(раздел [8.3](../ch08/03-cfg.md)). Поставить её можно и в ветку макроса
`macro_rules!`, которая разбирает неверный ввод (глава 23).

<div class="box c">

**Как в C.** `_Static_assert(sizeof(struct log_header) == 12, "…")` и
`offsetof` в C11 решают первую задачу этого раздела. Вторую — инвариант
таблицы — уже нет: условие `_Static_assert` не может пройти циклом по
массиву, а элемент `constexpr`-массива C23 в нём не константа
(`constexpr.c`, раздел [25.2](02-const-fn.md)). Остаётся проверка при
запуске или внешний скрипт.

</div>
