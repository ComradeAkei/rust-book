# 25.8. Задачи

Все задачи решаются кодом. Заготовки — в `exercises/ch25`, тесты, общие
для заготовок и решений, — в `tests-shared/ch25.rs`. Библиотека
заготовок — `no_std`, как и решения, и собирается как есть: функции с
`todo!()` вызываются только при выполнении, а проверки при компиляции
ждут, пока вы их включите.

```console
$ cargo test -p ch25-exercises            # все задачи
$ cargo test -p ch25-exercises task_c     # одна задача
$ cargo test -p ch25-solutions            # эталон
```

Тесты с префиксом `rustc_` запускают закреплённые rustc и cargo: A
собирает фрагмент под Cortex-M3, B — крейт задач под ту же цель, C — пробы
против крейта, D — крейт с урезанным бюджетом ОЗУ. Разборы — в
[приложении E](../appendix-e/ch25.md), но сначала попробуйте сами.

## B. CRC-32 и синус без build.rs

CRC-32 (IEEE 802.3, zlib, Ethernet) — отражённый вариант: биты байта
идут младшим вперёд, и сдвиг — вправо, с полиномом 0xEDB88320.
Напишите в `b_crc.rs`:

- `const fn crc32_table(poly: u32) -> [u32; 256]` — элемент `t[b]` —
  восемь шагов «сдвиг вправо, при выпавшей единице — `xor` полинома»
  для `b`;
- `static CRC32_TABLE` из неё, во flash;
- `const fn crc32(data: &[u8]) -> u32` — начальное значение `!0`, на
  байт `crc = (crc >> 8) ^ T[(crc ^ byte) & 0xFF]`, в конце `!crc`;
- `CHECK = crc32(b"123456789")` и проверку при сборке, что это
  0xCBF43926 — контрольное значение алгоритма.

Вторая часть — таблица синуса из задачи [8.B](../ch08/09-tasks.md):
`SINE[i] = round(32767 · sin(i · π/512))` для `i` от 0 до 256. Там её
печатал в файл `build.rs` с `f64::sin` и `round`; здесь `sine_table` —
`const fn`, а `f64::sin` в константе нет (раздел
[25.2](02-const-fn.md)). Таблица должна совпасть с таблицей `build.rs`
*бит в бит*: тест `b_sine_matches_build_rs` сравнивает её с
`ch08_solutions::b_sine::SINE`. Тест `rustc_b_tables_in_rodata` собирает
крейт под Cortex-M3 и проверяет, что обе таблицы — в `.rodata` и
нужного размера.

Сравните два подхода: `build.rs` из главы 8 и `const fn`. Что проще
читать и тестировать? Где видна ошибка в формуле? Что будет со временем
сборки, если таблица вырастет до 64 Ки элементов? Когда `build.rs` всё
равно нужен?

## C. ip!

```rust,ignore
let gateway = ip!("192.168.1.1");     // core::net::Ipv4Addr
let broken = ip!("192.168.1.300");    // ошибка сборки
```

В `c_ip.rs`:

- `const fn parse_ipv4(s: &str) -> Result<[u8; 4], IpError>` разбирает
  запись «a.b.c.d»: ровно четыре десятичных октета от 0 до 255, без
  пробелов, знаков и ведущих нулей («010» `inet_aton` прочтёт как
  восьмеричное 8, поэтому такую запись не принимает и
  `"010.0.0.1".parse::<Ipv4Addr>()`). Ошибки — варианты `IpError`. Тест
  `c_parse` проверяет и варианты ошибок, и что ваш разбор согласен со
  стандартной библиотекой, адрес строка или нет;
- `IpError::fail` паникует с текстом ошибки — «IPv4: октет больше 255» и
  т. д., список — в заготовке;
- `const fn ipv4(s: &str) -> Ipv4Addr` — адрес или паника;
- макрос `ip!` — адрес, разобранный *при компиляции*, даже когда
  макрос стоит в теле обычной функции:

```rust,ignore
{{#include ../../exercises/ch25/src/c_ip.rs:macro}}
```

Тест `rustc_c_macro` собирает пробы против вашего крейта: верные
адреса — в константе и в функции — должны собраться, а неверные в теле
функции — дать E0080 с нужным текстом. Пробы собираются полностью, как
`cargo build`: вспомните, что видит и чего не видит `cargo check`
(раздел [25.3](03-checks.md)).

## D. Бюджет ОЗУ

Драйверы станции держат буферы в `static`:

```rust,ignore
{{#include ../../exercises/ch25/src/d_budget.rs:drivers}}
```

Сделайте так, чтобы буферы, которые не помещаются в ОЗУ, ломали сборку
понятным сообщением:

- `build.rs` читает `firmware/memory.x` — тот же файл, по которому
  компонуются прошивки, — находит длину области `RAM` («16K»), вычитает
  4096 байт под стек и передаёт результат компилятору переменной
  окружения `CH25_RAM_BUDGET` (`cargo::rustc-env`). Если переменная с
  тем же именем задана при сборке, её значение заменяет вычисленное.
  Сборка должна повторяться при правке `memory.x` и при смене
  переменной;
- `const fn parse_budget` превращает строку в число, `BUDGET` — из
  `env!("CH25_RAM_BUDGET")`;
- `total` — сумма буферов, `USED = total(&DRIVERS)`;
- две проверки при компиляции. Первая — `USED` не больше `BUDGET`, с
  текстом «буферы драйверов не помещаются в бюджет ОЗУ». Вторая должна
  показать в ошибке, *на сколько* байт бюджет превышен. Число в текст
  `assert!` в константе не подставить (раздел [25.3](03-checks.md)), так
  что напечатать его придётся чем-то другим.

Тест `rustc_d_over_budget_stops_build` собирает крейт с
`CH25_RAM_BUDGET=4000`: сборка должна упасть, а в выводе — быть и текст
первой проверки, и число 3936 в виде «found one with a size of 3936».
С `CH25_RAM_BUDGET=7936` — ровно по буферам — сборка проходит.
