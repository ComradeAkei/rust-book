# 25.7. Сквозной проект: таблица CRC при компиляции

В главе 6 `crc16` кадра стала `const fn`, и её контрольное значение
проверяется при сборке (раздел [6.11](../ch06/11-project.md)). Тогда же
было обещано вычислять при компиляции и таблицы. Шаг главы 25 — таблица
CRC-16/CCITT-FALSE, посчитанная компилятором, и обновление CRC по ней.

## Что уже есть

```rust
{{#include ../../project/telemetry-frame/src/lib.rs:crc}}
```

Побитовый вариант: на каждый байт восемь шагов сдвига с условным
`xor` полинома 0x1021. Кода мало, памяти не нужно, но на каждый байт
кадра — восемь итераций внутреннего цикла.

## Таблица

```rust
{{#include ../../project/telemetry-frame/src/lib.rs:crc_table}}
```

`CRC16_TABLE[b]` — результат восьми шагов для старшего байта `b`.
Обновление по таблице — сдвиг, `xor` и одна загрузка на байт. Таблицу
строит блок в инициализаторе `static`: при компиляции, без `build.rs` и
без 256 чисел в исходнике. Константа `const _` проверяет контрольное
значение уже табличного варианта, а тесты в
`project/telemetry-frame/tests/crc_table.rs` сверяют оба варианта на
всех одно- и двухбайтовых входах при пяти начальных значениях и на
4 КиБ псевдослучайных данных:

```console
$ cargo test -p telemetry-frame --test crc_table
test observed_speed ... ignored, замер скорости, запускать в release
test table_entries ... ok
test table_matches_bitwise ... ok
```

`crc16_update` никуда не делся: декодер кадра пользуется им, как и
прежде, а табличный вариант — второй путь с тем же результатом.

## Что получилось в машинном коде

Обёртки с [неискажёнными][g-mangling] именами в `code/ch25/src/project.rs` дают
найти оба тела в ассемблере:

```rust
{{#include ../../code/ch25/src/project.rs:wrappers}}
```

При `opt-level = "s"` — так собирается отладочная прошивка — побитовый
вариант под Cortex-M3 остаётся двумя вложенными циклами:

```text
.LBB13_2:
	ldrb.w	r3, [r0, r12]
	eor.w	r4, r2, r3, lsl #8
	movs	r3, #8
.LBB13_3:
	sxth	r5, r4
	lsls	r2, r4, #1
	cmp	r5, #0
	it	mi
	eormi.w	r2, lr, r4, lsl #1
	subs	r3, #1
	mov	r4, r2
	bne	.LBB13_3
```

Восемь инструкций внутреннего цикла на каждый бит, `movw lr, #4129` —
полином 0x1021. Табличный — семь инструкций на байт, и одна из них —
`ldrh` из `CRC16_TABLE`:

```text
.LBB14_2:
	ldrb	r3, [r0], #1
	uxth.w	lr, r2
	subs	r1, #1
	eor.w	r3, r3, lr, lsr #8
	ldrh.w	r3, [r12, r3, lsl #1]
	eor.w	r2, r3, r2, lsl #8
	bne	.LBB14_2
```

Тест `rustc_crc_table_at_opt_s` проверяет и цикл по восьми битам, и
`ldrh` в табличном варианте.

## LLVM знает этот приём

А при `opt-level = 3` — так собираются release-прошивки книги и
release-сборки на хосте — тела двух функций совпадают инструкция в
инструкцию, развёрнутые на четыре байта за итерацию. Только побитовый
вариант читает не `CRC16_TABLE`, а `.L.crctable`:

```text
ch25_crc_bitwise:
	…
	movw	r8, :lower16:.L.crctable
	…
	ldrh.w	r1, [r8, r1, lsl #1]
```

LLVM 22 узнаёт цикл побитового CRC, сам строит таблицу на 256
элементов и подставляет табличный алгоритм. Тест
`rustc_observed_llvm_builds_crc_table_at_o3` фиксирует это под
thumbv7m-none-eabi и x86-64. Замер на x86-64 показывает то же со
стороны скорости:

```console
$ cargo test --release -p telemetry-frame --test crc_table -- --ignored --nocapture
побитово 287 МиБ/с, по таблице 294 МиБ/с, в 1.0 раза
```

Абсолютные числа от запуска к запуску гуляют на десяток процентов
(другой прогон дал 327 и 333), а отношение остаётся около единицы:
release-сборка побитового варианта — уже табличная.

Значит ли это, что своя таблица не нужна? Нет, и причин три. Это
наблюдение, а не гарантия: другая версия LLVM или чуть другая запись
цикла — и оптимизация не сработает. При `opt-level = "s"` и `"z"`, с
которыми часто собирают прошивки ради размера, LLVM таблицу не строит.
А если в одной программе есть оба варианта, во flash оказываются две
одинаковые таблицы по 512 байт — своя и `.L.crctable`. Явная таблица
делает стоимость видимой в исходнике: 512 байт `.rodata` и одна загрузка
на байт, при любом уровне оптимизации.

## Проверка

| Тест | Что проверяет |
|---|---|
| `table_matches_bitwise` | таблица против побитового цикла: все одно- и двухбайтовые входы, пять начальных значений, 4 КиБ данных |
| `table_entries` | `CRC16_TABLE[1] = 0x1021`, `CRC16_TABLE[255] = 0x1EF0` |
| `const _` в `lib.rs` | контрольное значение 0x29B1 табличного варианта — при сборке |
| `same_crc` (`code/ch25`) | обёртки дают одно и то же на кадре и на «123456789» |
| `rustc_crc_table_at_opt_s` | при `s` побитовый — цикл по битам, табличный — `ldrh` |
| `rustc_observed_llvm_builds_crc_table_at_o3` | при 3 LLVM строит свою `.L.crctable` |
| `observed_speed` (`#[ignore]`) | скорость обоих вариантов в release |

запуска и драйверами (главы 26 и 27).
