# 20. Потоки, Send и Sync

**Перед чтением.** Повторите [захват переменных замыканием](../ch12/01-capture.md),
[Arc](../ch14/04-arc.md) и [времена жизни](../ch05/01-elision.md).
Потоки — несколько последовательностей выполнения внутри одной программы;
они могут обращаться к одной памяти. Даже на одном процессорном ядре
они чередуются, поэтому нельзя рассчитывать, что один поток закончит
изменение данных до того, как другой начнёт их читать.

## Мотивирующая проблема

Многопоточность в C — это ответственность без страховки. Два потока пишут в
одну переменную без блокировки — гонка данных, неопределённое поведение;
компилятор не предупредит, а сам баг воспроизводится раз в тысячу запусков.
Поток забыл взять мьютекс — тишина до первого повреждения данных. Поток
переживает кадр, чьи локальные данные одолжил, — висячий указатель. Всё это
находит разве что [ThreadSanitizer][g-tsan], и то не всегда.

```rust
use std::rc::Rc;
use std::thread;

let counter = Rc::new(0);
let clone = Rc::clone(&counter);
thread::spawn(move || {
    // два потока меняют неатомарный счётчик ссылок Rc — гонка
    println!("{clone}");
});
```

В Rust этот код не компилируется. `Rc` не реализует [`Send`][g-send-sync], поэтому его
нельзя [переместить][g-move] в другой поток — и компилятор ловит это на `spawn`, а не
в рантайме. В этом суть главы: *отсутствие гонок данных — свойство системы
типов*. Два маркера, `Send` и `Sync`, делят все типы на потокобезопасные и
нет, компилятор выводит их автоматически, а API синхронизации построен так,
что доступ к общим данным невозможен без блокировки.

## Что делает Rust

Глава — про то, как Rust даёт настоящие потоки операционной системы и при
этом переносит проверку гонок на этап компиляции.

- `thread::spawn` и `join` ([20.1](01-spawn.md)) — запуск потока и
  возврат результата; `move` переносит [владение][g-ownership] в поток.
- `Send` и `Sync` ([20.2](02-marker.md)) — два маркера потокобезопасности,
  почему `Rc` не `Send`, а `Cell` не `Sync`, и когда маркер ставят вручную.
- Общее состояние ([20.3](03-shared.md)) — `Arc`, `Mutex`, `RwLock` и
  [отравление][g-poisoning] мьютекса при [панике][g-panic].
- [Области потоков][g-scoped-threads] ([20.4](04-scoped.md)) — `thread::scope`: одалживать
  локальные данные без `Arc`, когда потоки гарантированно завершатся.
- Передача сообщений ([20.5](05-channels.md)) — каналы [`mpsc`][g-mpsc] и ожидание
  условия через `Condvar` без активного цикла.
- Цена ([20.6](06-padding.md)) — [ложное разделение][g-false-sharing] кэш-линий и как его
  убирают выравниванием.

Принцип тот же, что в [главе 16](../ch16/index.md): опасное (ручной `unsafe
impl Send`) заперто за инвариантом и снабжено `// SAFETY`, а гарантия
отсутствия гонок там, где возможно, — на типах, а не на дисциплине.

## Код главы

Глава [хостовая][g-host]: потоки операционной системы, `Mutex`, каналы. В [`no_std`][g-no-std]
потоков нет — на Cortex-M их роль играют прерывания (глава 21),
поэтому под Cortex-M [крейт][g-crate] не собирается. Miri умеет исполнять потоки и ловит
гонки данных.

```console
$ cargo test -p ch20                 # потоки, Arc/Mutex, scope, каналы, doc-тесты
$ cargo test -p ch20-solutions       # задачи A–D (C — свой futex-мьютекс)
```

Безопасность unsafe-обёрток ([20.2](02-marker.md) и задача A) проверена
Miri; гарантия от гонок для остального — на `Send`/`Sync`, а не на Miri.
