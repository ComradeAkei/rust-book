# 4.6. Где проверка ошибается

Проверка заимствований *консервативна*: всё, что она принимает, корректно,
но не всё корректное она принимает. Раздел показывает самый известный
случай, новую проверку, которая его решает, и приём, которым обходят
проверку в структурах данных с циклами.

## Условный возврат заимствования

```rust
{{#include ../../code/ch04/rejected/get_or_insert.rs}}
```

Программа корректна: если ключ найден, функция возвращает ссылку и
больше ничего не делает; если нет, ссылки `v` не существует, и `insert`
никому не мешает. rustc 1.97 думает иначе:

```text
error[E0502]: cannot borrow `*map` as mutable because it is also borrowed as immutable
 --> get_or_insert.rs:9:5
  |
5 | pub fn get_or_insert(map: &mut BTreeMap<u32, String>, k: u32) -> &String {
  |                           - let's call the lifetime of this reference `'1`
6 |     if let Some(v) = map.get(&k) {
  |                      --- immutable borrow occurs here
7 |         return v;
  |                - returning this value requires that `*map` is borrowed for `'1`
8 |     }
9 |     map.insert(k, String::new());
  |     ^^^^^^^^^^^^^^^^^^^^^^^^^^^^ mutable borrow occurs here
```

Причина в том, как NLL представляет время жизни. Ссылка, которую
возвращают, должна жить столько же, сколько `'1` — заимствование `map` у
вызывающего, то есть до конца функции и дальше. NLL считает время жизни
*одним* множеством точек программы, общим для всех путей. Раз на одном
пути заимствование `map.get(&k)` должно дожить до конца функции, оно
считается живым во всех точках до конца функции, в том числе на пути,
который идёт к `insert`. Что на этом пути ссылки `v` нет, NLL не
учитывает.

## Polonius

Polonius — новая формулировка проверки заимствований. Она отслеживает
не «где жива ссылка», а «из какого заимствования может происходить
значение в этой точке», и делает это отдельно для каждой точки. На пути
к `insert` значение, связанное с `map.get(&k)`, не существует, и
конфликта нет. Состояние на октябрь 2026 года:

| Компилятор | `get_or_insert.rs` |
|---|---|
| rustc 1.97.0 (stable) | E0502 |
| rustc 1.100.0-beta.7 | E0502 |
| nightly 1.101.0 (2026-10-21), без флагов | принимает |
| nightly 1.101.0, `-Zpolonius=next` | принимает |
| nightly 1.101.0, `-Zpolonius=off` | E0502 |

На nightly новая проверка уже включена по умолчанию, а флагом
`-Zpolonius=off` возвращается прежняя. Тест `code/ch04/tests/rejected.rs`
собирает программу закреплённым rustc и nightly с `-Zpolonius=next` и
сверяет результат с таблицей, так что, когда Polonius дойдёт до stable,
тест об этом сообщит.

```console
$ rustc +nightly --edition 2024 --crate-type lib -Zpolonius=next code/ch04/rejected/get_or_insert.rs
```

Polonius принимает не всё корректное. Есть программы, которые
отвергает и он; одну из них вы найдёте в задаче
[4.D](07-tasks.md#d-polonius).

До тех пор на stable пишут обходные пути:

Первый ищет ключ дважды. Второй — обычный для словарей: `entry` ищет один

из проверки не ссылку, а индекс или флаг, и взять ссылку заново, когда
конфликтующая операция позади.

## Графы: арена и индексы

Дерево устройств на шинах: у каждого узла есть родитель и дети. В C это
`struct node *parent` и массив `struct node *children[]`, ссылки в обе
стороны. Ссылками Rust так не сделать: `&` на родителя запрещает менять
родителя, пока жив ребёнок, а `&mut` на одно значение бывает только одна.

Есть два выхода. Первый — указатели с подсчётом ссылок `Rc` и
`RefCell`, перенос проверки во время выполнения (глава [14](../ch14.md)).
Второй — *арена*: все узлы лежат в одном векторе и принадлежат ему, а
связи между ними — номера.

```rust
{{#include ../../code/ch04/src/arena.rs:arena}}
```

Проверке заимствований здесь нечего запрещать: дерево владеет вектором,
вектор — узлами, а `NodeId` — просто число. `rename` получает `&mut self`
и меняет один узел, а номера других узлов в руках у вызывающего этому
не мешают.

Что даёт арена кроме согласия компилятора:

- номер `u32` занимает 4 байта, указатель на x86-64 — 8; на Cortex-M с
  сотней узлов хватит и `u8`;
- узлы лежат подряд, обход идёт по кэшу, а не по куче;
- арену можно сохранить во flash или передать по сети без
  преобразования указателей;
- на МК вектор заменяется статическим массивом, и куча не нужна вовсе.

Цена — ошибки, которые проверка заимствований ловила бы, становятся
логическими. Номер удалённого узла указывает на чужой узел, если на его
место положили новый. Это не неопределённое поведение (индекс проверяется
при обращении), но и не правильный ответ. Если узлы удаляются, к номеру
добавляют *поколение*: счётчик в узле, который растёт при каждом
повторном использовании места, и номер с устаревшим поколением
отвергается.

<div class="box trick">

**Трюк.** `Option<NodeId>` с `NodeId(u32)` занимает 8 байт: у `u32` нет
ниши, и признаку `None` нужно своё место (тест в `arena.rs`). Если
нумеровать узлы с единицы и хранить номер в `NonZeroU32`, `None` займёт
ноль, и `Option<NodeId>` станет 4 байта, как в разделе
[6.4](../ch06/04-niches.md). Для дерева на МК с тысячами узлов это
половина памяти связей.

</div>

<div class="box c">

**Как в C.** Арена с индексами — старый приём C для встраиваемых систем
без кучи: пулы фиксированного размера и `uint8_t next` вместо `struct
node *next`. В Rust этот приём — не экономия ради экономии, а
стандартный способ строить графы, и на нём устроены, например,
компиляторы: rustc хранит узлы своих промежуточных представлений в
векторах с типизированными номерами.

</div>
