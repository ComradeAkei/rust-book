# 4.2. Перезаимствование, NLL и двухфазные заимствования

Правило читателей и писателя строгое. Чтобы им можно было пользоваться,
компилятор делает три вещи, которых в тексте программы не видно. Без них
половина обычного кода не компилировалась бы.

## Перезаимствование

`&mut T` не `Copy`: две копии уникальной ссылки нарушили бы её
уникальность. Значит, передача `&mut` в функцию должна её перемещать, и
после `bump(r)` переменная `r` была бы пуста. Это не так:

```rust
{{#include ../../code/ch04/src/borrows.rs:reborrow}}
```

Когда тип параметра известен как `&mut u32`, компилятор пишет вместо
`bump(r)` вызов `bump(&mut *r)`: новая ссылка заимствуется *через* `r` на
время вызова. Это *перезаимствование* (reborrow). Пока живёт новая ссылка, `r`
заморожена; когда вызов кончился, `r` снова в деле. То же можно написать
явно, как `r2` в примере: между `let r2` и последним использованием `r2`
обращаться к `r` нельзя, а после — можно.

Перезаимствования вкладываются друг в друга, как кадры стека: `n`
заимствована через `r`, `r` — через `r2`. Внутренний уровень должен
закончиться раньше внешнего. На этой картине построена модель [Stacked
Borrows][g-stacked-borrows], по которой Miri проверяет `unsafe`-код (приложение
[C](../appendix-c.md)).

Неявного перезаимствования нет, если тип параметра [обобщённый][g-generic]: `T`
может оказаться чем угодно, и компилятор просто перемещает ссылку.

```text
error[E0382]: use of moved value: `r`
 --> e0382.rs:7:13
  |
5 |     let r = &mut n;
  |         - move occurs because `r` has type `&mut u32`, which does not implement the `Copy` trait
6 |     consume(r);
  |             - value moved here
7 |     consume(r);
  |             ^ value used here after move
  |
help: consider creating a fresh reborrow of `r` here
  |
6 |     consume(&mut *r);
  |             ++++++
```

Здесь `fn consume<T>(_: T)`. Подсказка компилятора и есть решение:
перезаимствовать явно.

## NLL: заимствование до последнего использования

```rust
{{#include ../../code/ch04/src/borrows.rs:nll}}
```

`first` смотрит в вектор, и `v.push` его меняет. Но `first` больше не
используется после того, как число скопировано в `copy`, и к моменту
`push` заимствования уже нет. Компилятор считает [время жизни][g-lifetime] ссылки по
*графу потока управления* (control-flow graph, CFG): от создания до последнего использования на
каждом пути. Это *нелексические времена жизни*, NLL (non-lexical
lifetimes, RFC 2094).

До NLL заимствование длилось до конца блока `{ }`, в котором создана
ссылка, и функция `nll` не компилировалась: приходилось заключать `first`
в отдельный блок. NLL включили в Rust 1.31 для [редакции][g-edition] 2018, а с
версии 1.63 прежней проверки в компиляторе нет.

NLL не значит, что компилятор «догадывается» о намерениях. Если ссылка
нужна после `push`, ошибка остаётся, как во введении к главе: там `peak`
используется в `println!` после `push`.

### Как прочитать E0502

В этом варианте ссылка нужна после изменения вектора, поэтому код
отвергается:

```rust,compile_fail,E0502
let mut v = vec![10, 20];
let first = &v[0];             // 1. заимствуем элемент для чтения
v.push(30);                    // 2. хотим изменить вектор
println!("{first}");          // 3. всё ещё нужна прежняя ссылка
```

Сообщение связывает именно эти три места: `immutable borrow occurs
here` — начало доступа через `first`; `mutable borrow occurs here` —
конфликтующий `push`; `immutable borrow later used here` — причина,
по которой первый доступ ещё нельзя закончить. Если `push` увеличит
буфер, его прежний адрес может стать недействительным.

Есть два разных исправления. Если нужно только напечатать первый
элемент, перенесите печать перед `push`: после неё ссылка не нужна.
Если число нужно сохранить для дальнейших вычислений, скопируйте его:
`let first = v[0];`. В этом примере элементы имеют тип `i32`, то есть
`Copy`: `first` станет отдельным числом, а не ссылкой внутрь вектора.
Для другого типа сначала выясните, нужно ли заимствование, передача
владения или явное клонирование; добавлять `.clone()` автоматически
не стоит.

## Двухфазные заимствования

```rust
{{#include ../../code/ch04/src/borrows.rs:two_phase}}
```

Вызов метода — это вызов функции с получателем в первом аргументе
(раздел [4.4](04-deref.md)): `v.push(v.len())` значит
`Vec::push(&mut *v, v.len())`. Аргументы вычисляются слева направо,
поэтому `&mut *v` берётся *до* того, как `v.len()` читает вектор. Буквально
по правилу это E0502, и если написать вызов функцией, компилятор так и
скажет:

```text
error[E0502]: cannot borrow `v` as immutable because it is also borrowed as mutable
 --> twophase.rs:3:23
  |
3 |     Vec::push(&mut v, v.len());
  |     --------- ------  ^ immutable borrow occurs here
  |     |         |
  |     |         mutable borrow occurs here
  |     mutable borrow later used by call
```

Методы спасает *двухфазное заимствование* (two-phase borrow). `&mut`, которое компилятор
берёт для получателя сам, сначала только *резервируется*: в этой фазе оно
ведёт себя как разделяемое и не мешает читать `v`. Изменяемым оно
становится, *активируется*, в момент вызова, когда аргументы уже
вычислены. К этому моменту `v.len()` уже вернула число, и конфликта нет.

Двухфазным бывает только то `&mut`, которое компилятор вставил сам: для
получателя метода и при неявном перезаимствовании, как во второй строке
`two_phase`, где `v` уже ссылка. Написанное руками `&mut v` или `&mut *v` —
обычное заимствование, отсюда ошибка выше.

Двухфазное заимствование не спасает, если чтение нужно *во время* вызова:

```text
error[E0502]: cannot borrow `v` as mutable because it is also borrowed as immutable
 --> extend.rs:3:5
  |
3 |     v.extend_from_slice(&v);
  |     ^^-----------------^--^
  |     | |                 |
  |     | |                 immutable borrow occurs here
  |     | immutable borrow later used by call
  |     mutable borrow occurs here
```

Здесь это защищает от настоящей ошибки: `extend_from_slice` может
перенести буфер, пока копирует из него же. Программа на C с `memcpy` из
буфера в его же конец после `realloc` — ровно случай из введения.

<div class="box hood">

**Под капотом.** Все три механизма — свойства проверки, а не машинного
кода. Ни перезаимствование, ни двухфазность не порождают инструкций:
`&mut *r` — тот же адрес, что `r`. Проверка работает на [MIR][g-mir], [промежуточном
представлении][g-ir] из раздела [3.3](../ch03/03-flags.md), где каждое
заимствование — отдельная операция с известными точками использования.
Поэтому NLL и смотрит на поток управления, а не на фигурные скобки.

</div>
