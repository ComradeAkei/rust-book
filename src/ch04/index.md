# 4. Заимствование и ссылки

## Мотивирующая проблема

Прошивка копит отсчёты двух каналов датчика в растущих буферах. Буфер
устроен как `Vec` из главы 3: указатель, длина, ёмкость, и при нехватке
места `push` вызывает `realloc`. Программа находит максимум температуры и
запоминает *указатель* на него, чтобы не копировать отсчёт. Потом приходит
девятый отсчёт:

```c
{{#include ../../code/ch04/c/samples.c}}
```

Ошибка в одной строке: `peak` указывает внутрь `temp.data`, а `push`
может этот буфер перенести. Буферы двух каналов лежат в куче рядом, расти
на месте блоку `temp` некуда, и `realloc` выделяет новый блок, копирует
данные и освобождает старый. `peak` теперь указывает в освобождённую
память. `-Wall -Wextra`, `-fanalyzer` и `clang --analyze` молчат. Без
санитайзера программа печатает мусор, и каждый раз разный:

```console
$ gcc -O2 samples.c && ./a.out && ./a.out && ./a.out
максимум 40419
максимум 18741
максимум 34959
```

Разный он потому, что glibc 2.39 хранит в освобождённом блоке свои
служебные поля, и одно из них случайное для каждого процесса. AddressSanitizer
показывает, что произошло:

```console
$ gcc -O1 -g -fsanitize=address samples.c && ASAN_OPTIONS=strip_path_prefix=$PWD/ ./a.out
=================================================================
==27823==ERROR: AddressSanitizer: heap-use-after-free on address 0x50200000005e ...
READ of size 2 at 0x50200000005e thread T0
    #0 0x5627e3a25795 in main samples.c:37
    ...
0x50200000005e is located 14 bytes inside of 16-byte region [0x502000000050,0x502000000060)
freed by thread T0 here:
    #0 0x7f04ff0fc778 in realloc ../../../../src/libsanitizer/asan/asan_malloc_linux.cpp:85
    #1 0x5627e3a253f4 in push samples.c:15
```

Это та же ошибка, что в главе 3, — обращение к освобождённой памяти, —
но причина другая. Владелец буфера здесь один, `temp`, и освобождает
его правильно. Сломался *наблюдатель*: указатель, который смотрит в чужие
данные, пока владелец их меняет. В C++ такие правила записаны в
стандарте как «инвалидация итераторов»: после `push_back`, вызвавшего
перераспределение, все указатели и итераторы в вектор недействительны.
Компилятор их не проверяет.

## Что делает Rust

- Указатель, который смотрит на чужое значение и не владеет им,
  называется *ссылкой* и бывает двух видов. `&T` — разделяемая: через неё
  можно читать, таких ссылок может быть сколько угодно. `&mut T` —
  уникальная: через неё можно менять значение, и пока она жива, других
  путей к значению нет. Правило коротко: *много читателей или один
  писатель*.
- Создание ссылки называется *заимствованием*. Компилятор проверяет, что
  заимствование не переживает владельца и не пересекается с конфликтующим.
  Та же программа на Rust не компилируется:

  ```text
  error[E0502]: cannot borrow `temp` as mutable because it is also borrowed as immutable
   --> samples.rs:4:5
    |
  3 |     let peak = temp.iter().max().unwrap(); // ссылка на максимум
    |                ---- immutable borrow occurs here
  4 |     temp.push(1500); // девятый отсчёт: буфер растёт
    |     ^^^^^^^^^^^^^^^ mutable borrow occurs here
  5 |     println!("максимум {peak}");
    |                         ---- immutable borrow later used here
  ```

  `push` требует `&mut temp`, а `peak` — читатель, который ещё нужен.
  Компилятору не надо знать, что `push` вызывает `realloc`: сигнатура
  `fn push(&mut self, value: T)` уже говорит, что функция может менять
  вектор как угодно.
- Проверка идёт только во время компиляции. Ссылка в машинном коде —
  обычный адрес, без счётчиков и флагов (раздел [4.1](01-refs.md)).
- Правило работает и в обратную сторону. Раз через `&mut T` значение
  больше никто не видит, а под `&T` оно не меняется, компилятор сообщает
  это LLVM, и тот держит значения в регистрах и векторизует циклы там,
  где C обязан перечитывать память (раздел [4.5](05-noalias.md)).

## Код главы

```console
$ cargo test -p ch04 -p ch04-solutions                  # примеры и решения
$ cargo +nightly test --doc -p ch04                     # коды ошибок в doc-тестах
$ cargo +nightly miri test -p ch04 -p ch04-solutions    # те же тесты под Miri
$ cargo asm -p ch04 --lib ch04_count_flags 0            # noalias и векторизация, раздел 4.5
$ bash code/ch04/c/run.sh                               # samples.c под ASan, count.c у GCC и clang
```

Числа в тексте получены на rustc 1.97.0 (LLVM 22.1.6) и nightly 1.101.0
(2026-10-21, LLVM 23.1.4) для `x86_64-unknown-linux-gnu`,
`thumbv6m-none-eabi`, `thumbv7m-none-eabi` и `thumbv7em-none-eabihf`,
GCC 13.3, arm-none-eabi-gcc 13.2.1 и clang 18.1. Ассемблер снят командой
`cargo asm --simplify` из release-сборки, если не сказано иное.
