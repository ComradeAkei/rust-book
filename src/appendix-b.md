# Приложение B. Изменения edition 2024, важные для системного кода

Редакция (edition) — набор правил, по которым компилятор читает исходник.
Её выбирают для каждого крейта строкой `edition` в `Cargo.toml`. Edition
2024 стабилизирована в Rust 1.85, и все крейты книги собраны с ней.
Крейты разных редакций свободно компонуются в одну программу: редакция
меняет только разбор и проверки исходника, но не ABI и не стандартную
библиотеку. Библиотека на 2021 работает в прошивке на 2024 без оговорок.

Большая часть изменений 2024 касается `unsafe`: язык требует явно
отмечать каждое место, где программист берёт обещание на себя. Для
системного кода это главное. Ниже собраны изменения, которые встречаются
в книге; полный список — в Edition Guide.

## Код приложения

```console
$ cargo test -p appendix-b -p appendix-b-2021
$ cargo +nightly test --doc -p appendix-b -p appendix-b-2021
```

Модули из `code/appendix-b/src/shared/` компилируются дважды: в крейте
`appendix-b` с edition 2024 и в `appendix-b-2021`, который подключает те
же файлы через `#[path]`. Тесты двух крейтов проверяют разный результат
на одном и том же исходнике. Код, который в одной из редакций не
компилируется, проверяют doc-тесты `compile_fail`. Коды ошибок в них
rustdoc сверяет только на nightly, поэтому вторая команда нужна.

## Сводка

| блоки `extern` | `extern "C" { ... }` | `unsafe extern "C" { ... }`, функции помечаются `safe` или `unsafe` | B.1 |

| тело `unsafe fn` | целиком небезопасный контекст | безопасно, операциям нужен свой `unsafe` (предупреждение) | B.1 |

| тип `!` без контекста | превращается в `()` | остаётся `!` | B.1 |

## B.1. unsafe стал видимым

### Блоки extern

Объявление внешней функции — само по себе обещание: сигнатура совпадает с
настоящей, и типы аргументов соответствуют ABI. Компилятор проверить
этого не может, а неверная сигнатура — неопределённое поведение уже при
вызове. Поэтому в 2024 обещание пишется явно:

```rust,ignore
{{#include ../code/appendix-b/src/compile_errors.rs:extern_block}}
```

Взамен появилась возможность пометить отдельную функцию безопасной:

```rust
{{#include ../code/appendix-b/src/ffi.rs:unsafe_extern}}
```

`getpid()` вызывается без блока `unsafe`, `strlen` — только внутри него.
Решение `safe` принимается один раз, в объявлении, и должно быть верным
для любых аргументов. Например, `abs` из libc безопасной объявить нельзя:
`abs(INT_MIN)` в C — неопределённое поведение. Подробно FFI разобран в
[главе 18](ch18/01-abi.md).

### Небезопасные атрибуты

```rust,ignore
{{#include ../code/appendix-b/src/compile_errors.rs:no_mangle}}
```

Атрибут `no_mangle` выглядит безобидно, но он создаёт глобальный символ,
и компилятор не знает, с чем этот символ встретится при компоновке.
Функция `malloc` без декорирования молча заменила бы аллокатор libc во
всей программе. То же с `export_name` и `link_section`:

```rust
{{#include ../code/appendix-b/src/ffi.rs:unsafe_attrs}}
```

В прошивках для Cortex-M так кладут данные в нужную область памяти
([гл. 8](ch08/08-sections.md), [гл. 27](ch27.md)). Макросы `#[entry]` и `#[exception]`
из `cortex-m-rt` раскрываются как раз в `export_name` и `link_section`.

### Тело unsafe fn

`unsafe fn` означает «вызывающий обязан выполнить условия». До 2024 её
тело заодно было одним большим блоком `unsafe`, и операция, требующая
отдельного обоснования, ничем не выделялась. Теперь это предупреждение:

```rust,ignore
{{#include ../code/appendix-b/src/compile_errors.rs:unsafe_op}}
```

Правильно — блок на каждую операцию и комментарий `SAFETY` у каждого
блока:

```rust
{{#include ../code/appendix-b/src/statics.rs:unsafe_op}}
```

Глава 16 и [приложение C](appendix-c.md) требуют этого от всего
`unsafe`-кода книги, а CI отклоняет предупреждения через
`clippy -D warnings`.

### static mut

Глобальная изменяемая переменная — обычное дело в C-прошивке: счётчик
тиков, который увеличивает прерывание таймера. В Rust `static mut` всегда
требовала `unsafe`, но ссылка на неё была разрешена:

```rust,ignore
{{#include ../code/appendix-b/src/compile_errors.rs:static_mut_ref}}
```

Ссылка `&COUNTER` обещает, что пока она жива, значение никто не изменит.
Прерывание, которое увеличивает счётчик, нарушает это обещание, и
оптимизатор вправе прочитать значение один раз и больше не перечитывать.
Поэтому в 2024 создать ссылку на `static mut` нельзя, а сырой указатель
`&raw mut` можно: он ничего не обещает. Но лучше обойтись без `static mut`:

```rust
{{#include ../code/appendix-b/src/statics.rs:static_mut}}
```

На Cortex-M0 нет атомарного `fetch_add` (ARMv6-M без
`LDREX`/`STREX`), и там счётчик держат в `critical_section::Mutex`
([гл. 21](ch21/04-hardware.md), [гл. 27](ch27.md)).

### set_var и remove_var

```rust,ignore
{{#include ../code/appendix-b/src/compile_errors.rs:set_var}}
```

<div class="box ref">

**Справка: почему `setenv` не потокобезопасна.** Окружение процесса — это
массив указателей `environ`, который libc хранит без блокировок. `getenv`
возвращает указатель внутрь этого массива, а `setenv` может перевыделить
массив или освободить старую строку. Если один поток вызывает `setenv`, а
другой в это время читает результат `getenv`, второй читает
освобождённую память. В руководстве glibc `setenv` помечена
`MT-Unsafe const:env`. Стандартная библиотека Rust защищает свои
обращения к окружению внутренней блокировкой, но код на C о ней не знает,
а `getenv` вызывают многие функции libc: `getaddrinfo`, `localtime`
(переменная `TZ`) и другие. Поэтому безопасной `set_var` быть не может.

</div>

Если переменная нужна дочернему процессу, окружение своего процесса
менять не надо вовсе:

```rust
{{#include ../code/appendix-b/src/statics.rs:env}}
```

Тест `child_environment` проверяет, что дочерний `printenv` видит
`TELEMETRY_PORT=4242`, а в окружении теста её нет. `set_var` остаётся для
начала `main`, до запуска потоков, с комментарием `SAFETY` об этом.

### Тип ! без контекста

Если компилятор не может вывести тип выражения, которое никогда не
завершается (`return`, `panic!()`, `loop {}`), раньше он подставлял `()`.
В 2024 тип остаётся `!`:

```rust,ignore
{{#include ../code/appendix-b/src/compile_errors.rs:never}}
```

Для системного кода опасен другой вариант того же правила: вывод типа
внутри `unsafe`. Код вида `let x = match ... { 0 => unsafe {
mem::zeroed() }, _ => return };` в 2021 создавал `()`, а в 2024 создал
бы значение типа `!`, то есть немедленное UB. Поэтому rustc 1.97 такой
код не компилирует ни в одной редакции: срабатывает запрещающий линт
`never_type_fallback_flowing_into_unsafe`. Решение одно — указать тип явно.

## B.2. Время жизни временных значений

### Условие if let

Временное значение в условии `if let` в 2021 жило до конца всей
конструкции, включая ветку `else`. С `MutexGuard` это давало взаимную
блокировку на ровном месте:

```rust
{{#include ../code/appendix-b/src/shared/temporaries.rs:relock}}
```

`cache.lock()` создаёт временный guard, `*` разыменовывает его, и
значение `Option<u32>` копируется в образец. Сам guard в 2021 живёт до
закрывающей скобки `else`, и повторный `lock()` в `else` ждёт мьютекс,
который держит этот же поток. В 2024 guard уничтожается до входа в
`else`. Разница видна на журнале:

```rust
{{#include ../code/appendix-b/src/shared/temporaries.rs:if_let}}
```

```rust
{{#include ../code/appendix-b/src/lib.rs:tests_2024}}
```

```rust
{{#include ../code/appendix-b-2021/src/lib.rs:tests_2021}}
```

Тот же исходник `temporaries.rs` в крейте 2021 даёт
`["else", "drop scrutinee"]`, и `relock_in_else` возвращает `false`: в
`else` мьютекс всё ещё занят.

<div class="box trap">

**Ловушка.** Временное значение в выражении `match` по-прежнему живёт до
конца всего `match`, во всех редакциях. `cargo fix --edition` знает об
этом и, чтобы не менять поведение, переписывает такие `if let` в `match`:

```rust,ignore
match *cache.lock().unwrap() { Some(v) => { v > 0 } _ => { cache.try_lock().is_ok() }}
```

После автоматической миграции взаимная блокировка остаётся на месте.
Просмотрите каждое такое место и верните `if let`, если новое поведение
и есть то, что нужно.

</div>

### Хвостовое выражение

Последнее выражение блока без точки с запятой — его значение. Временные
значения в нём в 2021 жили дольше локальных переменных блока:

```rust
{{#include ../code/appendix-b/src/shared/temporaries.rs:tail}}
```

В 2024 журнал `["drop temporary", "drop local"]`, в 2021 наоборот. Из-за
старого правила не компилировался очевидный код:

```rust,ignore
{{#include ../code/appendix-b-2021/src/lib.rs:tail_2021}}
```

Временный `Ref` из `c.borrow()` уничтожался после `c`, то есть пережил
бы `RefCell`, из которого взят. В 2024 этот код компилируется.

## B.3. Захват времён жизни в impl Trait

Тип возврата `impl Trait` скрывает настоящий тип, но компилятор должен
знать, какие параметры функции этот тип может содержать. В 2021 скрытый
тип захватывал только параметры-типы, а время жизни — только если его
назвали явно:

```rust,ignore
{{#include ../code/appendix-b-2021/src/lib.rs:rpit_2021}}
```

В 2024 захватывается всё, что видно в сигнатуре. Чаще всего это то, что
нужно, но иногда захват лишний:

```rust,ignore
{{#include ../code/appendix-b/src/compile_errors.rs:overcapture}}
```

Итератору `0..v.len()` срез не нужен, а компилятор по сигнатуре считает,
что нужен, и держит заимствование `buf`. Точный список захваченного
задаёт `use<..>`:

```rust
{{#include ../code/appendix-b/src/rpit.rs:rpit}}
```

`use<>` — «не захватывает ничего», `use<'a, T>` — только перечисленное.
`cargo fix --edition` сам добавляет `use<..>` туда, где 2021 захватывал
меньше, чем захватит 2024. Механизм разобран в [разделе 5.7](ch05/07-capture.md).

## B.4. Образцы

Когда образец без `&` сопоставляется со ссылкой, Rust неявно берёт ссылку
на части: в `if let Some(x) = opt` при `opt: &Option<u32>` получается
`x: &u32`. В 2021 слово `mut` в таком образце молча сбрасывало это
правило, и `x` становился копией `u32`:

```rust
{{#include ../code/appendix-b-2021/src/lib.rs:binding_2021}}
```

Одно слово меняло тип переменной, и прочитать это из кода было трудно.
В 2024 так нельзя:

```rust,ignore
{{#include ../code/appendix-b/src/compile_errors.rs:binding}}
```

Нужно написать ссылочный образец явно, и тогда `mut x` снова означает
копию:

```rust
{{#include ../code/appendix-b/src/rpit.rs:binding_modes}}
```

То же правило запрещает `ref` и `&` внутри неявно-ссылочного образца
([гл. 2](ch02/03-match.md#режимы-связывания)).

## B.5. Мелкие изменения языка

`Box<[T]>` получил `IntoIterator` по значению. Вызов `b.into_iter()` в
2021 по историческим причинам выбирал реализацию для `&Box<[T]>`:

```rust
{{#include ../code/appendix-b/src/shared/misc.rs:boxed_slice}}
```

Тест в 2024 получает `core::option::Option<u32>`, в 2021 —
`core::option::Option<&u32>`, и компилятор 2021 предупреждает
`boxed_slice_into_iter`.

Фрагмент `$e:expr` в `macro_rules!` теперь принимает и блоки
`const { ... }`, и `_`. Порядок правил макроса из-за этого может дать
другой результат:

```rust
{{#include ../code/appendix-b/src/shared/misc.rs:expr_fragment}}
```

В 2024 обе функции возвращают `"expr"`, в 2021 — `"const-блок"` и
`"подчёркивание"`. Старое поведение сохраняет фрагмент `$e:expr_2021`,
его и подставляет `cargo fix --edition`.

Слово `gen` зарезервировано под будущие генераторы: `let gen = 1;` даёт
``expected identifier, found reserved keyword `gen` ``. Старый идентификатор
пишется как `r#gen`. В прелюдию добавлены `Future` и `IntoFuture`, и
`fn f<F: Future>()` не требует импорта; в 2021 это ошибка E0405.

## B.6. Cargo, rustdoc и миграция

Резолвер зависимостей версии 3 учитывает поле `rust-version`: из
нескольких подходящих версий зависимости он выбирает ту, что
поддерживает объявленную минимальную версию компилятора. Для пакета с
edition 2024 он включён по умолчанию, но в виртуальном workspace (как в
этом репозитории) его указывают явно: `resolver = "3"` в корневом
`Cargo.toml`.

Doc-тесты пакета с edition 2024 rustdoc собирает в одну программу, и они
выполняются заметно быстрее. Doc-тест, который меняет глобальное
состояние процесса (окружение, текущий каталог, обработчики сигналов),
может помешать соседним; такой тест помечают атрибутом
`standalone_crate`. Doc-тесты `compile_fail` по-прежнему компилируются
по одному.

Переход крейта на новую редакцию:

```console
$ cargo fix --edition        # ещё на 2021: правит код под правила 2024, сохраняя поведение
$ # в Cargo.toml: edition = "2024"
$ cargo build && cargo test
```

На крейте со всеми примерами этого приложения `cargo fix --edition`
сделал следующее: добавил `unsafe` к блоку `extern` и `#[unsafe(...)]` к
`no_mangle`, обернул операции в теле `unsafe fn` в блоки `unsafe`,
обернул вызов `set_var` в `unsafe` с комментарием `// FIXME: Audit that
the environment access only happens in single-threaded code.`, переписал
`if let` с временным значением в `match`, добавил `use<>` к `impl
Iterator`, сделал образец явным (`&Some(mut x)`), заменил
`into_iter()` у `Box<[T]>` на `iter()`, `expr` на `expr_2021` и `gen` на
`r#gen`. Ссылку на `static mut` он не исправил, и после смены редакции
сборка остановилась на ней. Хвостовые выражения он тоже не трогает:
код, который зависел от старого порядка уничтожения, надо найти самому.

<div class="box trick">

**Трюк.** Перед миграцией включите группу линтов
`rust_2024_compatibility` в 2021: `#![warn(rust_2024_compatibility)]`.
Компилятор покажет все места, где поведение изменится, включая те, что
`cargo fix` правит молча. Особенно полезны `if_let_rescope` и
`tail_expr_drop_order`: в них меняется порядок деструкторов, а значит,
время удержания мьютексов и момент освобождения ресурсов.

</div>
