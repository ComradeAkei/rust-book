# 0.2. cargo: сборка, профили, проверки

*cargo* — система сборки и менеджер пакетов Rust: он скачивает
зависимости, вызывает rustc с нужными ключами, запускает тесты и примеры,
а сторонние подкоманды вроде `cargo asm` добавляют ему новые команды.

## Workspace книги

Весь код книги — один *workspace*: набор крейтов с общим `Cargo.lock`,
общим каталогом сборки `target/` и общими [профилями][g-profile]. В корневом
`Cargo.toml` перечислены его члены:

- `code/chNN` — примеры глав, их фрагменты попадают в текст;
- `exercises/chNN` — заготовки задач, они не проходят тесты, пока задачи не
  решены;
- `solutions/chNN` — эталонные решения;
- `project/` — сквозной проект.

Поле `default-members` говорит, что собирать и тестировать, когда пакет не
указан: всё, кроме заготовок. Поэтому `cargo test` в корне зелёный, а
`cargo test -p ch00-exercises` падает, пока вы не решите задачи. Прошивки
живут в отдельном workspace `firmware/`: у них другая цель по умолчанию,
свой скрипт компоновщика и свой способ запуска.

Команды, которыми пользуется книга:

| Команда | Что делает |
|---|---|
| `cargo check -p ch00` | Проверка типов и [заимствований][g-borrowing] без генерации кода. Самая быстрая обратная связь |
| `cargo build -p ch00 --release --target thumbv7m-none-eabi` | Сборка под Cortex-M3 |
| `cargo test -p ch00` | Модульные и интеграционные тесты, [doc-тесты][g-doctest], сборка примеров |
| `cargo run -p ch00 --example fold` | Сборка и запуск примера из `examples/` |
| `cargo doc -p ch00 --open` | Документация из `///`-комментариев |
| `cargo clippy --workspace --all-targets` | [Линтер][g-lint] (раздел [0.5](05-checks.md)) |
| `cargo fmt --all` | Форматирование по `rustfmt.toml` |

## Профили

*Профиль* (profile) — именованный набор параметров компилятора. Встроенных профилей
два: `dev` для `cargo build` и `release` для `cargo build --release`.
Значения по умолчанию в cargo 1.97:

| Параметр | dev | release | Что меняет |
|---|---|---|---|
| `opt-level` | 0 | 3 | Уровень оптимизации: 0–3, `"s"` и `"z"` для размера |
| `debug` | `true` | `false` | Отладочная информация [DWARF][g-dwarf]: строки, переменные, типы |
| `debug-assertions` | `true` | `false` | `debug_assert!` и [проверки предусловий][g-ub-checks] в `core` |
| `overflow-checks` | `true` | `false` | [Паника][g-panic] при целочисленном переполнении |
| `lto` | `false` | `false` | Оптимизация всей программы на этапе компоновки |
| `codegen-units` | 256 | 16 | На сколько частей делится крейт для параллельной кодогенерации |
| `incremental` | `true` | `false` | Повторное использование результатов прошлой сборки |
| `panic` | `"unwind"` | `"unwind"` | Раскрутка стека или немедленное завершение |
| `strip` | `"none"` | `"debuginfo"` | Что вырезать из готового файла |

В корневом `Cargo.toml` книги профиль release дополнен строкой
`debug = true`: листинги `cargo asm` и сессии gdb должны показывать строки
исходника. У прошивок в `firmware/Cargo.toml` свои профили: `dev` с
`opt-level = "s"`, потому что без оптимизации форматирование из `core` не
помещается во флеш-память, и `release` с [LTO][g-lto] и одной [единицей
кодогенерации][g-codegen-unit].

Что cargo на самом деле передаёт компилятору, видно с ключом `-v`.
Передаются только отличия от умолчаний самого rustc:

```console
$ cargo build -p ch00 --example overflow --release -v
     Running `rustc --crate-name overflow ... -C opt-level=3 ... -C debuginfo=2 ...`
```

## Одна строка, два поведения

```rust
{{#include ../../code/ch00/examples/overflow.rs:overflow}}
```

```console
$ cargo run -p ch00 --example overflow
thread 'main' (11392) panicked at code/ch00/examples/overflow.rs:12:16:
attempt to add with overflow
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
$ echo $?
101

$ cargo run -p ch00 --example overflow --release
255 + 1 = 0
```

Это не неопределённое поведение, как в C, а два разрешённых языком
варианта. *Reference* (The Rust Reference), справочник языка, обязывает сборку с отладочными проверками паниковать
при переполнении целого, а в остальных сборках разрешает либо панику, либо
результат по модулю 2ⁿ. rustc выбирает между ними по флагу
`overflow-checks`. Код, который полагается на [заворачивание][g-wrapping], обязан
написать его явно (`wrapping_add`), а код, которому нужна проверка в любом
профиле, — `checked_add`. Оба семейства методов разобраны в главе 1.

<div class="box trap">

**Ловушка.** Тест, который проходит в `cargo test`, может упасть в
release, и наоборот. Если логика зависит от переполнения, проверьте оба
профиля: `cargo test` и `cargo test --release`. Ещё хуже обратная
ситуация: в dev до переполнения счётчика миллисекунд дело не доходит,
потому что отладочный запуск длится минуты, а в release 32-битный счётчик
молча обнуляется через 2³² мс, то есть через 49,7 суток. Ровно так в 1999
году зависали Windows 95 и 98, проработавшие без перезагрузки семь недель.

</div>

<div class="box trick">

**Трюк.** Чтобы попробовать параметр профиля, не обязательно править
`Cargo.toml`. Ключ `--config` переопределяет любую настройку cargo из
командной строки:

```console
$ cargo run -p ch00 --example overflow --release --config 'profile.release.overflow-checks=true'
thread 'main' (11716) panicked at code/ch00/examples/overflow.rs:12:16:
attempt to add with overflow
```

С `-v` видно, что к флагам rustc добавилось `-C overflow-checks=on`. Ключ
принимает и путь к файлу `.toml` с целыми таблицами настроек. Этим
пользуется задача 0.B.

</div>

<div class="box c">

**Как в C.** Профили — это `-O0 -g` и `-O2` в Makefile, но с двумя
отличиями. Первое: в C флаги задают только скорость и отладку, а
семантика программы от них не зависит (кроме программ с UB, где зависит
всё). В Rust профиль переключает одну документированную вещь — поведение
при переполнении. Второе: в C знаковое переполнение — UB, и GCC с `-O2`
удаляет проверки вида `if (x + 1 < x)`. Ближайший аналог `overflow-checks`
в C — `-ftrapv` или `-fsanitize=signed-integer-overflow`, но оба ловят
только знаковые типы. Беззнаковые проверяет лишь Clang с
`-fsanitize=unsigned-integer-overflow`, и это уже не стандарт, а
диагностика.

</div>

## Единицы кодогенерации и LTO

rustc компилирует крейт целиком, а не файл за файлом, как C. Чтобы
использовать все ядра, он делит крейт на *единицы кодогенерации* (codegen
units) и отдаёт их LLVM параллельно. Плата за скорость: каждая единица
оптимизируется отдельно, и функция из одной единицы не [встраивается][g-inlining] в
другую. В release rustc частично возвращает упущенное: значение
`lto = false` в cargo означает не «без LTO», а «ThinLTO между единицами
одного крейта». По-настоящему выключает его только `lto = "off"`. А
`codegen-units = 1` отдаёт LLVM весь крейт одним модулем.

*LTO* (link-time optimization) идёт дальше: оптимизирует всю программу вместе
со всеми зависимостями, включая стандартную библиотеку. `lto = "thin"`
делает это по частям и параллельно, `lto = true` («fat») — одним модулем.
Сколько это даёт на практике, вы измерите в задаче 0.B.
