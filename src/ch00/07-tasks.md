# 0.7. Задачи

Заготовки лежат в `exercises/ch00`, тесты общие для заготовок и решений
лежат в `tests-shared/ch00.rs`. Проверка:

```console
$ cargo test -p ch00-exercises            # задачи A, B и C
$ cargo test -p ch00-exercises task_c     # одна задача
$ cd firmware && bash run-demos.sh        # задача D вместе с остальными прошивками
```

Пока задачи не решены, тесты падают: на `todo!()`, на незаполненных
ответах или на слишком большом файле. Тесты задач A и B сами запускают
cargo и `nm`, поэтому нужен `nm` из binutils или `llvm-nm` (приложение D).
Разборы решений в [приложении E](../appendix-e/ch00.md), но сначала
попробуйте сами.

## A. Какие функции доживут до release

Пример `code/ch00/examples/vanish.rs` содержит пять функций:

```rust
{{#include ../../code/ch00/examples/vanish.rs:five}}
```

Не собирая пример, решите для каждой функции, останется ли её символ в
исполняемом файле release-сборки. Ответы запишите в
`exercises/ch00/src/a_vanish.rs` (`Some(true)` — останется) и для
каждого добавьте комментарий: какой механизм её сохранит или уберёт.
Только после этого запустите `cargo test -p ch00-exercises task_a`. Тест
соберёт пример, прочитает таблицу символов и покажет ошибки построчно:

```text
№1 crc_step         ваш ответ: есть, на самом деле: нет
```

Для каждой ошибки найдите механизм, который вы не учли, и подтвердите
его двумя инструментами: `cargo asm -p ch00 --example vanish` (что есть
в объектном файле крейта) и `nm -C` (что есть в готовом файле). Для
`nm` берите файл из обычной `cargo build --release`: `cargo asm`
пересобирает крейт со своими ключами в тот же каталог `target`. Какими
ключами, покажет `cargo asm -vv`. Инструменты ответят по-разному для
двух функций, и причины у них разные. Объясните обе.

Вопрос к отчёту: как изменить вызов функции №3 в `main`, чтобы её символ
остался, не трогая атрибуты самой функции?

## B. Hello world на диете

Пример `hello` из `code/ch00/examples` в release-профиле книги весит
4,2 МиБ (раздел [0.3](03-asm.md)). Уменьшите его в два этапа.

Первый этап — только настройки профиля. Допишите ключи в
`exercises/ch00/tiny.toml` и собирайте пример так:

```console
$ cargo build --release -p ch00 --example hello --config exercises/ch00/tiny.toml
$ ls -l target/release/examples/hello
```

Ключи добавляйте по одному и после каждого записывайте размер в таблицу.
Для каждой строки объясните, что именно исчезло из файла: проверяйте
`size -A` и `cargo bloat`, а не догадки. Затем включите каждый ключ
отдельно поверх `debug = false` и сравните со вкладом в цепочке. Почему
вклад одного и того же ключа зависит от того, что включено до него?
Тест `task_b::tiny_profile` ждёт файл не больше 300 000 байт, который
по-прежнему печатает `Hello, world!`.

Второй этап — без стандартной библиотеки Rust. Крейт
`exercises/ch00/hello-nostd` сейчас обычный hello world со своим
workspace. Сделайте из него программу с [`#![no_std]`][g-no-std] и `#![no_main]`,
которая печатает ту же строку через `write` из libc, завершается с
кодом 0 и весит не больше 16 КиБ. Тест `task_b::hello_without_std`
проверяет вывод, код возврата и размер. Что в этой программе
выполняется до вашей функции `main` и кто её вызывает?

Исследовательская часть, на nightly: соберите `hello` первого этапа,
пересобрав стандартную библиотеку из исходников с теми же настройками
(`-Zbuild-std`), а затем ещё и со стратегией паники `immediate-abort`.
Объясните, откуда берётся каждая из двух разниц в размере.

## C. Сумма массива на двух архитектурах

В `exercises/ch00/src/c_sum.rs` реализуйте три функции:

- `ch00c_sum_wrapping` — сумма по модулю 2³², как сложение `uint32_t` в
  C;
- `ch00c_sum_wide` — точная сумма в `u64`;
- `ch00c_sum_checked` — точная сумма, если она помещается в `u32`, иначе
  `None`. Промежуточные переполнения не в счёт: для `[u32::MAX, 1]`
  ответ `None`, хотя сумма по модулю 2³² равна нулю.

Тесты проверяют все длины от 0 до 67, чтобы задеть и основной цикл, и
хвост. Когда они пройдут, снимите ассемблер всех трёх функций для двух
целей:

```console
$ cargo asm -p ch00-exercises --lib ch00c_sum_wrapping
$ cargo asm -p ch00-exercises --lib --target thumbv7em-none-eabihf ch00c_sum_wrapping
```

В отчёте для каждой функции и цели объясните: в каких регистрах пришли
указатель и длина и как вернулся результат (у `Option<u32>` два слова);
во что превратился цикл — векторные инструкции, [развёртка][g-unrolling], отдельный
хвост; почему `ch00c_sum_wide` на x86_64 обрабатывает за итерацию вдвое
меньше элементов, чем `ch00c_sum_wrapping`, а на Cortex-M4F не
[векторизуется][g-vectorization] ни одна из функций, хотя в ARMv7E-M есть SIMD-инструкции.

Вторая часть. Первое, что приходит в голову для `ch00c_sum_checked`, —
`try_fold` с `checked_add`. Это правильно, но такой цикл не
векторизуется. Объясните по ассемблеру почему, а затем перепишите
функцию так, чтобы на x86_64 её основной цикл стал векторным, как у
`ch00c_sum_wide`, и докажите, что промежуточная сумма не переполняется
ни на каком срезе, даже из 2³² элементов.

## D. От сброса до main

Прошивка `firmware/ch00-reset` почти ничего не делает в `main`:

```rust
{{#include ../../firmware/ch00-reset/src/main.rs:statics}}
```

```rust
{{#include ../../firmware/ch00-reset/src/main.rs:main}}
```

Всё интересное происходит раньше. Допишите сценарий gdb
`exercises/ch00/reset.gdb`, который на Cortex-M4F (`mps2-an386`) проходит
путь от сброса до первой строки `main` и показывает:

1. начальные SP и PC и откуда ядро их взяло;
2. момент, когда обнуляется `.bss` (переменная `BOOTS`), и инструкцию,
   которая это сделала;
3. момент, когда `.data` копируется из флеш-памяти (`SIGNATURE`), и
   адрес, откуда пришло значение;
4. момент, когда включается FPU (регистр CPACR, `0xE000_ED88`);
5. остановку в `main` и стек вызовов в этой точке.

Сценарий не должен зависеть от адресов кода: они меняются от любой
правки прошивки. Команды запуска QEMU и gdb записаны в заголовке
сценария. Учтите, что QEMU обнуляет ОЗУ при старте, а настоящий кристалл
нет. Как доказать, что `BOOTS` обнулил именно стартовый код, а не
эмулятор?

В отчёте опишите по своему выводу всё, что выполняется до `main`, и
ответьте на два вопроса. Почему начальное значение `SIGNATURE` занимает
место и во флеш-памяти, и в ОЗУ, а `BOOTS` в образе прошивки не занимает
ни байта? Что случится, если FPU не включить? Ответ на второй вопрос
проверьте прошивкой:

```console
$ cargo run --release -p ch00-reset --bin nocp --target thumbv7em-none-eabihf
```

Её код — в `firmware/ch00-reset/src/bin/nocp.rs`. Объясните каждое
число в её выводе.
