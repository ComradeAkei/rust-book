# 22. Асинхронность изнутри

**Перед чтением.** Понадобятся [перемещения](../ch03/01-ownership.md),
[замыкания](../ch12/01-capture.md) и [потоки](../ch20/01-spawn.md).
Асинхронная задача умеет приостановиться, сохранив состояние, и продолжить
работу позже. Она не обязана иметь отдельный поток ОС. Сначала разберите
один вызов poll и его результат; [исполнители][g-executor] и [закрепление][g-pinning] в памяти
появятся после этого.

## Мотивирующая проблема

Сервер держит тысячу соединений. Поток на соединение — это тысяча стеков
(у `std::thread` по умолчанию 2 МиБ адресного пространства каждый, у
pthread обычно 8 МиБ — по `ulimit -s`) и тысяча задач в планировщике ядра,
большинство из которых просто ждут байтов. В C эту
проблему решают одним потоком и циклом событий — и платят читаемостью:

```c
/* C: libuv-стиль — логика разорвана по колбэкам, состояние — руками */
struct conn { uv_tcp_t tcp; char buf[4096]; size_t len, sent; int state; };

static void on_write(uv_write_t *req, int status) {
    struct conn *c = req->data;
    if (status < 0) { close_conn(c); return; }
    c->state = READING;                 /* вернуться к чтению */
    uv_read_start((uv_stream_t *)&c->tcp, alloc_cb, on_read);
}

static void on_read(uv_stream_t *s, ssize_t n, const uv_buf_t *b) {
    struct conn *c = s->data;
    if (n <= 0) { close_conn(c); return; }
    c->state = WRITING;                 /* что ждём — помним сами */
    uv_read_stop(s);
    /* ... запустить запись, продолжение — в on_write ... */
}
```

Последовательный алгоритм «прочитать — отправить — повторить» разрезан на
колбэки; локальные переменные переехали в `struct conn`, номер шага — в
поле `state`, а [время жизни][g-lifetime] буфера держится на дисциплине программиста.
Это ручной **конечный автомат**. На микроконтроллере то же самое делают
protothreads — макросы поверх `switch`, превращающие функцию в автомат, где
локальные переменные нельзя держать через точку ожидания.

## Что делает Rust

`async fn` — это тот же автомат, но построенный **компилятором**. Код пишется
последовательно, `.await` отмечает точку ожидания, а компилятор сам
раскладывает живые через неё переменные по состояниям, считает размер и
проверяет [заимствования][g-borrowing]. Никакого рантайма язык не навязывает: [`Future`][g-future] —
просто значение с методом `poll`, и кто его опрашивает — решает программа.

- `Future`, `poll`, `Context`, [`Waker`][g-waker] ([22.1](01-future.md)) — интерфейс
  между задачей и тем, кто её исполняет, и простейший `block_on`.
- `async fn` как автомат ([22.2](02-state.md)) — во что компилируется
  `.await`, что попадает в состояние и от чего зависит размер future.
- [`Pin`][g-pinning] и `Unpin` ([22.3](03-pin.md)) — зачем [самоссылающемуся][g-self-referential] автомату
  обещание «не двигать» и как его даёт система типов.
- [Исполнитель][g-executor] и [реактор][g-reactor] ([22.4](04-executor.md)) — очередь задач на
  будильниках, `epoll` и io_uring, [`Send`][g-send-sync] у задач, tokio.
- `select`, `join` и отмена ([22.5](05-cancel.md)) — отмена через `drop` и
  [cancellation safety][g-cancel-safety].
- Async на микроконтроллере ([22.6](06-bare.md)) — исполнитель без кучи на
  `RawWaker`, сон в `wfi`, embassy.

Главная мысль та же, что в главах 20 и 21: опасное заперто за инвариантом.
Самоссылку нельзя сдвинуть, потому что `Pin` не выдаёт `&mut`; будильник
можно отдать в другой поток, потому что он `Send + Sync`; а автомат,
держащий `MutexGuard` через `.await`, не уйдёт в многопоточный исполнитель,
потому что он не `Send`.

## Код главы

Примеры 22.1–22.6 лежат в `code/ch22`. Future, автоматы, `Pin`, `select` и
исполнитель без кучи (22.6) собираются без std — на все три [цели][g-target] Cortex-M;
исполнитель с очередью на `Arc` (22.4) и таймер на потоке — [хостовые][g-host].

```console
$ cargo test -p ch22                   # примеры и doc-тесты Pin
$ cargo test -p ch22-solutions         # задачи A–D2
$ cd firmware && cargo run --release -p ch22-async     # SysTick и wfi в QEMU
$ printf 'ping\n' | cargo run --release -p ch22-tasks  # задача D1: SysTick и UART
```

Размеры автоматов, приведённые в тексте, сняты `size_of_val` на rustc 1.97
для x86-64 и закреплены тестами группы `observed`: [раскладка][g-layout] автоматов не
стабилизирована. Гарантии языка (что живое через `.await` хранится в
автомате) проверяют отдельные тесты. Все однопоточные примеры проходят
Miri в обеих моделях [алиасинга][g-aliasing].
