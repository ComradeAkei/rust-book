# 22.7. Задачи

Все задачи решаются кодом: заготовки — в `exercises/ch22`, тесты, общие для
заготовок и решений, — в `tests-shared/ch22.rs`. В программе курса у главы
две задачи «D»; как и в главе 1, они разведены по номерам: D1 — исполнитель
для микроконтроллера, D2 — отмена.

$ cargo test -p ch22-exercises b_         # одна задача
$ cargo test -p ch22-solutions            # эталон

[приложении E](../appendix-e/ch22.md), но сначала попробуйте сами.

## B. Исполнитель с таймерами

Однопоточный исполнитель с очередью задач, как в [22.4](04-executor.md),
плюс таймеры: `handle.sleep(ms).await`. Время виртуальное: когда готовых
задач нет, исполнитель «перематывает» часы на ближайший срок и будит всех,
чей срок настал. Так тест с десятью тысячами таймеров по минуте проходит за
миллисекунды, а порядок срабатывания детерминирован. Структуры, ручка
`Handle` и будильник через `Arc` даны; ваше дело — `Runtime::run`,
`Sleep::poll` и `Drop` для `Sleep`.

```rust
{{#include ../../exercises/ch22/src/b_timers.rs:skeleton}}
```

Таймеры — в `BinaryHeap<Reverse<Timer>>`, упорядоченные по сроку, а при
равном сроке — по порядку постановки (`seq`). Тесты требуют: равные сроки
срабатывают в порядке постановки, `sleep(0)` готов сразу, задачи могут
ставить задачи, а `Sleep`, проигравший `select` и уроненный, не будит и *не
двигает часы* (`b_cancelled_sleep_does_not_move_the_clock`): после
`select(sleep(10), sleep(1000))` исполнитель обязан закончить на 10, а не
на 1000. Для этого у таймера в куче и у `Sleep` общая ячейка с будильником,
и `Drop` её опустошает.

## C. Реактор на epoll и эхо-сервер

Вторая половина рантайма из [22.4](04-executor.md): реактор. Задача,
получившая `WouldBlock`, оставляет реактору интерес (читать или писать) и
будильник; исполнитель, когда готовых задач нет, спит в `epoll_wait` и
будит тех, чьи дескрипторы ожили. Системные вызовы `epoll_create1`,
`epoll_ctl`, `epoll_wait` и `close` даны — прямой инструкцией `syscall`, как
[`futex`][g-futex] в задаче C главы 20, без крейта libc:

```rust

```

Исполнитель, сервер и для сравнения сервер «поток на соединение» тоже даны.
Ваше дело — реактор (`arm`, `still_waiting`, `wait`), future готовности
`Ready::poll` и обработчик соединения `echo`:

```rust
{{#include ../../exercises/ch22/src/c_epoll.rs:reactor}}
```

Дескрипторы ставьте с `EPOLLONESHOT`: сработав, дескриптор выключается до
следующего `arm`, и у него не больше одного ждущего. Тесты: тысяча
клиентов одновременно — сервер обязан держать все соединения сразу на
одном потоке (`peak == 1000`); передача 16 МиБ с опоздавшим читателем; и
запись в локальный сокет, которая гарантированно упирается в
`WouldBlock` и обязана дождаться `EPOLLOUT`. Задача — только Linux x86-64,
под Miri её тесты помечены `ignore`.

Затем сравните реактор с потоками по памяти и времени:

```console
$ cargo test -p ch22-solutions --release -- --ignored c_compare --nocapture
```

Тест снимает RSS процесса в момент, когда живы все 1000 соединений, у
обоих серверов. Объясните разницу на соединение и почему время почти
одинаково.

## D1. Исполнитель без кучи для Cortex-M

Развитие [22.6](06-bare.md): задач несколько, у каждой свой флаг
готовности, а будильник задачи — адрес её флага. Обработчик прерывания
поднимает флаг той задачи, чьё событие пришло, и исполнитель опрашивает
только её. Задачи живут в *арене*: тип future безымянный, в `static` его не
записать, поэтому арена хранит future как байты `'static`-буфера и отдаёт
`Pin<&'static mut dyn Future>`. Ваше дело — `Arena::alloc` и
`Executor::run`:

Источники событий для прерываний — счётчик `Signal` и очередь байтов
`ByteQueue` (кольцо SPSC из [21.5](../ch21/05-spsc.md) на [атомиках][g-atomic] без RMW)
— даны. Тесты на хосте имитируют прерывания в `idle` и требуют, чтобы
чужие события соседку не будили (`d1_only_woken_task_is_polled`: опросов
ровно `[4, 6]` при 8 снах), а поднятый флаг завершённой задачи не заставлял
исполнитель крутиться.

На железе то же самое делает прошивка `firmware/ch22-tasks` на Cortex-M3
(QEMU `lm3s6965evb`): задачу 0 будит SysTick, задачу 1 — прерывание приёма
UART0, а строку для UART0 QEMU берёт со стандартного ввода:

```console
$ cd firmware && printf 'ping\n' | cargo run --release -p ch22-tasks
```

Прошивка собрана на эталоне. Чтобы запустить свою реализацию, замените в
`firmware/ch22-tasks/Cargo.toml` зависимость на `ch22-solutions = { package
= "ch22-exercises", path = "../../exercises/ch22", default-features = false
}` — код прошивки менять не нужно. В разборе сравните устройство с
embassy: где у него лежат задачи, на что указывает будильник, как он спит.

## D2. Отменобезопасное чтение кадров

Кадр — байт длины `N` и `N` байт тела; источник отдаёт по байту за опрос,

одна отмена посреди кадра сбивает поток: следующим «байтом длины»
