# 8.2. Крейты, пакеты и рабочие пространства

## Три слова

*Крейт* (crate) — единица компиляции: одно дерево модулей, один вызов `rustc`,
один результат (библиотека или программа). В C единица компиляции —
файл, в Rust — весь крейт, поэтому компилятор видит все модули сразу и
проверяет видимость, типы и [заимствования][g-borrowing] через границы файлов.

*Пакет* (package) — то, что описывает один `Cargo.toml`: не больше одной
библиотеки, сколько угодно программ (`src/bin/*.rs`), тесты, примеры и
[сценарий сборки][g-build-script] `build.rs`. Каждый из них — отдельный крейт. У
`ch08-sections` в `firmware` два крейта-программы, `target` и `boot`, и
крейт-библиотека с общим [`#[panic_handler]`][g-panic-handler].

*Рабочее пространство* (workspace) — несколько пакетов с общим
`Cargo.lock` и общим каталогом `target`. Этот репозиторий — два
пространства. В корневом живут примеры глав, заготовки, решения и
проект, все для [хоста][g-host]. Прошивки вынесены в `firmware`: у них своя [цель][g-target]
по умолчанию (`thumbv7m-none-eabi`), свой [скрипт компоновки][g-linker-script] и свой
раннер QEMU в `firmware/.cargo/config.toml`, и в общем пространстве эти
настройки мешали бы хостовым тестам.

## Что лежит в rlib

Библиотека для других крейтов Rust собирается в `rlib` — архив `ar`, как
`.a` в C, но с дополнительным членом:

```console
$ ar t target/release/libch08.rlib
lib.rmeta
lib.rmeta-link
ch08-dbc3f91b9c39215e.ch08.a82abf8906bb433a-cgu.0.rcgu.o
$ ar x target/release/libch08.rlib && wc -c lib.rmeta lib.rmeta-link ch08-*.o
35400 lib.rmeta
  640 lib.rmeta-link
20880 ch08-dbc3f91b9c39215e.ch08.a82abf8906bb433a-cgu.0.rcgu.o
56920 total
```

Объектный файл — машинный код крейта. `lib.rmeta` — *метаданные крейта*
(crate metadata): сигнатуры, типы, их [раскладка][g-layout], реализации [трейтов][g-trait], а для
обобщённых и встраиваемых функций — их тела в [промежуточном представлении][g-ir]
[MIR][g-mir]. Метаданные заменяют заголовки C, но пишет их компилятор из того же
исходника, поэтому разойтись с кодом они не могут. Когда крейт
`ch08-sections` вызывает `ch08::generated::sensor`, rustc читает
сигнатуру из метаданных `ch08`, а не из текста, который кто-то вручную
держал в согласии с реализацией.

В метаданных же лежит причина, по которой маленькие функции из
`ch08` в release-сборке не имеют машинного кода в самой библиотеке
(раздел [8.1](01-modules.md)): их MIR конкретизируется и встраивается в
крейте, который их вызывает. Тот же механизм делает возможными
обобщённые функции без заголовочных шаблонов: `checksum::<[u8; 4]>`
появится там, где её впервые вызвали с массивом.

<div class="box c">

**Как в C.** Заголовок — договор, который компилятор не проверяет на
соответствие реализации. Поменяли тип параметра в `.c` и забыли в
`.h` — каждый файл компилируется без ошибок, а вызов передаёт аргумент
не в том регистре (глава 0, раздел [0.4](../ch00/04-abi.md)). В Rust
такой рассинхронизации нет, потому что заголовка нет: Cargo пересобирает
зависимые крейты, когда меняются метаданные их зависимостей.

</div>

## Версии и Cargo.lock

Зависимости прошивок описаны один раз для всего пространства
`firmware`:

```toml
{{#include ../../firmware/Cargo.toml:deps}}
```

а пакеты на них ссылаются:

```toml
{{#include ../../firmware/ch08-sections/Cargo.toml:deps}}
```

Строка `"0.7.7"` — не точная версия, а требование `^0.7.7`: подходит
любая `0.7.x` не ниже `0.7.7`. Cargo понимает версии по правилам
semver: несовместимые изменения поднимают старший номер, а у версий
`0.x` их роль играет второй. Значит, `^0.7.7` — это `>=0.7.7, <0.8.0`, а
`^1.2.3` было бы `>=1.2.3, <2.0.0`.

Какая версия выбрана на самом деле, записано в `Cargo.lock`:

```toml
[[package]]
name = "cortex-m"
version = "0.7.9"
source = "registry+https://github.com/rust-lang/crates.io-index"
checksum = "844b9697e922c99847eed515c6eb6d101e7ce62ff556fcaec243798291427ee8"
```

Файл фиксирует точную версию и контрольную сумму каждого крейта во всём
дереве, поэтому сборка через год возьмёт ту же 0.7.9, даже если к тому
времени выйдет 0.7.10. Обновляет его только явная команда `cargo update`.
`Cargo.lock` нужно хранить в репозитории: для прошивки это вопрос
воспроизводимости, а с 2023 года Cargo советует то же и для библиотек.

Дерево зависимостей показывает `cargo tree`. Начало дерева
`ch08-sections`:

```console
$ cd firmware && cargo tree -p ch08-sections
ch08-sections v0.1.0 (/home/user/rust-book/firmware/ch08-sections)
├── ch08 v0.1.0 (/home/user/rust-book/code/ch08)
├── cortex-m v0.7.9
│   ├── bare-metal v0.2.5
│   │   [build-dependencies]
│   │   └── rustc_version v0.2.3
│   │       └── semver v0.9.0
│   │           └── semver-parser v0.7.0
│   ├── bitfield v0.13.2
│   ├── cortex-m-macros v0.7.8 (proc-macro)
│   │   ├── proc-macro2 v1.0.107
│   │   …
│   ├── critical-section v1.2.0
│   ├── embedded-hal v0.2.7
│   │   ├── nb v0.1.3
│   │   │   └── nb v1.1.0
│   │   └── void v1.0.2
│   ├── embedded-hal v1.0.0
│   └── volatile-register v0.2.2
│       └── vcell v0.1.3
```

В нём видно три вещи, которых нет в мире C.

**Две старшие версии одного крейта.** `cortex-m` зависит сразу от
`embedded-hal` 0.2 и 1.0 (в его `Cargo.toml` они переименованы в `eh0` и
`eh1`), чтобы реализовать трейты обеих. Для компилятора это два разных
крейта с разными хешами в именах символов (раздел
[8.7](07-symbols.md)): трейт `OutputPin` из 0.2 и трейт из 1.0 — разные
трейты, и тип, реализующий один, не реализует другой. В C две версии
одной библиотеки в одной программе столкнулись бы именами.

**Мост между версиями.** `nb` 0.1.3 зависит от `nb` 1.1.0 и
переэкспортирует его типы: `pub use nb::{block, Error, Result};`. Код,
написанный против 0.1, получает тот же `nb::Error`, что и код против
1.x, и типы совпадают. Приём называется semver trick.

**Код для хоста.** `cortex-m-macros` помечен `(proc-macro)`, а
`rustc_version` стоит под `[build-dependencies]`. Процедурные макросы и
сценарии сборки выполняются во время компиляции, поэтому собираются для
машины сборки, x86_64, хотя вся прошивка — для ARM (раздел
[8.5](05-build-rs.md)).

<div class="box ref">

**Справка: редакции.** *Редакция* (edition) — свойство крейта, а не
сборки: крейт на edition 2021 и крейт на 2024 собираются в одну
программу и вызывают друг друга. Редакция меняет синтаксис и правила
вывода, но не [ABI][g-abi] и не метаданные. Что поменялось в 2024 для системного
кода, разобрано в [приложении B](../appendix-b.md).

</div>
