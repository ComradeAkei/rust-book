# 8.9. Задачи

Заготовки лежат в `exercises/ch08`, тесты, общие для заготовок и решений,
лежат в `tests-shared/ch08.rs`. Проверка:

```console
$ cargo test -p ch08-exercises            # все задачи
$ cargo test -p ch08-exercises task_c     # одна задача
```

Задача A собирает пробы компилятором, задача B — библиотеку под
Cortex-M0, задача C запускает `make`, cargo и компилятор C, задача D —
cargo во вложенном рабочем пространстве. Пока задачи не решены, тесты
падают на `todo!()` или на ошибках сборки. Два теста, `task_b_flash` и
`task_d_alone`, проходят и на заготовке: они сторожат то, что уже
работает, чтобы решение его не сломало. Разборы решений в
[приложении E](../appendix-e/ch08.md), но сначала попробуйте сами.

## A. Видимость в четырёх модулях

В `code/ch08/fragments/a.rs` лежит библиотека `station` с модулями
`hal`, `hal::uart`, `hal::dma` и `app`. Места ⟨1⟩–⟨5⟩ отмечены
комментариями, место ⟨6⟩ — другой крейт, который подключил `station`
зависимостью.

```rust
{{#include ../../code/ch08/fragments/a.rs}}
```

Для каждого из восьми элементов определите без компилятора, из каких
мест обращение к нему компилируется:

1. константа `CLOCK_HZ`;
2. поле `Uart::baud`;
3. поле `Uart::fifo`;
4. метод `Uart::reset`;
5. функция `hal::dma::start`, вызванная по этому пути;
6. тип `hal::DmaChannel`;
7. поле `.0` значения типа `hal::DmaChannel`;
8. функция `app::render`.

Ответ запишите в `exercises/ch08/src/a_visibility.rs`: строка на
элемент, по символу на место, `+` — обращение компилируется, `-` — нет.
Например, `"+-----"` значит «видно только из корня крейта».

Тест вставляет обращение к элементу сразу после метки места по полному
пути `crate::…` (из другого крейта — `station::…`) и собирает все 48
вариантов. Путь везде один и тот же, поэтому решает только видимость:
проба может сломаться лишь ошибкой видимости (E0603, E0616 или E0624), а
итог должен совпасть с ответом. Подсказка: для элемента 5 важен не
только `pub` перед функцией, а для элементов 6 и 7 — что именно
открывает `pub use`.

## B. Таблица синуса для Cortex-M0

У Cortex-M0 нет FPU: каждое действие с `f32` компилируется в вызов
программной эмуляции из `compiler_builtins` (`__aeabi_fmul`,
`__aeabi_fadd` и других), и стоит десятки тактов. Синус в такой
прошивке берут из таблицы, а таблицу выгоднее посчитать при сборке.

Во-первых, в `exercises/ch08/build.rs` вычислите четверть периода в
формате Q15: `SINE[i] = round(32767 · sin(i · π/512))` для
`i = 0..=256`. Сценарий работает на машине сборки, плавающая точка там
разрешена.

Во-вторых, в `exercises/ch08/src/b_sine.rs` напишите синус по таблице:

```rust
{{#include ../../exercises/ch08/src/b_sine.rs:sin}}
```

Остальные три четверти периода получаются из первой отражением, а
между точками таблицы нужна интерполяция. Ошибка должна быть не больше
2 единиц младшего разряда на всех 65536 углах, а значения
`sin_q15(0x4000)` и `sin_q15(0xc000)` — ровно 32767 и −32767.

В-третьих, проверьте, что таблица лежит во flash, а в коде нет
программной плавающей точки:

```console
$ cargo build -p ch08-exercises --lib --release --target thumbv6m-none-eabi
$ llvm-readelf -SW target/thumbv6m-none-eabi/release/libch08_exercises.rlib | grep SINE
$ llvm-nm -u target/thumbv6m-none-eabi/release/libch08_exercises.rlib | grep __aeabi_f
```

Тест `task_b_flash` делает то же самое: собирает библиотеку под
`thumbv6m-none-eabi`, находит `SINE` в объектном файле и требует, чтобы
она лежала в секции `.rodata`, занимала 514 байт и чтобы среди
неопределённых символов не было ни одной функции программной плавающей
точки. Заготовка этот тест проходит. Решение должно его не сломать.

Вопросы к отчёту. Какой была бы ошибка без интерполяции, если брать
ближайшую точку таблицы? В какую секцию и почему попадёт таблица,
объявленная как `static mut`, и что станет с проверкой, если объявить
её `const`? Сколько flash займёт таблица и сколько заняла бы полная,
на весь период, при том же шаге?

## C. staticlib для программы на C

Часть 1. В `exercises/ch08/c` лежит программа `main.c`, заголовок
`station.h`, недописанный `Makefile` и крейт `station`, в котором уже
есть внутренние функции на Rust: `crc8`, `scale_for` и `Scale::apply`.
Заголовок обещает C две функции:

```c
{{#include ../../exercises/ch08/c/station.h}}
```

Нужно:

- выбрать в `station/Cargo.toml` тип крейта, который даёт архив для
  компоновщика C;
- написать в `station/src/lib.rs` функции из `station.h` поверх
  готовых внутренних;
- дописать в `Makefile` правило для `$(OUT)/station-demo`: компилятор
  C, архив и системные библиотеки, которые нужны `std` внутри архива.

Тест вызывает `make OUT=<каталог>`, запускает программу и сверяет её
вывод:

```text
crc8("123456789") = 0xf4
crc8(пусто) = 0x00
датчик 1: 1000 -> 10000
датчик 7: 1000 -> 25000
датчик 12: 1000 -> 2000
датчик 3: нет в таблице
```

Затем он проверяет, что в архиве есть `std`, `core` и
`compiler_builtins`, а в объектных файлах самого крейта `station_crc8` и
`station_scale` определены как глобальные символы. Обратите внимание на
вторую строку вывода: `station_crc8(NULL, 0)` — законный вызов по
контракту заголовка. Подумайте, что из этого следует для обёртки на
Rust.

Посмотрите на символы своего крейта:

```console
$ cd exercises/ch08/c && make
$ ar t build/target/release/libstation.a | grep -c .
$ ar x build/target/release/libstation.a $(ar t build/target/release/libstation.a | grep ^station-)
$ nm station-*.o && nm -C station-*.o
```

Объясните каждую строку: почему у одних имён схема `_R`, у других
никакой; почему внутренние функции помечены `t`, а не `T`, как в `rlib`
из раздела [8.1](01-modules.md); сколько экземпляров `crc8` попало в
архив и почему именно столько.

Часть 2. В `exercises/ch08/src/c_mangle.rs` напишите разбор имён
символов Rust:


Тест сверяет результат на 17 именах v0 и 7 именах legacy, снятых с

## D. Неаддитивные возможности

В `exercises/ch08/d-station` лежит рабочее пространство из трёх
пакетов: библиотека `units` и две программы. Табло `panel` включает у
`units` возможность `celsius`, выгрузка `export` — `fahrenheit`. Каждый
пакет по отдельности собирается и работает, а вместе — нет:

```console
$ cd exercises/ch08/d-station
$ cargo run -q -p panel
табло: 21.50 °C
табло: -4.05 °C
табло: 0.00 °C
$ cargo run -q -p export
выгрузка: 70.70 °F
выгрузка: 24.71 °F
выгрузка: 32.00 °F
$ cargo build --workspace
error[E0428]: the name `UNIT` is defined multiple times
  --> units/src/lib.rs:17:1
...
error: units: включите одну шкалу, celsius или fahrenheit
```

Найдите причину (`cargo tree -e features -i units --workspace`) и
перестройте `units` так, чтобы возможности стали аддитивными.
Требования теста:

- `panel` и `export`, собранные по одному, печатают то же, что и
  сейчас;
- `cargo build --workspace` проходит, и обе программы печатают то же
  самое;
- `units` собирается и без возможностей, и со всеми сразу:
  `cargo check -p units --no-default-features` и `--all-features`.

Менять можно любые файлы рабочего пространства, но вывод программ
должен остаться прежним до байта.

Вопросы к отчёту. Чем отличается исполняемый файл `panel`, собранный
отдельно, от собранного вместе с `export`: размером, кодом, именами
символов? Какие ещё способы развести шкалы вы видите (отдельные
крейты, параметр типа, выбор во время работы) и чем каждый платит?
