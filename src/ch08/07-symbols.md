# 8.7. Имена символов и манглинг

## Зачем декорировать имена

Компоновщик знает о программе только имена символов и ничего не знает о
модулях, крейтах и обобщённых функциях. А в программе на Rust
`uart::reset` и `dma::reset` — разные функции, `checksum::<[u8; 4]>` и
`checksum::<&[u8]>` — две разные конкретизации одной функции, а две
старшие версии `embedded-hal` из раздела [8.2](02-crates.md) содержат
одноимённые типы и функции. Чтобы всё это поместилось в плоское
пространство имён компоновщика, rustc кодирует полный путь в имени
символа. Это называется *манглингом* (name mangling).

Функции из `code/ch08/src/symbols.rs` выбраны так, чтобы показать все
случаи: метод, обобщённая функция с двумя конкретизациями, обычная
функция и два имени, заданных вручную.

## Схема v0

В rustc 1.97 все символы, включая стандартную библиотеку, по умолчанию
кодируются схемой v0 (RFC 2603). Имя начинается с `_R`, дальше идёт
путь, записанный префиксной грамматикой: заглавная буква — вид узла, за
ней его части. Разберём метод `send`:

```text
_R                                 символ Rust, схема v0
Nv                                 имя из пространства значений (функция) внутри …
  M                                … собственной реализации, impl Uart { … }:
    NtCser9eqLlbKoo_4ch087symbols  где написан impl: модуль ch08::symbols
    NtB2_4Uart                     для какого типа: Uart в пути со смещения 2
  4send                            имя функции
```

Идентификаторы записаны с длиной: `4ch08`, `7symbols`. Корень крейта
обозначен `C`, а `s` + `er9eqLlbKoo` + `_` — его *дизамбигуатор*, хеш в
системе счисления с основанием 62. Cargo вычисляет его из имени,
версии и источника пакета и настроек сборки, поэтому две версии одного
крейта в одной программе получают разные дизамбигуаторы (у отладочной
сборки `ch08` он тоже другой, `s2zcVwUOuYdq_`).
`B2_` — ссылка назад: «то же, что начинается со смещения 2 после `_R`»,
то есть уже записанный путь `ch08::symbols`. Ссылки делают имена
обобщённого кода короче, ведь путь `core::iter::traits::iterator`
встречается в них снова и снова.

Обобщённые аргументы записываются явно:

```text
_RINvNtCser9eqLlbKoo_4ch087symbols8checksumAhj4_EB4_
  I … E                     путь с обобщёнными аргументами
   Nv … 8checksum           ch08::symbols::checksum
   A h j4_                  [u8; 4]: массив (A) из u8 (h), длина — usize (j) 4
  B4_                       крейт, где создана конкретизация
```

Базовые типы закодированы одной строчной буквой: `h` — `u8`, `t` —
`u16`, `m` — `u32`, `j` — `usize`, `l` — `i32`, `e` — `str`. `R` — ссылка,
`S` — срез, поэтому вторая конкретизация, `RSh`, — это `&[u8]`. Хвост
`B4_` — путь крейта, в котором конкретизация создана: обобщённую
функцию из `ch08` может конкретизировать и другой крейт, и тогда
одинаковые экземпляры из разных крейтов не столкнутся. Полный разбор
схемы для подмножества, которое встречается в обычном коде, — задача
[8.C](09-tasks.md).

## Схема legacy

До v0 rustc использовал схему, совместимую с C++ (Itanium ABI), и её
можно включить на nightly:

```console
$ cargo +nightly rustc --release -p ch08 --lib -- -Zunstable-options -Csymbol-mangling-version=legacy
$ nm libch08.rlib | grep -E ' [TD] '
0000000000000000 T _ZN4ch087symbols4Uart4send17h6c33827056ee2774E
0000000000000000 T _ZN4ch087symbols4both17h24d8b2b2eef48db3E
0000000000000000 T _ZN4ch087symbols8checksum17h795711b048e42a49E
0000000000000000 T _ZN4ch087symbols8checksum17h932408d09e2c7265E
…
$ nm -C libch08.rlib | grep checksum
0000000000000000 T ch08::symbols::checksum
0000000000000000 T ch08::symbols::checksum
```

`_ZN … E` — вложенное имя C++ из компонентов с длинами, последний
компонент `17h…` — хеш из 16 шестнадцатеричных цифр. В хеш спрятано
всё, что не поместилось в путь: крейт, его версия и обобщённые
аргументы. Поэтому две конкретизации `checksum` после разбора выглядят
одинаково, и отличить `<[u8; 4]>` от `<&[u8]>` по имени нельзя. Метод
пишется как `Uart::send`, без указания, что это `impl`. Символы,
недопустимые в именах ассемблера, закодированы: `<` — `$LT$`, `::`
внутри компонента — `..`, пробел — `$u20$`, так что реализация
`AsRef` для `&T` выглядит как
`_ZN55_$LT$$RF$T$u20$as$u20$core..convert..AsRef$LT$U$GT$$GT$6as_ref17h…E`.

| | v0 | legacy |
|---|---|---|
| Префикс | `_R` | `_ZN`, как у C++ |
| Обобщённые аргументы | в имени | только в хеше |
| Крейт и версия | дизамбигуатор `Cs…_` | только в хеше |
| Собственный `impl` | `<ch08::symbols::Uart>::send` | `ch08::symbols::Uart::send` |
| Повторы путей | ссылки `B…_` | повторяются целиком |
| Разбор | `nm -C`, `llvm-cxxfilt`, `rustfilt` | любой разборщик C++; коды `$LT$` понимает GNU `c++filt` |

<div class="box c">

**Как в C.** В C манглинга нет: функция `uart_reset` в объектном файле
называется `uart_reset`. Поэтому в C нет перегрузки, пространств имён
и обобщённых функций, а две библиотеки с функцией `init` не
скомпонуются вместе (или скомпонуются молча, как показано ниже). C++
решил ту же задачу схемой Itanium, и legacy-схема Rust была её
подмножеством: `llvm-cxxfilt` разбирает её как имя C++, оставляя
`$LT$` как есть, а GNU `c++filt` знает и эти коды.

</div>

## Имя без декорирования

Функции, которые вызывает C, ассемблер или код запуска, должны
называться предсказуемо. Атрибут `#[unsafe(no_mangle)]` отключает
манглинг и оставляет имя как есть (`station_reset`, `ch08_bump`), а
`#[unsafe(export_name = "station_version")]` задаёт имя символа явно,
не меняя имени функции в Rust (`version`). В edition 2024 оба атрибута
требуют `unsafe`, и опыты из `code/ch08/dup` показывают, почему.

**Два крейта, одно имя.** Драйверы UART и DMA независимо экспортировали
функцию для C с одним и тем же именем:

```rust
{{#include ../../code/ch08/dup/uart.rs:uart}}
```

```rust
{{#include ../../code/ch08/dup/dma.rs:dma}}
```

```rust
{{#include ../../code/ch08/dup/main.rs:main}}
```

```console
$ rustc --edition 2024 --crate-type rlib uart.rs
$ rustc --edition 2024 --crate-type rlib dma.rs
$ rustc --edition 2024 main.rs --extern uart --extern dma -L .
$ ./main
4
```

Ни ошибки, ни предупреждения, и оба вызова попали в функцию из `dma`.
Если в `main.rs` поменять вызовы местами, программа печатает 2: теперь
оба вызова ушли в `uart`. `rlib` — архив, и компоновщик берёт из
архивов объектный файл, только когда в нём есть ещё не найденный
символ. Первый же архив закрыл `station_reset`, второй объектный файл
компоновщику не понадобился, и повторного определения он не увидел.
Какой архив окажется первым, решает порядок в команде компоновки,
которую строит rustc, а не автор программы. Это та же беда, что
`-fcommon` в C из введения, только без единого флага.

**Одно имя в одном крейте** rustc замечает сам:

```rust
{{#include ../../code/ch08/dup/same.rs:same}}
```

```text
error: symbol `station_reset` is already defined
  --> same.rs:10:5
   |
10 |     pub extern "C" fn station_reset() -> u32 {
   |     ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
```

**Имя из libc.** Пространство имён у программы общее с библиотекой C, и
функция без манглинга может подменить чужую:

```rust
{{#include ../../code/ch08/dup/malloc.rs:malloc}}
```

```console
$ ./malloc
memory allocation of 4 bytes failed
memory allocation of 1 bytes failed
skipping backtrace printing to avoid potential recursion
Aborted
```

Своя `malloc` заменила `malloc` из libc для всего процесса. Первый
запрос — 4 байта, а не 16 из `vec!`: память выделяет ещё код запуска
`std` до `main`. Аллокатор `std` получил нулевой указатель и прервал
программу, а попытка сообщить об этом снова упёрлась в ту же `malloc`. Ни
одной строки `unsafe` в теле нет, а поведение программы сломано целиком
— поэтому сам атрибут помечен `unsafe`: компилятор не может проверить,
что выбранное имя ни с чем не столкнётся. Тест
`cargo_no_mangle_clashes` в `code/ch08/tests/cargo.rs` воспроизводит все
три опыта.

<div class="box trick">

**Трюк.** Имена без манглинга, которые экспортирует библиотека, лучше
снабжать общим префиксом, как в C (`station_`), а в крейте держать их в
одном модуле `ffi`: тогда весь внешний интерфейс виден в одном месте,
а `rg 'no_mangle|export_name'` по проекту находит все глобальные имена.
Обёртки из задачи 8.C устроены именно так.

</div>
