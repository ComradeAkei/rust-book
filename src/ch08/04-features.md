# 8.4. Возможности

## Объявление и включение

*Возможность* (feature) — именованный переключатель пакета, который
превращается в условие `feature = "имя"` для `#[cfg]`. Крейт `code/ch08`
объявляет одну:

```toml
{{#include ../../code/ch08/Cargo.toml:features}}
```

`default` — список возможностей, включённых, если пользователь не сказал
иначе. Прошивка подключает `ch08` с `default-features = false` (раздел
[8.2](02-crates.md)), и библиотека собирается без `std`. Из командной
строки возможности включают `--features a,b`, а `--no-default-features`
и `--all-features` делают то, что написано. Возможность может включать
другие возможности (`full = ["dma", "log"]`) и необязательные
зависимости: `log = ["dep:defmt"]` подключит крейт `defmt`, только если
кто-то включил `log`.

## Унификация

Главное свойство возможностей не видно из одного `Cargo.toml`. Cargo
собирает каждый крейт в дереве зависимостей один раз на сборку, с
*объединением* всех возможностей, которые запросил хоть кто-нибудь. Это
называется *унификацией* (feature unification), и она делает
возможности глобальными для сборки.

Рабочее пространство `code/ch08/unify` показывает, к чему это ведёт.
Библиотека `report` форматирует строку журнала и умеет печатать числа в
шестнадцатеричном виде:

```toml
{{#include ../../code/ch08/unify/report/Cargo.toml:features}}
```

```rust
{{#include ../../code/ch08/unify/report/src/lib.rs:line}}
```

Программа `app-a` хочет десятичный вывод, программа `app-b` — 
шестнадцатеричный:

```toml
# app-a/Cargo.toml
{{#include ../../code/ch08/unify/app-a/Cargo.toml:deps}}
```

```toml
# app-b/Cargo.toml
{{#include ../../code/ch08/unify/app-b/Cargo.toml:deps}}
```

Одна и та же программа `app-a` печатает разное в зависимости от того,
что собрано рядом:

```console
$ cargo build -q -p app-a && ./target/debug/app-a
кадр 1: 42
$ cargo build -q --workspace && ./target/debug/app-a
кадр 1: 0x2a
```

Во второй сборке `report` скомпилирован один раз, с возможностью `hex`,
которую запросил `app-b`, и `app-a` получила чужое поведение. Причину
показывает `cargo tree` с ребрами-возможностями, развёрнутый от
`report`:

```console
$ cargo tree -e features --workspace -i report
report v0.1.0 (/home/user/rust-book/code/ch08/unify/report)
├── report feature "default" (command-line)
│   ├── app-a v0.1.0 (/home/user/rust-book/code/ch08/unify/app-a)
│   │   └── app-a feature "default" (command-line)
│   └── app-b v0.1.0 (/home/user/rust-book/code/ch08/unify/app-b)
│       └── app-b feature "default" (command-line)
└── report feature "hex"
    └── app-b v0.1.0 (/home/user/rust-book/code/ch08/unify/app-b) (*)
```

Тест `cargo_unify_changes_behaviour` в `code/ch08/tests/cargo.rs`
воспроизводит обе сборки и сверяет вывод. В настоящем проекте `report`
лежал бы в чужом крейте на crates.io, а `app-b` был бы тестовой
утилитой: CI собирает `--workspace` и видит одно поведение, а прошивка,
собранная отдельно, — другое.

## Правило аддитивности

Отсюда правило: включение возможности может только *добавлять* —
функции, типы, реализации трейтов, варианты поддержки. Оно не должно
убирать что-то из API или менять поведение того, что уже есть, потому
что автор `app-a` не контролирует, кто ещё включит эту возможность в
той же сборке. `hex` нарушает правило: она меняет смысл `line`.
Аддитивный вариант — две функции, `line` и `line_hex`, и выбор на
стороне вызывающего; так перестраивается рабочее пространство в задаче
[8.D](09-tasks.md).

Образец аддитивной возможности — `std` в `code/ch08`. Без неё крейт
работает на голом железе, с ней появляются тесты и всё, что требует ОС.
Если в одной сборке библиотеку подключат и с `std`, и без, она
соберётся с `std`, и тот, кто об этом не просил, получит лишь функции,
которые не вызывает. Для прошивки, правда, и это сломало бы сборку:
под `thumbv7m-none-eabi` стандартной библиотеки нет. Это ещё одна
причина держать прошивки в отдельном рабочем пространстве, как в этой
книге.

Взаимоисключающие возможности (`celsius` и `fahrenheit`, `stm32f1` и
`stm32f4`) правило нарушают по определению. Если без них не обойтись,
крейт хотя бы ловит запрещённое сочетание при компиляции:

```rust,ignore
#[cfg(all(feature = "celsius", feature = "fahrenheit"))]
compile_error!("units: включите одну шкалу, celsius или fahrenheit");
```

Это честнее молча выбранной ветки, но сборка всего пространства всё
равно сломается. Как выглядит такая поломка и как её перестроить,
разбирает задача D.

<div class="box hood">

**Под капотом.** Унификация идёт не по всему графу без разбора. Resolver
версии 2 и новее (у edition 2024 по умолчанию версия 3: то же, что 2,
плюс выбор версий с учётом `rust-version`) не смешивает возможности
трёх видов зависимостей. Зависимости сценариев сборки и процедурных
макросов собираются для хоста отдельно от тех же крейтов для цели.
Возможности, запрошенные только `[dev-dependencies]`, не попадают в
обычную сборку, а зависимости для другой платформы
(`[target.'cfg(…)'.dependencies]`) не включают возможностей там, где не
используются. Поэтому `serde` с `std` у хостовой утилиты в
`[build-dependencies]` не превратит прошивку в программу с `std`.
