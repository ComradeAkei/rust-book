# 8.8. Секции и размещение в памяти

## Карта памяти

У микроконтроллера две области памяти, и ведут они себя по-разному.
Flash сохраняет содержимое без питания, но писать в неё программа
обычной инструкцией `str` не может. ОЗУ пишется как угодно, но после
включения питания содержит мусор. Прошивки книги описывают обе области
в общем файле `firmware/memory.x`:

```text
{{#include ../../firmware/memory.x}}
```

Скрипт компоновки `link.x` из крейта `cortex-m-rt` раскладывает по этим
областям *выходные секции*:

| Секция | Где лежит | Что в ней | Что делает код запуска |
|---|---|---|---|
| `.vector_table` | flash, с адреса 0 | начальный SP и адреса обработчиков | ничего: её читает процессор |
| `.text` | flash | машинный код | ничего |
| `.rodata` | flash | неизменяемые данные | ничего |
| `.data` | ОЗУ, а копия значений во flash | изменяемые данные с начальным значением | копирует из flash |
| `.bss` | ОЗУ | изменяемые данные, равные нулю | обнуляет |
| `.uninit` | ОЗУ | то, что код запуска не трогает | ничего |

Выходные секции собираются из входных: каждая функция и каждая
статическая переменная лежат в объектном файле в своей секции
(`.text.ch08_bump`, `.rodata.…SENSORS`), а `link.x` правилами вроде
`*(.data .data.*)` решает, в какую выходную секцию они попадут.

## Куда попадают static и const

Прошивка `target` из раздела [8.3](03-cfg.md) использует данные трёх
видов:

```console
$ llvm-size -A target/thumbv7m-none-eabi/release/target
section              size        addr
.vector_table        1024           0
.text                4416        1024
.rodata               652        5440
.data                   4   536870912
.gnu.sgstubs            0        6112
.bss                    8   536870916
.uninit                 0   536870924
$ llvm-nm -n -C target/thumbv7m-none-eabi/release/target
…
00001670 r ch08::generated::SENSORS
000017cc R __erodata
000017cc A __sidata
20000000 d target::EVENTS
20000000 D __sdata
20000004 b cortex_m_semihosting::export::HSTDOUT
…
```

- Таблица `SENSORS` из `build.rs` — неизменяемый `static`. Она лежит
  в `.rodata` по адресу 0x1670, во flash, и ОЗУ не занимает. Её третий
  элемент, `sensor(7)`, программа нашла по адресу 0x16a0: 0x1670 плюс
  два раза по 24 байта.
- Счётчик `EVENTS` — `static AtomicU32` с начальным значением 41. Атомик
  меняется через общую ссылку, то есть обладает внутренней
  изменяемостью, и flash ему не подходит. Он лежит в `.data` по адресу
  0x2000_0000, а его начальное значение — во flash по адресу
  `__sidata` = 0x17cc, откуда его скопирует код запуска:

  ```console
  $ llvm-objdump -s -j .data target
   20000000 29000000                             )...
  $ llvm-readelf -lW target
    Type   Offset   VirtAddr   PhysAddr   FileSiz MemSiz  Flg Align
    LOAD   0x020000 0x20000000 0x000017cc 0x00004 0x00004 RW  0x10000
  ```

  0x29 — это 41. У сегмента два адреса: виртуальный (где переменная
  живёт) и физический (откуда её загружают).
- Переменная `HSTDOUT` из `cortex-m-semihosting` начинается с нуля и
  поэтому лежит в `.bss`: во flash для неё нет ничего, код запуска
  просто обнулит 8 байт.

`const` в этом списке нет и не может быть: у константы нет адреса, её
значение подставляется в каждое место использования, как `#define`.
Если взять ссылку на `const`, компилятор создаст безымянную копию в
`.rodata`. Одна это копия на все такие места или своя для каждого, язык
не обещает; rustc 1.97 обходится одной (раздел
[25.1](../ch25/01-consts.md)).

Отсюда простое правило для прошивки. Неизменяемая таблица — `static`
без `mut` и без внутренней изменяемости: тогда она во flash. `static
mut` или `static` с `Cell`, атомиками, `Mutex` лежат в ОЗУ, а если
начальное значение не нулевое — ещё и во flash. Проверка этого правила
для таблицы синуса — задача [8.B](09-tasks.md).

<div class="box c">

**Как в C.** В C неизменяемость нужно попросить: `int16_t table[] =
{…}` без `const` попадёт в `.data` и займёт и flash, и ОЗУ, а код
запуска скопирует её при каждой загрузке. В Rust по умолчанию наоборот:
`static` неизменяем, и в ОЗУ его переносит только явное `mut` или
тип с внутренней изменяемостью.

</div>

<div class="box hood">

**Под капотом.** На Linux та же `SENSORS` в `nm` помечена `D`, а не
`R` (раздел [8.1](01-modules.md)). Она содержит ссылки на строки, а
разделяемые библиотеки и PIE загружаются по произвольному адресу, и
загрузчик должен вписать в таблицу настоящие адреса. Поэтому таблица
лежит в `.data.rel.ro`: записываемой при загрузке и защищённой от
записи сразу после неё (RELRO). Прошивка компонуется по фиксированным
адресам, перемещений при загрузке нет, и та же таблица остаётся в
`.rodata`.

</div>

## Своя секция

Атрибут `#[unsafe(link_section = "имя")]` кладёт функцию или
статическую переменную во входную секцию с заданным именем, а скрипт
компоновки решает, куда её поместить. `link.x` из `cortex-m-rt`
определяет для этого секцию `.uninit`:

```text
  .uninit (NOLOAD) : ALIGN(4)
  {
    . = ALIGN(4);
    __suninit = .;
    *(.uninit .uninit.*);
    . = ALIGN(4);
    __euninit = .;
  } > RAM
```

`NOLOAD` означает, что в образе прошивки для неё ничего нет, а код
запуска её не обнуляет. Значит, то, что программа записала туда, живёт
до выключения питания, в том числе после программного сброса.
Прошивка `boot` считает загрузки:

```rust
{{#include ../../firmware/ch08-sections/src/bin/boot.rs:uninit}}
```

```rust
{{#include ../../firmware/ch08-sections/src/bin/boot.rs:main}}
```

```console
$ cd firmware && cargo run --release -q -p ch08-sections --bin boot
загрузка 0: .uninit 0x2000000c, RUNS = 0 по адресу 0x20000000
загрузка 1: .uninit 0x2000000c, RUNS = 0 по адресу 0x20000000
загрузка 2: .uninit 0x2000000c, RUNS = 0 по адресу 0x20000000
```

`SCB::sys_reset` перезапускает процессор: заново выполняется код
запуска, `.bss` обнуляется, и `RUNS` после каждого сброса снова 0, хотя
программа его увеличила. Счётчик в `.uninit` переживает оба сброса. Так
устроены журналы аварий и счётчики перезагрузок в настоящих прошивках:
обработчик HardFault записывает причину в `.uninit`, а после
перезапуска программа её читает. Вывод одинаков на Cortex-M0, M3 и M4F,
его проверяет `firmware/run-demos.sh`.

Метка `MAGIC` нужна, потому что после включения питания в ОЗУ
неизвестно что. QEMU заполняет его нулями, настоящий кристалл — чем
придётся, и без проверки программа приняла бы мусор за счётчик. Читать
мусор безопасно только потому, что любой набор из 8 байт —
допустимое значение `[u32; 2]`; для `bool` или перечисления это было бы
неопределённым поведением. Поэтому переменная объявлена как
`MaybeUninit`, и тип самой переменной не обещает ничего.

<div class="box trap">

**Ловушка.** `link_section` в edition 2024 требует `unsafe`, потому что
компилятор не знает, что сделает с секцией скрипт компоновки. Положите
`static` с ненулевым значением в `.bss`, и код запуска затрёт его
нулём; положите функцию в секцию, которая окажется в ОЗУ без
копирования, и процессор выполнит мусор. Имя секции — договор со
скриптом компоновки, который проверяете только вы.

</div>

<div class="box check">

**Проверь себя.** Где окажется `static LIMITS: [u16; 4] = [0; 4];` —
в `.rodata` или в `.bss`? А `static mut LOG: [u8; 64] = [0; 64];`?
Что увидит программа `boot`, если её остановить отладчиком и сбросить
командой `monitor reset` в gdb, и почему ответ зависит от того, как
отладчик сбрасывает процессор?

</div>
