# 8.6. Типы крейтов

## Что умеет собрать rustc

Тип крейта задаёт, что получится на выходе компиляции:

| Тип | Результат | Для кого |
|---|---|---|
| `bin` | исполняемый файл | для запуска |
| `rlib` | `lib*.rlib`: метаданные и объектный код | для других крейтов Rust |
| `staticlib` | `lib*.a`: крейт и всё, от чего он зависит | для компоновщика C |
| `cdylib` | `lib*.so`: разделяемая библиотека с C-интерфейсом | для `dlopen` и C-программ |
| `dylib` | `lib*.so` с метаданными Rust | для Rust той же версии компилятора |
| `proc-macro` | библиотека для компилятора | процедурные макросы |

`lib` в `Cargo.toml` по умолчанию означает `rlib`. Пакет `code/ch08/ffi`
просит три типа сразу:

```toml
{{#include ../../code/ch08/ffi/Cargo.toml:types}}
```

```rust
{{#include ../../code/ch08/ffi/src/lib.rs:lib}}
```

Функция `scale` — для пользователей на Rust, `sensor_scale` — та же
функция для C: соглашение о вызовах C и имя без декорирования (раздел
[8.7](07-symbols.md)). Release-сборка даёт три файла:

```console
$ cargo build --release
$ wc -c target/release/libsensorlib.{a,rlib,so}
21963152 target/release/libsensorlib.a
    5582 target/release/libsensorlib.rlib
  401504 target/release/libsensorlib.so
22370238 total
```

Разница в четыре тысячи раз — не опечатка.

## rlib

`libsensorlib.rlib` — метаданные и один объектный файл самого крейта,
как в разделе [8.2](02-crates.md). Ни `std`, ни `core` внутри нет: их
подставит компоновщик, когда будет собирать программу, и подставит один
раз на всю программу, сколько бы крейтов от них ни зависело.

## staticlib

Архив для C должен быть самодостаточным: компоновщик C ничего не знает
о `std` и не найдёт её сам. Поэтому `staticlib` несёт с собой всё:

```console
$ ar t target/release/libsensorlib.a | wc -l
328
$ ar t target/release/libsensorlib.a | grep -v compiler_builtins
sensorlib.sensorlib.b10b0e7107562ce1-cgu.0.rcgu.o
sensorlib.amz5qnviymuvfipz9gewvabj9.rcgu.o
panic_abort-63750dae4970d099.panic_abort.60069ca033cb2c90-cgu.0.rcgu.o
std-ca8536218e109c03.std.bcb96dfbba0ab899-cgu.0.rcgu.o
object-9464813eb8f4d63d.object.29aabc33c82717ab-cgu.0.rcgu.o
memchr-…
addr2line-…
gimli-…
…
alloc-d5238ef8bbdabd19.alloc.2ea6bcb46fca0c42-cgu.0.rcgu.o
core-e2798d8a0cf2374b.core.940e698046960fd5-cgu.0.rcgu.o
45c91108d938afe8-absvdi2.o
45c91108d938afe8-absvsi2.o
…
```

Из 328 членов 273 — `compiler_builtins` (встроенные функции вроде
деления 128-битных чисел, по объекту на функцию, чтобы компоновщик брал
только нужные), ещё 35 — функции из `compiler-rt`, которые
`compiler_builtins` берёт в виде кода на C, остальное — `std` и её зависимости,
включая разбор отладочной информации для трассировок (`gimli`,
`addr2line`, `object`). Глобальных определённых символов в архиве 2109.
Нашему крейту из этого нужна одна функция, но архив — просто склад
объектных файлов, и выбирать, что взять, будет компоновщик C.

Кроме архива, программе на C нужны системные библиотеки, на которые
опирается `std`. Их список печатает rustc:

```console
$ cargo rustc --release --lib --crate-type staticlib -- --print native-static-libs
note: native-static-libs: -lgcc_s -lutil -lrt -lpthread -lm -ldl -lc
```

Эти флаги ставят в команде компоновки *после* архива: компоновщик
проходит библиотеки слева направо и берёт из каждой только то, что
нужно уже прочитанным файлам. Что получается в итоге, видно на
программе из задачи [8.C](09-tasks.md), которая вызывает две функции из
такого же архива:

```console
$ size station-demo
   text	   data	    bss	    dec	    hex	filename
 925865	  32192	    344	 958401	  e9fc1	station-demo
$ size station-demo-gc        # то же с -Wl,--gc-sections
   text	   data	    bss	    dec	    hex	filename
 299223	  10608	    168	 309999	  4baef	station-demo-gc
```

Компоновщик берёт из архива объектный файл целиком, если ему нужен
хотя бы один символ оттуда, а `std` — один большой объектный файл.
rustc кладёт каждую функцию в свою секцию, поэтому `--gc-sections`
выбрасывает недостижимые и сокращает код втрое.

<div class="box trap">

**Ловушка.** Два `staticlib` из Rust в одной программе на C — это две
копии `std`, `core` и `compiler_builtins`. Программа с `libsensorlib.a`
и архивом из задачи C компонуется и работает, но только потому, что
компоновщик не берёт из второго архива то, что уже нашёл в первом: чья
копия `std` достанется коду второго крейта, решает порядок архивов в
командной строке. Это та же механика, что молча выбирает одно из двух
одинаковых имён в разделе [8.7](07-symbols.md). Надёжнее один
`staticlib` на программу: крейт-фасад, который зависит от остальных
крейтов Rust и экспортирует всё, что нужно C.

</div>

## cdylib

Разделяемая библиотека уже прошла компоновку, поэтому из `std` в ней
только то, что достижимо из экспортированных функций и конструкторов
`std`. Экспортирует она ровно одно имя:

```console
$ nm -D --defined-only target/release/libsensorlib.so
00000000000116c0 T sensor_scale
$ readelf -d target/release/libsensorlib.so | grep NEEDED
 0x0000000000000001 (NEEDED)             Shared library: [libgcc_s.so.1]
 0x0000000000000001 (NEEDED)             Shared library: [libc.so.6]
 0x0000000000000001 (NEEDED)             Shared library: [ld-linux-x86-64.so.2]
```

`pub fn scale` в таблице экспорта нет: для `cdylib` наружу выходят
только символы с C-именами, остальное компоновщик делает локальным.
Внутри всё же 295 590 байт кода: `std` регистрирует два конструктора в
`.init_array` (по 8 байт на указатель), и всё, что достижимо из них и
из обработки паники, тоже попало в файл.

## dylib и proc-macro

`dylib` — разделяемая библиотека для Rust: с метаданными и с
экспортом всех символов крейта по их Rust-именам. ABI Rust не
стабилизирован, поэтому её можно использовать только с программой,
собранной тем же компилятором с теми же флагами. На практике её
применяют для ускорения пересборки больших проектов, а не для
распространения.

`proc-macro` — тоже разделяемая библиотека, но для самого компилятора:
rustc загружает её при сборке и вызывает макросы. Отсюда пометка
`(proc-macro)` в выводе `cargo tree` из раздела [8.2](02-crates.md) и то,
что такие крейты собираются для хоста.

<div class="box c">

**Как в C.** `staticlib` и `cdylib` — обычные `.a` и `.so`, и C-код
работает с ними так же, как с любыми другими: заголовок с прототипами,
`-L` и `-l` при компоновке. Заголовок rustc не пишет; его держат
вручную или генерируют утилитой `cbindgen` (глава 18). Обратная
сторона, вызов C из Rust, — тоже глава 18.

</div>
