# 17.1. MaybeUninit: память без значения

В C память часто сначала выделяют, а затем заполняют: `malloc` уже
вернул блок, но значений в него ещё не записали. Обычный указатель
на этот блок не показывает, завершена ли инициализация. Чтение
неинициализированного значения может привести к неопределённому
поведению; наличие адреса не делает такое чтение допустимым.
В Rust эту разницу выражают типом. Чтение неинициализированного
значения — неопределённое поведение, и, более того, само создание ссылки `&T` или
`&mut T` на место, где ещё нет корректного `T`, уже UB — ссылка обещает
валидное значение по инварианту из [16.2](../ch16/02-invariants.md).

`MaybeUninit<T>` — это честный тип для такой памяти. Он резервирует место и
выравнивание под `T`, но не обещает, что внутри лежит корректное значение.
Прочитать `T` из него можно только через `assume_init`, и это `unsafe`:
вызывающий берёт на себя ответственность за то, что инициализация и правда
состоялась. Имя метода буквально означает «считать инициализированным»:
он не заполняет память и не проверяет её. В отличие от `Option<T>`,
`MaybeUninit<T>` не хранит флаг «есть значение»; сведения о заполненности
должен вести ваш алгоритм.

## Сначала одна ячейка

Перед заполнением структуры проследите все состояния одного числа:

```rust
use std::mem::MaybeUninit;

let mut slot = MaybeUninit::<u32>::uninit(); // место есть, u32 ещё нет
slot.write(42); // безопасно: записали корректный u32
// SAFETY: единственная ячейка полностью заполнена вызовом write выше.
let value = unsafe { slot.assume_init() };
assert_eq!(value, 42);
```

| После строки | Что уже можно утверждать |
|---|---|
| `uninit()` | есть место размера и выравнивания `u32`; читать число нельзя |
| `write(42)` | в этом месте лежит корректное число `42` |
| `assume_init()` | вызывающий забрал готовое значение как обычный `u32` |

`write` меняет содержимое памяти. `assume_init` принимает обещание
автора, что содержимое уже пригодно для `T`; инициализации он не
выполняет. Последовательность «сначала `assume_init`, потом запись»
ошибочна уже на первом шаге. Контракты этих операций приведены в
[документации `MaybeUninit`](https://doc.rust-lang.org/std/mem/union.MaybeUninit.html#method.write).

<details>
<summary>Почему для обычной переменной проще let value = 42u32?</summary>

В этом примере `MaybeUninit` не нужен: он только показывает переходы.
Обычный `let` сразу создаёт готовое значение и обходится без `unsafe`.
Обёртка нужна, когда запись и получение готового значения приходится
разделить, как в примерах ниже.

</details>

## Собрать значение по частям

Классический случай — значение, которое заполняется не разом, а полями или
порциями. Выделяем место под `Point`, пишем поля через [сырые указатели][g-raw-pointer] и
только когда заданы оба — объявляем готовым:

```rust
{{#include ../../code/ch17/src/maybe_uninit.rs:parts}}
```

Запись идёт через `&raw mut (*p).x` — сырой указатель на поле, без создания
ссылки `&mut` на незаполненную структуру. Это существенно: пока хотя бы
одно поле не записано, `Point` целиком некорректен, и `&mut Point` на него
был бы UB ещё до первой записи. `assume_init` стоит последним: к этому
моменту все поля заполнены, и мы забираем готовый `Point` из обёртки.

## Массив без Copy и Default

Второй частый случай — массив, который инициализируется поэлементно, когда
`T` не `Copy` и заводить значение-заглушку нежелательно или невозможно:

```rust
{{#include ../../code/ch17/src/maybe_uninit.rs:array}}
```

`[const { MaybeUninit::uninit() }; N]` создаёт массив неинициализированных
ячеек: блок `const {}` вычисляется отдельно для каждого элемента и не
требует `T: Copy`. Обычное повторение `[value; N]` для такой записи
потребовало бы копируемого значения. Цикл
задаёт каждую, а финальное чтение опирается на факт, который гарантирует
язык: [раскладка][g-layout] `[MaybeUninit<T>; N]` в точности совпадает с `[T; N]` —
тот же размер, то же выравнивание. Поэтому прочитать массив ячеек как
массив значений можно, и `// SAFETY` ссылается именно на заполненность всех
`N` элементов.

<div class="box c">

**Как в C.** `MaybeUninit<T>` — это ровно то, чем в C является любая
`malloc`-память или непроинициализированная локальная переменная: место под
значение, которого там пока нет. Разница в том, что C позволяет читать её
без пометки (и платит за это UB, размазанным по программе из
[мотивирующей проблемы](../ch16/index.md) главы 16), а Rust заставляет
пройти через `assume_init` и назвать момент, когда память стала
валидной. `calloc` отвечает `MaybeUninit::zeroed()` — но и после
обнуления `assume_init` корректен только для типов, которым нулевой
образец годится: для `u32` это `0`, для `bool` — `false`, а для ссылки
нулевой адрес недопустим. Не путайте нулевые байты с неинициализированными:
неинициализированный `bool` недопустим, хотя обнулённый допустим. Это различие
показано и в [документации MaybeUninit](https://doc.rust-lang.org/std/mem/union.MaybeUninit.html#method.zeroed).

</div>

<div class="box hood">

**Под капотом.** `MaybeUninit<T>` устроен как `union` из двух полей:
`value: ManuallyDrop<T>` и пустого `uninit: ()` — маркера «значения
нет». Поэтому он не роняет своё
содержимое при сбросе: `union` не знает, какое поле «живо», а значит и
дропать нечего. Это и спасает в примере с массивом — если на середине
инициализации случится [паника][g-panic], уже записанные элементы не уронятся
автоматически (их придётся ронять вручную в обработчике, если это важно),
но и двойного освобождения не будет.

</div>

<div class="box ref">

**Как в стандартной библиотеке.** Тот же договор — у
`Vec::with_capacity`: буфер выделен, но хвост за `len` — это
неинициализированные ячейки (`spare_capacity_mut` так и отдаёт его, как
`&mut [MaybeUninit<T>]`), и `Vec` аккуратно переводит их в живые по мере
`push`. Тот же механизм — в `Read::read_buf` и `BorrowedBuf` (оба пока
только на nightly), которые дают читать прямо в неинициализированный
буфер без предварительного обнуления.
Из [главы 16](../ch16/index.md): `MaybeUninit` — это и есть пятая
возможность `unsafe` (поле `union`), запертая за безопасным типом.

</div>
