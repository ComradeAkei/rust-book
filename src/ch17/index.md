# 17. Низкоуровневая работа с памятью

## Мотивирующая проблема

Разобрать заголовок файла в C часто пишут так: взять буфер и наложить на
него структуру.

```c
struct hdr { uint32_t magic; uint16_t type; uint64_t entry; };

struct hdr *parse(char *buf) {
    return (struct hdr *)buf;   /* наложили структуру на байты */
}
```

Три мины, и компилятор молчит про все.

1. **Выравнивание.** `buf` пришёл откуда угодно — из `read`, из `mmap`,
   из середины другого буфера. `entry` — `uint64_t`, ему нужен адрес,
   кратный 8. Если `buf` не выровнен, чтение `->entry` на x86 чуть
   медленнее, а на ARM без поддержки невыровненного доступа — аппаратное
   исключение.
2. **Строгий алиасинг.** Обращение к байтам через `struct hdr *` и через
   `char *` компилятор при `-fstrict-aliasing` считает не пересекающимся
   и вправе переставить или выкинуть. Это UB по типам, невидимое в
   исходнике.
3. **Порядок байт.** `magic` прочитается в порядке платформы. Файл с
   диска имеет свой порядок, и на другой машине всё поедет.

Та же задача в Rust заставляет назвать каждое из этих решений явно: либо
проверить выравнивание и переосмыслить байты под `unsafe`, либо собрать
поля `from_le_bytes` — и тогда ни выравнивание, ни алиасинг, ни порядок
байт не подведут. Это задача B этой главы.

## Что делает Rust

Глава — про инструменты, которыми в Rust работают с сырой памятью, и про
то, какой договор каждый из них требует.

- `MaybeUninit<T>` ([17.1](01-maybe-uninit.md)) — честный тип для «памяти,
  где ещё нет значения». Ссылку на неинициализированное брать нельзя, и
  тип это кодирует.
- Операции с указателями ([17.2](02-ptr.md)) — `read`/`write`,
  `copy_nonoverlapping`, `swap`, невыровненное чтение: ими двигают
  значения там, где владение само не выражается.
- `NonNull` и `PhantomData` ([17.3](03-nonnull.md)) — кирпичи умных
  указателей: ниша «не null» и сведения о владении, которых в указателе
  физически нет.
- `transmute` ([17.4](04-transmute.md)) — самый острый инструмент и его
  безопасные замены; типы нулевого размера.
- `volatile` ([17.5](05-volatile.md)) — обращение к регистру устройства,
  которое нельзя выкинуть или слить. Что оно даёт и, главное, чего не
  даёт.
- Типы динамического размера ([17.6](06-dst.md)) — толстые указатели,
  срезы, `str`, `dyn`, и как сделать свой DST с хвостовым массивом.

Общий принцип тот же, что в [главе 16](../ch16/index.md): опасное
заперто за безопасным API, каждый `unsafe`-блок сопровождён `// SAFETY`,
всё проверено под Miri — в обеих моделях алиасинга и, где речь о
тегированных указателях, со строгим provenance.

## Код главы

Все фрагменты взяты из файлов репозитория и проверяются:

```console
$ cargo test -p ch17                          # примеры, asm-тест, doc-тесты
$ cargo +nightly miri test -p ch17            # те же под Miri (Stacked Borrows)
$ MIRIFLAGS=-Zmiri-tree-borrows cargo +nightly miri test -p ch17
$ cargo +nightly miri test -p ch17-solutions  # решения задач B, C, D
$ MIRIFLAGS=-Zmiri-strict-provenance cargo +nightly miri test -p ch17-solutions  # задача C
$ bash code/ch17/ub/run.sh                     # каталог transmute (задача A)
$ cargo build -p ch17 --no-default-features --features alloc --target thumbv7m-none-eabi
```

Ассемблер снят с release-сборки `rustc 1.97.0` для
`x86_64-unknown-linux-gnu` закреплённым `cargo rustc --emit asm`. Ядро
главы (`MaybeUninit`, указатели, `volatile`, `NonNull`) собирается в
`no_std` и живёт на голом Cortex-M; типы динамического размера с хвостом
требуют кучи (`alloc`).
