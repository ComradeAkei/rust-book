для заготовок и решений, — в `tests-shared/ch17.rs`. Задача A решается не

## A. Каталог transmute

Каталог в `solutions/ch17/tests/ub.rs` — восемь вызовов `transmute`,
разбитых на три группы. Три корректны (обычные тесты), например
переосмысление `f32` как `u32`:

```rust
{{#include ../../solutions/ch17/tests/ub.rs:a_ok}}
```

Три дают неопределённое поведение — создают значение, нарушающее инвариант
валидности типа, поэтому UB возникает уже в строке `transmute`. Они
помечены `#[ignore]` и гоняются под Miri поодиночке:

```rust
{{#include ../../solutions/ch17/tests/ub.rs:a_ub}}
```

Ещё два вообще не компилируются — они живут как `compile_fail`-doc-тесты в
`solutions/ch17/src/lib.rs`: `transmute` между разными размерами (E0512) и
`&T` в `&mut T` (запрещён как заведомое UB).

Для каждого из восьми назовите, в какой он группе и почему: для корректных
— какая безопасная замена делает то же ([17.4](04-transmute.md)); для UB —
какой инвариант нарушен и в какой строке Miri его ловит; для не
компилирующихся — что именно отвергает компилятор. Затем для любого
корректного объясните, почему `transmute` там законен, но замена всё равно
лучше.

```console
$ cargo +nightly miri test -p ch17-solutions --test ch17-ub a_ub_invalid_bool -- --ignored
$ cargo test -p ch17-solutions --doc            # два compile_fail
```

## B. Разбор заголовка ELF64

Разберите первые 32 байта заголовка ELF64 двумя способами: без копирования
(переосмыслив срез как `&Elf64Header`) и безопасно (собрав поля через
`from_le_bytes`).

```rust
{{#include ../../exercises/ch17/src/b_elf.rs:skeleton}}
```

Версия без копирования обязана проверить размер буфера **и** выравнивание
под `Elf64Header`, иначе чтение — UB; весь `unsafe` снабдите `// SAFETY`,
объясняющим, почему для этого типа любой битовый образец валиден. Безопасная
версия не должна содержать ни `unsafe`, ни зависимости от выравнивания, ни
от порядка байт. Тест проверяет, что оба разбора дают одно, что
невыровненный буфер версия без копирования отвергает, и гоняется под Miri.

```console

```

## C. Тегированный указатель

Упакуйте три бита состояния в младшие разряды адреса `*const Node`. `Node`
выровнен на 8, поэтому три младших бита его адреса всегда нули — их и займёт
тег. Работайте через строгий API provenance (`map_addr`/`addr`), а не
через касты `usize`:

```rust
{{#include ../../exercises/ch17/src/c_tagged.rs:skeleton}}
```

`map_addr` меняет только адрес, сохраняя provenance исходного указателя, —
поэтому по очищенному `ptr()` можно законно обращаться к `Node`, а `tag()`
читает биты, не трогая право доступа. Решение обязано проходить
`-Zmiri-strict-provenance`:

```console
$ cargo +nightly miri test -p ch17-exercises --test ch17 c_
$ MIRIFLAGS=-Zmiri-strict-provenance cargo +nightly miri test -p ch17-exercises --test ch17 c_
```

## D. Свой тип динамического размера

Реализуйте `Record<T>` — заголовок `tag` и хвост `[T]` переменной длины в
ОДНОМ выделении ([17.6](06-dst.md)). Для сравнения дан `TwoBox<T>`, где те
же данные лежат в двух блоках кучи.

```rust
{{#include ../../exercises/ch17/src/d_record.rs:skeleton}}
```

Раскладку ручного выделения сделайте той же, что выведет компилятор, иначе
`Box` освободит не так. Своего `Drop` не пишите и объясните в комментарии,
почему: элементы хвоста роняет автоматический drop-glue `Box<Record>` —
ручной `Drop` дал бы двойное освобождение. Тест кладёт в хвост значения с
деструктором-счётчиком и проверяет, что каждый уронен ровно один раз; затем
сравните с `TwoBox` — на сколько выделений кучи и разыменований меньше у
хвостового DST.

```console

```
