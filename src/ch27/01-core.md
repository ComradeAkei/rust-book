# 27.1. Ядро: режимы, стеки, исключения

## Что знает процессор

<div class="box ref">

**Справка: регистры Cortex-M3.** Шестнадцать регистров общего
назначения: r0–r12, SP (r13), LR (r14) и PC (r15). Указателей стека два
— *MSP* (main stack pointer, основной) и *PSP* (process stack pointer,
стек процесса), и в каждый момент SP — один из них. Регистр состояния xPSR
— три регистра в одном слове: APSR (флаги N, Z, C, V, Q в битах 27–31),
IPSR (номер текущего исключения, биты 0–8) и EPSR (бит T, бит 24:
процессор выполняет код [Thumb][g-thumb]). Отдельно — регистры маски: [PRIMASK][g-primask] (1 —
запрещены все прерывания, кроме [NMI][g-nmi] и HardFault), FAULTMASK и BASEPRI
(раздел [27.2](02-nvic.md)), и CONTROL: бит 0 nPRIV (1 — код в режиме
[Thread][g-thread-handler] непривилегированный), бит 1 SPSEL (1 — режим Thread работает на PSP).

</div>

Режимов два (thread mode и handler mode). **Thread** — обычный код: после
сброса процессор начинает в нём, привилегированным и на MSP. **Handler** —
обработчики исключений: всегда привилегированный и всегда на MSP.
Различает их IPSR: ноль — Thread, иначе — номер исключения, которое сейчас
обслуживается.

```rust
{{#include ../../code/ch27/src/exc.rs:exception}}
```

Номера 1–15 — исключения ядра, одинаковые у всех Cortex-M3: сброс, NMI,
HardFault, три класса сбоев, [SVCall][g-svcall], [PendSV][g-pendsv], [SysTick][g-systick]. С 16 — внешние
прерывания, у LM3S6965 их 38, с номерами от 0 до 43: прерывание 0 — порт
GPIOA, 5 — UART0, 19 — таймер TIMER0A. Адреса обработчиков лежат в таблице
векторов с адреса 0 в том же порядке, а слово 0 таблицы — начальное
значение MSP; таблицу векторов прошивки разбирает задача
[27.A](10-tasks.md).

## Вход в исключение и выход из него

Когда приходит исключение, процессор до первой инструкции обработчика
делает четыре вещи:

1. кладёт на текущий стек — MSP или PSP — *кадр исключения* (exception
   frame), восемь слов: r0–r3, r12, LR, PC прерванного кода (адрес, с
   которого продолжить) и xPSR;
2. записывает в LR особое значение *EXC_RETURN* (exception return);
3. переключается в режим Handler на MSP, IPSR получает номер
   исключения;
4. загружает PC из таблицы векторов.

Восемь слов — именно те регистры, которые по [AAPCS][g-aapcs] функция вправе
испортить: r0–r3, r12 и LR. Остальные, r4–r11, обработчик сохранит сам,
если тронет, — как любая функция на C или Rust. Поэтому обработчик
прерывания на Cortex-M — обычная функция, без `__attribute__((interrupt))`
и без [пролога][g-prologue] на ассемблере.

```rust
{{#include ../../code/ch27/src/exc.rs:frame}}
```

Выход — `bx lr`, как из функции. Но в LR не адрес, а EXC_RETURN:
0xFFFF_FFxx, из области, где кода нет. Процессор узнаёт такое
значение в PC, снимает кадр с нужного стека и возвращается туда, где
его прервали. Младшие биты говорят, куда:

```rust
{{#include ../../code/ch27/src/exc.rs:exc_return}}
```

| EXC_RETURN | Возврат в | Кадр на |
|---|---|---|
| 0xFFFF_FFF1 | Handler (вложенное исключение) | MSP |
| 0xFFFF_FFF9 | Thread | MSP |
| 0xFFFF_FFFD | Thread | PSP |

У Cortex-M4F с включённым [FPU][g-fpu] бит 4 EXC_RETURN равен нулю, когда в
кадре ещё 18 слов регистров FPU: 0xFFFF_FFE9 и 0xFFFF_FFED.

## Опыт: системный вызов

Исключение *SVCall* (supervisor call) вызывается инструкцией: `svc #n`.
Так ядро ОС на Cortex-M принимает системные вызовы, а аргументы передаются в
регистрах, как в обычную функцию:

```rust
{{#include ../../firmware/ch27-core/src/main.rs:syscalls}}
```

Номер вызова — не в регистре, а в самой инструкции: `svc #1` — это
полуслово 0xDF01. Обработчик найдёт его по сохранённому PC: он указывает
на инструкцию после `svc`. Кадр обработчик возьмёт со стека, а какой из
двух стеков, скажет бит 2 EXC_RETURN:

```rust
{{#include ../../firmware/ch27-core/src/main.rs:handler}}
```

`SVCall` — функция без пролога (`#[unsafe(naked)]`, раздел
[19.2](../ch19/02-naked.md)): тело целиком на ассемблере, компилятор не
добавит ни одной инструкции. Шесть инструкций выбирают стек, кладут адрес
кадра в r0 и EXC_RETURN в r1 и переходят в `svc_rust` — обычную функцию с
соглашением C, которая получает кадр как `&mut Frame`. Изменить `frame.r0`
— значит изменить r0, который увидит прерванный код после возврата: так
системный вызов возвращает результат.

```console
$ cd firmware && cargo run --release -p ch27-core
main: Thread, IPSR 0, CONTROL 0x0, MSP 0x20003f88, PSP 0x00000000
svc #1 (20, 22) = 42
  SVCall: SvCall, IPSR 11, EXC_RETURN 0xfffffff9 = ExcReturn { to_thread: true, psp: false, fpu_frame: false }
  кадр по адресу 0x20003fc0: pc 0x000004b4, lr 0x00000e27, xpsr 0x61000000, SP до входа 0x20003fe0
на PSP: Thread, IPSR 0, CONTROL 0x2, MSP 0x20003fe0, PSP 0x20000390
svc #1 (40, 2) = 42
  SVCall: SvCall, IPSR 11, EXC_RETURN 0xfffffffd = ExcReturn { to_thread: true, psp: true, fpu_frame: false }
  кадр по адресу 0x200003c8: pc 0x000004f4, lr 0x00000e27, xpsr 0x21000000, SP до входа 0x200003e8
```

Разберём.

- `main` — режим Thread (IPSR 0), CONTROL 0: привилегированный, на MSP.
  PSP после сброса — ноль: его никто не настраивал.
- Внутри `svc_rust` IPSR 11 — SVCall, EXC_RETURN 0xFFFF_FFF9: вернуться в
  Thread на MSP.
- Кадр — восемь слов, 32 байта ниже SP прерванного кода: 0x2000_3FC0 и
  0x2000_3FE0. PC в кадре 0x4B4 — адрес после `svc #2`, которая лежит по
  адресу 0x4B2 (`llvm-objdump -d`): `sys_report` [встроилась][g-inlining] в `main`. LR —
  то, что лежало в LR прерванного кода, адрес возврата из последнего
  вызова внутри `hprintln!`. В xPSR 0x6100_0000 — флаги Z и C и бит T:
  IPSR прерванного кода — ноль.
- После перехода на PSP CONTROL = 2 (SPSEL), и тот же вызов приходит с
  EXC_RETURN 0xFFFF_FFFD: кадр — на PSP, в массиве `PSTACK`. MSP остался
  там, где его оставил `main`, — на нём теперь работают только
  обработчики.

Переход на PSP тоже на ассемблере:

```rust
{{#include ../../firmware/ch27-core/src/main.rs:psp}}
```

<div class="box trap">

**Ловушка.** Записать PSP и CONTROL прямо в теле `main` через `asm!` —
первое, что приходит в голову, и оно не работает: локальные переменные
`main` и адреса возврата остались на MSP, а код после `isb` ищет их на
PSP. В опыте с такой записью прошивка печатала мусор вместо чисел. Сменить
стек можно только там, где компилятор ничего не держит на старом: в
[naked-функции][g-naked-function], которая продолжает выполнение в новой функции, никогда
не возвращаясь.

</div>

Два стека — основа любой ОС на Cortex-M. Задачи работают в режиме
Thread на своих стеках через PSP, ядро и обработчики — на MSP. Стек
задачи переполнился — обработчики и ядро живы. Переключатель задач в
задаче [27.D1](10-tasks.md) — следующий шаг: *PendSV* (pendable service
call) — исключение, которое программа ставит в ожидание сама, — меняет PSP
на стек другой задачи.

<div class="box c">

**Как в C.** CMSIS даёт `__get_IPSR()`, `__get_CONTROL()`, `__set_PSP()`
и `__set_CONTROL()` — функции из одной инструкции `mrs` или `msr`, в
Rust им соответствуют `cortex_m::register::*`. Системный вызов в
FreeRTOS и других ОС устроен так же: `svc` в коде задачи, обработчик
SVCall на ассемблере, который определяет стек по биту 2 LR и передаёт
адрес кадра функции на C. Разница — в типах: в C кадр — `uint32_t *` и
индексы 0–7 по комментарию, здесь — `&mut Frame` с полями [`#[repr(C)]`][g-layout].

</div>

<div class="box hood">

**Под капотом.** Процессор выравнивает кадр на 8 байт (бит STKALIGN
регистра CCR): если SP прерванного кода не кратен 8, он сдвигает стек
ещё на слово и ставит бит 9 сохранённого xPSR. `Frame::sp_before`
учитывает этот бит, и «SP до входа» в выводе — честный. При возврате
процессор смотрит на тот же бит и снимает лишнее слово.

</div>

<div class="box check">

**Проверь себя.** Почему `svc_rust` объявлена `extern "C"`? Что будет,
если в `SVCall` заменить последнюю `b {rust}` на `bl {rust}`, а после неё
поставить `bx lr`? Какое значение EXC_RETURN получит обработчик SVCall,
если `svc` выполнить внутри обработчика другого исключения?

</div>
