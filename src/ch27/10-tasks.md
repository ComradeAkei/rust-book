# 27.10. Задачи

Все задачи решаются кодом. Заготовки — в `exercises/ch27`, тесты, общие
для заготовок и решений, — в `tests-shared/ch27.rs`. Библиотека задач —
`no_std` и собирается как есть: функции с `todo!()` паникуют только при
вызове. Её проверяют на хосте, а прошивки задач C, D1 и D2 — ваши;
образец, который работает с решениями, — `firmware/ch27-tasks`.

```console
$ cargo test -p ch27-exercises            # все задачи
$ cargo test -p ch27-exercises task_c     # одна задача
$ cargo test -p ch27-solutions            # эталон
$ cd firmware && cargo run --release -p ch27-tasks --bin d1_switch
```

Тесты с префиксом `rustc_` запускают закреплённые rustc и cargo: A
собирает прошивку `ch27-nvic` и разбирает её ELF, B — крейт задач под
Cortex-M3 в ассемблер. Разборы — в [приложении E](../appendix-e/ch27.md),
но сначала попробуйте сами.

## A. Таблица векторов из ELF

Скрипт компоновки cortex-m-rt кладёт с адреса 0 секцию `.vector_table`:
начальный SP, 15 адресов обработчиков исключений ядра и адреса
обработчиков прерываний из PAC (раздел [27.3](03-pac.md)). Напишите
разбор, который находит её в файле ELF без сторонних крейтов:

```rust,ignore
{{#include ../../exercises/ch27/src/a_vectors.rs:api}}
```

- `vector_table(elf)` — проверить, что это ELF32 little-endian, найти
  таблицу заголовков секций (`e_shoff`, `e_shentsize`, `e_shnum`) и
  таблицу их имён (`e_shstrndx`), найти по имени `.vector_table` и
  вернуть её адрес и байты. Файл может быть обрезан: ни одного
  индексирования без проверки, ошибка — `Truncated`;
- `get(i)` — слово `i`, `len()` — число слов, `interrupts()` — сколько
  их после 16 слов ядра;
- `check()` — начальный SP выровнен на 8 байт, у каждого ненулевого
  адреса обработчика взведён бит 0. Нули — зарезервированные слова.

Тест `rustc_a_table_matches_symbols` собирает `ch27-nvic` и сверяет
таблицу с символами ELF: слово 0 — `_stack_start`, 1 — `Reset`, 3 —
`HardFault`, 11 — `SVCall`, 15 — `DefaultHandler` (своего SysTick у
прошивки нет), 16–18 — `GPIOA`, `GPIOB`, `GPIOC`, 19 — снова
`DefaultHandler`, а число прерываний — размер `__INTERRUPTS`, делённый
на 4. `rustc_a_broken_tables` портит копию файла: чётный адрес
HardFault, невыровненный SP, переименованная секция, обрезанный файл.

Вопросы к отчёту. Почему адреса обработчиков в таблице нечётные, а
`llvm-objdump -d` показывает функции по чётным адресам? Что сделает
процессор при сбросе, если у Reset бит 0 сброшен? Где в таблице
окажется ваш обработчик, если назвать его `UART0`, а прерывание UART0
не разрешить в NVIC?

## B. Байт в UART0 тремя способами

Отправьте один байт в UART0 — подождать, пока в FIFO передатчика есть
место (бит TXFF регистра FR сброшен), и записать байт в DR — тремя
способами в `b_three.rs`:

- `ch27_b_raw(byte)` — как в C: адрес 0x4000_C000, смещения и номер
  бита числами, `read_volatile` и `write_volatile`;
- `ch27_b_pac(byte)` — через `pac::Uart0::ptr()`, регистры `fr` и `dr`,
  поля `txff` и `data`;
- `ch27_b_hal(serial, byte)` — через `embedded_io::Write` у `Serial`.

Тест `rustc_b_three_ways_one_code` собирает крейт под Cortex-M3 без LTO
и требует, чтобы у трёх функций совпали мнемоники инструкций, не было
ни одного `bl` и `blx`, была ровно одна запись и хотя бы одно чтение —
FR в цикле ожидания.

Вопросы к отчёту. Уберите `#[inline]` у `Serial::write` в
`code/ch27-hal/src/serial.rs` и прогоните тест снова: что изменилось в
ассемблере `ch27_b_hal` и почему? Какие пути паники появились и откуда?
Почему `ch27_b_raw` и `ch27_b_pac` могли оказаться одной функцией с
двумя именами, а `ch27_b_hal` — нет?

## C. Команды по UART

Консоль станции: байты приходят по одному из обработчика прерывания
приёма, редактор собирает из них строку с эхом и забоем, как в
терминале, а разбор превращает строку в команду. UART редактору не
нужен — эхо он пишет в любой `Sink`:

```rust,ignore
{{#include ../../exercises/ch27/src/c_lines.rs:sink}}
```

```rust,ignore
{{#include ../../exercises/ch27/src/c_lines.rs:editor}}
```

`feed` получает один байт:

- `\r` или `\n` заканчивает строку, эхо — `\r\n`; пустая строка —
  `Pending`, так что пара `\r\n` даёт одну строку, а не две;
- забой 0x08 и DEL 0x7F стирают последний символ, эхо — `\x08 \x08`; в
  пустой строке они ничего не делают;
- печатные символы ASCII 0x20..=0x7E копятся с эхом. Символ, который
  не поместился, вместо эха даёт звонок 0x07 — один раз, — и строка до
  конца отбрасывается: `TooLong`;
- остальные байты молча пропускаются.

Разбор — слова через пробелы, регистр важен:

```rust,ignore
{{#include ../../exercises/ch27/src/c_lines.rs:command}}
```

Число — только десятичные цифры: `"+50".parse::<u32>()` дал бы 50, а
команда `period +50` должна быть ошибкой `BadNumber`. Тесты `c_*`
проверяют эхо байт в байт, забой, переполнение, мусор и таблицу из 18
строк для разбора.

Прошивка: обработчик UART0 перекладывает байты в `Spsc` из главы 21,
`main` спит, пока очередь пуста, — без пропущенного пробуждения (раздел
[27.6](06-interrupts.md)), — кормит редактор и отвечает на команды. `push`
и `pop` у очереди — `unsafe fn`: обоснуйте у каждого вызова, почему
писатель и читатель по одному, как в станции [27.9](09-project.md). Ввод
QEMU берёт со стандартного ввода, Enter — `\r`:

```console
$ cd firmware && (sleep 1; printf 'status\rperiod 50\rperiod 5\rbogus\rstart\rstatus\rthis line is far too long for the editor\rquit\r') \
    | cargo run --release -p ch27-tasks --bin c_uart
команды: status, start, stop, period <мс>
status
период 100 мс, остановлена
period 50
ok: период 50 мс
period 5
ошибка: период вне 10..10000 мс
bogus
ошибка: неизвестная команда
start
ok: запущена
status
период 50 мс, идёт
this line is far too long for th
ошибка: строка длиннее 32 байт
quit
строк 7, потеряно байт 0
```

`sleep 1` здесь не для красоты. Байты, пришедшие до того, как прошивка
настроила UART, в QEMU теряются: без паузы пропадает первая буква
`status`, а короткий ввод из файла может не дойти до прошивки вовсе.

Вопросы к отчёту. Почему очередь приёма — на 128 байт, если на линии
115 200 бод байт приходит раз в 87 мкс? Что будет с эхом, если
пользователь нажмёт забой сразу после переполнения? Почему обработчик
UART0 сбрасывает в ICR запрос RX, хотя тот снимает и чтение FIFO?

## D1. Переключатель задач на PendSV

Две задачи, у каждой свой стек и своё значение PSP. Обработчик PendSV —
самого низкого приоритета — сохраняет r4–r11 уходящей задачи на её стек,
спрашивает у очереди, чья очередь, и восстанавливает r4–r11 следующей;
r0–r3, r12, LR, PC и xPSR сохраняет и восстанавливает сам процессор
(раздел [27.1](01-core.md)). На хосте проверяется то, что можно
проверить без процессора, — начальный кадр и очередь:

```rust,ignore
{{#include ../../exercises/ch27/src/d1_switch.rs:frame}}
```

- `Stack::prepare(entry, arg)` — стек выглядит так, будто задачу
  прервал PendSV до её первой инструкции: у вершины — 16 слов, сначала
  r4–r11 со значениями 0x0404_0404 … 0x0B0B_0B0B, затем r0 = `arg`, r1–r3
  и r12 — нули, LR = `NO_RETURN`, PC — точка входа без бита 0, xPSR —
  только бит T. Вернуть адрес сохранённого r4 — начальный PSP;
- `RoundRobin::add` — добавить задачу с её PSP или вернуть PSP, если
  места нет; `current` — номер текущей;
- `RoundRobin::switch(saved)` — запомнить PSP уходящей задачи и вернуть
  PSP следующей по кругу. При первом вызове уходящей задачи нет, и
  `saved` отбрасывается; без задач — паника «нет задач».

Прошивка: PendSV на ассемблере (`#[unsafe(naked)]`), `yield_now` —
запрос PendSV, задачи A и B уступают друг другу трижды, потом A
включает SysTick и крутится, не уступая, — очередь задаче B отдаёт
SysTick:

```console
$ cd firmware && cargo run --release -p ch27-tasks --bin d1_switch
начальный PSP: A 0x20000400, B 0x20000800
журнал: [ A0| B0 A1 B1 A2 B2 A* B
переключений 8, A крутилась без yield: true
PSP задачи B 0x200007f0
```

`[` и `|` — аргументы задач из r0 начального кадра, `A*` — A включила
SysTick, последний `B` — B получила процессор без единого `yield_now`
со стороны A. Переключений восемь: из `main` в A, шесть раз по
`yield_now` и один по SysTick.

Вопросы к отчёту. Почему при первом переключении PSP должен указывать
на запасной стек `BOOT`, хотя уходящей задачи нет? Почему PendSV — самого
низкого приоритета, а не SysTick? Оцените по руководству Cortex-M3,
сколько тактов занимает переключение: вход в исключение, `stmdb` и
`ldmia` по восьми регистрам, код очереди, выход. В QEMU этого не
измерить — счётчика тактов DWT в модели нет, — поэтому оценка остаётся
оценкой.

## D2. Разбор CFSR и HFSR

В `d2_faults.rs` — перечисление `Fault` с именами битов CFSR и HFSR и
заготовка [итератора][g-iterator] `Faults`. Напишите:

- `faults(cfsr, hfsr)` — установленные биты по порядку: CFSR от
  младшего к старшему, затем HFSR. Зарезервированные биты не дают
  ничего. Номера битов — в ARMv7-M Architecture Reference Manual;
- `insn_len(first)` — длина инструкции Thumb по первому полуслову:
  32-битные начинаются с 0b11101, 0b11110 или 0b11111 в старших пяти
  битах, остальные — 16. Это [`const fn`][g-const-fn].

Тест `d2_every_bit_once` требует 22 разных имени для 19 битов CFSR и 3
битов HFSR и ни одного — для зарезервированных; `d2_known_values`
сверяет значения из прошивок главы; `d2_instruction_length` — длины
семи инструкций, среди которых `b .` (0xE7FE): 16-битная, хотя
начинается с 0b11100.

Прошивка: включить UsageFault и ловушку деления на ноль, вызвать три
сбоя и после каждого продолжить работу. Обработчик разбирает CFSR вашим
кодом и правит сохранённый кадр: для UNDEFINSTR и DIVBYZERO —
пропустить инструкцию (`pc += insn_len`), для INVSTATE — вернуть бит T
в xPSR, и функция по чётному адресу выполнится.

```console
$ cd firmware && cargo run --release -p ch27-tasks --bin d2_faults
udf #42: CFSR 0x00010000
  UFSR.UNDEFINSTR
udiv на 0: CFSR 0x02000000
  UFSR.DIVBYZERO
  после пропуска udiv в r0 осталось делимое: 100
переход по чётному адресу: CFSR 0x00020000
  UFSR.INVSTATE
  ping вернула 7
три сбоя пройдены; зарезервированный бит 14 даёт имён: 0
```

<div class="box trap">

**Ловушка.** В QEMU 8.2.2 кадр сбоя DIVBYZERO содержит значения
регистров, устаревшие на несколько инструкций того же блока трансляции:
первая версия опыта, где `udiv` стояла посреди функции, после возврата
из обработчика получала в r1 и r2 не то, что было перед `udiv`, и иногда
падала в HardFault. На кристалле так не бывает. Образец ставит `udiv`
первой инструкцией отдельной naked-функции: после `bl` блок трансляции
начинается с неё, и устаревать нечему.

</div>

Вопросы к отчёту. Почему для INVSTATE нельзя «пропустить инструкцию»,
как для UNDEFINSTR? Почему обработчик сбрасывает CFSR записью
прочитанного значения? Что будет, если сбой случится внутри самого
обработчика UsageFault?
