# 27.5. HAL и embedded-hal 1.0

## Трейты, а не функции производителя

HAL из раздела [27.4](04-ownership.md) — уровень над PAC: вместо
регистров — выводы, UART, таймеры. Но драйвер микросхемы на плате —
дисплея, датчика, сдвигового регистра — не должен знать, чей это HAL.
Для этого есть **embedded-hal 1.0**: набор трейтов, которые HAL
реализует, а драйверы — требуют.

| Трейт | Что умеет |
|---|---|
| `digital::OutputPin` | `set_high`, `set_low`, `set_state` |
| `digital::StatefulOutputPin` | `is_set_high`, `is_set_low`, `toggle` |
| `digital::InputPin` | `is_high`, `is_low` |
| `delay::DelayNs` | `delay_ns`, `delay_us`, `delay_ms` |
| `spi::SpiDevice`, `i2c::I2c` | транзакции на шине (глава 9, задача [9.D](../ch09/08-tasks.md)) |

Последовательного порта в embedded-hal 1.0 нет: он переехал в крейт
embedded-io с трейтами `Read` и `Write`, общими с `std::io` по смыслу.
У каждого трейта — связанный тип ошибки (`ErrorType`). Выводы HAL этой
главы ошибиться не могут, и их ошибка — `Infallible`: образец `Ok(())`
неопровержим (раздел [7.2](../ch07/02-convert.md)), и обрабатывать
нечего.

## Драйвер 74HC595

74HC595 — сдвиговый регистр: восемь выходов по трём проводам. По фронту
SRCLK бит со входа SER вдвигается в регистр, по фронту RCLK регистр
защёлкивается на выходы Q0–Q7. Драйвер — в `code/ch27`, и про LM3S6965
он не знает ничего:

```rust
{{#include ../../code/ch27/src/hc595.rs:driver}}
```

Три параметра типа, три вывода, одна ошибка `E` на всех. `release`
возвращает выводы: драйвер владел ими, пока был нужен, и отдаёт
обратно, а не держит до конца программы.

Поскольку драйвер знает только трейт, его можно проверить на хосте —
моделью микросхемы, которая видит фронты:

```rust
{{#include ../../code/ch27/src/hc595.rs:model}}
```

Тест `byte_reaches_outputs` выдвигает пять байтов и проверяет выходы
модели и порядок фронтов — восемь SRCLK, один RCLK на байт, —
`error_stops_the_transfer` — что ошибка вывода выходит из `write` сразу
и защёлка не дёргается. Ни один из тестов не нуждается в плате или в
QEMU.

На LM3S6965 тот же драйвер получает выводы порта B:

```rust
{{#include ../../firmware/ch27-periph/src/main.rs:hc595}}
```

```console
74HC595 <- 0xa5; выводы PB2..PB0 после write: 001
```

Микросхемы в QEMU нет, и прошивка проверяет то, что видно: состояние
выводов после передачи. Защёлка и такт — в нуле, а на SER остался
последний выдвинутый бит, бит 0 байта 0xA5, — единица.

## Во что компилируется драйвер

Обобщённый драйвер поверх трейтов поверх PAC — четыре слоя абстракции.
Тест `rustc_hc595_is_inlined_and_unrolled` собирает
`ch27_hc595_write` из `probe.rs` под Cortex-M3 и требует, чтобы
вызовов не осталось. Начало тела:

```text
ch27_hc595_write:
	push	{r7, lr}
	mov	r7, sp
	uxtb	r0, r1
	mov.w	r12, #2
	lsrs	r2, r0, #7
	movw	r0, #20488
	movt	r0, #16384
	ubfx	r3, r1, #6, #1
	str	r2, [r0, #-4]
	movs	r2, #0
	str.w	r12, [r0]
	str	r2, [r0]
	str	r3, [r0, #-4]
	ubfx	r3, r1, #5, #1
	…
	movs	r1, #4
	str.w	r12, [r0]
	str	r2, [r0]
	str	r1, [r0, #8]
	str	r2, [r0, #8]
	pop	{r7, pc}
```

r0 — 0x4000_5008, адрес DATA порта B с маской вывода PB1 (такт);
`[r0, #-4]` — маска PB0 (данные), `[r0, #8]` — маска PB2 (защёлка).
Цикл по восьми битам развёрнут, `ubfx` достаёт очередной бит в r3, и на
каждый бит — три записи: данные, фронт и спад такта. Плюс две записи
защёлки — 26 `str`, ни одного `ldr`, ни одного `bl`. Так выглядел бы
код на C, написанный руками под эту плату.

## UART через embedded-io

Делитель скорости HAL считает функцией из раздела
[25.2](../ch25/02-const-fn.md):

```rust
{{#include ../../code/ch27-hal/src/serial.rs:baud}}
```

Прошивка берёт его в `const`, и ошибка скорости проверяется при сборке:

```rust
{{#include ../../firmware/ch27-periph/src/main.rs:serial}}
```

```console
UART0: 115200 бод при 12 МГц, IBRD 6, FBRD 33
```

12 000 000 · 4 / 115 200 ≈ 416,7, округлённо 417 = 6 · 64 + 33.
Ошибка — −799 ppm, в пределах 2 %. А скорость 921 600 при 12 МГц
недостижима: PL011 делит частоту на 16, и выше 750 000 бод не
получится; `const` с такой скоростью не соберётся с текстом «UART:
делитель меньше 1, скорость недостижима при этой частоте».

`Serial::new` принимает выводы в режиме `Alternate`, и только PA0 и PA1
(раздел [27.4](04-ownership.md)). Чтение и запись:

```rust
{{#include ../../code/ch27-hal/src/serial.rs:io}}
```

`write` может записать меньше, чем просили, но не ноль: она ждёт места
для первого байта и пишет, пока FIFO передатчика не заполнится.
Записать всё — дело `write_all` из трейта, а `writeln!` работает через
`core::fmt::Write`, которую `Serial` реализует поверх `write_all`.
`flush` ждёт, пока передатчик опустеет: на плате без неё сброс или
`debug::exit` в конце прошивки оборвали бы последний байт. В QEMU байт
уходит сразу при записи в DR.

<div class="box trap">

**Ловушка.** Комментарий перед `impl` и `#[inline]` у трёх методов — не
украшение. Без них `write` из другого крейта — вызов `bl`, как
`bitband::alias` в разделе [27.4](04-ownership.md), а у вызывающего
остаются пути паники `slice_index_fail` и `panic_fmt`: `write_all`
паникует, если `write` вернула `Ok(0)`, и режет буфер `&buf[n..]`, а без
тела `write` компилятор не знает, что `n` не ноль и не больше длины
буфера. Задача
[27.B](10-tasks.md) сравнивает запись байта тремя способами — сырым
указателем, PAC и HAL — и требует одинакового машинного кода; без
`#[inline]` она не проходила.

</div>

## Задержка

```rust
{{#include ../../code/ch27-hal/src/delay.rs:delay}}
```

SysTick считает такты ядра вниз от 2²⁴ − 1 по кругу. Задержка ждёт,
пока накопится нужное число тактов, и учитывает перенос через ноль.
Гарантия `DelayNs` — «не меньше»: прерывание посреди ожидания только
удлинит её.

```rust
{{#include ../../firmware/ch27-periph/src/main.rs:delay}}
```

```console
delay_us(100): прошло не меньше 1200 тактов: true
```

100 мкс при 12 МГц — 1200 тактов. Точное число прошивка не печатает: в
QEMU SysTick идёт по часам хоста (раздел [27.1](01-core.md)), и сколько
тактов «прошло», зависит от загрузки машины, на которой запущен QEMU.

## Сколько это стоит

```console
$ cargo build --release -p ch27-periph
$ llvm-size target/thumbv7m-none-eabi/release/ch27-periph
   text	   data	    bss	    dec	    hex	filename
   6072	      0	      4	   6076	   17bc	target/thumbv7m-none-eabi/release/ch27-periph
```

ОЗУ под данные — четыре байта, и заняты из них два:
`DEVICE_PERIPHERALS` из PAC и такой же флаг `TAKEN` у
`CorePeripherals` в cortex-m. Всё владение периферией — `Peripherals`,
порты, выводы, `Serial`, `Delay`, драйвер 74HC595 — значения нулевого
размера или из одного-двух полей нулевого размера. Из 6 КиБ кода
`main` — меньше 1 КиБ, а около 3,5 КиБ — `core::fmt` ради `writeln!`
(раздел [26.3](../ch26/03-cortex-m.md)).

<div class="box c">

**Как в C.** HAL производителя — функции вида
`HAL_GPIO_WritePin(GPIOB, GPIO_PIN_0, GPIO_PIN_SET)`, у каждого
производителя свои. Драйвер дисплея, написанный под HAL одного
производителя, под другим не собирается, и библиотеки драйверов
приходят с прослойкой «портирования» из указателей на функции. Трейты
embedded-hal — та же прослойка, но статическая: драйвер обобщён по
выводу, и после мономорфизации от прослойки не остаётся ни вызовов, ни
указателей.

</div>

<div class="box hood">

**Под капотом.** Вокруг embedded-hal 1.0 — ещё три крейта.
embedded-hal-async — те же трейты с `async fn` для исполнителей вроде
embassy (раздел [27.8](08-rtic.md)). embedded-hal-bus делит одну шину
SPI или I2C между несколькими драйверами: каждому — свой `SpiDevice`
со своим выбором кристалла поверх общей `SpiBus`. embedded-hal-nb —
неблокирующий вариант в стиле версии 0.2 для тех, кто уже на нём
написан.

</div>
