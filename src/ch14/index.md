# 14. Умные указатели и внутренняя изменяемость

## Мотивирующая проблема

Конфигурацию датчика читают сразу несколько подсистем: журнал, отправитель
телеметрии, сторож, который следит за периодом опроса. Кто из них
освободит её последним, заранее не известно, и в C время жизни таких
объектов ведут счётчиком ссылок вручную — так устроен `struct kref` в
ядре Linux. Программа `code/ch14/c/kref.c` — уменьшенная копия этой
схемы. `config_get` берёт ссылку, `config_put` отдаёт, последний
освобождает:

```c
{{#include ../../code/ch14/c/kref.c:11:40}}
```

Журнал держит свою ссылку, пока открыт. Отправитель забирает ссылку
вызывающего — и это записано только в комментарии:

```c
{{#include ../../code/ch14/c/kref.c:42:70}}
```

На изменение конфигурации подписываются обработчики. Список подписчиков
растёт через `realloc`, а сторож, увидев период больше секунды,
подписывает ещё один обработчик — прямо из рассылки:

```c
{{#include ../../code/ch14/c/kref.c:72:115}}
```

Четыре сценария, каждый с одной ошибкой: ссылка, не отданная на пути
ошибки (`leak`); ссылка, отданная дважды (`double`); подписка во время
рассылки (`notify`); счётчик, который меняют два потока (`race`):

```c
{{#include ../../code/ch14/c/kref.c:117:171}}
```

GCC и clang с `-Wall -Wextra` молчат. Программа отрабатывает до конца и
печатает почти правдоподобные строки:

```console
$ gcc -O2 -Wall -Wextra -pthread -o kref kref.c
$ ./kref
подписчиков: 3, вызовов: 1 0 1 (ожидалось 1 1 1)
журнал не открыт, ссылок: 2 (ожидалось 1)
журнал: период 5 мс
```

**Ссылка, не отданная на пути ошибки.** `logger_open` взял ссылку и
вернул `-1`, не отдав её. Счётчик остался на единицу больше, последний
`config_put` довёл его до единицы, а не до нуля, и конфигурация не
освободится никогда. Утечку видит только LeakSanitizer, и только если
программа дошла до выхода:

```console
$ gcc -O1 -g -fsanitize=address,undefined -pthread -o kref-asan kref.c
$ ./kref-asan leak
==19369==ERROR: LeakSanitizer: detected memory leaks
Direct leak of 24 byte(s) in 1 object(s) allocated from:
    #0 0x7fdcfbcfd9c7 in malloc ../../../../src/libsanitizer/asan/asan_malloc_linux.cpp:69
    #1 0x5620ebaf470a in config_new kref.c:19
```

**Ссылка, отданная дважды.** `sender_start` забрал ссылку вызывающего,
но вызывающий об этом не помнил и отдал её ещё раз. Конфигурация
освобождена, пока журнал на неё ссылается, и журнал читает из
освобождённого блока. 5 вместо 100 — старшие 32 бита служебного
указателя, который glibc записала в начало блока, когда положила его в
список свободных:

```console
$ ./kref-asan double
==19372==ERROR: AddressSanitizer: heap-use-after-free on address 0x503000000044 …
READ of size 4 at 0x503000000044 thread T0
    #0 0x55a94f89a11b in scenario_double kref.c:136
freed by thread T0 here:
    #0 0x7f58b16fc4d8 in free ../../../../src/libsanitizer/asan/asan_malloc_linux.cpp:52
    #1 0x55a94f89984c in config_put kref.c:39
```

**Подписка во время рассылки.** `config_set_period` держит `s` — адрес
элемента массива — и зовёт обработчик. Сторож подписывает новый,
`realloc` переносит массив, и `s->calls++` после возврата пишет в
освобождённую память. Счётчик вызовов сторожа потерян: 0 вместо 1.
Третий подписчик свой вызов получил — цикл перечитывает `nsubs` и `subs`
на каждом шаге. ASan указывает на запись, но не на причину:

```console
$ ./kref-asan notify
==19367==ERROR: AddressSanitizer: heap-use-after-free on address 0x504000000038 …
READ of size 4 at 0x504000000038 thread T0
    #0 0x5606c243bc2e in config_set_period kref.c:99
freed by thread T0 here:
    #0 0x7fed76cfc778 in realloc ../../../../src/libsanitizer/asan/asan_malloc_linux.cpp:85
    #1 0x5606c243b5ae in subscribe kref.c:86
```

**Неатомарный счётчик.** `c->refs++` — это чтение, сложение и запись,
и два потока теряют обновления друг друга. Скрипт
`code/ch14/c/run.sh` запускает гонку двадцать раз; исходы одного такого
прогона:

| Что напечатано | Запусков |
|---|---|
| `потоки: ссылок 1 (ожидалось 1)` | 1 |
| `потоки: ссылок` от 2 до 13 | 11 |
| `потоки: ссылок 1646792222` | 1 |
| `free(): double free detected in tcache 2`, код 134 | 3 |
| `tcache_thread_shutdown(): unaligned tcache chunk detected`, код 134 | 4 |

Верный ответ — один раз из двадцати. В одиннадцати запусках счётчик
остался больше единицы, и конфигурация утекла. В остальных восьми он
раньше времени дошёл до нуля, и блок освободили, пока второй поток с ним
работал: вместо счётчика напечатан кусок служебного указателя glibc, а
семь раз glibc сама поймала порчу своих списков и прервала программу.
ThreadSanitizer находит гонку с первого раза: `kref.c:32 in config_get`
против `kref.c:38 in config_put`.

Статические анализаторы не следят за значением счётчика. `gcc
-fanalyzer` предупреждает дважды, оба раза о сценарии `double`. `clang
--analyze` — пять раз о «Use of memory after it is freed»: в `notify` и
`double` по делу, ещё в трёх местах, где ошибки нет, потому что считает,
что любой `config_put` мог освободить блок. Утечку не видит ни один.
`run.sh` проверяет все эти выводы.

## Что делает Rust

Счётчик ссылок в Rust — это тип. `Rc<Config>` держит конфигурацию и
счётчик в одном блоке кучи; `Rc::clone` — это `config_get`, а
`config_put` вызывает компилятор сам, когда клон выходит из области
видимости или его уничтожают:

```rust
{{#include ../../code/ch14/src/rc.rs:config}}
```

```rust
{{#include ../../code/ch14/src/rc.rs:kref}}
```

Ошибка на пути `Err` не теряет ссылку: клон — локальная переменная
`Logger::open`, и он уничтожается при выходе из функции любым путём.
Что `Sender::start` забирает ссылку, видно из типа параметра: `Rc<Config>`
по значению. Отдать её второй раз нельзя — после перемещения переменной
нет (`E0382`, глава 3). Отправить `Rc` в другой поток не даёт трейт
`Send`:

```console
error[E0277]: `Rc<Config>` cannot be sent between threads safely
   --> src/main.rs:6:24
    |
  6 |     std::thread::spawn(move || mine.period_ms);
    |     ------------------ -------^^^^^^^^^^^^^^^
    |     |                  |
    |     |                  `Rc<Config>` cannot be sent between threads safely
    |     |                  within this `{closure@src/main.rs:6:24: 6:31}`
    |     required by a bound introduced by this call
    |
    = help: within `{closure@src/main.rs:6:24: 6:31}`, the trait `Send` is not implemented for `Rc<Config>`
```

Для потоков есть `Arc` с атомарным счётчиком. А список подписчиков,
который меняют во время обхода, в Rust живёт в `RefCell`, и та же
подписка из обработчика вместо записи в освобождённую память даёт
панику с точным местом: `RefCell already borrowed`.

- `Box<T>` — единственный владелец значения в куче. Размер — один
  указатель, для среза и трейт-объекта — два (раздел [14.1](01-box.md)).
- `Deref` и `DerefMut` делают из своего типа указатель: `*x`, вызовы
  методов значения и приведения `&Box<String>` к `&str` (раздел
  [14.2](02-deref.md)). Тип, который ведёт себя как указатель и сам
  управляет тем, на что указывает, называют *умным указателем* (smart
  pointer): `Box`, `Rc`, `Arc`.
- `Rc<T>` и `Weak<T>` — подсчёт ссылок в одном потоке: счётчики и
  значение в одном блоке, слабые ссылки не продлевают жизнь значения
  (раздел [14.3](03-rc.md)).
- `Arc<T>` — то же с атомарным счётчиком: `lock inc` на x86-64,
  `ldrex`/`strex` на Cortex-M3, на Cortex-M0 `Arc` нет вовсе (раздел
  [14.4](04-arc.md)).
- *Внутренняя изменяемость* — изменение через `&`. Законна только
  внутри `UnsafeCell`; `Cell` и `RefCell` построены на нём (раздел
  [14.5](05-cells.md)).
- `OnceCell`, `LazyCell`, `OnceLock` и `LazyLock` вычисляют значение
  один раз, при первом обращении (раздел [14.6](06-lazy.md)).
- `Cow` заимствует, пока можно, и копирует, когда надо (раздел
  [14.7](07-cow.md)).

`cargo asm --simplify` из release-сборки; для Cortex-M к ней добавлены
`--no-default-features --features alloc --target <цель>`.
