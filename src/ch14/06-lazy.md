# 14.6. Ленивая инициализация

Коэффициенты калибровки, таблица CRC, имя станции — значения, которые
вычисляют или узнают один раз, а читают всё время работы. В C для
этого есть `static` внутри функции с флагом «уже посчитано» или
`pthread_once`. В Rust — четыре типа, по два на каждый вопрос:

| | Функция известна при создании | Значение задают позже |
|---|---|---|
| Один поток, `core` | `LazyCell<T, F>` | `OnceCell<T>` |
| Много потоков, `std` | `LazyLock<T, F>` | `OnceLock<T>` |

Все четыре — ячейки: заполняются через `&self` и стоят на
`UnsafeCell`. Но изменить значение после заполнения нельзя, и поэтому
они, в отличие от `RefCell`, выдают обычную `&T` на всё время жизни
ячейки.

## OnceCell: посчитать при первом обращении

Канал АЦП с калибровкой по двум точкам. Коэффициенты нужны при каждом
пересчёте, но считать их при создании канала незачем — канал может так
и не понадобиться:

```rust
{{#include ../../code/ch14/src/lazy.rs:channel}}
```

`get_or_init` возвращает `&T`: если ячейка пуста, сначала вызывает
замыкание и кладёт результат. `value` принимает `&self`, и канал можно
держать в `Rc` или отдавать по общей ссылке, а коэффициенты всё равно
посчитаются один раз — тест `channel_fits_once` проверяет счётчик
`fits` после трёх пересчётов. Точки калибровки −40,00 °C при отсчёте 0
и 125,00 °C при 4095 дают −4000, 12499 и 4252 сотых для отсчётов 0,
4095 и 2048: наклон в 1/65536 округлён вниз, и последняя точка
потеряла сотую.

Замыкание, которое во время инициализации обращается к той же ячейке,
— ошибка: значения ещё нет, а начать второе заполнение нельзя.
`OnceCell` паникует:

```console
thread 'main' (1755) panicked at /rustc/2d8144b7880597b6e6d3dfd63a9a9efae3f533d3/library/core/src/cell/once.rs:300:66:
reentrant init
```

У `OnceLock` в той же ситуации исход, по документации, не определён, и
нынешняя реализация зависает: поток ждёт сам себя.

## LazyCell: функция известна заранее

`LazyCell` хранит замыкание вместе с ячейкой и вызывает его при первом
разыменовании. Таблица CRC нужна, только если кадр придётся проверять:

```rust
{{#include ../../code/ch14/src/lazy.rs:lazycell}}
```

```rust
{{#include ../../code/ch14/src/lazy.rs:crc}}
```

Тест `lazycell_builds_only_when_needed` проверяет, что без проверки
таблица не строится ни разу, а с проверкой строится один раз и даёт
контрольную сумму 0x29B1 для строки `123456789` — стандартное
проверочное значение CRC-16/CCITT-FALSE. `LazyCell` и `OnceCell` лежат в
`core` и работают в [`no_std`][g-no-std]: в прошивке их держат в структуре
драйвера, но не в `static`, потому что они не `Sync`.

## OnceLock и LazyLock: для static

Общую для всех потоков таблицу кладут в `static`, и ячейка должна быть
`Sync`: первый поток, который до неё дошёл, строит значение, остальные
ждут, а все последующие читают без всякой синхронизации, кроме одной
загрузки:

```rust
{{#include ../../code/ch14/src/lazy.rs:lazylock}}
```

```rust
{{#include ../../code/ch14/src/lazy.rs:oncelock}}
```

`set` заполняет `OnceLock` один раз и возвращает отвергнутое значение
при втором вызове — тест `station_set_once`. Таблица в `CRC_TABLE`
сверена с побитовым `crc16` из `telemetry-frame` (тест
`table_crc_matches_project`).

Сколько стоит обращение к `LazyLock` после инициализации, видно в
ассемблере:

```rust
{{#include ../../code/ch14/src/codegen.rs:lazy_get}}
```

```console
$ cargo asm -p ch14 --lib --simplify ch14_lazy_crc
ch14_lazy_crc:
	push r15
	push r14
	push rbx
	sub rsp, 16
	mov rbx, qword ptr [rip + ch14::lazy::CRC_TABLE@GOTPCREL]
	mov eax, dword ptr [rbx + 512]
	test eax, eax
	jne .LBB106_1
	test rsi, rsi
	je .LBB106_3
…
.LBB106_7:
	mov r8d, eax
	shr r8d, 8
	xor r8b, byte ptr [rdi + rcx]
	shl eax, 8
	movzx r8d, r8b
	movzx r8d, word ptr [rbx + 2*r8]
	xor eax, r8d
…
.LBB106_1:
…
	call qword ptr [rip + <std::sys::sync::once::futex::Once>::call@GOTPCREL]
```

Таблица — 512 байт с начала `static`, состояние `Once` — 32-битное
слово сразу за ней, по смещению 512. Быстрый путь — одна загрузка и
сравнение с нулём: в `std` на futex ноль означает «готово»
(`COMPLETE`), а любое другое значение уводит на медленный путь в
`Once::call`, который построит таблицу или подождёт поток, который её
строит. Проверка стоит до цикла, один раз на вызов, а сам цикл берёт
таблицу по `rbx` без всяких проверок — тест `rustc_lazy_checked_once`
следит за этим. Загрузка состояния по смыслу — `Acquire`, но на x86-64
это обычный `mov`: модель памяти x86 сама не переставляет чтения с
последующими чтениями (глава 21).

<div class="box trap">

**Ловушка: отравление.** Если инициализатор `LazyLock` запаниковал,
ячейка остаётся *отравленной*, и каждое следующее обращение паникует
снова — с другим сообщением. Тест `lazylock_is_poisoned_after_panic` в
`code/ch14/src/tricks.rs` ловит обе паники: первая несёт сообщение
инициализатора, «датчик не ответил», вторая — `LazyLock instance has
previously been poisoned`. Если ошибка инициализации ожидаема — датчик
может не ответить при старте, — её возвращают значением:
`LazyLock<Result<Table, Error>>` или `OnceLock`, заполненный тем, кто
умеет обработать отказ.

</div>

<div class="box c">

**Как в C.** `pthread_once(&once, init)` — это `OnceLock` без значения:
функция инициализации кладёт результат в отдельную глобальную
переменную, и ничто не мешает прочесть её до `pthread_once`. Здесь
значение лежит внутри ячейки, и прочесть его, минуя проверку, нельзя.
`static` внутри функции в C++ (не в C) с потокобезопасной
инициализацией — ближайший аналог `LazyLock`, и компилятор C++ ставит
перед ним ту же проверку флага.

</div>
