# 13. Итераторы

## Мотивирующая проблема

Обработка отсчётов в C — это циклы по индексам, и почти каждая ошибка в
них — ошибка на единицу или на знак. Программа `code/ch13/c/loops.c` —
четыре функции из обработки отсчётов АЦП, каждая с классической
ошибкой:

```c
{{#include ../../code/ch13/c/loops.c:10:47}}
```

С `-Wall -Wextra` GCC предупреждает один раз, о сравнении беззнакового
`i >= 0`. clang с теми же флагами молчит и о нём: его предупреждение
`-Wtautological-unsigned-zero-compare` включает только `-Wtype-limits`.
Статические анализаторы обоих компиляторов, `gcc -fanalyzer` и `clang
--analyze`, не находят ничего. А на нормальных данных программа
печатает почти верные числа:

```console
$ gcc -O2 -Wall -Wextra -o loops loops.c
loops.c:26:30: warning: comparison of unsigned expression in '>= 0' is always true [-Wtype-limits]
$ ./loops
окон по 3: 4, первая сумма 922, последняя 974
последний выше 500: 3
отсчёты: 10 12 900 950 11 13 (n = 6)
без выбросов: 10 12 950 11 13 (n = 5)
```

**`n - w` при `n < w`.** Для двух отсчётов и окна из трёх `n - w` в
`size_t` — не минус один, а `SIZE_MAX`, и `window_sums` идёт по памяти,
пока не упадёт:

```console
$ ./loops short
Segmentation fault
```

**`i >= 0` для беззнакового.** Условие истинно всегда, и если ни один
отсчёт не выше порога, `last_above` переходит от `i = 0` к `SIZE_MAX`,
то есть к `x[-1]`, и читает память перед массивом, пока не встретит
что-нибудь большое. Вместо `-1` функция возвращает отрицательный
«индекс», который зависит от компилятора и от того, что лежит в стеке:

```console
$ ./loops last
последний выше 1000: -6
$ ./loops-clang last
последний выше 1000: -1205
```

**`x[i + 1]` при `i = n - 1`.** `deltas` читает `x[n]`, отсчёт за концом
массива, и пишет `d[n - 1]` — разность, которой не должно быть: если
вызывающий отвёл под `d` ровно `n - 1` элементов, это ещё и запись за
концом. Вывод при этом верный: лишний элемент никто не печатает. Ошибку видит только
[санитайзер][g-sanitizer]:

```console
$ gcc -O1 -g -fsanitize=address -o loops-asan loops.c
$ ./loops-asan deltas
==25887==ERROR: AddressSanitizer: stack-buffer-overflow on address 0x7f808210002c …
READ of size 2 at 0x7f808210002c thread T0
    #0 0x55d266de953c in deltas loops.c:36
```

Так же [ASan][g-asan] ловит `window_sums` (`stack-buffer-overflow`) и `last_above`
(`stack-buffer-underflow`), но только на тех данных, на которых ошибка
случилась.

**Изменение массива во время обхода.** `drop_spikes` убирает выброс
сдвигом хвоста, а `i++` перешагивает через отсчёт, который встал на
место убранного. Из двух соседних выбросов 900 и 950 остаётся второй.
Памяти программа не портит, и этого не видит никто: ни компилятор, ни
анализатор, ни ASan. Скрипт `code/ch13/c/run.sh` проверяет все эти
выводы.

## Что делает Rust

*Итератор* — значение, у которого можно попросить следующий элемент,
пока они не кончатся. Цикл, который он заменяет, пишет библиотека один
раз, и ошибок на единицу в нём нет:

```rust
{{#include ../../code/ch13/src/basics.rs:intro}}
```

`windows(w)` отдаёт перекрывающиеся окна-срезы, и если окно шире [среза][g-slice],
окон просто нет. `rposition` ищет с конца и возвращает `Option<usize>`:
`None` вместо `-1`, без беззнакового счётчика, который надо уменьшать.
`windows(2)` даёт ровно `n - 1` пар, и `w[1]` в каждой существует.
`retain` удаляет элементы на месте и сам следит за тем, что куда
сдвинулось. А тот же обход с удалением, что в C, не компилируется:

```console
error[E0502]: cannot borrow `v` as mutable because it is also borrowed as immutable
3 |     for (i, s) in v.iter().enumerate() {
  |                   --------------------
  |                   |
  |                   immutable borrow occurs here
  |                   immutable borrow later used here
4 |         if *s > 500 {
5 |             v.remove(i);
  |             ^^^^^^^^^^^ mutable borrow occurs here
```

Итератор держит заём вектора, и пока цикл не кончился, менять вектор
нельзя: то, что в C было договорённостью, здесь — правило [заимствования][g-borrowing]
из главы 4.

- [Трейт][g-trait] `Iterator` — один обязательный метод `next` и больше полусотни
  методов, которые достаются даром. `for` работает с любым типом, который
  реализует `IntoIterator`, и три формы `for` по коллекции — это три
  разных итератора (раздел [13.1](01-iterator.md)).
- *Адаптеры* — `map`, `filter`, `zip`, `chain`, `windows` и другие —
  строят из итератора новый и ничего не делают, пока элемент не
  попросили (раздел [13.2](02-adapters.md)).
- *Потребители* — `sum`, `fold`, `find`, `collect` — запускают цепочку
  и останавливаются, как только ответ известен (раздел
  [13.3](03-consumers.md)).
- Свой итератор — тип с `next`, а если он знает длину и умеет идти с
  конца, то и с `ExactSizeIterator` и `DoubleEndedIterator`.
  Простые итераторы строятся из [замыкания][g-closure] (раздел [13.4](04-custom.md)).
- Цепочка адаптеров компилируется в один цикл, часто без проверок
  границ и с [SIMD][g-simd] на x86-64; на Cortex-M видна [развёртка][g-unrolling] и инструкции
  [DSP][g-dsp] (раздел [13.5](05-codegen.md)).

## Код главы

```console
$ cargo test -p ch13 -p ch13-solutions            # примеры и решения
$ cargo +nightly test --doc -p ch13               # коды ошибок в doc-тестах
$ bash code/ch13/c/run.sh                         # loops.c
$ cargo run --release -p ch13 --example bench     # время на элемент
$ cargo asm -p ch13 --lib --simplify ch13_chain_fold
$ cd firmware && cargo run --release -p ch13-iter
```

Числа в тексте получены на rustc 1.97.0 (LLVM 22.1.6) и nightly 1.101.0
(2026-10-21) для `x86_64-unknown-linux-gnu` и трёх [целей][g-target] Cortex-M, GCC
13.3, clang 18.1 и glibc 2.39, прошивки — в QEMU 8.2.2. Время снято на
виртуальной машине с процессором Intel Xeon с [AVX2][g-sse-avx] и меняется от запуска
к запуску на 10–20 %. Ассемблер снят командой `cargo asm --simplify` из
release-сборки; для Cortex-M к ней добавлены `--no-default-features
--target <цель>`.
