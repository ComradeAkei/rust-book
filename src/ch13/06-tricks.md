# 13.6. Трюки и ловушки

## rev().enumerate() и enumerate().rev()

Порядок адаптеров меняет смысл. `rev().enumerate()` сначала разворачивает,
потом нумерует — с нуля от конца. `enumerate().rev()` нумерует исходный
порядок и потом идёт с конца, сохраняя номера:

```rust
{{#include ../../code/ch13/src/tricks.rs:rev_enumerate}}
```

Нужен индекс в исходном массиве при обходе с конца — второе. Чтобы
сохранить номера, `enumerate` должен знать заранее, какой номер у
последнего элемента, то есть длину: `Enumerate` реализует
`DoubleEndedIterator`, только если внутренний итератор —
`ExactSizeIterator`. У `Chars` длины нет — число символов UTF-8 не
узнать, не пройдя строку, — и компилятор отказывает:

```console
error[E0277]: the trait bound `Chars<'_>: ExactSizeIterator` is not satisfied
2 |     s.chars().enumerate().rev().next()
  |                           ^^^ the trait `ExactSizeIterator` is not implemented for `Chars<'_>`
  |
  = note: required for `Enumerate<Chars<'_>>` to implement `DoubleEndedIterator`
```

Для строки индекс последнего символа даёт `s.char_indices().next_back()`
— байтовое смещение, а не номер символа, — или `s.chars().count()`
отдельным проходом.

## take_while съедает разделитель

```rust
{{#include ../../code/ch13/src/tricks.rs:take_while}}
```

Чтобы узнать, что условие ложно, `take_while` должен получить элемент
из исходного итератора, и вернуть его обратно не может: у итератора нет
операции «положить назад». Запятая в `"12,34"` прочитана, не прошла
условие и пропала, и после `take_while` из исходного итератора выходит
`3`, а не `,`. `peekable` с `next_if` сначала смотрит, а забирает,
только если подходит, — запятая остаётся на месте.

То же относится к любому разбору «до разделителя» через `by_ref()`:
`skip_while` теряет то, что пропустил, — так и задумано, — а
`take_while` теряет ещё и первый неподходящий элемент, о чём легко
забыть.

## zip молчит о разных длинах

```rust
{{#include ../../code/ch13/src/tricks.rs:zip_len}}
```

`same_bytes(b"\xa5\x01", b"\xa5\x01\x03")` — `(true, false)`. `zip`
кончился вместе с коротким срезом, `all` по двум парам — `true`, и
лишний байт третьего никто не увидел. Для сравнения
последовательностей есть `Iterator::eq`, `cmp` и `partial_cmp`: они
сравнивают и длины. А если `zip` нужен и длины обязаны совпасть, это
проверяют до цикла: `assert_eq!(a.len(), b.len())`.

## sum переполняется в типе результата

```rust
{{#include ../../code/ch13/src/tricks.rs:overflow}}
```

`sum::<u8>()` по байтам складывает в `u8`, и `200 + 100` в отладочной
сборке — паника `attempt to add with overflow`, в release — 44. Тест
`sum_overflows_in_result_type` проверяет оба поведения. Тип результата
надо расширять *до* сложения, через `map(u32::from)`: `sum::<u32>()` по
итератору `&u8` не компилируется — `u32` не реализует `Sum<&u8>`, — и
это к лучшему. Нужна сумма по модулю — `fold(0u8, |a, &b|
a.wrapping_add(b))`, нужна с проверкой — `try_fold` с `checked_add` из
раздела [13.3](03-consumers.md).

## Побочные эффекты в ленивой цепочке

```rust
{{#include ../../code/ch13/src/tricks.rs:side_effects}}
```

`effects()` — `[0, 3, 4, 5]`. `let _ = data.iter().map(tick)` заглушил
предупреждение `unused_must_use` и не запустил ничего: цепочка
построена и тут же уничтожена. `for_each` запустил все три вызова.
`peek` вызвал замыкание для первого элемента и запомнил результат, и
следующий `next` отдал запомненное без нового вызова: второй `next`
дал пятый вызов, а не шестой.

Вывод: `map` — для преобразования, а не для действия. Если действие —
главное, пишут `for_each` или `for`, и тогда оно случится, даже если
результат никому не нужен. Если оно — отладочное, есть `inspect`, и
его назначение видно из имени.

## Нулевой шаг

`windows(0)`, `chunks(0)`, `chunks_exact(0)` и `step_by(0)` — паника,
а не пустой итератор и не бесконечный цикл:

| Вызов | Сообщение паники |
|---|---|
| `[1, 2, 3].windows(0)` | `window size must be non-zero` |
| `[1, 2, 3].chunks(0)` | `chunk size must be non-zero` |
| `(0..3).step_by(0)` | `assertion failed: step != 0` |

Паника случается при создании итератора, а не при первом `next`. Если
размер окна приходит извне — из конфигурации, из кадра, — его проверяют
до вызова, как любое деление на ноль. `std::num::NonZero` в сигнатуре
делает это обещание частью типа.

<div class="box trap">

**Ловушка.** Ловушки раздела, кроме первой, — ошибки логики, а не
памяти: ни одна не приводит к UB, и ни одну не находит компилятор. Их ловят тесты
на краевых данных — пустой вход, вход короче окна, разные длины, байт
на границе разделителя, переполнение суммы — те же, что нужны и
C-программе из введения. Разница в том, что в Rust на этих данных
тест падает с понятной паникой или неверным ответом, а не портит
память.

</div>
