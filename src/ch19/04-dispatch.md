# 19.4. Выбор реализации во время выполнения

У нас две версии суммы: `sum_sse2` работает везде, `sum_avx2` быстрее, но
звать её можно только там, где есть AVX2. Решать, какая доступна, нужно в
рантайме — один бинарник запускают и на старом Xeon без AVX2, и на свежем
Ryzen. Наличие фичи сообщает макрос `is_x86_feature_detected!`: он читает
`cpuid` и возвращает `bool`.

`cpuid` — медленная инструкция с сериализацией, но платить за неё на
каждой проверке не приходится: макрос выполняет её один раз и кэширует
результат в статической переменной, дальше — атомарное чтение и проверка
бита. Остаются проверка и ветвление в каждом вызове. Поэтому выбор делают
один раз и кэшируют в указателе на функцию:

```rust
{{#include ../../code/ch19/src/dispatch.rs:dispatch}}
```

Разберём. `SumFn` — тип указателя на *безопасную* функцию `fn(&[i32]) ->
i32`. Но `sum_avx2` — `unsafe fn`, её нельзя положить туда напрямую, поэтому
есть обёртка-мостик `avx2_wrap`: безопасная снаружи, внутри зовёт
`sum_avx2` в `unsafe`. Это корректно, потому что `avx2_wrap` попадает в кэш
*только* если `best` увидел AVX2 — инвариант держится конструкцией, а не
надеждой. `best` вызывается один раз через `OnceLock::get_or_init`; дальше
`sum` — проверка «`OnceLock` уже заполнен?» (атомарное чтение с `Acquire`)
и косвенный вызов по закэшированному указателю, без повторного определения
фич.

<div class="box trick">

**Трюк — указатель вместо ветвления.** Альтернатива — `if
is_x86_feature_detected!(…) { … } else { … }` в каждом вызове. `cpuid` там
не повторяется — макрос читает закэшированный бит, — но проверка и
ветвление остаются в каждом вызове и мешают встраиванию. Кэш-указатель
решает, какую реализацию звать, один раз за время жизни процесса. Сама
стандартная библиотека Rust так не делает: `memchr` в `core` написан без
SIMD-диспетчеризации, хеширование — скалярное, а сравнение срезов уходит в
`memcmp`/`bcmp` из libc. Приём живёт в библиотеках: крейт `memchr` держит
указатель на функцию в `AtomicPtr` и при первом вызове заменяет его
лучшей реализацией, а glibc выбирает `memcpy`, `strlen` или тот же
`memcmp` через `ifunc` — при загрузке программы.

</div>

<div class="box trap">

**Ловушка — `OnceLock` и `static mut`.** Соблазнительно кэшировать в `static
mut DISPATCH: SumFn`, но запись и чтение `static mut` из разных потоков —
гонка данных, то есть UB ([глава 16](../ch16/index.md)). `OnceLock`
инициализируется ровно один раз даже при гонке потоков и дальше читается без
блокировки. Для безусловно-первого-использования годится и
`std::sync::Once`, но `OnceLock<SumFn>` заодно хранит само значение.

</div>

<div class="box hood">

**Под капотом.** `is_x86_feature_detected!` живёт в `std`, а не в `core`,
но не из-за кэша: атомарная статическая переменная есть и в `core`. Макросы
для всех архитектур собраны в крейте `std_detect`, а на ARM и других
платформах фичи спрашивают у ОС (`getauxval`, `sysctl`), о которой `core`
ничего не знает; x86-части хватило бы `cpuid` и `xgetbv`. В `no_std` фичу
задают статически через `target-feature`. Первый вызов читает `cpuid` (и
`xgetbv` — включила ли ОС сохранение регистров AVX), дальше — атомарное
чтение `Relaxed` из статической памяти и проверка бита.
`OnceLock::get_or_init` на каждом вызове проверяет, заполнен ли он (чтение
`Acquire`), а `best` зовёт один раз. В сумме: один `cpuid` и один вызов
`best` за весь процесс, потом — проверка `OnceLock` и косвенный вызов по
указателю.

</div>

Этот приём — проверить фичу раз, закэшировать указатель — и есть
стандартный способ отгрузить один бинарник, который использует AVX2 там,
где он есть, и не падает там, где его нет. В [задаче C](07-tasks.md) вы
соберёте такой же диспетчер для поиска байта.
