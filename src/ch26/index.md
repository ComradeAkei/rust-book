# 26. no_std: программа без операционной системы

## Мотивирующая проблема

Стандарт C различает две среды. *Размещённая* (hosted) — с операционной
системой и всей библиотекой: `printf`, `malloc`, `fopen`, `exit`.
*Автономная* (freestanding) — без них: стандарт обещает там только
заголовки без функций, `<stddef.h>`, `<stdint.h>`, `<limits.h>`,
`<stdarg.h>` и ещё несколько. Прошивку собирают с `-ffreestanding
-nostdlib`, и дальше программист остаётся с тремя чужими файлами:

- **код запуска** `startup_xxx.s` от производителя — таблица векторов и
  обработчик сброса, который копирует `.data` и обнуляет `.bss`, прежде
  чем вызвать `main`;
- **скрипт компоновки** `xxx_flash.ld` — оттуда же, на сотни строк, и
  правят его, не читая;
- **newlib** или её урезанный вариант — ради `printf` и `memcpy`, с
  заглушками `_write`, `_sbrk` и `_exit`, без которых не собирается.

Граница между «работает без ОС» и «нужна ОС» в C проходит по
компоновке. `snprintf` — в той же библиотеке, что и `fopen`; что `printf`
тянет `_write`, а `malloc` — `_sbrk`, программист узнаёт по ошибке
компоновщика `undefined reference to '_sbrk'`, если повезёт, и по
зависанию на плате, если заглушка есть, но пустая.

Даже `-ffreestanding` не значит «без библиотеки»: руководство GCC прямо
требует, чтобы автономная среда сама предоставила `memcpy`, `memmove`,
`memset` и `memcmp`, — компилятор вставляет их вызовы в код, где их не
писали.

## Что делает Rust

Стандартная библиотека Rust — три слоя, и граница между ними видна
компилятору, а не компоновщику:

- **`core`** — то, что не требует от среды ничего, кроме нескольких
  функций памяти: `Option`, `Result`, итераторы, срезы, `str`,
  форматирование, атомики, `Cell` и `RefCell`;
- **`alloc`** — то, что требует кучи, но не ОС: `Box`, `Vec`, `String`,
  `Rc`, `format!`. Кучу даёт глобальный распределитель, который
  программа объявляет сама;
- **`std`** — всё остальное, и ему нужна ОС: потоки, файлы, часы,
  переменные окружения, раскрутка стека при панике.

`#![no_std]` оставляет крейту только `core`; `alloc` подключается
явно. Обращение к `Vec` без `alloc` — ошибка компиляции с номером
строки, а `std` для Cortex-M0 нет вовсе: rustc скажет об этом при первом
`extern crate std`, задолго до компоновки.

Что остаётся программисту — немного, но всё на виду: обработчик паники
`#[panic_handler]`, точка входа, скрипт компоновки, код запуска и
распределитель памяти, если нужен `alloc`. Функции памяти, которых
требует компилятор, даёт крейт `compiler_builtins`, который rustc
подключает сам. Обычно всё это берут готовым из `cortex-m-rt` — эта
глава делает то же руками.

- **`core`, `alloc` и `std`** ([26.1](01-layers.md)) — один код на трёх
  слоях, возможности крейта, ошибки, которыми компилятор говорит о
  слоях.
- **Linux без libc** ([26.2](02-linux.md)) — `_start`, стек процесса,
  системные вызовы инструкцией `syscall`, почему без LTO не
  компонуется.
- **Cortex-M без cortex-m-rt** ([26.3](03-cortex-m.md)) — таблица
  векторов на Rust, обработчик сброса, свой скрипт компоновки, вывод
  через semihosting.
- **`.data`, `.bss` и код запуска** ([26.4](04-startup.md)) — куда
  компоновщик кладёт изменяемый `static`, если скрипт о нём не знает, и
  что должен сделать код запуска.
- **`memcpy` без libc** ([26.5](05-memcpy.md)) — откуда в коде берутся
  вызовы, которых никто не писал, и кто их обслуживает.
- **Тесты `no_std` на хосте** ([26.6](06-testing.md)) — как один крейт
  тестируется со `std` и собирается без неё.

## Код главы

Примеры 26.1, 26.2 и 26.5 лежат в `code/ch26`: библиотека `no_std` с
возможностями `alloc` и `std`, фрагменты, которые компилятор должен
отвергнуть, и программа `code/ch26/start` со своим `_start` — отдельный
крейт со своим workspace и профилями. Прошивки разделов 26.3–26.5 — в
`firmware/ch26-bare`, шаг проекта — в `firmware/ch26-station`, задачи —
в `exercises/ch26` и `solutions/ch26`, прошивки задач C и D —
`firmware/ch26-boot` и `firmware/ch26-tasks`.

```console
$ cargo test -p ch26                  # слои, системные вызовы, _start, ассемблер, ошибки no_std
$ cargo test -p ch26-solutions        # задачи A, B и D
$ cd firmware && cargo run --release -p ch26-bare           # разделы 26.3–26.4 в QEMU
$ cd firmware && cargo run --release -p ch26-bare --bin mem # раздел 26.5
$ cd firmware && cargo run --release -p ch26-station        # шаг проекта
```

Тексты сообщений сняты с rustc 1.97.0 (LLVM 22, компоновщик rust-lld),
ассемблер — `cargo rustc --release -- --emit asm` под
x86_64-unknown-linux-gnu, thumbv7m-none-eabi и thumbv6m-none-eabi, вывод
программ — на ядре Linux 6.18 и в QEMU. Тесты `rustc_*` сверяют
сообщения, ассемблер и поведение программ с закреплённым компилятором
при каждом прогоне.
