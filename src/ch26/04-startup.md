# 26.4. .data, .bss и код запуска

## Изменяемый static без кода запуска

`Reset` в `ch26-bare` не копирует `.data` и не обнуляет `.bss`. Что
будет, если в прошивке всё-таки появится изменяемый `static` с
начальным значением? Возможность `orphan-data` добавляет один:

```rust,ignore
{{#include ../../firmware/ch26-bare/src/main.rs:orphan}}
```

`main` увеличивает его на единицу и печатает. Скрипт `ch26.ld` о `.data`
не знает, и без защиты компоновщик поступил бы с ней как с любой
секцией-*сиротой* (orphan): разместил бы по своему усмотрению. Защита —
блоки `GUARD`: секция `.ram (NOLOAD)` в ОЗУ собирает все `.data` и
`.bss`, а `ASSERT` требует, чтобы она была пустой:

```console
$ cargo build --release -p ch26-bare --features orphan-data
  = note: rust-lld: error: ch26.ld: изменяемый static, а код запуска не готовит .data и .bss
```

Ошибка сборки с понятным текстом вместо прошивки, которая работает
неправильно. С `CH26_NO_GUARD=1` `build.rs` вырезает блоки `GUARD` из
скрипта, и сборка проходит:

```console
$ CH26_NO_GUARD=1 cargo run --release -p ch26-bare --features orphan-data
…
COUNTER = 5 (ожидалось 6)
$ llvm-objdump -h target/thumbv7m-none-eabi/release/ch26-bare
Idx Name                                       Size     VMA      Type
  1 .vector_table                              00000040 00000000 DATA
  2 .text                                      00000918 00000040 TEXT
  3 .rodata                                    000000dc 00000958 DATA
  4 .data._RNvCsaVtM0AFvqQa_9ch26_bare7COUNTER 00000004 00000a34 DATA
```

rust-lld положил сироту `.data._R…COUNTER` сразу за `.rodata` — во
flash, по адресу 0xa34, в отдельный сегмент с флагами `RW`. Начальное
значение 5 там действительно лежит, и `main` его читает. А `COUNTER +=
1` — обычная инструкция `str` по адресу во flash, и память от неё не
меняется: flash программируют через её контроллер особой
последовательностью, а не записью по адресу. QEMU запись молча
отбросил, и `COUNTER` остался равен 5.

<div class="box hood">

**Под капотом.** У lld есть ключ `--orphan-handling=error`, который
превращает любую сироту в ошибку. Здесь он не годится: сиротами для
этого скрипта оказываются и `.debug_*`, и `.comment`, и
`.ARM.attributes`, и пришлось бы перечислять их все. Секция-ловушка с
`ASSERT` ловит ровно то, что нужно: входные секции `.data*` и `.bss*`.

</div>

## Два адреса одной секции

У `.data` два адреса. **VMA** (virtual memory address) — где секция живёт
при выполнении: в ОЗУ, там её читает и пишет код. **LMA** (load memory
address) — где лежат её начальные значения в образе: во flash, потому что
ОЗУ после включения питания ничего не помнит. Секции `.bss` нужен только
VMA: её начальное значение — нули, и в образе для неё нет ни байта. Вот
как это записано в `link.x` cortex-m-rt 0.7.7:

```text
  .data : ALIGN(4)
  {
    . = ALIGN(4);
    __sdata = .;
    *(.data .data.*);
    . = ALIGN(4); /* 4-byte align the end (VMA) of this section */
  } > RAM AT>FLASH
  . = ALIGN(4);
  __edata = .;

  /* LMA of .data */
  __sidata = LOADADDR(.data);

  .bss (NOLOAD) : ALIGN(4)
  {
    . = ALIGN(4);
    __sbss = .;
    *(.bss .bss.*);
    *(COMMON); /* Uninitialized C statics */
    . = ALIGN(4); /* 4-byte align the end (VMA) of this section */
  } > RAM
  . = ALIGN(4);
  __ebss = .;
```

`> RAM AT>FLASH` — VMA в области `RAM`, LMA в `FLASH`. `LOADADDR(.data)`
— LMA, и символ `__sidata` («start of initialization data») отдаёт её
коду запуска. `NOLOAD` у `.bss` — в образе пусто. Все границы выровнены
на 4, и `ASSERT` в конце скрипта это проверяют: код запуска копирует и
обнуляет словами.

## Что делает код запуска

Обработчик сброса, которого нет в `ch26-bare`, делает четыре шага:

1. обнуляет слова от `__sbss` до `__ebss`;
2. копирует слова из flash начиная с `__sidata` в ОЗУ от `__sdata` до
   `__edata`;
3. на Cortex-M4F открывает FPU: биты CP10 и CP11 в регистре `CPACR`
   (0xE000_ED88), затем `dsb` и `isb`;
4. вызывает `main`.

Писать эти шаги на Rust нельзя. Пока они не выполнены, `static` в ОЗУ
содержат мусор, а компилятор вправе считать, что каждый из них уже
равен своему начальному значению, — в любой функции, включая ту, что
обнуляет. Цикл обнуления на Rust LLVM к тому же узнает и заменит вызовом
`memset` (раздел [26.5](05-memcpy.md)). Поэтому код запуска пишут на
ассемблере: cortex-m-rt — в `global_asm!` (раздел
[25.6](../ch25/06-flash.md)), задача [26.C](08-tasks.md) — в
naked-функции (раздел [19.2](../ch19/02-naked.md)).

Секции, которые код запуска не трогает, тоже бывают нужны: `.uninit`
переживает программный сброс, потому что его не обнуляют (раздел
[8.8](../ch08/08-sections.md)). А `.rodata` код запуска не трогает
никогда: константы и таблицы читаются прямо из flash.

<div class="box trap">

**Ловушка.** QEMU загружает ELF сам, по заголовкам программы, и в
опытах задачи C первая загрузка прошла даже без цикла копирования:
начальное значение `.data` уже лежало в ОЗУ. На плате так не будет —
программатор пишет только flash. Поэтому проверка кода запуска в
задаче C переживает два программных сброса подряд: в опытах пропуск
копирования проявился на второй загрузке, а пропуск обнуления — на
третьей.

</div>

<div class="box c">

**Как в C.** Тот же код — в `startup_stm32f4xx.s` любого проекта на
STM32: `CopyDataInit` и `FillZerobss` на ассемблере, символы `_sidata`,
`_sdata`, `_edata`, `_sbss`, `_ebss` из скрипта производителя, затем
`SystemInit` и `main`. C тоже нельзя выполнять до этих циклов, по той
же причине: глобальные переменные с инициализатором.

</div>
