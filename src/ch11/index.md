# 11. Динамическая диспетчеризация

Нужны [трейты](../ch09/01-traits.md) и
[обобщённые функции](../ch10/01-generics.md). Вспомните различие между
самим значением и [ссылкой на него](../ch04/01-refs.md).
В главе 10 конкретный тип выбирался для каждой копии функции.
Здесь одна функция сможет по очереди работать с разными датчиками,
получая вместе с адресом данных сведения о том, какие методы вызвать.
Именно выбор метода во время работы называется [динамической
диспетчеризацией][g-dynamic-dispatch]. Для первого чтения важна эта идея; устройство
каждого служебного поля разберём после неё.

## Мотивирующая проблема

Глава 9 начиналась с таблицы указателей на функции, которую C
использует вместо интерфейса. В ядре Linux тот же приём доведён до
системы: у каждого драйвера своя `struct file_operations`, указатель на
неё лежит в каждом открытом файле, а данные драйвера получают из общей
части макросом `container_of`. Программа `code/ch11/c/fops.c` устроена
так же и заодно меряет, во что обходится вызов через таблицу:

```c
{{#include ../../code/ch11/c/fops.c}}
```

```console
$ gcc -O2 -Wall -Wextra -o fops fops.c
$ ./fops
sizeof(struct thermo) = 24, sizeof(struct counter) = 24
thermo: 6, counter: 999
write: -22, 0
$ ./fops bench sorted
по порядку: 1.45 нс на вызов (сумма 115425000000)
$ ./fops bench shuffled
вперемешку: 6.33 нс на вызов (сумма 115425000000)
```

Ни GCC, ни clang с `-Wall -Wextra` не предупреждают, [санитайзеры][g-sanitizer] молчат,
и программа верна. Но у самого приёма четыре свойства, за которые
платят все его пользователи.

**Таблица — часть каждого объекта.** Отсчёт термодатчика занимает два
байта, а `struct thermo` — 24: шесть байт выравнивания, указатель на
таблицу и указатель на имя. Тысяча объектов — шестнадцать килобайт
служебных указателей, и устройство, которое лежит во flash, обязано
хранить их там же.

**Объект и таблицу связывает программист.** `thermo_read` получает
`struct dev *` и верит, что тот вложен в `struct thermo`: `container_of`
вычитает смещение поля и ничего не проверяет. Что объекту досталась
именно `thermo_ops`, известно только функции `new_dev`, которая собрала
пару. Глава 9 показала, что бывает, если таблицу и данные перепутать.

**Необязательный метод проверяет каждый вызывающий.** У термодатчика
нет `write`, поле в таблице — `NULL`, и `dev_write` возвращает
`-EINVAL`, как `vfs_write` в ядре. Забыть проверку можно в любом из
мест, где метод вызывают.

**Цена вызова зависит от порядка объектов.** Сумма в обоих замерах одна:
объекты те же, переставлены только указатели на них. Но вперемешку
каждый вызов в четыре с лишним раза дороже. В цикле `poll` один и тот же
`call QWORD PTR [rax]` прыгает то в `thermo_read`, то в `counter_read`.
Процессор должен знать адрес перехода раньше, чем прочитает его из
таблицы, и угадывает его по истории. По порядку типов адрес меняется два
раза за проход, вперемешку — непредсказуемо. Модель предсказателя из
`valgrind` считает промахи:

```console
$ valgrind --tool=cachegrind --cache-sim=no --branch-sim=yes ./fops bench sorted 1000
==27331== Mispredicts:        8,994  (    6,807 cond +     2,187 ind)
==27331== Mispred rate:         0.4% (      0.6%     +       0.2%   )
$ valgrind --tool=cachegrind --cache-sim=no --branch-sim=yes ./fops bench shuffled 1000
==27324== Mispredicts:      521,514  (    6,815 cond +   514,699 ind)
==27324== Mispred rate:        24.7% (      0.6%     +      51.3%   )
```

Две смены типа на тысячу вызовов против промаха в каждом втором вызове.
Защита от Spectre v2, с которой собирают ядро Linux, делает картину ещё
хуже: с [retpoline][g-retpoline] (`-mindirect-branch=thunk`) каждый косвенный вызов
идёт через переходник, который нарочно не даёт предсказателю угадать
адрес, и стоит 14 нс в любом порядке. Скрипт `code/ch11/c/run.sh` проверяет все эти выводы, а
время печатает для сведения.

На Cortex-M0, M3 и M4 предсказателя нет: косвенный вызов — загрузка
адреса из таблицы во flash и `blx` по регистру, после которого конвейер
наполняется заново. Порядок объектов там не важен, а цена — та самая
загрузка и невозможность [встроить][g-inlining] метод.

## Что делает Rust

[Обобщения][g-generic] из главы 10 решают задачу, когда тип известен при компиляции.
Если набор типов становится известен только во время работы — датчики
описаны в конфигурации, драйвер выбирается по идентификатору микросхемы,
обработчики регистрирует пользователь, — нужен *объект трейта* `dyn
Trait`, и реализация метода выбирается во время работы. Это
*динамическая диспетчеризация* (dynamic dispatch); выбор при
компиляции, как у обобщений из главы 10, — статическая.

- `&dyn Sensor` — *толстый указатель*: адрес данных и адрес [таблицы
  методов][g-vtable]. Таблица живёт в указателе, а не в объекте, и `Thermo`
  остаётся двухбайтовым (раздел [11.1](01-dyn.md)).
- Таблицу строит компилятор, одну на пару «тип — трейт»: [деструктор][g-destructor],
  размер, выравнивание и методы. Связать объект с чужой таблицей нельзя
  (раздел [11.2](02-vtable.md)).
- Не всякий трейт годится для `dyn`: обобщённый метод или `Self` по
  значению в таблицу не положить. `where Self: Sized` убирает такой метод
  из таблицы, не ломая трейт (раздел [11.3](03-compat.md)).
- Объект можно положить в `Box`, `Rc` или оставить на стеке за
  `&mut dyn FnMut`, без кучи (раздел [11.4](04-objects.md)).
- `Any` проверяет тип во время работы, а объект подтрейта приводится к
  объекту [супертрейта][g-supertrait] (раздел [11.5](05-any.md)).
- Во что обходится косвенный вызов на x86-64 и Cortex-M, когда LLVM
  превращает его в прямой и что делает с ним retpoline (раздел
  [11.6](06-cost.md)).
- Если набор типов закрыт, перечисление и `match` часто лучше `dyn`
  (раздел [11.7](07-closed.md)).

## Код главы

```console
$ cargo test -p ch11 -p ch11-solutions            # примеры и решения
$ cargo +nightly test --doc -p ch11               # коды ошибок в doc-тестах
$ cargo +nightly test -p ch11 --features nightly --test nightly
$ bash code/ch11/c/run.sh                         # fops.c: таблица, предсказатель, retpoline
$ cargo asm -p ch11 --lib --simplify ch11_read_dyn
$ cd firmware && cargo run --release -p ch11-dyn  # таблицы методов во flash
```

Числа в тексте получены на rustc 1.97.0 (LLVM 22.1.6) и nightly 1.101.0
(2026-10-21) для `x86_64-unknown-linux-gnu` и трёх [целей][g-target] Cortex-M, GCC
13.3, clang 18.1, glibc 2.39 и valgrind 3.22, прошивки — в QEMU 8.2.2.
Время вызова снято на виртуальной машине с процессором Intel Xeon с
поддержкой eIBRS и меняется от запуска к запуску на 10–20 %. Ассемблер
снят командой `cargo asm --simplify` из release-сборки; для Cortex-M к
ней добавлены `--no-default-features --target <цель>`.
