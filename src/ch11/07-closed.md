# 11.7. Закрытый набор типов

## Перечисление вместо dyn

`dyn Sensor` нужен, когда набор типов открыт: датчик может написать
другой крейт, и станции о нём знать не обязательно. Но в прошивке
станции все датчики обычно перечислены в одном месте. Тогда хватит
перечисления с вариантом на каждый тип:

```rust
{{#include ../../code/ch11/src/closed.rs:enum}}
```

`AnySensor` — обычный тип с размером: 8 байт на x86-64 и на Cortex-M.
Он лежит в массиве по значению, без указателей, кучи и таблиц, и
реализует тот же `Sensor`, так что обобщённый код из главы 10 примет
его наравне с `Thermo`. `From` позволяет писать `Thermo { raw: 32
}.into()` там, где ждут `AnySensor`.

## Вызов через match

```rust

```

```console
$ cargo asm -p ch11 --lib --simplify ch11_read_enum
ch11_read_enum:
	cmp word ptr [rdi], 1
	jne .LBB36_2
	mov eax, dword ptr [rdi + 4]
	ret
.LBB36_2:
	movsx eax, word ptr [rdi + 2]
	imul ecx, eax, 100
	lea eax, [rcx + 15]
	test ecx, ecx
	cmovns eax, ecx
	sar eax, 4
	ret
$ cargo asm -p ch11 --lib --simplify --no-default-features --target thumbv7m-none-eabi ch11_read_enum
ch11_read_enum:
	push {r7, lr}
	mov r7, sp
	ldrsh.w r1, [r0, #2]
	movs r2, #100
	muls r1, r2, r1
	add.w r2, r1, r1, lsr #28
	ldr r1, [r0, #4]
	ldrh r0, [r0]
	cmp r0, #0
	it eq
	asreq r1, r2, #4
	mov r0, r1
	pop {r7, pc}
```

Раскладку видно по смещениям. Тег занимает два байта по смещению 0,
`Thermo` — со смещения 2, `Counter` — с 4. Тегу хватило бы и байта, но
между ним и `raw` всё равно осталось бы выравнивание, и rustc отдал тегу
всё место до поля (раздел [6.3](../ch06/03-enums.md)). Вместо загрузки
из таблицы и косвенного вызова — сравнение тега и прямой переход, а оба
тела `read` встроены. На Cortex-M3 перехода нет вовсе: LLVM вычисляет
обе ветки, а `it eq` с `asreq` выбирает результат — для такого
короткого `read` это дешевле, чем переход, который сбросил бы конвейер.

Цикл опроса по массиву перечислений тоже обходится без вызовов:

```rust
{{#include ../../code/ch11/src/closed.rs:poll}}
```

```console
$ cargo asm -p ch11 --lib --simplify ch11_poll_enum
ch11_poll_enum:
	…
.LBB33_5:
	mov rdx, rdi
	cmp byte ptr [rdi], 0
	je .LBB33_13
	mov edi, dword ptr [rdx + 4]
	cmp byte ptr [rdx + 8], 0
	jne .LBB33_16
	jmp .LBB33_15
.LBB33_13:
	movsx edi, word ptr [rdx + 2]
	imul r8d, edi, 100
	…
```

LLVM раскрыл цикл на два элемента за проход (`[rdx]` и `[rdx + 8]`), а
на Cortex-M3 — на четыре. С `dyn` раскрывать было нечего: тело вызова
неизвестно. Ветвление по тегу предсказывается так же, как косвенный
переход: по порядку типов почти без промахов, вперемешку — с промахом в
каждом втором элементе. Но промах условного перехода дешевле, а если
ветки короткие, LLVM, как на M3, обходится без перехода.

## Когда что

| | `dyn Trait` | Перечисление | Обобщение |
|---|---|---|---|
| Набор типов | открыт: новый тип добавляет кто угодно | закрыт: новый вариант — правка перечисления | известен в каждой точке вызова |
| Разные типы в одной коллекции | да, за указателем | да, по значению | нет |
| Размер элемента | два слова плюс объект где-то ещё | самый большой вариант плюс тег | размер типа |
| Вызов | косвенный, через таблицу | сравнение тега или [таблица переходов][g-jump-table] | прямой, обычно встроен |
| Копий кода | одна | одна, с `match` внутри | по копии на тип |
| Нужна ли куча | для владения — `Box` | нет | нет |

`match` с большим числом вариантов LLVM превращает в таблицу переходов,
и это снова косвенный переход — с теми же отношениями с предсказателем,
что у `dyn`. Где проходит граница, меряет задача C в разделе
[11.8](08-tasks.md): 2, 8 и 64 типа, по порядку и вперемешку.

Писать `match` в каждом методе перечисления скучно, и для этого есть
крейт `enum_dispatch`: атрибут на трейте и перечислении генерирует те
же реализации, что выписаны выше. Устроен он как процедурный макрос, их
разбирает [глава 24](../ch24/index.md).

<div class="box c">

**Как в C.** Перечисление с данными — это [размеченное объединение][g-tagged-union],
`struct sensor { enum kind k; union { struct thermo t; struct counter
c; }; }` и `switch` по `k`. Разница в том, кто проверяет. В C можно
прочитать `u.c`, когда записан `u.t`, а `switch` без ветки для нового
вида соберётся с предупреждением `-Wswitch`, если нет `default`, и
молча, если есть. В Rust данные варианта доступны только внутри его
ветки `match`, а `match` без нового варианта не соберётся (E0004) — и
так во всех местах программы, где разбирают `AnySensor`.

</div>

<div class="box trap">

**Ловушка.** Размер перечисления — размер самого большого варианта.
Добавьте в `AnySensor` датчик с буфером `[i16; 64]`, и каждый
элемент станции вырастет с 8 до 130 с лишним байт, даже если такой
датчик один. Clippy предупреждает об этом линтом `large_enum_variant`, но
только когда варианты различаются больше чем на 200 байт, и здесь
промолчит. Лекарство — положить большой вариант в `Box` или хранить
его отдельно. Для публичного перечисления
есть вторая сторона: новый вариант ломает чужие `match`, и если набор
не окончательный, перечисление помечают `#[non_exhaustive]` — тогда
пользователи обязаны писать ветку `_`.

</div>
