# 3. Владение и перемещение

## Мотивирующая проблема

Прошивка копит кадры телеметрии в очереди отправки. Кадр создаётся в
`produce`, кладётся в очередь, а `flush` отправляет и освобождает всё,
что накопилось. Если связь пропала, `produce` сообщает об ошибке:

```c
{{#include ../../code/ch03/c/queue.c}}
```

Программа собирается без единого предупреждения с `-Wall -Wextra`. Ни
статический анализатор GCC (`-fanalyzer`), ни `clang --analyze` ошибки не
видят. А она есть: `enqueue` передала очереди *владение* (ownership) кадром, то есть
обязанность его освободить, но путь ошибки `goto err` об этом не знает и
освобождает кадр сам. Очередь хранит висячий указатель, и `flush` читает
освобождённую память, а затем освобождает её второй раз. Без [санитайзера][g-sanitizer]
результат зависит от аллокатора: у автора программа падала с SIGSEGV,
не успев ничего напечатать. С санитайзером ошибку видно точно:

```console
$ gcc -O1 -g -fsanitize=address queue.c && ./a.out
=================================================================
==11271==ERROR: AddressSanitizer: heap-use-after-free on address 0x502000000030 ...
READ of size 8 at 0x502000000030 thread T0
    #0 0x55d0d4ff23e5 in flush queue.c:20
    #1 0x55d0d4ff23e5 in main queue.c:51

0x502000000030 is located 0 bytes inside of 16-byte region [0x502000000030,0x502000000040)
freed by thread T0 here:
    #0 0x7faa4a2fc4d8 in free ../../../../src/libsanitizer/asan/asan_malloc_linux.cpp:52
    #1 0x55d0d4ff2378 in produce queue.c:43

previously allocated by thread T0 here:
    #0 0x7faa4a2fd9c7 in malloc ../../../../src/libsanitizer/asan/asan_malloc_linux.cpp:69
    #1 0x55d0d4ff22a2 in produce queue.c:29
```

Комментарий «очередь становится владельцем» — единственное место, где
записан договор о владении. Компилятор его не читает. В больших
программах на C такие договоры живут в документации (`the caller must
free`, `takes ownership of`), в соглашениях об именах (`_get` и `_put`,
`_create` и `_destroy`) и в головах. Ошибки в них дают три класса
ошибок: использование после освобождения, двойное освобождение и утечку.
По данным команды безопасности Chromium, около 70 % серьёзных уязвимостей
браузера — ошибки работы с памятью, и самая частая из них — использование
после освобождения.

## Что делает Rust

- У каждого значения ровно один *владелец*: переменная, поле, элемент
  коллекции. Когда владелец исчезает, значение уничтожается, и
  освобождение памяти, закрытие файла, возврат канала DMA выполняет
  [деструктор][g-destructor], `Drop`. Вызывать его руками не нужно и нельзя.
- Передача значения в функцию или присваивание *перемещает* его: владение
  переходит к новому месту, а старое становится недоступным. Тот же путь
  ошибки на Rust не компилируется:

  ```text
  error[E0382]: use of moved value: `f`
    --> produce.rs:19:14
     |
  16 |     let f = Frame { payload: vec![seq; 64] };
     |         - move occurs because `f` has type `Frame`, which does not implement the `Copy` trait
  17 |     q.enqueue(f); // владение передано очереди...
     |               - value moved here
  18 |     if !link_up {
  19 |         drop(f); // ...а путь ошибки об этом не знает
     |              ^ value used here after move
  ```

- Порядок уничтожения определён правилами языка, а не порядком строк в
  `goto cleanup`, и выполняется при любом выходе из функции: `return`, `?`,
  `break`, [паника][g-panic].
- Копирование побитовое и неявное только для типов `Copy`, у которых нет
  деструктора. Всё остальное копируется явно, вызовом `clone`.

Перемещение — это `memcpy` байтов значения, и обычно оптимизатор его
стирает. Раздел [3.5](05-machine.md) показывает, когда копия остаётся и
сколько стека она стоит на Cortex-M с 16 КиБ ОЗУ.
