# 3.6. Стражи и границы гарантий

## Ресурс как значение

Всё, что было в этой главе, складывается в приём, который в C++ называют
RAII (resource acquisition is initialization): ресурс захватывается при
создании значения и освобождается в его деструкторе. Значение становится
*правом* на ресурс, и к праву применяются правила владения: его можно
переместить, вернуть из функции, положить в структуру, а освободится
ресурс ровно один раз, на любом пути выхода из области видимости,
включая ранний `return`, оператор `?` и панику на хосте.

В стандартной библиотеке так устроено почти всё: `Vec` и `Box` владеют
памятью, `File` закрывает дескриптор в `drop`, `MutexGuard` отпускает
мьютекс (раздел [2.6](../ch02/06-temporaries.md) показал, чем грозит
забытый временный `MutexGuard`). Отдельной функции `unlock` у мьютекса в стабильном Rust нет
вовсе: секция кончается вместе со стражем.

<div class="box c">

**Как в C.** Ближайший аналог в C — расширение GCC и Clang
`__attribute__((cleanup(f)))`: при выходе переменной из области
видимости вызывается `f(&переменная)`. На нём с версии 6.5 построены
макросы `guard(mutex)(&lock)` и `__free(kfree)` в ядре Linux
(`include/linux/cleanup.h`). Чего у расширения нет, так это
перемещения: нельзя вернуть такой ресурс из функции или отдать другому
владельцу, не отключив очистку вручную.

</div>

## Страж критической секции

Обработчик прерывания и основной код делят данные. Пока основной код их
меняет, прерывание надо запретить, а потом вернуть как было. Страж:

```rust
{{#include ../../firmware/ch03-irq/src/main.rs:guard}}
```

<div class="box ref">

**Справка: PRIMASK.** Однобитовый регистр ядра Cortex-M. Если бит
установлен, ядро не принимает исключения с настраиваемым приоритетом,
то есть все прерывания, кроме NMI и HardFault. Ставит бит инструкция
`cpsid i` (`interrupt::disable()` в крейте `cortex-m`), снимает
`cpsie i`. Прерывание, пришедшее при установленном бите, не теряется:
оно остаётся в ожидании и выполняется сразу после `cpsie i`. Тот же
механизм есть на M0, M3 и M4.

</div>

Деструктор не разрешает прерывания безусловно, а возвращает то
состояние, которое застал конструктор. Без этого вложенная секция,
закончившись, открыла бы внешнюю. Опыт проверяет пять случаев. Прерывание
SysTick ставится в ожидание программно, и счётчик тиков показывает,
выполнился ли обработчик:

```rust
{{#include ../../firmware/ch03-irq/src/main.rs:main}}
```

```console
$ cd firmware
$ cargo run --release -p ch03-irq
let _g = ...: PRIMASK = 1, тиков 0
после блока:  PRIMASK = 0, тиков 1
let _ = ...:  PRIMASK = 0, тиков 2
вложенная, IrqGuard:   PRIMASK = 1, тиков 2
после внешней:         PRIMASK = 0, тиков 3
вложенная, NaiveGuard: PRIMASK = 0, тиков 4
drop(outer), inner жив:  PRIMASK = 0, тиков 5
```

С `--target thumbv6m-none-eabi` (Cortex-M0, плата micro:bit) вывод тот
же. Построчно:

1. Страж `_g` жив до конца блока: прерывание ждёт, тиков 0. Блок
   кончился, страж уничтожен, ожидавшее прерывание выполнилось: тиков 1.
2. `let _ = IrqGuard::new()` уничтожает стража в той же строке. Секция
   кончилась, не начавшись: прерывание выполняется сразу, тиков 2.
3. Вложенный `IrqGuard` застал прерывания запрещёнными и оставил их
   запрещёнными. Внешняя секция цела, тиков по-прежнему 2.
4. Вложенный `NaiveGuard` разрешил прерывания в своём деструкторе, и
   обработчик выполнился посреди внешней секции: тиков 4.
5. Внешний `IrqGuard` уничтожен вызовом `drop` раньше внутреннего. Он
   застал прерывания разрешёнными и разрешил их, хотя внутренний страж
   ещё жив: обработчик выполнился внутри его секции, тиков 5.

Последний случай показывает предел стража: правильный порядок
уничтожения обеспечивают области видимости, но `drop` и `mem::forget`
позволяют его нарушить. Поэтому в крейтах `cortex-m` и `critical-section`
основной способ войти в критическую секцию — функция с замыканием,
`interrupt::free(|cs| ...)` и `critical_section::with(|cs| ...)`. Секция
кончается при выходе из замыкания, и вложенность секций повторяет
вложенность вызовов: нарушить её нельзя.

## let _ и let _g

Строка 2 опыта — самая частая ошибка со стражами. `_g` — переменная:
имя, которое начинается с подчёркивания, только отключает предупреждение
о неиспользуемой переменной. `_` — не переменная, а образец, который
ничего не связывает. Значение справа от `let _ =` никуда не попадает,
остаётся временным и уничтожается в конце инструкции. Если же справа
стоит не выражение, а уже существующая переменная, `let _ = x;` её не
трогает: перемещать некуда, и `x` живёт дальше, как жил.

Атрибут `#[must_use]` у конструктора ловит только половину ошибок.
Строка `IrqGuard::new();` даёт предупреждение (rustc 1.97.0, файл
`mu.rs` с тем же стражем, но без железа):

```text
warning: unused return value of `IrqGuard::new` that must be used
 --> mu.rs:8:5
  |
8 |     IrqGuard::new();
  |     ^^^^^^^^^^^^^^^
  |
  = note: страж без имени уничтожается сразу, и секция кончается, не начавшись
  = note: `#[warn(unused_must_use)]` (part of `#[warn(unused)]`) on by default
help: use `let _ = ...` to ignore the resulting value
  |
8 |     let _ = IrqGuard::new();
  |     +++++++
```

Подсказка компилятора предлагает ровно ту ошибку, от которой атрибут
должен был защитить: `let _ =` — общепринятый способ сказать «результат
мне не нужен», и `must_use` он гасит. Строку 2 ловят два линта, которые
по умолчанию выключены:

```console
$ cargo clippy -p ch03-irq -- -W let_underscore_drop -W clippy::let_underscore_must_use
warning: non-binding `let` on a result of a `#[must_use]` function
   --> ch03-irq/src/main.rs:104:9
    |
104 |         let _ = IrqGuard::new(); // страж уничтожен на этой же строке
    |         ^^^^^^^^^^^^^^^^^^^^^^^^
...
warning: non-binding let on a type that has a destructor
   --> ch03-irq/src/main.rs:104:9
...
help: consider binding to an unused variable to avoid immediately dropping the value
    |
104 |         let _unused = IrqGuard::new(); // страж уничтожен на этой же строке
    |              ++++++
```

`let_underscore_drop` встроен в rustc и срабатывает на любой тип с
деструктором, `clippy::let_underscore_must_use` — на результат функции с
`#[must_use]`. В проекте со стражами их стоит включить в `[lints]`.

## Деструктор не гарантирован

Раздел 3.4 показал `mem::forget`. Утечку можно получить и без него, на
одних счётчиках ссылок:

```rust
{{#include ../../code/ch03/examples/leaks.rs:leaks}}
```

```console
$ cargo run -p ch03 --example leaks
после цикла Rc живы: 2
после mem::forget живы: 3
после обычного блока живы: 3
```

Два узла ссылаются друг на друга через `Rc`. Когда переменные `a` и `b`
исчезают, счётчик ссылок каждого узла падает с 2 до 1, но не до нуля, и
деструкторы не вызываются никогда. Ни одной строки `unsafe` в программе
нет.

Отсюда правило, которое язык выучил на собственной ошибке. В 2015 году,
перед выходом Rust 1.0, в стандартной библиотеке была функция
`thread::scoped`: она возвращала страж, деструктор которого дожидался
потока, а поток пользовался ссылками на стек родителя. Утечка стража
через цикл `Rc` давала потоку жить дольше этих ссылок. Функцию убрали,
а `mem::forget` сделали безопасной (RFC 1066), чтобы никто больше не
считал деструктор обязательным. Её место с версии 1.63 занимает
`std::thread::scope`, которая устроена через замыкание, как
`interrupt::free`: потоки дожидаются при выходе из функции, а не в
деструкторе.

**Безопасность памяти не может зависеть от того, что деструктор
выполнится.** Деструктор хорош для освобождения ресурсов. Если утечка
стража даёт только утечку ресурса (память, дескриптор, запрещённые
навсегда прерывания), это ошибка, но не неопределённое поведение. Если
утечка ломает инвариант, на который опирается `unsafe`, нужен другой
API.

## Паника в деструкторе

```rust
{{#include ../../code/ch03/examples/double_panic.rs:flaky}}
```

```console
$ cargo run -p ch03 --example double_panic

thread 'main' (16610) panicked at code/ch03/examples/double_panic.rs:27:5:
первая паника
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
drop c
drop b

thread 'main' (16610) panicked at code/ch03/examples/double_panic.rs:18:13:
деструктор тоже паникует
stack backtrace:
...
  16:     0x559964373dbd - <double_panic[e79cf3716dd45090]::Flaky as core[940e698046960fd5]::ops::drop::Drop>::drop
                               at /home/claude/rust-book/code/ch03/examples/double_panic.rs:18:13
  17:     0x559964373d0a - core[940e698046960fd5]::ptr::drop_glue::<double_panic[e79cf3716dd45090]::Flaky>
...

thread 'main' (16610) panicked at /rustc/2d8144b7880597b6e6d3dfd63a9a9efae3f533d3/library/core/src/panicking.rs:233:5:
panic in a destructor during cleanup
thread caused non-unwinding panic. aborting.
```

Первая паника начинает раскрутку. Раскрутка уничтожает `_c`, потом `_b`,
и деструктор `_b` паникует второй раз. Две раскрутки одновременно не
бывает: вторая паника в деструкторе во время очистки — это вызов
`panic_in_cleanup` из площадки приземления (раздел 3.2), и процесс
завершается через `abort` с кодом 134. Деструктор `_a` уже не
выполняется: строки `drop a` в выводе нет. Полная трассировка
печатается, даже когда `RUST_BACKTRACE` не задана.

Отсюда второе правило: **деструктор не должен паниковать**. Если
освобождение ресурса может закончиться ошибкой, деструктор делает что
может и молчит, а для тех, кому ошибка важна, у типа есть явный метод.
`File` при уничтожении закрывает дескриптор и игнорирует ошибку
`close`; документация советует вызвать `sync_all`, если ошибки записи
нужно обработать. `BufWriter` в деструкторе сбрасывает буфер и тоже
игнорирует ошибку, а `into_inner` возвращает её.

На микроконтроллере паника не раскручивает стек (раздел 3.2), и ни
первая, ни вторая паника деструкторов не вызывают. Если периферию надо
оставить в безопасном состоянии, это делает обработчик паники.
