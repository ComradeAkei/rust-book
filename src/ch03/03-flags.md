# 3.3. Частичные перемещения и флаги drop

## Перемещение поля

Из структуры можно забрать одно поле, не трогая остальные:

```rust
{{#include ../../code/ch03/src/drop_flags.rs:partial}}
```

Журнал: `["header забран", "header", "конец функции", "payload"]`. Поле
`header` уничтожено там, где кончился его новый владелец `h`, то есть в
`drop(h)`. Поле `payload` осталось в `p` и уничтожено в конце функции.
Компилятор отслеживает владение с точностью до поля, поэтому после
`let h = p.header;` разрешено читать `p.payload`, но нельзя пользоваться
`p` целиком: передать в функцию, вернуть или переместить в другую
переменную (ошибка E0382). Образцы `let`, `match` и `if let` работают так
же: имя в образце, связанное по значению, забирает свою часть значения.
Образец `_` ничего не связывает и ничего не забирает.

Синтаксис обновления структуры `..base` — тоже частичное перемещение:

```rust
{{#include ../../code/ch03/src/drop_flags.rs:update}}
```

`_cfg` получил новое имя и порт из `base`. В `base` остался `name`, и он
уничтожается вместе с остатком `base`, последним: журнал `["cfg собран",
"cfg.name", "base.port", "base.name"]`. Если бы все недостающие поля были
`Copy`, `base` остался бы целым и доступным.

Забрать поле нельзя в двух случаях.

- У структуры есть свой `Drop` (ошибка E0509). Деструктор получает
  `&mut self` и вправе прочитать любое поле, а одного из полей уже нет.
- Значение не ваше: оно за ссылкой или это элемент вектора по индексу
  (ошибка E0507). Владелец не узнал бы, что в его значении дыра.

В обоих случаях поле можно *обменять*: забрать, оставив на его месте
другое значение. Это делают `mem::take` и `mem::replace` из
[раздела 3.4](04-mem.md).

## Флаг drop

В примерах выше компилятор знает, перемещено ли значение, в каждой точке
программы. Так бывает не всегда. Аренда канала DMA уходит передаче,
только если устройство ответило:

```rust

```

```rust
{{#include ../../code/ch03/src/flags.rs:flag}}
```

В конце `ch03_send_when_ready` канал надо вернуть, если аренда осталась у
функции, и нельзя трогать, если её забрала `ch03_start`. Какой путь
выполнялся, станет известно только во время работы. Компилятор заводит
для `lease` скрытую логическую переменную — *флаг drop*: истина, пока
значение на месте, ложь после перемещения. В конце области видимости
деструктор вызывается, только если флаг истинен.

Флаг виден в MIR — промежуточном представлении, на котором работает
проверка заимствований и в котором компилятор расставляет деструкторы
(rustc 1.97.0, release, вывод сокращён):

```text
$ cargo asm -p ch03 --lib --mir ch03_send_when_ready
fn ch03_send_when_ready(_1: Lease, _2: u32) -> bool {
    debug lease => _1;
    debug tries => _2;
    let mut _0: bool;
    ...
    let mut _13: bool;
    ...
    bb0: {
        _13 = const true;
        _0 = const false;
        ...
    bb3: {
        StorageLive(_10);
        _13 = const false;
        _10 = move _1;
        _9 = ch03_start(move _10) -> [return: bb4, unwind: bb13];
    }
    ...
    bb11: {
        drop(_1) -> [return: bb9, unwind continue];
    }

    bb12 (cleanup): {
        drop(_1) -> [return: bb10, unwind terminate(cleanup)];
    }

    bb13 (cleanup): {
        switchInt(copy _13) -> [0: bb10, otherwise: bb12];
    }
    ...
    bb17: {
        StorageDead(_21);
        switchInt(copy _13) -> [0: bb9, otherwise: bb11];
    }
}
```

`_1` — параметр `lease`, `_0` — возвращаемое значение `sent`, `_13` —
флаг. В начале он истинен (`bb0`), перед перемещением в `ch03_start`
сбрасывается (`bb3`). Выход из функции (`bb17`) и путь раскрутки при
панике (`bb13`) проверяют флаг и вызывают `drop(_1)` только при
истинном флаге.

<div class="box ref">

**Справка: MIR.** Компилятор Rust переводит программу в несколько
представлений: синтаксическое дерево, HIR (дерево без синтаксического
сахара), MIR и LLVM IR. MIR — граф базовых блоков `bbN` с явными
переходами, как в книжках по компиляторам. Каждый блок кончается
переходом: `goto`, `switchInt`, `return`, вызовом с двумя продолжениями
(`return:` и `unwind:`). Блоки с пометкой `cleanup` выполняются при
раскрутке стека. Проверка заимствований, расстановка деструкторов и
флагов работают именно на MIR. Увидеть его можно через
`cargo asm --mir` или `cargo rustc -- --emit=mir`.

</div>

## Флаг в машинном коде

В отладочной сборке флаг — честный байт в кадре стека (Cortex-M3,
сокращено):

```text
$ cargo asm -p ch03 --lib --dev --target thumbv7m-none-eabi ch03_send_when_ready
ch03_send_when_ready:
	push {r7, lr}
	mov r7, sp
	sub sp, #48
	str r1, [sp, #4]
	strb r0, [r7, #-38]
	str r1, [sp, #40]
	movs r0, #0
	strb r0, [r7, #-9]
	movs r2, #1
	strb r2, [r7, #-9]
	strb r0, [r7, #-37]
	...
.LBB57_4:
	movs r0, #0
	strb r0, [r7, #-9]
	ldrb r0, [r7, #-38]
	bl ch03_start
	movs r0, #1
	strb r0, [r7, #-37]
	b .LBB57_3
	...
.LBB57_7:
	ldrb r0, [r7, #-37]
	str r0, [sp]
	ldrb r0, [r7, #-9]
	lsls r0, r0, #31
	cbnz r0, .LBB57_9
	b .LBB57_8
.LBB57_8:
	ldr r0, [sp]
	and r0, r0, #1
	add sp, #48
	pop {r7, pc}
.LBB57_9:
	sub.w r0, r7, #38
	bl core::ptr::drop_glue::<ch03::flags::Lease>
	b .LBB57_8
```

Аренда (номер канала, один байт) лежит по адресу `r7 - 38`, `sent` — по
`r7 - 37`, флаг — по `r7 - 9`. В начале флаг записан в 1, перед
`bl ch03_start` — в 0. На выходе `lsls r0, r0, #31` оставляет от флага
младший бит, и `cbnz` уходит на вызов кода уничтожения `Lease`, если бит
установлен.

В оптимизированной сборке отдельного байта нет. LLVM замечает, что флаг
всегда равен `!sent`: аренда перемещена ровно тогда, когда передача
запущена. Одна переменная в регистре служит и результатом, и флагом
(x86_64, сокращено):

```text
$ cargo asm -p ch03 --lib ch03_send_when_ready
ch03_send_when_ready:
	push rbp
	push r15
	push r14
	push r12
	push rbx
	mov ebp, esi
	mov ebx, edi
	...
	call r12
	test al, al
	je .LBB63_1
	cmp r14d, ebp
	setb r14b
	movzx edi, bl
	call qword ptr [rip + ch03_start@GOTPCREL]
	...
.LBB63_2:
	xor r14d, r14d
	...
.LBB63_6:
	test r14b, r14b
	jne .LBB63_8
	movzx edi, bl
	call qword ptr [rip + ch03_release@GOTPCREL]
.LBB63_8:
	mov eax, r14d
	pop rbx
	pop r12
	pop r14
	pop r15
	pop rbp
	ret
```

`r14b` — это `sent`: единица, если устройство ответило (`setb` после
поиска), ноль, если попытки кончились (`xor r14d, r14d`). На выходе
`test r14b, r14b` решает и то, вернуть ли канал, и что вернуть из
функции. На Cortex-M3 ту же роль играет `r6`:

```text
$ cargo asm -p ch03 --lib --target thumbv7m-none-eabi ch03_send_when_ready
ch03_send_when_ready:
	...
	mov r4, r0
	cbz r1, .LBB16_9
	mov r5, r1
	movs r6, #0
.LBB16_2:
	mov r0, r6
	bl ch03_ready
	cbnz r0, .LBB16_5
	adds r6, #1
	cmp r5, r6
	bne .LBB16_2
	mov r6, r0
	b .LBB16_6
.LBB16_5:
	mov r6, r0
	mov r0, r4
	bl ch03_start
.LBB16_6:
	bl ch03_work
	subs r5, #1
	bne .LBB16_6
	cbz r6, .LBB16_9
	movs r0, #1
	ldr r11, [sp], #4
	pop {r4, r5, r6, r7, pc}
.LBB16_9:
	mov r0, r4
	bl ch03_release
	movs r0, #0
	ldr r11, [sp], #4
	pop {r4, r5, r6, r7, pc}
```

В первом цикле `r6` — счётчик попыток. Когда цикл кончается, в `r6`
кладут ответ `ch03_ready`: ноль, если устройство так и не ответило, и не
ноль, если ответило. После второго цикла `cbz r6` выбирает путь с
`ch03_release` или без него. При `tries == 0` функция сразу уходит на
`ch03_release`: `cbz r1, .LBB16_9` в самом начале.

Часто флаг исчезает совсем: LLVM копирует хвост функции в обе ветки, и
в каждой копии известно, перемещено ли значение. Поэтому в примере после
поиска стоит второй цикл: он делает хвост слишком большим для
копирования, и флаг остаётся виден.

<div class="box c">

**Как в C.** Флаг drop — то, что программист на C пишет руками:

```c
bool owned = true;
...
if (ready) { start(lease); owned = false; }
...
if (owned) release(lease);
```

Разница в том, что в Rust его ставит и проверяет компилятор, и забыть
сбросить его нельзя. Флаг живёт в кадре функции, а не в значении:
`size_of::<Lease>()` равен 1, никакого скрытого бита «перемещено» в
самом значении нет. В C++ всё наоборот: после `std::move` объект
остаётся живым, его деструктор вызывается всегда, и класс сам хранит
признак «из меня переместили» (обычно нулевой указатель).

</div>

<div class="box hood">

**Под капотом.** До 2016 года Rust хранил признак перемещения в самом
значении: при перемещении источник заполнялся особым байтовым шаблоном,
и деструктор проверял, не он ли это. Это стоило записи в память на
каждое перемещение и лишних байт в некоторых типах. RFC 320
«non-zeroing dynamic drop» заменил шаблон на флаги в кадре функции, и
после перехода компилятора на MIR флаги расставляются на нём, как в
листинге выше.

</div>
