# 3.2. Drop и порядок уничтожения

## Деструктор

*Деструктор* (destructor) — код, который выполняется при уничтожении
значения; в Rust это реализация [трейта][g-trait] `Drop`:

```rust
pub trait Drop {
    fn drop(&mut self);
}
```

Компилятор вызывает `drop` сам, когда владелец значения исчезает. Метод
получает `&mut self`, а не `self`: после него компилятор уничтожает поля
значения, и `drop` не должен их забирать. Вызвать `x.drop()` руками нельзя
(ошибка E0040): иначе деструктор выполнился бы второй раз в конце области
видимости. Чтобы уничтожить значение раньше, его перемещают в функцию
`std::mem::drop`, которая есть в *прелюдии* (prelude) — наборе имён,
видных в каждом [модуле][g-module] без `use`. В документации стандартной
библиотеки сказано, что она «не магия» и определена буквально так:

```rust
pub fn drop<T>(_x: T) {}
```

Значение переходит в параметр `_x` и уничтожается в конце этой пустой
функции. Ничего, кроме правил владения из раздела 3.1, здесь нет.

Чтобы видеть порядок уничтожения, в этой главе, как и в разделе
[2.6](../ch02/06-temporaries.md), есть тип `Noisy`: его деструктор
записывает имя значения в журнал потока, а тесты сверяют журнал с
ожидаемым.

## Локальные переменные

```rust
{{#include ../../code/ch03/src/drop_order.rs:locals}}
```

Локальные переменные уничтожаются в порядке, обратном объявлению: журнал
`["конец блока", "b", "a"]`. Причина та же, что у лестницы меток
`goto cleanup` в C: то, что создано позже, может зависеть от созданного
раньше. [Страж][g-guard], который держит шину занятой, объявлен после шины, и
освобождается раньше неё. В главе 4 это правило станет обязательным:
переменная, которая ссылается на другую, должна исчезнуть первой.

## Поля структуры

```rust
{{#include ../../code/ch03/src/drop_order.rs:fields}}
```

Здесь порядок другой. Сначала выполняется `Sensor::drop`, пока все поля
ещё живы: деструктор структуры может ими пользоваться, например
выключить датчик через шину. Затем поля уничтожаются *в порядке
объявления*, сверху вниз: `bus`, потом `irq`. Порядок, в котором поля
перечислены при создании значения, роли не играет.

<div class="box c">

**Как в C.** В C порядок освобождения полей задаёт программист в функции
`sensor_deinit`, и ничто не мешает ему ошибиться. C++ уничтожает члены
класса в порядке, *обратном* объявлению, по аналогии с локальными
переменными. Rust выбрал прямой порядок и закрепил его в языке: на него можно
полагаться. Решение принято в *RFC* (request for comments) 1857 — так в
Rust называют документы, которыми предлагают и обсуждают изменения языка. Если поле должно умереть раньше соседа,
объявите его выше. Если порядок нужен не тот, что даёт объявление, есть
`ManuallyDrop` из раздела 3.4.

</div>

<div class="box hood">

**Под капотом.** Код, который уничтожает значение целиком, компилятор
порождает сам, отдельно для каждого типа. В rustc 1.97 это функция
`core::ptr::drop_glue::<T>`, её имя встречается в отладочных листингах и
трассировках (в старых версиях она называлась `drop_in_place`). Вызвать
её из своего кода можно через `unsafe fn core::ptr::drop_in_place`. Для
`Sensor` она вызывает `Sensor::drop`, а затем код уничтожения каждого
поля. После
[встраивания][g-inlining] от этого остаются три вызова `log` (rustc 1.97.0, x86_64,
release; адреса строк заменены многоточием):

```text
$ cargo asm -p ch03 --lib ch03::drop_order::fields
ch03::drop_order::fields:
	push rbx
	...
	mov esi, 12
	call qword ptr [rip + ch03::drop_order::log@GOTPCREL]
	...
	mov esi, 3
	call qword ptr [rip + ch03::drop_order::log@GOTPCREL]
	...
	mov esi, 3
	pop rbx
	jmp qword ptr [rip + ch03::drop_order::log@GOTPCREL]
	mov rbx, rax
	jmp .LBB23_4
	mov rbx, rax
	...
	call qword ptr [rip + ch03::drop_order::log@GOTPCREL]
.LBB23_4:
	...
	call qword ptr [rip + ch03::drop_order::log@GOTPCREL]
	mov rdi, rbx
	call _Unwind_Resume@PLT
	call qword ptr [rip + core::panicking::panic_in_cleanup@GOTPCREL]
```

В `esi` — длина строки: 12 байт у `"Sensor::drop"`, по 3 у `"bus"` и
`"irq"`. Последний вызов — переход `jmp`: уничтожать после него нечего.
Всё, что ниже, — [посадочные площадки][g-landing-pad] (landing pads), код для случая,
когда `log` паникует. Если паника вылетела из `Sensor::drop`, площадка
всё равно уничтожает `bus` и `irq` и продолжает [раскрутку][g-unwinding] через
`_Unwind_Resume`. Если из деструктора `bus` — уничтожает `irq`. Если же
паника случилась в самой площадке, во время очистки, вызывается
`panic_in_cleanup`, и процесс завершается. Этот случай разобран в
разделе 3.6.

</div>

## Кортежи, массивы и векторы

```rust
{{#include ../../code/ch03/src/drop_order.rs:collections}}
```

Элементы кортежа, массива и вектора уничтожаются по порядку, от первого
к последнему, как поля. Переменные `_t` и `_v` — по-прежнему в обратном
порядке. Журнал: `["v[0]", "v[1]", "t.0", "t.1"]`. Вектор сначала
уничтожает элементы, затем освобождает буфер в куче.

## Присваивание и затенение

```rust
{{#include ../../code/ch03/src/drop_order.rs:reassign}}
```

Присваивание `x = ...` уничтожает старое значение `x` сразу, перед тем
как записать новое: иначе старое значение стало бы недостижимым и
утекло. *Затенение* (shadowing) `let _y = ...` создаёт *новую* переменную с тем же
именем. Старая переменная недоступна по имени, но жива до конца блока и
уничтожается в общем обратном порядке.

## Временные значения

Где кончается жизнь временного значения в `match`, `if` и `let`, разобрано
в разделе [2.6](../ch02/06-temporaries.md). Здесь два случая, важные для
порядка уничтожения: временное значение в аргументе вызова и ссылка на
временное значение в `let`.

```rust
{{#include ../../code/ch03/src/drop_order.rs:temporaries}}
```

Журнал: `["peek", "врем.", "следующая инструкция", "конец блока",
"продлённое"]`. Временное значение живёт до конца инструкции, поэтому
ссылка на него действительна всё время вызова `peek`, а уничтожение
происходит после возврата. Если же ссылку на временное значение сразу
кладут в переменную `let`, компилятор продлевает значению жизнь до конца
блока, как обычной переменной: иначе `_r` сразу стала бы висячей.

<div class="box trap">

**Ловушка.** Правила для временных значений менялись между [редакциями][g-edition]
языка (раздел 2.6 и приложение
[B.2](../appendix-b.md#b2-время-жизни-временных-значений)). С редакции
2024 временные значения хвостового выражения блока уничтожаются *раньше*
локальных переменных этого блока:

```rust
{{#include ../../code/ch03/src/drop_order.rs:tail}}
```

Журнал: `["хвост", "x"]`. В редакции 2021 тот же код даёт
`["x", "хвост"]`. Книга пишет на редакции 2024 (`edition` в
`Cargo.toml` [рабочего пространства][g-workspace]). Код, который зависит от порядка
уничтожения временных значений, при переносе между редакциями лучше
переписать так, чтобы порядок задавали явные переменные.

</div>

## Паника и раскрутка стека

```rust
{{#include ../../code/ch03/src/drop_order.rs:unwinding}}
```

Паника на [хосте][g-host] по умолчанию раскручивает стек: управление идёт вверх по
кадрам до `catch_unwind` или до вершины потока, и в каждом кадре
выполняются деструкторы живых переменных в том же обратном порядке. Тест
видит `["b", "a"]` и после паники. Поэтому мьютекс, файл и буфер,
которыми владеют переменные, освобождаются и при панике.

Компилятор следит и за значениями, которые строятся частями:

```rust
{{#include ../../code/ch03/src/drop_order.rs:partial_array}}
```

Первый элемент массива создан, второй паникует, третий так и не начали
строить. Уничтожается только `arr[0]`: журнал `["arr[0]"]`. Массива
`_arr` ещё нет, и уничтожать его как целое нельзя.

<div class="box ref">

**Справка: паника на микроконтроллере.** У [целей][g-target] `thumbv*-none-eabi*`
стратегия паники по умолчанию `abort` (поле `panic-strategy` в выводе
`rustc +nightly -Z unstable-options --print target-spec-json --target
thumbv7m-none-eabi`). Раскрутки нет: паника вызывает
обработчик [`#[panic_handler]`][g-panic-handler], а он не возвращается — останавливает ядро,
перезагружает его или пишет сообщение через [semihosting][g-semihosting]. Деструкторы при
этом *не выполняются*. Значит, на МК нельзя рассчитывать, что `Drop`
вернёт периферию в безопасное состояние при панике: это работа
обработчика паники и *сторожевого таймера* (watchdog), который
перезагружает зависшее ядро. Разделы 3.3 и 3.6 возвращаются
к тому, чего `Drop` не гарантирует.

</div>
