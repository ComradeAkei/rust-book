# 3.1. Владение и перемещение

## Владелец

Правила владения в Rust короткие:

1. У каждого значения есть владелец: переменная, поле структуры, элемент
   массива или коллекции, временное значение.
2. Владелец в каждый момент один.
3. Когда владелец выходит из области видимости, значение уничтожается.

Третье правило заменяет `free`, `fclose` и `goto cleanup`. Компилятор сам
вставляет вызов деструктора в каждую точку, где владелец перестаёт
существовать, и делает это на всех путях выхода из функции.

```rust
{{#include ../../code/ch03/src/ownership.rs:move}}
```

`vec![0xA5; 64]` выделяет 64 байта в куче, и `frame` ими владеет. Вызов
`send(frame)` *перемещает* значение: параметр `frame` функции `send`
становится новым владельцем, а переменная `frame` в `produce` — пустым
местом, обращаться к которому нельзя. Буфер освобождается один раз, в
конце `send`, когда исчезает её параметр. Попытка прочитать `frame` после
вызова — ошибка E0382, та же, что во введении к главе.

Функция может вернуть владение обратно, и тогда значение перемещается
наружу:

```rust
{{#include ../../code/ch03/src/ownership.rs:give_back}}
```

Отдавать значение в функцию и забирать обратно ради того, чтобы на него
посмотреть, неудобно. Для этого есть заимствование, тема
[главы 4](../ch04/index.md). Здесь важно другое: перемещение — основной
способ передать ответственность за ресурс, и компилятор следит, чтобы
после передачи у старого владельца не осталось ничего, кроме имени.

## Что именно перемещается

`Vec<u8>` и `String` в памяти — три машинных слова: указатель на буфер в
куче, ёмкость и длина. Перемещение копирует эти три слова и не трогает
байты в куче:

```rust
{{#include ../../code/ch03/src/ownership.rs:string_parts}}
```

```rust
{{#include ../../code/ch03/src/ownership.rs:move_is_shallow}}
```

После `let b = a;` у `b` тот же указатель, та же ёмкость и та же длина,
что были у `a`. Два владельца одного буфера на мгновение существуют в
памяти, но компилятор запрещает пользоваться первым. Поэтому деструктор
выполнится один раз.

<div class="box c">

**Как в C.** Присваивание структуры в C — тоже побитовая копия:
`struct frame g = f;` копирует указатель `data`, и теперь буфером «владеют»
и `f`, и `g`. Язык не знает, кто из них освободит память, и `free` в обоих
местах даёт двойное освобождение. C++ решает это конструкторами
копирования и перемещения: при `g = std::move(f)` выполняется
пользовательский код, который обнуляет указатель в `f`. В Rust при
перемещении не выполняется никакой код: байты копируются, а источник
объявляется недоступным во время компиляции. Обнулять его не нужно,
потому что его никто не прочитает. У этого решения есть следствие,
которое разбирает задача [3.D](07-tasks.md#d-самоссылка-и-перемещение):
значение не может узнать, что его переместили.

</div>

## Перемещение в цикле

Перемещение в теле цикла — частая ошибка при переписывании кода с C:
повтор отправки по ошибке связи отдаёт буфер на первой же итерации.

```text
error[E0382]: use of moved value: `frame`
 --> lp.rs:8:14
  |
6 |     let frame = vec![0xA5; 64];
  |         ----- move occurs because `frame` has type `Vec<u8>`, which does not implement the `Copy` trait
7 |     for _attempt in 0..3 {
  |     -------------------- inside of this loop
8 |         send(frame); // повтор отправки при ошибке
  |              ^^^^^ value moved here, in previous iteration of loop
```

Компилятор предлагает два выхода, и оба верны в зависимости от задачи:
`send` может принимать `&[u8]` вместо `Vec<u8>` (заимствование, глава 4),
или каждой попытке нужна своя копия, `frame.clone()`.

## Copy и Clone

Для простых значений перемещение без запрета на источник безвредно:
копия `u32` ничем не владеет, и уничтожать её не нужно. Такие типы
помечаются `Copy`, и присваивание копирует их, оставляя источник
доступным:

```rust
{{#include ../../code/ch03/src/ownership.rs:copy}}
```

`Copy` — это обещание: побитовая копия значения полностью равноценна
оригиналу. Отсюда два правила, которые проверяет компилятор:

- тип с деструктором не может быть `Copy` (ошибка E0184): иначе каждая
  копия выполнила бы деструктор, и буфер освободился бы дважды;
- `Copy` можно вывести, только если все поля `Copy` (ошибка E0204):
  `Frame` с полем `Vec<u8>` не может быть `Copy`.

`Copy` по умолчанию у целых, `f32` и `f64`, `bool`, `char`, у сырых
указателей и указателей на функции, у разделяемой ссылки `&T`, а также у
массивов и кортежей из `Copy`-элементов. Не `Copy`: `String`, `Vec`,
`Box` и изменяемая ссылка `&mut T`. Последнее важно для главы 4: две
копии `&mut T` дали бы два изменяющих доступа к одному значению.

`Clone` — явная копия. Её реализация может делать что угодно: у
`Vec` и `String` она выделяет новый буфер и копирует байты, у счётчика
ссылок `Rc` увеличивает счётчик. Вызов `.clone()` всегда виден в коде, и
дорогая копия не прячется за знаком `=`.

<div class="box trap">

**Ловушка.** `#[derive(Clone, Copy)]` ставят по привычке, чтобы
компилятор не ругался на перемещения. Для значений-данных это нормально,
но для типов, которые означают *право* на что-то, `Copy` разрушает смысл.
Если тип `Uart0` означает «этот код единственный управляет UART0», то
`Copy` позволит сделать сколько угодно таких прав и настроить порт из
двух мест сразу. Раздел [6.9](../ch06/09-registers.md) и
[глава 27](../ch27/04-ownership.md) строят на некопируемых типах доступ к периферии.

</div>
