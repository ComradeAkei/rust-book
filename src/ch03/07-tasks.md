## B. Страж области

В `exercises/ch03/src/b_scope_guard.rs` реализуйте страж, который
выполняет действие над значением при выходе из области видимости:

```rust
let mut g = ScopeGuard::new(value, |v| on_exit(v));
g.do_something();                       // Deref и DerefMut к значению
let value = ScopeGuard::into_inner(g);  // обезвредить: действие не выполнится
```

Требования:

1. Действие выполняется ровно один раз при любом выходе из области
   видимости: обычном, через `return` и `?`, при панике.
2. `into_inner` возвращает значение и не выполняет действие. И значение,
   и замыкание уничтожаются ровно по разу.
3. Страж не занимает ни байта сверх значения и замыкания: ни флага
   «обезврежен», ни `Option` внутри. `ScopeGuard<u64, fn(u64)>` занимает
   16 байт на x86_64, а страж с замыканием без захватов — 8.
4. Крейт собирается без `std` (`#![no_std]`).

Подсказка: требование 3 закрывает очевидный путь через
`Option<F>` и `take`. Вспомните раздел 3.4.

Вторая часть: на `ScopeGuard` постройте транзакцию над регистрами
периферии:

```rust
{{#include ../../code/ch03/src/regs.rs:regs}}
```

`Transaction::begin(&mut regs)` открывает транзакцию, `write` пишет в
регистр сразу (устройство должно видеть новые значения), но запоминает
старое. `commit` подтверждает изменения. Если транзакцию не подтвердили
и она уничтожена (ранний `return`, `?`, паника), все изменённые регистры
возвращаются к старым значениям: каждый ровно одной записью, в порядке,
обратном *первому* изменению. Регистров 16, поэтому журнал старых
значений помещается в массив фиксированного размера без кучи. Тесты
проверяют историю записей `Regs::history()` целиком, так что лишняя
запись при откате тоже ошибка.

## C. Цена перемещения

Структуры `#[repr(C)] struct W(pub [u32; N])` с `N` от 1 до 48 передают
в функции и возвращают из них по значению. Найдите для x86_64 и для
`thumbv7em-none-eabihf` (Cortex-M4F):

- наибольший размер аргумента, который целиком передаётся в регистрах;
- наибольший размер результата, который целиком возвращается в
  регистрах;

отдельно для Rust ABI (обычная `fn`) и для `extern "C"`. Кроме того,
найдите наименьший размер, при котором копия для вызова `fn f(w: W)` из
`&W` (раздел 3.5, `ch03_seal_copy`) становится вызовом `memcpy`.

Пороги находятся опытами: напишите в `exercises/ch03/src/c_abi.rs`

и возвращают такие структуры, и смотрите их LLVM IR и ассемблер:


В IR ищите, как выглядит параметр: набор целых или массив чисел,
`ptr` с атрибутом `byval` или `dead_on_return`, скрытый параметр `sret`
для результата. Тест `cargo test -p ch03-exercises task_c` сам соберёт
пробный крейт со всеми 48 размерами для обеих целей (это занимает
несколько секунд) и для каждого ответа покажет первый размер, на котором
вы ошиблись, вместе с сигнатурой функции из IR.

В отчёте ответьте:

1. Почему пороги для аргумента и результата у `extern "C"` на
   Cortex-M4F разные? Найдите правило в стандарте AAPCS.
2. Что происходит с аргументом `extern "C"` на Cortex-M4F, который не
   помещается в регистры целиком? Посмотрите ассемблер вызывающей
   стороны для структуры в 4 КиБ и сравните с тем, что для такой же
   функции на C даёт `clang --target=thumbv7em-none-eabihf -O2`.
3. Почему Rust ABI не совпадает с C ABI той же платформы, и чем это
   грозит, если забыть `extern "C"` у функции, которую вызывает код на C?

## D. Самоссылка и перемещение

Раздел 3.1 сказал, что значение не может узнать о своём перемещении.
Эта задача показывает, к чему это приводит. Буфер приёма хранит курсор —
сырой указатель на следующую свободную ячейку собственного массива:

```rust
pub struct RxBuf {
    buf: [u8; CAP],
    cursor: *mut u8,   // указывает внутрь self.buf
    // ...
}
```

В C такая структура обычна: например, пустой список `list_head` в ядре
Linux указывает сам на себя. Скопировать её присваиванием нельзя, но язык
этого не запрещает.

Реализуйте в `exercises/ch03/src/d_self_ref.rs`:

1. `RxBuf`: `init` ставит курсор на начало `buf`, `push` пишет байт по
   курсору и сдвигает его, `received` возвращает принятые байты. Метод
   `moved` отвечает, переехал ли буфер после `init`. Добавьте для этого
   нужные поля. Тест `naive_notices_move` перемещает буфер в `Box` и
   ждёт `true`.
2. Два теста с `#[ignore]` запустите под Miri в обеих моделях
   алиасинга. Miri останавливает всю программу на первом же
   неопределённом поведении, поэтому каждый тест запускается отдельно:

   ```console
   $ cargo +nightly miri test -p ch03-exercises -- --ignored --exact task_d::naive_returned_ub
   $ cargo +nightly miri test -p ch03-exercises -- --ignored --exact task_d::naive_in_place_ub
   $ export MIRIFLAGS=-Zmiri-tree-borrows    # и те же две команды ещё раз
   ```

   `naive_returned_ub` возвращает буфер из функции и пишет в него.
   `naive_in_place_ub` ничего не перемещает: `init`, затем `push` на том
   же месте. Объясните, почему Miri находит неопределённое поведение в
   обоих, и почему второе вообще не связано с перемещением.
3. `RxIdx` — исправление первое: никаких указателей внутрь себя, только
   индекс. Размер не больше `CAP + 1` байт.
4. `PinnedRx` — исправление второе: указатель остаётся, но значение,
   однажды размещённое, больше не двигается. `new` возвращает
   `Pin<Box<Self>>`, `push` принимает `self: Pin<&mut Self>`. Поле
   `PhantomPinned` запрещает доставать значение из `Pin`. Внутри `push`
   вам понадобится `unsafe` с комментарием `SAFETY`.

Тесты `index_survives_moves` и `pinned_survives_moves` перемещают оба
исправления всеми доступными способами и проверяют содержимое. Оба
исправления должны пройти Miri в обеих моделях.

В отчёте сравните исправления: размер, число проверок в `push` по
ассемблеру, что можно делать с каждым значением после создания. `Pin`
подробно разбирается в [главе 22](../ch22.md) вместе с `async`, здесь
достаточно понять, от чего он защищает.
